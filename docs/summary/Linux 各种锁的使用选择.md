
## 分步选择
这是一个非常经典且重要的问题。Linux 内核提供了丰富的并发控制原语，选择正确的锁不仅关乎代码的正确性（避免死锁、崩溃），更直接决定了系统的性能。

选择锁的核心逻辑主要取决于两个因素：
1.  **上下文（Context）**：你的代码是在中断/软中断中运行（不可睡眠），还是在进程上下文中运行（可睡眠）？
2.  **访问模式（Access Pattern）**：是读多写少，还是写操作频繁？是保护数据，还是同步执行顺序？

以下是详细的分类总结和选择指南：

---

### 1. 核心分类：能不能睡眠？

这是第一道分水岭。

*   **原子上下文（Atomic Context）**：包括**硬件中断（IRQ）、软中断（Softirq）、自旋锁持有期间**。
    *   **特点**：绝对**严禁睡眠**，严禁调度。
    *   **只能用**：自旋锁（Spinlock）、RWLock、RCU。
*   **进程上下文（Process Context）**：包括**用户进程系统调用、内核线程**。
    *   **特点**：可以睡眠（Block），发生上下文切换。
    *   **可用**：互斥锁（Mutex）、信号量（Semaphore）、读写信号量（rw_semaphore）、完成量（Completion），当然也可以用自旋锁（但不推荐，除非临界区极短）。

---

### 2. 各类锁的详细画像

#### ① 自旋锁 (Spinlock)
*   **机制**：如果不成功，CPU 就“原地打转”（忙等待），直到锁被释放。
*   **适用场景**：
    *   **中断上下文**必须使用。
    *   **临界区非常短**（几行代码，没有复杂耗时操作）。
*   **注意**：持有自旋锁期间不能睡眠，否则会导致死锁。

#### ② 互斥锁 (Mutex)
*   **机制**：如果不成功，当前线程会**睡眠**（让出 CPU），放入等待队列，等锁释放后被唤醒。
*   **适用场景**：
    *   **进程上下文**。
    *   **临界区较长**，或者临界区内包含可能导致睡眠的函数（如 `copy_to_user`, `kmalloc`）。
    *   这是最常用的排他锁，替代了早期的二值信号量。

#### ③ 读写锁 (RWLock / rw_semaphore)
Linux 有两种读写锁：
*   `rwlock_t`：**读写自旋锁**。底层是自旋锁，不可睡眠。适用于中断上下文的读多写少。
*   `rw_semaphore`：**读写信号量**。底层是信号量，可睡眠。适用于进程上下文的读多写少。
*   **适用场景**：
    *   **读多写少**（如 100:1）。
    *   需要**强一致性**（读者必须看到最新数据）。

#### ④ 信号量 (Semaphore)
*   **机制**：维护一个计数器（Counter）。
*   **适用场景**：
    *   **计数大于 1**：控制并发数量（如限制最多 5 个线程同时访问某个硬件资源）。
    *   **复杂的同步**：但在简单的互斥场景下，现在推荐使用 Mutex，因为 Mutex 性能更好且支持优先级继承。

#### ⑤ 完成量 (Completion)
*   **机制**：一种同步原语，而非锁。A 线程发起操作，然后等待；B 线程完成后通知 A。
*   **适用场景**：
    *   **执行顺序同步**：例如“启动一个设备，等待设备初始化完成”。
    *   替代古老的“信号量初始化为0”的同步用法，Completion 不存在竞态问题，更安全。

#### ⑥ RCU (Read-Copy Update)
*   **机制**：读者无锁（性能极高），写者复制新数据->更新指针->延迟回收旧数据。
*   **适用场景**：
    *   **极端读多写少**（读占比 > 90%）。
    *   **通过指针访问**的动态数据结构（链表、哈希表）。
    *   读者能容忍短暂的旧数据。

---

### 3. 终极选择指南（决策树）

请按照以下步骤进行选择：

#### 第一步：你在什么上下文？
*   **我在中断/软中断中**（或持有了自旋锁）：
    *   **只能选**：Spinlock, RWLock, RCU。
    *   *转第三步*。
*   **我在进程/内核线程中**：
    *   **可以选**：Mutex, Semaphore, Completion, Spinlock, RCU。
    *   *转第二步*。

#### 第二步：临界区是否需要睡眠（或操作很重）？
*   **是（如由内存分配、IO 操作、拷贝用户数据）**：
    *   必须选睡眠锁：Mutex, rw_semaphore。
    *   *转第三步*。
*   **否（临界区极短，只是改几个变量）**：
    *   Spinlock 也是可选的（虽然在进程上下文，但为了减少上下文切换开销，短临界区用 Spinlock 效率可能更高）。

#### 第三步：是保护数据，还是同步执行顺序？
*   **同步顺序（等待某事完成）**：
    *   选 **Completion**。
*   **保护数据**：
    *   *转第四步*。

#### 第四步：读写比例如何？
*   **写操作频繁**（或读写相当）：
    *   不可睡眠 -> **Spinlock**。
    *   可睡眠 -> **Mutex**。
*   **读多写少**（读远多于写）：
    *   **能容忍旧数据 & 指针结构** -> 首选 **RCU**（性能最好）。
    *   **必须强一致性**：
        *   不可睡眠 -> **rwlock_t**。
        *   可睡眠 -> **rw_semaphore**。

#### 第五步：是独占访问还是允许多个持有者？
*   **独占（同一时间只能一个人进）**：Mutex / Spinlock。
*   **计数（允许 N 个人同时进）**：Semaphore。

---

### 4. 汇总对比表

| 锁类型 | 上下文 | 行为 (等待时) | 读写并行 | 典型用途 | 备注 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Spinlock** | 原子/进程 | **忙等待 (Spin)** | 否 | 中断处理、极短临界区 | 严禁睡眠，持有时间要短 |
| **Mutex** | 进程 | **睡眠 (Sleep)** | 否 | 一般的互斥保护 | 互斥的首选，开销比信号量小 |
| **rwlock_t** | 原子/进程 | 忙等待 | 是 | 中断里的读多写少 | 容易导致写者饥饿 |
| **rw_semaphore**| 进程 | 睡眠 | 是 | 业务逻辑里的读多写少 | 譬如文件系统元数据读写 |
| **RCU** | 任意(读) | **不等待** | **是** | 网络路由、配置、链表 | 读者性能最强，写者开销大 |
| **Semaphore** | 进程 | 睡眠 | 否 | 资源计数、控制并发数 | 简单的互斥请用 Mutex |
| **Completion** | 进程 | 睡眠 | N/A | A 等待 B 完成 | 用于同步，不是为了互斥 |

### 5. 一句话总结
*   **中断里改数据** -> **Spinlock**
*   **线程里改数据** -> **Mutex**
*   **读特别多，且是指针链表** -> **RCU**
*   **等别人干完活** -> **Completion**
*   **读写分明且要强一致** -> **rw_semaphore / rwlock**

## 最新推荐及淘汰


在现代 Linux 内核（5.x 和 6.x）中，锁的演进方向非常明确：**追求极致的多核扩展性（Scalability）、降低缓存行颠簸（Cache-line Bouncing），以及为了支持实时性（PREEMPT_RT）而进行的底层语义重构。**

下面是 5.x 之后内核锁机制的“红黑榜”及全景指南：

---

### 第一梯队：强烈推荐 / 绝对主流（闭眼用）

当你在 5.x/6.x 时代写新的内核模块或驱动时，以下机制应该是你的首选方案。

#### 1. RCU (Read-Copy-Update) —— “读多写少”的绝对王者
*   **适用场景**：读多写少，且读操作不能睡眠（如网络路由表、文件描述符表等核心数据结构）。
*   **专家点评**：**内核里最伟大的发明之一。** 它的读端开销几乎为零（没有原子指令，不修改任何内存，完全不引起缓存颠簸）。在现代内核中，RCU 正在疯狂吞噬以前属于 `rwlock` 甚至普通 `spinlock` 的领地。
*   **状态**：**极度推荐**。现在提交新代码，如果是读多写少的场景不用 RCU，大概率会被 Maintainer 打回。

#### 2. Mutex (`struct mutex`) —— 睡眠锁的默认选择
*   **适用场景**：临界区较长、允许上下文睡眠（如涉及 I/O 操作、内存分配）的通用互斥场景。
*   **专家点评**：现代内核的 `mutex` 极其优化，支持**乐观自旋（Optimistic Spinning）**。如果持有锁的进程正在其他 CPU 上运行，当前等待的进程会像自旋锁一样短暂自旋，而不是立刻陷入睡眠休眠（这避免了昂贵的上下文切换开销）。它还自带**严格的所有权检查**和**优先级继承（PI）**。
*   **状态**：**推荐**。凡是能睡眠的地方，优先用 `mutex`。

#### 3. Spinlock (`spinlock_t`) —— 非睡眠锁的默认选择
*   **适用场景**：临界区极短、绝对不能睡眠的上下文（如中断处理程序、软中断中）。
*   **专家点评（5.x/6.x 巨变）**：注意！在 5.x/6.x 时代，由于 PREEMPT_RT（实时补丁）被并入主线，**`spinlock_t` 的语义已经裂变了**。
    *   在非 RT 内核：它依然是传统的自旋锁（底层是 `qspinlock` 排队自旋锁，解决了公平性和锁饥饿）。
    *   在 RT 内核（`CONFIG_PREEMPT_RT=y`）：**它会被映射为可睡眠的 `rt_mutex`**。这意味着在 RT 内核下，持有 `spinlock_t` 是可以被抢占的。这是为了保证实时系统的低延迟响应。
*   **状态**：**推荐**。常规短临界区的标准做法。

#### 4. Raw Spinlock (`raw_spinlock_t`) —— 真正的“硬核”自旋锁
*   **适用场景**：调度器底层、中断控制器底层、以及无论是否开启 RT 都**绝对不能睡眠且不能被抢占**的极度底层代码。
*   **专家点评**：它在任何配置下都是真正的、死等的自旋锁。
*   **状态**：**按需使用**。普通驱动开发者基本用不到，除非你是在写最底层的 Architecture 代码或核心框架。滥用会被骂，因为它会破坏内核的实时响应性。

---

### 第二梯队：特定场景神器（按需使用，表现优异）

#### 1. SeqLock（顺序锁，`seqlock_t`）
*   **适用场景**：保护简短、频繁被读取且偶尔被修改的复合数据（比如时间戳 `jiffies_64`、VFS 中的路径名解析）。
*   **专家点评**：写者获取自旋锁并增加序列号，读者不加锁直接读，读完检查序列号是否改变。如果有写者介入，读者就重试。它彻底避免了读操作对缓存行的修改，性能极高。
*   **状态**：**推荐（在特定场景下）**。比 `rwlock` 强太多。

#### 2. 读写信号量 (`struct rw_semaphore` / `down_read` / `down_write`)
*   **适用场景**：允许睡眠的读多写少场景（最典型的就是 Linux 内存管理的 `mmap_lock`，以前叫 `mmap_sem`）。
*   **专家点评**：和 `rwlock` 不同，读写信号量允许睡眠，且内核社区对其进行了大量优化（同样支持乐观自旋）。只要是在可以调度的上下文中，需要读写分离，用它就对了。
*   **状态**：**推荐**。

#### 3. 原子操作与 Per-CPU 变量 (Lockless Techniques)
*   **专家点评**：最高级的锁就是“无锁”。在 5.x/6.x 内核中，大量统计计数器、网络包计数都使用了 `DEFINE_PER_CPU` 变量。每个 CPU 只修改自己的本地变量，完全不需要锁，最后读取时汇总即可。配合 `atomic_t` 和 `cmpxchg`，这是突破多核性能瓶颈的终极武器。
*   **状态**：**极度推荐**。

---

### 第三梯队：已淘汰 / 不推荐 / 极力劝退（避雷区）

在代码审查时，如果你在新的 Patch 中使用了这些，我们通常会要求你重构。

#### 1. 读写自旋锁 (`rwlock_t`) ❌
*   **为什么不推荐**：前面提过，它的读者在获取锁时依然需要使用原子指令修改内存，导致严重的 **Cache Line Bouncing（缓存行颠簸）**。在多核服务器上，大量的并发读反而会导致锁性能断崖式下跌。
*   **现状**：内核 5.x/6.x 中虽然将它的底层替换成了 `qrwlock`（排队读写锁，解决了写者饥饿），但仍然**强烈不建议在新代码中使用**。
*   **替代方案**：RCU 或 SeqLock。

#### 2. 计数信号量 (`struct semaphore` / `down` / `up`) ❌
*   **为什么不推荐**：早在 2.6 末期和 3.x 时代，社区就决定将“互斥”功能从信号量中剥离。信号量没有严格的“所有者（Owner）”概念，不支持优先级继承，也无法进行精准的 Lockdep（死锁检测）跟踪。
*   **现状**：作为互斥锁的替代品，它已被彻底淘汰。现在内核中仅在极少数需要**“生产-消费”模型**或**限制并发数量**（比如只允许 5 个线程同时访问某个资源）的场景下，作为纯粹的计数器使用。
*   **替代方案**：需要互斥直接用 `mutex`；需要同步或等待事件用 `wait_queue` 或 `completion`。

#### 3. Bit Spinlocks (位自旋锁) ❌
*   **什么是它**：为了极致节省内存，直接使用某个数据结构（比如 `struct page` 的 flags）里面的一个 bit 作为自旋锁。
*   **为什么不推荐**：调试极其困难，**不支持 Lockdep**，并且在 PREEMPT_RT 下会导致极其严重的抢占问题。
*   **现状**：除了核心的 VFS 和 Memory Management 系统因为历史原因和内存极度抠门而在使用外，严禁普通开发者使用。
*   **替代方案**：老老实实用 `spinlock_t`。

#### 4. 大内核锁 (Big Kernel Lock, BKL) 
*   **状态**：**已入土为安**。早在 2.6.39 就已经被彻底从源码中拔除，这里只是顺带提一句，如果现在还有人跟你提 BKL，说明他的知识库该更新了。

---

### 专家的终极建议：现代内核加锁的“心法”

如果你要在 6.x 内核中写并发代码，请在脑海里走一遍这个决策树：

1.  **能不用锁吗？** -> 考虑 Per-CPU 变量、RCU、`atomic_t`。
2.  **必须用锁，临界区能睡眠吗？**
    *   能睡眠 -> 无脑选 `mutex`。
    *   能睡眠且读多写少 -> 选 `rw_semaphore`。
3.  **不能睡眠（比如在中断里），必须自旋吗？**
    *   无脑选 `spinlock_t`。（记住它在 RT 内核下其实会变成休眠锁，但你写代码时就当它是自旋锁）。
4.  **是极短时间戳/状态位的读多写少吗？** -> 选 `seqlock`。
5.  **绝对不能被抢占、绝对不准睡眠的核心底层逻辑？** -> `raw_spinlock_t`。
6.  **最后，永远、永远开启 Lockdep 编译你的内核！** `CONFIG_PROVE_LOCKING=y` 是内核开发者的防弹衣，它能在运行时抓出你 99% 的死锁隐患。
