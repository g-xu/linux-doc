## 设备模型
Linux 设备模型（Linux Device Model，简称 LDM）是 Linux 2.6 内核引入的一项革命性变革。它不仅仅是驱动程序的集合，而是一个**统一的、抽象的、分层的架构**，用于在内存中维护系统硬件的拓扑结构。

它的出现主要解决了以下核心问题：
1.  **电源管理**：按照依赖关系（父子关系）正确地挂起（Suspend）和唤醒（Resume）设备。
2.  **系统概览**：向用户空间提供系统硬件的视图（通过 **sysfs** 文件系统）。
3.  **热插拔（Hotplug）**：处理设备的动态添加和移除，并通知用户空间（如 udev）。
4.  **生命周期管理**：通过引用计数防止内核因访问已释放的内存而崩溃。

下面我将从**核心架构**、**底层实现**、**工作机制**和**代码层级**四个维度详细介绍 Linux 设备模型。

---

### 一、 核心架构：总线、设备与驱动

这是驱动开发者最常接触的“三位一体”概念。内核认为，任何设备都应该挂载在某条总线上。

#### 1. 总线 (Bus)
总线是 CPU 与设备交互的通道，也是设备模型中的“红娘”。
*   **职责**：管理挂载在它上面的设备（Devices）和注册在它上面的驱动（Drivers）。它负责将两者进行匹配。
*   **关键数据结构**：`struct bus_type`
*   **核心行为**：
    *   **Match (匹配)**：当一个新设备添加或新驱动注册时，总线会调用 `.match()` 回调函数。它通常比较设备的 ID（如 PCI Vendor ID）和驱动支持的 ID 表。
*   **例子**：PCI, USB, I2C, SPI, Platform (虚拟总线)。

#### 2. 设备 (Device)
代表物理上或逻辑上的硬件实体。
*   **职责**：描述硬件的属性（资源、地址、父设备等）。
*   **关键数据结构**：`struct device`
    *   `parent`：指向父设备的指针（构建设备树的关键）。
    *   `bus`：指向该设备挂载的总线。
    *   `driver`：指向绑定成功的驱动。
    *   `of_node`：指向设备树（Device Tree）节点（嵌入式常用）。
*   **注意**：在具体驱动中，通常嵌入在更大的结构体里，如 `struct pci_dev` 包含 `struct device dev`。

#### 3. 驱动 (Driver)
代表驱动程序软件代码。
*   **职责**：实现操作硬件的具体逻辑。
*   **关键数据结构**：`struct device_driver`
*   **核心行为**：
    *   **Probe (探测)**：当总线匹配成功后执行。负责初始化硬件、申请中断、注册字符/块设备等。
    *   **Remove (移除)**：设备拔出或模块卸载时执行。

---

### 二、 底层实现：Kobject 与 Sysfs

设备模型之所以能像乐高积木一样搭建起来，并展示在 `/sys` 下，依赖于底层的对象系统。

#### 1. Kobject (Kernel Object)
它是 Linux 设备模型的基石，所有设备对象的“基类”。
*   **功能**：
    *   **引用计数 (kref)**：核心功能。记录有多少地方引用了这个对象。只有计数为 0 时才真正释放内存。
    *   **层次结构**：包含 `parent` 指针，将对象连成树。
    *   **Sysfs 映射**：每个 kobject 对应 sysfs 中的一个目录。
*   **结构**：`struct kobject`

#### 2. Kset
Kobject 的集合。
*   **功能**：将具有相同特性的 Kobject 归类。例如，所有的 PCI 设备都在一个 Kset 中。Kset 内部包含一个 `list_head`，把底下的 Kobject 串起来。

#### 3. Sysfs 文件系统
Sysfs 是设备模型在用户空间的投影。它是一个基于内存的虚拟文件系统，挂载在 `/sys`。
*   **`/sys/bus/`**：按总线类型分类（pci, i2c...），每条总线下分 `devices` 和 `drivers`。
*   **`/sys/devices/`**：这是**最真实**的物理拓扑结构视图，展示了所有设备的父子层级关系。
*   **`/sys/class/`**：按**功能**分类（net, input, block...）。比如 `eth0` 在这里能找到，无论它是 PCI 网卡还是 USB 网卡。
*   **`/sys/dev/`**：按主次设备号（char/block）索引。

---

### 三、 工作机制：Binding 与 Uevent

#### 1. 绑定过程 (The Binding Process)
这是设备模型最核心的自动化流程：
1.  **添加设备**：硬件插入或设备树解析，内核注册 `struct device`。
2.  **总线介入**：设备被加入总线的设备链表。总线遍历驱动链表，对每个驱动调用 `.match()`。
3.  **匹配成功**：如果 `.match()` 返回 true，内核尝试绑定。
4.  **调用 Probe**：内核调用驱动的 `.probe()` 函数。
5.  **绑定完成**：如果 `.probe()` 成功，在 `/sys` 下建立符号链接（设备指向驱动，驱动指向设备）。

#### 2. 热插拔与 Uevent
当设备发生变化（添加/移除/属性改变）时，内核需要通知用户空间。
*   **Mechanism**：内核通过 Netlink Socket 发送一个 **Uevent** 消息。
*   **User space**：`udev` 或 `mdev` 守护进程监听这个消息。
*   **Action**：根据规则加载驱动模块（`modprobe`）、创建设备节点（`/dev/xxx`）或设置权限。

---

### 四、 两个特殊的视图：Class 与 Platform

#### 1. 类 (Class)
为了屏蔽底层的物理连接差异，Linux 抽象出了 Class。
*   **目的**：用户通常不关心“这个鼠标是 USB 的还是蓝牙的”，只关心“它是一个输入设备”。
*   **实现**：`struct class`。
*   **API**：`class_create()`, `device_create()`。这两个 API 常用于在写字符设备驱动时，自动在 `/dev` 下创建节点（不需要手动 mknod）。

#### 2. 平台总线 (Platform Bus)
在嵌入式系统（ARM/RISC-V SoC）中，很多外设（UART, I2C 控制器, GPIO）直接集成在芯片内部，不依附于 PCI 或 USB 这种具有自举（Enumeration）功能的物理总线。
*   **虚拟总线**：Linux 发明了 `platform_bus_type`。
*   **Platform Device**：通过设备树（Device Tree / DTS）描述的设备，被解析为 `platform_device`。
*   **Platform Driver**：驱动工程师编写的 `platform_driver`。
*   这是嵌入式 Linux 驱动开发中最主流的模式。

---

### 五、 总结图解

如果把 Linux 设备模型看作一家公司：

*   **Kobject** 是最基本的“员工档案”（带引用计数）。
*   **Device** 是“具体的员工”（硬件）。
*   **Driver** 是“岗位说明书”（软件逻辑）。
*   **Bus** 是“部门经理”（负责撮合员工和岗位）。
*   **Class** 是“职能工会”（所有司机归一类，所有厨师归一类，不管你在哪个部门）。
*   **Sysfs** 是“公司组织架构图”（对外展示）。

### 六、 开发者视角：常用 API

作为驱动开发者，你通常不需要直接操作 Kobject，而是使用封装好的 API：

1.  **注册驱动**：
    *   `platform_driver_register()`
    *   `i2c_driver_register()`
    *   `pci_register_driver()`

2.  **获取资源**（在 Probe 函数中）：
    *   `platform_get_resource()` (获取寄存器地址、中断号)
    *   `devm_kzalloc()` (受设备模型管理的内存分配，设备卸载时自动释放，**强烈推荐**)

3.  **创建接口**：
    *   `device_create_file()` (在 sysfs 中创建属性文件，供用户空间读写控制)

理解 Linux 设备模型是理解 Linux 驱动架构（尤其是电源管理和设备树）的关键钥匙。

## device vs cdev

对于字符设备，关于device 和 cdev的关系：

简单来说，**`cdev` 是“里子”（功能内核），`device` 是“面子”（设备模型与用户空间交互）。**

在现代Linux字符设备驱动开发中，这两者通常**不是二选一**的关系，而是**互补与合作**的关系。你需要结合使用它们，或者使用封装了这两者的更高层接口。

下面为你详细拆解两者的关系、区别以及使用策略。

---

### 1. 本质区别

#### **`cdev` (Character Device)**
*   **所属层级**：这是字符设备的**核心内核抽象**。
*   **核心作用**：它将**设备号（Major/Minor）**与**文件操作结构体（file_operations）**绑定在一起。
*   **工作机制**：当你在用户空间 `open("/dev/xxx")` 时，VFS（虚拟文件系统）通过设备号在内核的 `cdev_map` 中查找对应的 `cdev` 结构体，从而找到你写的 `read/write` 函数。
*   **如果没有它**：即便你在 `/dev` 下有一个设备文件，应用程序打开它时，内核也不知道该调用哪个驱动程序的函数。

#### **`device` (struct device / Linux Device Model)**
*   **所属层级**：这是**Linux设备模型（Linux Device Model）**的一部分。
*   **核心作用**：它在 **sysfs** (`/sys/devices/...`) 中创建节点，并向用户空间发送 **uevent** 事件。
*   **工作机制**：当你调用 `device_create()` 时，内核会在 sysfs 中生成信息。后台的 `udev` 或 `mdev` 守护进程会监听到这个事件，根据信息自动在 `/dev` 目录下创建设备节点文件（即自动执行 `mknod`）。
*   **如果没有它**：你的驱动可以正常工作，但是用户必须手动使用 `mknod` 命令创建设备节点，且无法在 sysfs 中查看设备层级信息，不支持热插拔自动加载。

---

### 2. 它们是如何配合的？（标准流程）

在写一个标准的字符设备驱动时，通常的流程是“**先造核，再造壳**”：

1.  **申请设备号** (`alloc_chrdev_region`)：拿到合法的 Major/Minor。
2.  **初始化 cdev** (`cdev_init` & `cdev_add`)：
    *   这是**“活起来”**的步骤。执行完这一步，内核就知道这个设备号对应你的驱动了。
    *   *此时：用户如果手动 mknod 创建节点，已经可以使用驱动了。*
3.  **创建类** (`class_create`)：在 `/sys/class` 下创建一个分类。
4.  **创建设备** (`device_create`)：
    *   这是**“显现出来”**的步骤。执行完这一步，`/dev/xxx` 会自动生成。
    *   `device_create` 内部会引用设备号，从而在逻辑上与 `cdev` 产生关联（虽然它们在代码结构上是独立的）。

---

### 3. 图解关系

```text

      |

      v

+-------------------------------------------------------------+
```

### 4. 在使用中如何选择？

既然明白了关系，选择的逻辑就非常清晰了：

#### **方案 A：标准的现代驱动（推荐）**
**策略**：**两者都用**。
**适用场景**：绝大多数通用的字符设备驱动。
**写法**：
1.  `cdev_init()` / `cdev_add()`：为了让内核能调用你的 `read/write`。
2.  `class_create()` / `device_create()`：为了自动生成 `/dev` 节点，方便用户使用，且符合Linux设备模型标准。

#### **方案 B：偷懒/简化模式（强烈推荐用于简单设备）**
**策略**：使用 **`misc_device` (混杂设备)** 接口。
**适用场景**：看门狗、简单的IO控制、不涉及复杂设备树绑定的简单字符设备。
**原理**：`misc_register()` 函数内部帮你封装好了 `cdev` 的注册和 `device` 的创建。你只需要填充一个结构体，调用一个函数，既有了功能，又自动生成了节点。
**写法**：
```c
static struct miscdevice my_misc_dev = {
    .minor = MISC_DYNAMIC_MINOR,
    .name = "my_device",
    .fops = &my_fops,
};
misc_register(&my_misc_dev); // 一步到位
```

#### **方案 C：复古/特殊模式**
**策略**：只用 `cdev`，不用 `device` 接口。
**适用场景**：
*   **极度裁剪的嵌入式系统**：没有 `udev/mdev`，为了省内存，所有 `/dev` 节点都是在构建根文件系统时静态创建好的。
*   **私有/隐藏设备**：不想让用户轻易在 `/dev` 下看到，或者需要特定权限手动创建节点的场景。
*   **教学演示**：为了演示 `mknod` 的原理。

### 总结

*   **cdev** 是**功能**：没有它，驱动无法响应 `open/read/write`。
*   **device** 是**展示**：没有它，`/dev` 目录下不会自动生成节点文件。

**最佳实践**：
对于一般的字符设备开发，请**同时使用** `cdev`（实现功能）和 `device`（实现自动节点创建），或者直接使用更简单的 **`misc_device`** 接口。不要只用其中一个，除非你非常清楚自己在做什么。
