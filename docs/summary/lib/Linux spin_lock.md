## spin_lock

这是一个关于 Linux 内核 **Spinlock (自旋锁)** 的深度介绍。

Spinlock 是 Linux 内核中最底层、最基础的同步原语。它是内核“并发安全”的基石，特别是在**中断上下文**和**多核（SMP）环境**下。

---
### 主要API

在使用这些 API 之前，请确保已包含头文件：
```c
#include <linux/spinlock.h>
```

| API 分类                             | API 函数 / 宏                            | 功能描述                                                          | 备注 / 注意事项                                                                            |
| :--------------------------------- | :------------------------------------ | :------------------------------------------------------------ | :----------------------------------------------------------------------------------- |
| **声明与初始化**                         | `DEFINE_SPINLOCK(x)`                  | **静态**定义并初始化一个名为 `x` 的自旋锁。                                    | 宏定义，通常用于全局变量。                                                                        |
|                                    | `spin_lock_init(lock)`                | **动态**初始化自旋锁。                                                 | 通常用于结构体成员的初始化。                                                                       |
| **基础加锁**<br>(仅进程上下文)               | `spin_lock(lock)`                     | 获取锁。如果锁已被占用，则**忙等待**（自旋）。<br>获取锁后会自动**禁止内核抢占**。               | **仅适用于**锁只在进程上下文中使用，且不会被中断打断的场景。                                                     |
|                                    | `spin_unlock(lock)`                   | 释放锁，并**开启内核抢占**。                                              | 必须与 `spin_lock` 配对使用。                                                                |
| **软中断安全**<br>(Softirq Safe)        | `spin_lock_bh(lock)`                  | 获取锁，同时**禁止软中断**（Bottom Halves）。                               | 适用于锁在**进程上下文**和**软中断/Tasklet**之间共享的场景。                                               |
|                                    | `spin_unlock_bh(lock)`                | 释放锁，并**重新开启软中断**。                                             | 必须与 `spin_lock_bh` 配对使用。                                                             |
| **硬中断安全**<br>(IRQ Safe)<br>**最常用** | `spin_lock_irqsave(lock, flags)`      | 1. 保存当前 CPU 状态（中断标志位）到 `flags`。<br>2. **禁止本地硬中断**。<br>3. 获取锁。 | **驱动开发最推荐使用的接口**。<br>适用于锁在**中断处理函数(ISR)**中被使用的情况。<br>`flags` 必须是 `unsigned long` 类型。 |
|                                    | `spin_unlock_irqrestore(lock, flags)` | 1. 释放锁。<br>2. 将 CPU 状态恢复为 `flags` 记录的状态（恢复中断）。                | 必须与 `spin_lock_irqsave` 配对使用。<br>注意：是 `restore` 不是 `enable`。                         |
| **硬中断(快速)**<br>(不保存状态)             | `spin_lock_irq(lock)`                 | 1. **禁止本地硬中断**。<br>2. 获取锁。                                    | **慎用**。它不保存中断状态。如果调用前中断已经被关闭，调用对应的 unlock 后中断会被错误地强行打开。                              |
|                                    | `spin_unlock_irq(lock)`               | 1. 释放锁。<br>2. **无条件开启硬中断**。                                   | 必须与 `spin_lock_irq` 配对使用。                                                            |
| **非阻塞尝试**<br>(Trylock)             | `spin_trylock(lock)`                  | **尝试**获取锁。如果成功返回 1，失败返回 0。不会自旋。                               | 适用于不能等待的场景。                                                                          |
|                                    | `spin_trylock_irqsave(lock, flags)`   | 关中断并尝试获取锁。                                                    | 组合功能。                                                                                |
| **状态查询**                           | `spin_is_locked(lock)`                | 检查锁当前是否被占用。                                                   | 返回 1 表示被锁，0 表示未锁。<br>通常用于 `BUG_ON` 断言检查，不建议用于逻辑判断。                                   |

### 如何选择正确的 API？

为了防止死锁，必须根据**锁的竞争者是谁**来选择 API：

| 场景：锁被谁共享？ | 你的代码运行在进程上下文时，应该用： | 你的代码运行在中断上下文时，应该用： |
| :--- | :--- | :--- |
| **仅进程 A vs 进程 B** | `spin_lock` | N/A |
| **进程 vs 软中断/Tasklet** | `spin_lock_bh` | `spin_lock` |
| **进程 vs 硬中断 (ISR)** | **`spin_lock_irqsave`** | `spin_lock` |
| **软中断 vs 硬中断** | **`spin_lock_irqsave`** | `spin_lock` |

### 1. 主要功能与核心概念

**Spinlock** 的设计初衷是为了保护那些**极其短小**的临界区代码。

*   **忙等待 (Busy Wait)**：
    *   当一个线程尝试获取 Spinlock 但锁被占用时，它**不会睡眠**（不会让出 CPU），而是会在一个循环中不断地检查锁是否被释放（即“原地自旋”）。
    *   这就像你在厕所门口，每隔 0.1 秒敲一次门问“好了吗？”，而不是回座位等待叫号。
*   **适用上下文**：
    *   它是唯一可以在**中断上下文 (Interrupt Context)**（如硬中断 ISR、软中断 Softirq）中使用的锁机制。
    *   因为中断上下文不能睡眠，所以 Mutex、Semaphore 等睡眠锁在中断中是禁用的，必须用 Spinlock。
*   **多核同步**：
    *   在单核（UP）系统中，自旋锁通常被优化为空操作（或者仅仅是禁止抢占），因为单核无法同时运行两个任务来竞争同一个锁。Spinlock 主要是为了解决 SMP（多对称处理器）架构下的并发竞争。

### 2. 实现原理 (演进史)

Linux Spinlock 的实现随着硬件的发展经历了多次迭代，为了解决性能和公平性问题。

#### 第一阶段：简单的原子变量 (Wild Spinlock) - *已弃用*
*   **原理**：使用一个整数（0表示空闲，1表示占用）。
*   **加锁**：使用原子指令（如 x86 的 `LOCK XCHG` 或 `CAS`）尝试将 0 变为 1。
*   **缺点**：**不公平**。当锁释放时，所有等待的 CPU 蜂拥而上（惊群效应），谁抢到算谁的，可能导致某些 CPU 饿死。

#### 第二阶段：票据自旋锁 (Ticket Spinlock) - *经典实现*
*   **原理**：类比银行排队叫号系统。锁结构体包含 `next`（发号器）和 `owner`（叫号器）。
*   **结构**：
    ```c
    struct spinlock {
        unsigned short owner; // 当前持有锁的号码
        unsigned short next;  // 下一个领取的号码
    };
    ```
*   **加锁流程**：
    1.  CPU A 申请锁：原子地获取 `next` 值并让 `next++`。假设拿到的是 5 号。
    2.  自旋：CPU A 不断检查 `owner` 是否等于 5。
*   **解锁流程**：
    1.  当前持有者释放锁：将 `owner++`（变为 5）。
    2.  CPU A 发现 `owner == 5`，成功进入临界区。
*   **优点**：**绝对公平 (FIFO)**，先来后到。
*   **缺点**：**Cache Line Bouncing (缓存行颠簸)**。
    *   所有等待的 CPU 都在读取同一个变量 (`owner`)。当持有者修改 `owner` 时，会导致所有等待 CPU 的 L1/L2 缓存失效，它们必须重新从内存拉取数据，造成总线风暴，严重影响性能。

#### 第三阶段：排队自旋锁 (Queued Spinlock / qspinlock) - *Linux 4.2+ 主流*
*   **原理**：为了解决缓存颠簸，采用了 **MCS Lock** 的变种。
*   **核心思想**：每个等待的 CPU 不再去刷全局的锁变量，而是**只刷自己私有的变量**。
*   **实现**：
    *   等待者在内存中构建一个**链表（Queue）**。
    *   每个等待者持有链表的一个节点，它只需要监视**前一个节点**的状态。
    *   当持有锁的人释放时，它只通知链表头部的那个节点。
*   **优点**：极大减少了缓存同步流量，支持海量 CPU 并发（如 64核+ 服务器）。
*   **大小**：尽管逻辑复杂，但 Linux 通过巧妙的位操作，将 `struct spinlock` 的大小依然控制在 **4 字节**。

### 3. API 变体与使用场景

选择正确的 API 是使用 Spinlock 的关键，否则会导致死锁。

| API 函数 | 功能描述 | 适用场景 | 备注 |
| :--- | :--- | :--- | :--- |
| `spin_lock(&lock)` | 获取锁，**禁止内核抢占**。 | 锁仅在**进程上下文**之间共享。 | 最轻量级。 |
| `spin_lock_bh(&lock)` | 获取锁，禁止抢占 + **禁止软中断**。 | 锁在**进程**和**软中断(Softirq/Tasklet)**之间共享。 | 防止软中断打断进程导致死锁。 |
| `spin_lock_irqsave(&lock, flags)` | 获取锁，禁止抢占 + **关闭本地硬中断** + 保存标志位。 | 锁在**进程**和**硬中断(ISR)**之间共享。 | **驱动开发最常用**，最安全。 |
| `spin_unlock(...)` | 对应的解锁函数。 | - | 必须成对使用。 |

---

### 4. 使用注意事项 (四大戒律)

在使用 Spinlock 时，违反以下规则通常会导致系统挂死（Hang）或崩溃（Oops）。

#### 1. 严禁睡眠 (NO SLEEPING)
*   **规则**：持有自旋锁期间，**绝对不能**调用任何可能导致睡眠或调度的函数。
*   **原因**：
    *   如果你持有锁并睡眠了（放弃 CPU），另一个线程想拿锁就会在 CPU 上死循环自旋。
    *   如果那个线程恰好是你的唤醒者，或者是高优先级的任务，系统就会进入**死锁**。
*   **禁止调用**：`msleep()`, `copy_from_user()`, `kmalloc(..., GFP_KERNEL)`, `mutex_lock()`, `down()` 等。

#### 2. 临界区必须极短 (Make it Fast)
*   **规则**：拿到锁，做完事，立刻释放。
*   **原因**：
    *   自旋锁等待者是**忙等待**，不干活只耗电。
    *   持有锁期间通常会关闭抢占甚至中断，这会增加系统的**调度延迟**和**中断延迟**，影响实时性。

#### 3. 避免死锁：防止中断抢占
*   **场景**：如果你的锁在 `进程A` 和 `中断处理函数(ISR)` 中共享。
*   **规则**：`进程A` 加锁时，必须使用 **`spin_lock_irqsave()`** 关闭中断。
*   **死锁演示**：
    1.  进程 A 获取锁 `L`。
    2.  发生中断，CPU 暂停进程 A，跳转执行 ISR。
    3.  ISR 代码也试图获取锁 `L`，并开始自旋等待。
    4.  **死锁**：ISR 等 A 释放，A 等 ISR 结束才能继续运行释放锁。

#### 4. 严禁递归 (No Recursion)
*   **规则**：同一个线程不能重复获取同一把自旋锁。
*   **原因**：Linux 的 Spinlock 是不可递归的。
    ```c
    spin_lock(&lock);
    spin_lock(&lock); // 还没解锁就再次加锁 -> 立即死锁
    ```

### 5. 总结

*   **Spinlock 是为了“短、平、快”而生的**：它用于保护那些只需几条指令就能完成的临界区（如修改链表指针、位图标记）。
*   **它是中断上下文的唯一选择**：在中断里不能用 Mutex。
*   **使用代价**：它是以消耗 CPU 周期为代价换取低延迟，如果临界区较长，请使用 `Mutex`。
*   **最常用的咒语**：在写驱动时，如果你不确定上下文，使用 `spin_lock_irqsave` 通常是最安全（虽然可能不是性能最优）的选择。

## spin_lock vs raw_spin_lock


在 Linux 内核开发中，`spin_lock` 和 `raw_spin_lock` 的选择主要取决于**你是否考虑“PREEMPT_RT”（实时内核补丁）的影响**。

简单来说：**对于 99% 的驱动开发和内核模块编写，请始终使用 `spin_lock`。只有在极少数涉及内核核心架构（如调度器、中断控制器）的代码中，才使用 `raw_spin_lock`。**

以下是详细的对比和选择逻辑：

### 1. 为什么会有这两套接口？

在标准的 Linux 内核（Mainline / Vanilla Kernel）中，这两者**几乎没有区别**。`spinlock_t` 的底层实现其实就是 `raw_spinlock_t`。

**分歧点在于 PREEMPT_RT（实时补丁）：**
Linux 社区为了支持硬实时特性（Hard Real-Time），引入了 PREEMPT_RT补丁。在这个补丁下，普通的 `spinlock` 被修改成了**可睡眠的互斥锁（Mutex）**，以减少不可抢占的时间（Latency）。但是，内核中有些核心代码（如调度器本身）是绝对不能睡眠的，因此保留了 `raw_spin_lock` 作为**真正的、永远自旋的锁**。

### 2. 行为对比表

| 特性 | 标准内核 (Standard Kernel) | 实时内核 (PREEMPT_RT Kernel) |
| :--- | :--- | :--- |
| **`spin_lock()`** | **自旋 (Spin)**<br>禁止抢占，不让出 CPU | **睡眠 (Sleep)**<br>底层变为 `rt_mutex`，可被抢占，竞争时会挂起 |
| **`raw_spin_lock()`** | **自旋 (Spin)**<br>禁止抢占 | **自旋 (Spin)**<br>依然禁止抢占，绝对不睡眠 |
| **中断上下文使用** | 都可以 | `spin_lock` 在硬中断中可能出问题 (因为变成了睡眠锁)；<br>`raw_spin_lock` 可以在任何上下文使用 |

### 3. 详细选择指南

#### 场景 A：使用 `spin_lock` (推荐)
**适用对象：** 设备驱动、文件系统、绝大多数内核子系统。

**理由：**
1.  **RT 兼容性**：当你使用 `spin_lock` 时，你的代码在标准内核下会“自旋”（高性能），而在 RT 内核下会自动变成“睡眠锁”（高实时性）。内核会自动帮你处理这种转换。
2.  **保护数据**：大多数时候，你加锁是为了保护某个数据结构（如链表、状态机）不被并发破坏。这种临界区稍微延长一点时间通常是可以接受的。

#### 场景 B：使用 `raw_spin_lock` (慎用)
**适用对象：** 调度器 (Scheduler)、低层中断处理代码、时钟子系统、RCU 内部实现、Lockdep 本身。

**理由：**
只有在以下极端情况下才使用 `raw_spin_lock`：
1.  **绝对不能睡眠的区域**：即使在 RT 内核中，你的临界区内也绝对不能发生上下文切换。例如，你在 `schedule()` 函数内部，或者在处理 CPU 上下文切换的极低层代码中。
2.  **极小的延迟要求**：你需要绝对禁止内核抢占，确保这几行代码原子执行，不被任何高优先级的实时任务打断。
3.  **防止死锁**：如果你的锁是在硬中断关闭（`local_irq_disable`）的情况下使用的，并且该区域必须在关中断下运行。在 RT 内核中，普通的 `spin_lock` 不会真正关中断（因为它是 mutex），而 `raw_spin_lock` 依然会关中断。

### 4. 代码层面的实现 (便于理解)

在 `include/linux/spinlock_types.h` 中，你可以看到这种包含关系：

```c
typedef struct spinlock {
    union {
        struct raw_spinlock rlock; // 标准内核其实就是包了一层 raw_spinlock
#ifdef CONFIG_DEBUG_LOCK_ALLOC
# define LOCK_PADSIZE (offsetof(struct raw_spinlock, dep_map))
        struct {
            u8 __padding[LOCK_PADSIZE];
            struct lockdep_map dep_map;
        };
#endif
    };
} spinlock_t;
```

但是在开启 `CONFIG_PREEMPT_RT` 后，`spinlock_t` 的定义会完全改变，变成基于 `rt_mutex` 的结构，而 `raw_spinlock` 保持不变。

### 5. 总结与决策图

当你需要加锁时，请遵循以下决策流程：

1.  **这是驱动程序或普通内核模块吗？**
    *   是 $\rightarrow$ 用 **`spin_lock`**。
    *   否 (我在写调度器或架构核心代码) $\rightarrow$ 见 2。

2.  **这个临界区是否非常短，且绝对不允许被抢占（即使被更高优先级的实时任务抢占也不行）？**
    *   是 $\rightarrow$ 用 **`raw_spin_lock`**。
    *   否 $\rightarrow$ 用 **`spin_lock`**。

3.  **这个临界区会被硬件中断处理函数 (Hard IRQ ISR) 调用吗？**
    *   是 $\rightarrow$ 在 RT 内核下，ISR 会被线程化 (Threaded IRQ)。
        *   如果你希望你的 ISR 在 RT 下依然在硬中断上下文运行（`IRQF_NO_THREAD`），你必须用 **`raw_spin_lock`**。
        *   如果你接受 ISR 被线程化（默认情况），用 **`spin_lock`**。

**一句话总结：除非你非常清楚为什么要禁止 RT 内核的抢占特性，否则永远使用 `spin_lock`。滥用 `raw_spin_lock` 会破坏 Linux 的实时性（增加了系统最大延迟）。**
