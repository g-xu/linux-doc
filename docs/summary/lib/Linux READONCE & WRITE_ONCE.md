## READONCE & WRITE_ONCE
`READ_ONCE()` 和 `WRITE_ONCE()` 是 Linux 内核并发编程中**最基础**、**最重要**的两个宏。

一句话总结：它们用于**约束编译器（Compiler）的行为**，确保对变量的读取和写入操作是**原子的（Atomic）**且**不被优化掉的**。

它们主要解决的是 **C 语言编译器优化在多线程/多核环境下带来的副作用**。

---

### 1. 为什么需要它们？（解决的三大问题）

现代编译器（如 GCC, Clang）非常智能，它们默认认为程序是**单线程**执行的。为了提升性能，编译器会进行各种激进的优化，但在内核并发场景下，这些优化可能会导致严重的 Bug。

`READ_ONCE` 和 `WRITE_ONCE` 主要防止以下三种编译器行为：

#### A. 防止“读取/写入撕裂” (Load/Store Tearing)
*   **问题：** 假设你在 32 位 CPU 上写一个 64 位的变量 `u64 global_val`。
    *   编译器可能会把它拆成**两条** 32 位的指令（先写高 32 位，再写低 32 位）。
    *   **后果：** 如果在写完高 32 位时发生中断或上下文切换，另一个 CPU 读这个变量，就会读到一个“一半是新值、一半是旧值”的错误数据（即数据撕裂）。
*   **解决：** `WRITE_ONCE` 会强制编译器生成一条指令（如果硬件支持原子操作该数据类型），确保写入是原子的。

#### B. 防止“读取融合/省略” (Load Fusing / Elision)
*   **问题：** 轮询代码。
    ```c
    // 原始代码：等待 flag 变为 0
    while (flag) {
        cpu_relax();
    }
    ```
    编译器认为 `flag` 在循环体内没有被修改，因此可能把它优化成：
    ```c
    // 优化后：flag 只读一次，如果是 1，就死循环
    if (flag) {
        while (1) { cpu_relax(); }
    }
    ```
    **后果：** 即使其他 CPU 修改了 `flag` 为 0，当前 CPU 永远看不到，陷入死循环。
*   **解决：** `READ_ONCE(flag)` 告诉编译器：“这个变量随时可能被别人修改，每次循环都必须去内存里重新读，不许用寄存器缓存。”

#### C. 防止“写入融合” (Store Fusing)
*   **问题：** 连续赋值。
    ```c
    a = 1;
    a = 2;
    ```
    编译器可能觉得 `a=1` 是多余的，直接优化成只执行 `a=2`。
    **后果：** 如果另一个线程在等待 `a` 变成 1 再做某事，它就永远等不到这个状态。
*   **解决：** `WRITE_ONCE(a, 1)` 强制编译器必须把 1 写进内存。

---

### 2. 实现原理 (Implementation)

这两个宏的核心手段是利用 C 语言的 **`volatile`** 关键字。

虽然内核社区通常不建议在变量定义时直接加 `volatile`（因为这会阻止所有优化），但在访问特定变量的**那一瞬间**，将其强制转换为 volatile 类型是合理的。

简化的伪代码逻辑如下：

```c
// READ_ONCE(x) 的逻辑
#define READ_ONCE(x)  (*(const volatile typeof(x) *)&(x))

// WRITE_ONCE(x, val) 的逻辑
#define WRITE_ONCE(x, val)  do { *(volatile typeof(x) *)&(x) = (val); } while (0)
```

*   **`volatile` 的作用：** 告诉编译器，这块内存是“易变的”，**必须**生成访存指令，不能使用寄存器缓存，不能省略，不能重排。
*   **类型转换：** 将变量地址强制转为 `volatile` 指针，再解引用。

---

### 3. 它们与“内存屏障”的区别（核心考点）

这是最容易混淆的地方：**`READ_ONCE` / `WRITE_ONCE` 仅仅是编译器屏障，不是 CPU 内存屏障。**

| 特性 | READ_ONCE / WRITE_ONCE | 内存屏障 (smp_mb, smp_load_acquire) |
| :--- | :--- | :--- |
| **约束对象** | **编译器** (Compiler) | **CPU** (Hardware) + 编译器 |
| **防止重排?** | 防止编译器重排指令。 | 防止 CPU 乱序执行指令。 |
| **保证可见性?**| 保证当前 CPU 确实发出了读写指令。 | 保证多核之间的数据可见性顺序。 |
| **开销** | 极低 (无额外指令，仅影响优化)。 | 较高 (可能阻塞流水线)。 |

**关键结论：**
如果两个变量之间存在**依赖关系**（例如：先写数据，再写标志位），光用 `WRITE_ONCE` 是不够的，必须配合 **内存屏障**。

**错误示例：**
```c
// CPU A
data = 100;
WRITE_ONCE(ready, 1); // 即使用了 WRITE_ONCE，CPU 硬件仍可能先执行 ready=1

// CPU B
if (READ_ONCE(ready)) // 读到了 1
    val = data;       // 但 data 可能还是 0（硬件乱序）
```

**正确示例：**
```c
// CPU A
data = 100;
smp_store_release(&ready, 1); // 包含了屏障 + WRITE_ONCE 的语义

// CPU B
if (smp_load_acquire(&ready))
    val = data;
```

---

### 4. 何时使用？(Best Practices)

在 Linux 内核开发中，以下场景必须使用 `READ_ONCE` / `WRITE_ONCE`：

1.  **访问共享变量时（无锁访问）：**
    当一个变量被多个 CPU 或中断处理程序访问，且没有使用锁（Spinlock/Mutex）保护时。
    *   例如：读取某个状态标志位、统计计数器。

2.  **轮询循环（Polling Loops）：**
    `while (READ_ONCE(condition)) ...`

3.  **防止撕裂（Anti-Tearing）：**
    修改指针、长整型数据时，确保原子性。

4.  **配合内存屏障使用时：**
    通常在内存屏障之间访问数据时使用，确保编译器配合。

### 总结

*   **`READ_ONCE(x)`**: "编译器大哥，别自作聪明，请务必去内存里把 `x` 读出来，别给我用寄存器里的旧值，也别把读操作优化没了。"
*   **`WRITE_ONCE(x, v)`**: "编译器大哥，请务必生成一条指令把 `v` 写入 `x`，别搞拆分，也别觉得这行代码没用就删了。"
*   **注意：** 它们管不了 **CPU** 乱序，如果需要多核同步，请找 `smp_mb` 或 `smp_store_release`。
