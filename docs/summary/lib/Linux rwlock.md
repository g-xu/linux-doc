
## rwlock
Linux 内核中的 **rwlock (Read-Write Lock)** 是一种特殊的自旋锁（Spinlock）机制，旨在针对**“读多写少”**的场景进行优化。

与普通的自旋锁（Spinlock）不同，rwlock 区分了“读者”和“写者”两种角色，允许多个读者并行访问临界区，但写者必须独占访问。

> 注意：现代Linux内核rwlock已经不推荐使用了，更推荐使用rcu/spinlock!!

---

### 1. 核心概念

rwlock 的设计遵循以下基本规则：

1.  **共享读 (Shared Read)**：
    *   当没有写者持有锁，也没有写者在等待锁（视实现而定）时，**多个读者**可以同时获得读锁进入临界区。
    *   读者之间互不干扰，并行执行。
2.  **独占写 (Exclusive Write)**：
    *   写者必须**独占**锁。
    *   当写者持有锁时，禁止任何其他读者或写者进入临界区。
    *   如果已有读者在临界区内，写者必须自旋等待，直到所有读者离开。

**本质**：`rwlock_t` 底层依然是**自旋锁**（Spinlock），这意味着在等待锁的过程中，CPU 会处于忙等待（Busy-wait）状态，**不会睡眠**。

---

### 2. 工作原理与底层实现

在 Linux 内核演进过程中，rwlock 的实现发生了很大变化，主要经历了从“原子计数器”到“排队锁”的转变。

#### 2.1 传统实现 (Legacy)
早期实现通常基于一个原子计数器（例如 32 位整数）：
*   **0x00000000**：解锁状态。
*   **正数**：表示当前读者的数量（例如 `0x00000003` 表示有 3 个读者）。
*   **负数/特定位掩码**：表示有写者持有锁（例如 `0x80000000`）。

这种实现简单，但存在严重的**写者饥饿（Writer Starvation）**问题：如果读者源源不断地来，计数器始终不归零，写者就永远拿不到锁。

#### 2.2 现代实现：QRWLock (Queued Read-Write Lock)
为了解决竞争激烈时的缓存颠簸（Cache Bouncing）和写者饥饿问题，现代 Linux（如 x86 架构）默认使用 **QRWLock**。

*   **排队机制**：它引入了 MCS 锁（一种基于链表的自旋锁）的概念。
*   **公平性**：
    *   当写者申请锁时，如果锁被读者占用，写者会把自己放入等待队列，并设置一个标志位（Waiting Flag）。
    *   一旦设置了写者等待标志，**新来的读者**将无法获取锁，必须等待。
    *   等当前临界区内已有的读者全部离开后，写者立即获得锁。
    *   这大大缓解了写者饥饿问题。

---

### 3. 核心 API 汇总

rwlock 的 API 与 spinlock 非常相似，只是区分了读和写。

#### 3.1 定义与初始化
```c
rwlock_t my_lock;

// 动态初始化
rwlock_init(&my_lock);

// 静态定义并初始化
DEFINE_RWLOCK(my_lock);
```

#### 3.2 读侧 API (Reader)
读者进入临界区极快，只有在有写者锁定时才会自旋。

```c
// 1. 获取读锁 (如果写者持有，则自旋等待)
read_lock(&my_lock);
/* 临界区 (只读操作) */
read_unlock(&my_lock);

// 2. 禁止中断版本 (如果临界区会被中断处理程序访问)
unsigned long flags;
read_lock_irqsave(&my_lock, flags);
/* ... */
read_unlock_irqrestore(&my_lock, flags);

// 3. 尝试获取 (成功返回非0，失败返回0，不等待)
if (read_trylock(&my_lock)) {
    /* ... */
    read_unlock(&my_lock);
}
```

#### 3.3 写侧 API (Writer)
写者具有排他性，开销较大。

```c
// 1. 获取写锁 (如果有读者或写者，则自旋等待)
write_lock(&my_lock);
/* 临界区 (读写操作) */
write_unlock(&my_lock);

// 2. 禁止中断版本
unsigned long flags;
write_lock_irqsave(&my_lock, flags);
/* ... */
write_unlock_irqrestore(&my_lock, flags);

// 3. 尝试获取
if (write_trylock(&my_lock)) {
    /* ... */
    write_unlock(&my_lock);
}
```

---

### 4. 适用场景

rwlock 并不是任何时候都比 spinlock 好，必须满足以下条件才建议使用：

1.  **读多写少**：读操作的频率远远高于写操作（例如 10:1 甚至 100:1）。
2.  **临界区短小**：因为 rwlock 是自旋锁，持有锁期间 CPU 不会调度，如果临界区过长，浪费 CPU 周期。
3.  **不能睡眠**：只能在原子上下文（Atomic Context）中使用（如中断上下文）。如果需要在临界区睡眠，请使用 **`rw_semaphore`**（读写信号量）。
4.  **数据强一致性**：读者必须看到最新的数据，不能容忍陈旧数据（这点与 RCU 不同）。

**典型场景：**
*   **任务链表遍历**：系统中经常遍历任务列表查找某个进程（读），但很少创建或销毁进程（写）。
*   **配置信息查询**：频繁读取配置，偶尔更新配置。

---

### 5. rwlock 与其他锁的对比

| 特性 | rwlock_t (读写自旋锁) | spinlock_t (普通自旋锁) | rw_semaphore (读写信号量) | RCU |
| :--- | :--- | :--- | :--- | :--- |
| **基础机制** | 自旋 (Busy-wait) | 自旋 (Busy-wait) | 睡眠 (Sleep) | 发布/订阅 + 宽限期 |
| **读写并行** | **支持** | 不支持 | **支持** | **支持 (且读者无锁)** |
| **上下文** | 原子上下文 (不可睡眠) | 原子上下文 (不可睡眠) | 进程上下文 (可睡眠) | 任意 (读侧) |
| **写者开销** | 高 (需等待所有读者) | 低 | 高 (上下文切换开销) | 高 (需复制/等待) |
| **读者开销** | 中 (需原子操作更新计数) | 高 (需等待锁) | 高 (上下文切换风险) | **极低 (接近零)** |

**结论**：
*   如果**写操作也非常频繁**，rwlock 的性能反而不如 spinlock（因为 rwlock 的原子操作更复杂，且存在缓存行竞争）。
*   如果**临界区需要睡眠**（如内存分配、IO操作），必须用 `rw_semaphore`。
*   如果**追求极致的读性能**，且能容忍短暂的旧数据，首选 **RCU**。

## APIs

以下是 Linux 内核 **rwlock (Read-Write Lock)** 模块主要 API 的详细汇总。

为了方便查阅，我将这些 API 分为 **定义与初始化**、**读侧操作**、**写侧操作** 以及 **非阻塞尝试** 四个类别。

### 1. 定义与初始化 (Definition & Initialization)

| API / 宏 | 功能描述 | 适用场景与备注 |
| :--- | :--- | :--- |
| **`DEFINE_RWLOCK(x)`** | **静态定义并初始化**。<br>声明一个名为 `x` 的全局 `rwlock_t` 变量并初始化为未锁定状态。 | 适用于全局变量或静态变量的定义。 |
| **`rwlock_init(lock)`** | **动态初始化**。<br>初始化一个已经存在的 `rwlock_t` 指针指向的锁。 | 适用于结构体内部嵌入的锁，或者动态分配内存（`kmalloc`）后的锁初始化。 |

---

### 2. 读侧 API (Reader Side)
**核心规则**：允许多个读者同时进入临界区，但如果有写者持有锁，则读者会自旋等待。

| API / 宏 | 功能描述 | 关键点与上下文 |
| :--- | :--- | :--- |
| **`read_lock(lock)`** | **获取读锁**。<br>1. 禁止内核抢占（Preemption）。<br>2. 若写者持有锁，则自旋等待。 | **基础版本**。适用于临界区**不会**被中断处理程序（Interrupt Handler）访问的场景。 |
| **`read_unlock(lock)`** | **释放读锁**。<br>1. 释放锁。<br>2. 重新开启内核抢占。 | 必须与 `read_lock` 配对使用。 |
| **`read_lock_irq(lock)`** | **禁止中断并获取读锁**。<br>1. 禁止本地硬中断。<br>2. 获取读锁。 | 适用于临界区会在中断上下文中被访问，且**确信当前中断是开启的**。 |
| **`read_unlock_irq(lock)`** | **释放读锁并开启中断**。<br>1. 释放锁。<br>2. 无条件开启本地硬中断。 | 必须与 `read_lock_irq` 配对使用。 |
| **`read_lock_irqsave(lock, flags)`** | **保存中断状态并获取读锁**。<br>1. 保存当前中断状态到 `flags`。<br>2. 禁止中断。<br>3. 获取读锁。 | **最安全、最通用**的版本。适用于不确定当前中断状态，或者在可能嵌套调用的函数中使用。 |
| **`read_unlock_irqrestore(lock, flags)`** | **释放读锁并恢复中断状态**。<br>1. 释放锁。<br>2. 将中断状态恢复为 `flags` 记录的状态。 | 必须与 `read_lock_irqsave` 配对使用。 |
| **`read_lock_bh(lock)`** | **禁止软中断并获取读锁**。<br>1. 禁止下半部（Bottom Halves / SoftIRQs）。<br>2. 获取读锁。 | 适用于临界区会被软中断（如网络协议栈、Tasklet）访问，但不会被硬中断访问的场景。 |
| **`read_unlock_bh(lock)`** | **释放读锁并开启软中断**。 | 必须与 `read_lock_bh` 配对使用。 |

---

### 3. 写侧 API (Writer Side)
**核心规则**：写者必须**独占**访问。如果有任何读者或写者持有锁，当前写者必须自旋等待。

| API / 宏 | 功能描述 | 关键点与上下文 |
| :--- | :--- | :--- |
| **`write_lock(lock)`** | **获取写锁**。<br>禁止抢占，独占临界区。 | **基础版本**。同 `read_lock`，仅用于无中断干扰场景。 |
| **`write_unlock(lock)`** | **释放写锁**。<br>释放锁，开启抢占。 | 必须与 `write_lock` 配对使用。 |
| **`write_lock_irq(lock)`** | **禁止中断并获取写锁**。<br>禁止硬中断 + 独占锁。 | 同 `read_lock_irq`，用于写侧。 |
| **`write_unlock_irq(lock)`** | **释放写锁并开启中断**。 | 必须与 `write_lock_irq` 配对使用。 |
| **`write_lock_irqsave(lock, flags)`** | **保存状态并获取写锁**。<br>保存 `flags` + 禁止中断 + 独占锁。 | **最常用**的写锁版本，防止死锁（如中断处理程序也要获取该锁）。 |
| **`write_unlock_irqrestore(lock, flags)`** | **释放写锁并恢复状态**。 | 必须与 `write_lock_irqsave` 配对使用。 |
| **`write_lock_bh(lock)`** | **禁止软中断并获取写锁**。<br>禁止 BH + 独占锁。 | 同 `read_lock_bh`，用于写侧。 |
| **`write_unlock_bh(lock)`** | **释放写锁并开启软中断**。 | 必须与 `write_lock_bh` 配对使用。 |

---

### 4. 非阻塞尝试 API (Try-Lock Variants)
**核心规则**：尝试获取锁，如果锁被占用（对于写者是被任何人占用，对于读者是被写者占用），**立即返回**，不进行自旋等待。

| API / 宏 | 功能描述 | 返回值 |
| :--- | :--- | :--- |
| **`read_trylock(lock)`** | **尝试获取读锁**。<br>如果当前没有写者持有锁，则获取成功。 | **非 0**：获取成功（此时需负责 unlock）。<br>**0**：获取失败（锁被写者占用）。 |
| **`write_trylock(lock)`** | **尝试获取写锁**。<br>如果当前没有任何人（读者或写者）持有锁，则获取成功。 | **非 0**：获取成功。<br>**0**：获取失败。 |

---

### 5. 速查：我该用哪个？

| 场景 | 推荐 API (X = read 或 write) |
| :--- | :--- |
| **普通线程上下文**，不涉及中断/软中断 | `X_lock()` |
| **中断上下文 (Hard IRQ)** 访问此数据 | `X_lock_irqsave()` (最稳妥) |
| **软中断上下文 (Soft IRQ / Tasklet)** 访问此数据 | `X_lock_bh()` |
| **不能阻塞/不能等待** | `X_trylock()` |
| **临界区内需要睡眠** | **错误！** 请改用 `rw_semaphore` (读写信号量)。 |
| **读操作极其频繁，写操作极少** | 考虑改用 **RCU**，性能更好。 |
### 6. 注意事项与常见陷阱 (Pitfalls)

#### 6.1 严禁在临界区睡眠
`rwlock_t` 是自旋锁，在 `read_lock` 或 `write_lock` 之后睡眠会导致**系统死锁**或报错（`scheduling while atomic`）。

#### 6.2 递归死锁 (Recursive Deadlock)
这是新手最容易犯的错误：

*   **错误场景 A（自死锁）**：
    写者获取锁后，再次尝试获取写锁或读锁 -> **死锁**。
*   **错误场景 B（升级锁死锁）**：
    读者已经持有了 `read_lock`，在不释放的情况下尝试调用 `write_lock` 想要“升级”权限。
    *   **结果**：写者会等待所有读者释放，而自己作为读者之一在等待写锁成功才释放，导致死锁。
    *   **修正**：必须先 `read_unlock`，再 `write_lock`（注意：这期间数据可能被修改）。

#### 6.3 中断安全性
如果临界区内的数据也会在**中断处理程序 (ISR)** 中被访问（无论是读还是写），那么在进程上下文中加锁时，必须使用 `_irq` 或 `_irqsave` 版本，否则会导致死锁。

*   *场景*：进程 A 持有 `write_lock` -> 中断发生 -> 中断处理程序尝试 `read_lock` -> 必须等待写者释放 -> CPU 被中断占用，进程 A 无法继续运行释放锁 -> **死锁**。

#### 6.4 缓存颠簸 (Cache Bouncing)
即使是读锁，获取锁时也需要对全局变量（锁状态）进行原子修改（增加读者计数）。在多核（Many-core）系统上，如果所有 CPU 都频繁争抢同一个 rwlock 的读锁，会导致严重的 Cache Line 在 CPU 之间跳来跳去，性能急剧下降。
*   **解决**：这种场景下，**RCU** 是更好的选择，因为 RCU 读者不需要写共享内存。

### 7. 总结

Linux 内核的 rwlock 模块是解决并发控制中“读写不对称”问题的利器。

*   **优点**：提高了读多写少场景下的并发度。
*   **缺点**：相比 spinlock 有更高的原子操作开销；相比 RCU 读者有开销。
*   **现状**：在现代 Linux 内核开发中，`rwlock` 的使用频率正在逐渐降低，越来越多的场景被 **RCU** 取代。但在必须保证数据强一致性且不可睡眠的短临界区场景下，rwlock 依然是不可或缺的工具。
