## 开篇:一桩你天天在制造、却没想过原理的"怪事"

你在一台"8 GB 内存"的机器上,同时开着浏览器、编辑器、几十个终端、一个数据库。你随手 `cat /proc/meminfo` 或打开任务管理器,把所有进程"申请"的内存加起来——轻轻松松超过 20 GB。可机器不但没崩,还跑得挺顺。

再想一个更具体的:你写一行 `char *p = malloc(1 << 30);`(申请 1 GB),它秒回、成功。可你这台机器此刻空闲物理内存也许只有几百 MB。**内存明明不够,为什么申请还成功了?** 而且——如果你申请完不去碰它,系统内存占用几乎纹丝不动;只有当你真的往 `p` 里写数据,内存才一点点被吃掉。

这两桩"怪事"背后,是同一套机器在运转。它要回答的核心问题只有一句:

> **进程想用内存,内核怎么把物理内存"给"它;当物理内存紧张时,又怎么把内存"收"回来?**

整份导读,都是这一个问题的不同侧面。给、映射、收——记住这三个字,下面每一节都在讲其中之一。

## §1 三十秒心智模型:内存管理就干三件事

把整个 mm 子系统扒到最简,它只干三件事:

```
        ┌─────────────────────────────────────────────────────┐
        │                进程说:我要内存                        │
        └───────────────────────┬─────────────────────────────┘
                                 │
     ①给      ②映射                              ③收
  ┌──────────────┐   ┌────────────────────┐   ┌──────────────────┐
  │ 从物理内存里  │   │ 把物理页"贴"到进程   │   │ 内存紧张时, 把不  │
  │ 抠出空闲页    │──▶│ 看到的虚拟地址上     │   │ 常用的页夺回来,  │
  │ (伙伴/slab)  │   │ (页表 + MMU 翻译)    │   │ 腾给更需要的人    │
  └──────────────┘   └────────────────────┘   └──────────────────┘
   谁在管空闲页?       进程看到的是"假"地址,      kswapd / 直接回收 /
   → 伙伴系统            MMU 按页表翻成真地址        swap / OOM
```

- **①给(分配)**:物理内存被切成固定大小的**页**(arm64 上通常 4 KB)。谁记着哪些页空着、要几页时给哪几页?——**伙伴系统**(buddy allocator)。小于一页的零碎对象(几十字节的内核结构体)再交给 **slab/SLUB** 二次切分。
- **②映射**:进程从来看不到真实物理地址。它看到的是一套**虚拟地址**,由 CPU 里的 **MMU** 按**页表**实时翻译成物理地址。这层"障眼法"让每个进程都以为自己独占一整块连续内存,也是开篇那 20 GB > 8 GB 不崩的根本原因。
- **③收(回收)**:内存会用完。内核平时留一批空闲页当缓冲,水位低了就让后台线程 **kswapd** 醒来回收;实在来不及就让当前申请者**自己**边申请边回收(直接回收);再不行,**OOM killer** 挑一个进程杀掉腾内存。

开篇的"怪事"现在有了雏形答案:`malloc(1GB)` 成功,是因为内核只在②里给你**记了一笔账**(划出一段虚拟地址),并没有真的①分配物理页——所以不占内存。等你真去写,才触发一次"缺页",内核这时才现给你一页真的物理内存。这套"用到才给"的机制叫**按需分页**(demand paging),是 §4 的主角。

> 想深入?这三件事的全局设计动机,内核文档在 `Documentation/mm/physical_memory.rst`(物理内存怎么组织)和 `Documentation/admin-guide/mm/concepts.rst`(管理员视角的总览)。

## §2 如果让你来设计:每个结构都是"撞墙后的补丁"

别急着背内核用了什么。假装你从零设计一个内存管理器,一步步撞墙,你会发现内核的每个结构,都是某次撞墙后打的补丁。

**第一版:按字节管理。** 最朴素:维护一张空闲字节表,谁要多少字节就划多少。马上撞墙——4 GB 内存有约十亿字节,给每个字节记一条元数据,元数据本身就把内存吃光了。而且 CPU 的 MMU 天生就按**固定块**做地址翻译,不认识"任意字节区间"。

> **补丁:按页管理。** 把物理内存切成固定大小(4 KB)的**页**,以页为最小分配单位。每个物理页配一个描述符 `struct page`(`include/linux/mm_types.h:73`)记录它的状态。元数据量一下降到原来的四千分之一。

**第二版:一条空闲页链表,要几页给几页。** 撞墙:进程常要**物理上连续**的多页(比如 DMA、大结构体)。用久了空闲页东一块西一块——明明总量够,却找不出连续的 4 页,这叫**外部碎片**。而且"找连续 N 页"要扫链表,慢。

> **补丁:伙伴系统。** 把空闲页按"2 的幂次"大小(1 页、2 页、4 页…直到 1024 页)分级管理,每级一条链表。要 4 页就直接从"4 页"那级摘一块;没有就把"8 页"的劈成两半。释放时,若相邻的"伙伴"也空闲就合并回大块。这样既能 O(1) 找到合适的连续块,又能主动对抗碎片。这是 §3 的重头戏。

**第三版:内核自己也要频繁申请几十字节的小对象**(一个 `task_struct`、一个 dentry)。撞墙:最小才给一整页(4 KB)?申请个 64 字节的对象浪费 98%,这叫**内部碎片**。

> **补丁:slab/SLUB。** 在伙伴系统之上再套一层:向伙伴要整页,自己切成同尺寸的小格子(比如全是 64 字节),按对象类型开"专卖店"(kmem_cache)。§6 速览。

**第四版:进程一 `malloc` 就真给物理页。** 撞墙:就是开篇那桩事——进程申请的远比实际用的多(申请 1 GB 只写了 4 KB)。真给,物理内存瞬间被"预定"光。

> **补丁:虚拟地址 + 按需分页。** `malloc` 时只在进程的地址空间里**登记一段区间**(一个 VMA,§5),页表先不填。等进程真去访问某个地址、MMU 发现页表是空的,才触发**缺页异常**,内核这时才现分配一页物理内存填进去。§4 的主流程。

**第五版:物理页迟早会用完。** 撞墙:按需分页让内存"超卖",总有一刻真不够。

> **补丁:回收 + swap + OOM。** 内核追踪哪些页最近没被用(LRU),紧张时把干净的文件页直接丢弃(还能从磁盘重读)、把脏的匿名页写到 **swap** 分区腾出来;后台 kswapd 平时就悄悄回收,维持一个缓冲水位;真到山穷水尽,OOM killer 挑个进程祭天。§6 + §7。

到这儿,mm 的骨架就立起来了——它不是设计师一次想全的,是被这五堵墙逼出来的。下面我们挑最硬的两块深挖:先是"给"的核心(伙伴系统 §3),再是"给 + 映射"如何在一次缺页里落地(§4)。

> 想深入?"为什么按页、为什么伙伴"的官方叙述在 `Documentation/mm/page_allocation.rst`;`struct page` 每个字段的含义在 `Documentation/mm/physical_memory.rst`。

## §3 重头戏:伙伴系统——空闲页的"分级货架"

这是"给"的心脏。请慢读,我们直觉→源码→一个例子跟到底。

### 直觉:2 的幂次分级 + 拆大块补小块 + 合并碎片

想象一个五金店卖木板,货架按长度分级:1 米、2 米、4 米、8 米……每级一摞。规则就两条:

1. **拿**:客人要 4 米,直接从"4 米"那摞抽一块;那摞空了,就去"8 米"摞抽一块,当着客人面**锯成两个 4 米**,一块给他、一块放回"4 米"摞。
2. **还**:客人还回一块 4 米,店员看它旁边那块"本来是同一块 8 米锯开的兄弟"(这就是"伙伴")在不在架上——在,就**拼回 8 米**放回"8 米"摞;不在,就单独搁"4 米"摞。

内核的伙伴系统一模一样,只是"长度"换成"2 的幂次页数",级别叫 **order**:order 0 = 1 页,order 1 = 2 页,order 2 = 4 页……上限 `MAX_ORDER = 11`(`include/linux/mmzone.h:28`),注意它是**开区间上界**,所以实际 order 取值 0…10,最大一块是 `1<<10 = 1024` 页 = **4 MB**(`MAX_ORDER_NR_PAGES`,`include/linux/mmzone.h:32`)。

每一级就是一条(准确说是每种迁移类型一条)空闲链表,合起来是一个数组 `free_area[MAX_ORDER]`(`struct free_area`,`include/linux/mmzone.h:105`),挂在每个内存区 `struct zone` 上(`include/linux/mmzone.h:704`)。

```
   order   一块的大小       free_area[order].free_list(空闲块链表)
   ─────   ───────────      ───────────────────────────────────────
    0        1 页 (4K)       □ □ □ □ □ ...
    1        2 页 (8K)       ▢▢   ▢▢
    2        4 页 (16K)      ▣▣▣▣
    3        8 页 (32K)      (空)          ← 想要它却空了, 就找 order4 劈开
    4       16 页 (64K)      ▤▤▤▤▤▤▤▤▤▤▤▤▤▤▤▤
    ...
    10    1024 页 (4M)       ← 最大块 MAX_ORDER_NR_PAGES
```

**为什么偏偏是 2 的幂次?** 因为"找伙伴"要 O(1)。一块起始页号是 pfn、order 是 k 的块,它的伙伴块起始页号就是 `pfn XOR (1<<k)`——一次异或就算出来,不用搜索。这是整个算法优雅的支点。

### 源码:拿一块(__rmqueue_smallest → expand)

分配的核心就两个函数,先看"拿":`__rmqueue_smallest`(`mm/page_alloc.c:2561`)从"够用的最小级"开始往上找第一个非空链表:

```c
// mm/page_alloc.c:2561  __rmqueue_smallest —— 从 order 级开始向上找第一个有货的级
for (current_order = order; current_order < MAX_ORDER; ++current_order) {
    area = &(zone->free_area[current_order]);
    page = get_page_from_free_area(area, migratetype);
    if (!page)
        continue;                       // 这级空了, 去上一级更大的块
    del_page_from_free_list(page, zone, current_order);  // 从空闲链表摘下
    expand(zone, page, order, current_order, migratetype);// 大块劈到刚好够用
    return page;
}
```

关键在 `expand`——当你要 order 2、却只在 order 4 找到货,这块 16 页要**劈两次**降到 4 页,劈下来的半块逐级放回各自的空闲链表(`mm/page_alloc.c:2347`):

```c
// mm/page_alloc.c:2347  expand —— 把 high 级的大块劈到 low 级, 劈下的半块放回
static inline void expand(struct zone *zone, struct page *page,
        int low, int high, int migratetype)
{
    unsigned long size = 1 << high;
    while (high > low) {                        // 还没劈到目标级
        high--;  size >>= 1;                    // 降一级, 块大小减半
        // page[size] 就是这块的"后半"——把它放回下一级的空闲链表
        add_to_free_list(&page[size], zone, high, migratetype);
        set_buddy_order(&page[size], high);     // 标记它现在是 high 级的伙伴块
    }
    // 循环结束, page 指向的前半块正好是 low 级, 交给调用者
}
```

### 源码:还一块(__free_one_page 的合并)

"还"的核心是 `__free_one_page`(`mm/page_alloc.c:1095`),精髓是**尽量往上合并**:

```c
// mm/page_alloc.c:1095  __free_one_page —— 释放并尽量与伙伴合并成更大的块
while (order < MAX_ORDER - 1) {
    buddy = find_buddy_page_pfn(page, pfn, order, &buddy_pfn); // pfn XOR (1<<order)
    if (!buddy)
        break;
    if (!page_is_buddy(page, buddy, order))    // 伙伴不空闲 / order 不匹配 → 停
        break;
    del_page_from_free_list(buddy, zone, order); // 伙伴也空闲 → 摘下它
    combined_pfn = buddy_pfn & pfn;              // 合并后大块的起始 pfn
    page = page + (combined_pfn - pfn);
    pfn = combined_pfn;
    order++;                                     // 升一级, 继续试着往上合并
}
// 合并到不能再合, 把最终这块挂进 free_area[order]
add_to_free_list(page, zone, order, migratetype);
```

一次释放可能连环合并好几级:还一块 order 0,伙伴在→合成 order 1,新块的伙伴又在→合成 order 2……直到伙伴不空闲或到顶。这就是伙伴系统能**主动缝合碎片**的原因,不像朴素链表越用越碎。

### 一个例子跟到底

假设某 zone 此刻 order 0…2 全空,order 3(8 页)有一块、order 4 有一块。进程要 **1 页**(order 0):

```
  申请 order 0:
    __rmqueue_smallest 从 order 0 找起 → 0/1/2 都空 → 命中 order 3 的那块 8 页
    del_page_from_free_list 摘下这 8 页
    expand(low=0, high=3):
        high=2: 把后 4 页放回 order 2        [order2: ▣▣▣▣]
        high=1: 把接着的 2 页放回 order 1     [order1: ▢▢]
        high=0: 把再接着的 1 页放回 order 0   [order0: □]
        剩下最前面的 1 页 → 返回给进程 ✓

  货架变化:  order3 -1块,  order2 +1块,  order1 +1块,  order0 +1块
            (一块 8 页, 1 页给出去, 7 页拆成 4+2+1 分层归架)

  稍后进程释放这 1 页:
    __free_one_page: 它的伙伴(相邻那 1 页)正好就在 order0 里 → 合成 2 页(order1)
    新的 2 页块伙伴又在 order1 → 合成 4 页(order2)
    再合成 8 页(order3) → 完美复原成最初那块 8 页 ✓
```

拆开是 `expand`,拼回是 `__free_one_page` 的 while 循环——一拆一合完全对称。这就是"伙伴"二字的含义。

> 想深入?伙伴系统的迁移类型(MIGRATE_MOVABLE 等,用于抗碎片和内存规整)、每 CPU 页缓存(pcp,绕过锁的快路径)、水位与 fallback,官方文档在 `Documentation/mm/page_allocation.rst`;分配总入口是 `__alloc_pages`(`mm/page_alloc.c:5578`),慢路径(触发回收 / 规整 / OOM)是 `__alloc_pages_slowpath`(`mm/page_alloc.c:5067`)——这条慢路径把 §3 的"给"和 §6 的"收"缝在一起,是通读 mm 的枢纽函数。

## §4 主流程:一次缺页,把"给 + 映射"合起来走一遍

现在回收开篇的伏笔。`malloc` 只登记了一段虚拟地址(§2 第四版补丁),页表还是空的。进程第一次去**写**这段地址会发生什么?——MMU 翻译时发现页表项是空的,翻不出物理地址,于是抛出一个**缺页异常**(page fault),CPU 陷入内核。这是 mm 最高频的主流程,把"给一页"和"映射进页表"两件事一次做完。

### arm64 的入口:从硬件异常到 handle_mm_fault

arm64 上,MMU 的异常先落到 `do_page_fault`(`arch/arm64/mm/fault.c:516`),它做完权限检查后转给 `__do_page_fault`(`arch/arm64/mm/fault.c:486`),后者的核心动作就一句——调用架构无关的总处理器 `handle_mm_fault`(`arch/arm64/mm/fault.c:499`):

```
   进程写一个没映射的地址
        │  MMU 翻译失败, 触发同步异常
        ▼
   do_page_fault            arch/arm64/mm/fault.c:516   ← arm64 专属入口
        │  找到出错地址所属的 VMA, 查权限(是不是真该给它这页?)
        ▼
   __do_page_fault          arch/arm64/mm/fault.c:486
        │
        ▼
   handle_mm_fault          mm/memory.c:5264            ← 从这里开始架构无关
        ▼
   __handle_mm_fault        mm/memory.c:5081            ← 逐级走 pgd→p4d→pud→pmd 页表
        ▼
   handle_pte_fault         mm/memory.c:4974            ← 到最后一级, 分派具体缺页类型
```

`__handle_mm_fault`(`mm/memory.c:5081`)负责逐级走多级页表(arm64 四级:pgd→pud→pmd→pte),走到最后一级把活交给 `handle_pte_fault`。

### 分派:这是哪种缺页?

`handle_pte_fault`(`mm/memory.c:4974`)是个分流器。它先看这一级页表项(pte)的状态,再看 VMA 的类型,决定走哪条路(`mm/memory.c:5028` 起):

```c
// mm/memory.c:5028  handle_pte_fault 的核心分派(精简)
if (!vmf->pte) {                       // pte 从没建立过 —— 全新的缺页
    if (vma_is_anonymous(vmf->vma))
        return do_anonymous_page(vmf); // 匿名内存(malloc/栈/堆): 现给一张零页
    else
        return do_fault(vmf);          // 文件映射(mmap 文件/代码段): 从文件读进来
}
if (!pte_present(vmf->orig_pte))       // pte 有内容但页不在内存
    return do_swap_page(vmf);          // 之前被换出去了 —— 从 swap 换回来
...
```

- **匿名页**(`do_anonymous_page`):malloc 出来的堆、栈这类"没有后备文件"的内存。第一次访问就现给一张清零的物理页。
- **文件页**(`do_fault`,`mm/memory.c:4724`):mmap 了一个文件、或程序代码段。内容要从文件里读进来。
- **换出页**(`do_swap_page`,`mm/memory.c:5035`):这页曾经在内存里,被 §6 的回收换到 swap 了,现在换回来。

我们跟最典型的第一条——匿名页缺页,它把 §3 的"给"和本节的"映射"完整合起来。

### do_anonymous_page:现给一页 + 填进页表

`do_anonymous_page`(`mm/memory.c:4138`)做的事,浓缩成一句:**向伙伴系统要一张清零的页,构造好页表项,填进页表**。看它的收尾几行(`mm/memory.c:4191` 起):

```c
// mm/memory.c:4138  do_anonymous_page(精简到主干)
page = alloc_zeroed_user_highpage_movable(vma, vmf->address); // ← 这里最终落到 §3 的伙伴系统, 要一张清零页
...
entry = mk_pte(page, vma->vm_page_prot);      // mm/memory.c:4206  用页帧号+权限造一个页表项
entry = pte_sw_mkyoung(entry);                // :4207  标记"年轻"(刚用过, 别急着回收)
if (vma->vm_flags & VM_WRITE)
    entry = pte_mkwrite(pte_mkdirty(entry));  // :4209  可写区间就置可写+脏

page_add_new_anon_rmap(page, vma, vmf->address); // :4230  登记反向映射(回收时靠它找到谁在用这页)
lru_cache_add_inactive_or_unevictable(page, vma);// :4231  挂进 LRU 链表(§6 回收的候选池)
set_pte_at(vma->vm_mm, vmf->address, vmf->pte, entry); // :4233  真正把页表项写进页表 ★
update_mmu_cache(vma, vmf->address, vmf->pte);   // :4236  刷新 MMU/TLB, 让翻译立即生效
```

打星那行 `set_pte_at` 是"映射"落地的一刻——从这行之后,进程那个虚拟地址就真的指向了一张物理页,MMU 再翻译就能成功。异常返回,进程的那条写指令**重新执行一次**,这次顺利写入。整个过程进程毫无感知,只是那条指令"慢了一点点"。

注意两个为后面埋的伏笔:`page_add_new_anon_rmap` 建的**反向映射**(rmap)和 `lru_cache_add_*` 挂的 **LRU 链表**——它们此刻看着多余,却正是 §6 回收时的两大抓手:LRU 告诉内核"哪页最近没用",rmap 告诉内核"这页被哪些进程映射着,要回收得先把这些页表项都断掉"。

> 想深入?缺页的完整分类(写时复制 COW `do_wp_page`、NUMA 迁移 `do_numa_page`、大页 THP)在 `mm/memory.c` 里一字排开;进程地址空间与缺页的官方叙述在 `Documentation/mm/process_addrs.rst`;arm64 异常向量如何走到 `do_page_fault` 见 `arch/arm64/mm/fault.c` 顶部与 `do_translation_fault`(`arch/arm64/mm/fault.c:660`)。

## §5 换个视角:进程眼里的地址空间长什么样

§4 里 `do_page_fault` 第一件事是"找到出错地址所属的 VMA"。VMA 是什么?这一节补上"映射"的另一半——进程侧的地址空间是怎么组织的。前面全在讲物理页(内核视角),现在翻到进程视角。

### mm_struct:一个进程的整张内存地图

每个进程(准确说每个地址空间)有一个 `struct mm_struct`(`include/linux/mm_types.h:529`),它是这个进程所有内存的总管。两个关键字段:

- `pgd`(`include/linux/mm_types.h:545`):这个进程**页表的根**。§4 里 MMU 翻译、`__handle_mm_fault` 逐级走页表,起点就是它。切换进程时把它装进 arm64 的 `TTBR` 寄存器,MMU 就换了一整套翻译规则——这就是进程间内存隔离的硬件基础。
- `mm_mt`(`include/linux/mm_types.h:531`):一棵 **maple tree**,挂着这个进程所有的 VMA。

> **6.1 的关键差异**:`mm_mt` 是 **maple tree**(一种对区间查询友好、缓存局部性好的 B 树变体)。很多老资料 / 老内核里这里是一棵**红黑树** `mm_rb`——那棵红黑树在 6.1 已经被删除。你若照着老书找 `mm->mm_rb` 会扑空,记住 6.1 起是 `mm->mm_mt`。遍历 VMA 用宏 `VMA_ITERATOR`(`include/linux/mm_types.h:828`)而不是老的 `for` 循环红黑树。

### VMA:一段"性质相同"的连续虚拟地址

`struct vm_area_struct`(`include/linux/mm_types.h:461`,简称 VMA)描述进程地址空间里**一段连续、且性质一致**的区间。核心字段:

```
   struct vm_area_struct            include/linux/mm_types.h:461
   ├─ vm_start   :464   区间起始虚拟地址
   ├─ vm_end     :465   区间结束虚拟地址   → [vm_start, vm_end) 就是这段区间
   ├─ vm_mm      :468   反指所属的 mm_struct
   ├─ vm_flags   :475   权限/属性: 可读?可写?可执行?匿名还是文件?
   ├─ vm_ops     :508   这段区间的操作回调(文件映射用, 缺页时 do_fault 会调 vm_ops->fault)
   └─ vm_file    :513   若是文件映射, 指向被映射的文件; 匿名映射为 NULL
```

一个进程的地址空间,就是若干个 VMA 拼起来的(中间有空洞):

```
   进程虚拟地址空间(低 → 高)
   ┌──────────┐  vm_flags: r-x, vm_file=可执行文件   ← 代码段(文件 VMA)
   │  .text   │
   ├──────────┤  r--, vm_file=可执行文件              ← 只读数据
   │  .rodata │
   ├──────────┤  rw-, vm_file=可执行文件              ← 已初始化数据
   │  .data   │
   ├──────────┤  rw-, vm_file=NULL                    ← 堆(匿名 VMA), malloc 从这里长
   │  heap  ↓ │
   ├──────────┤
   │  ......  │  ← 空洞: 没有 VMA 的地址, 访问直接 SIGSEGV
   ├──────────┤  rw-, vm_file=映射的文件              ← mmap 的文件
   │  mmap    │
   ├──────────┤
   │  stack ↑ │  rw-, vm_file=NULL                    ← 栈(匿名 VMA), 向下增长
   └──────────┘
```

现在 §4 那句"找到出错地址所属的 VMA"就清楚了:`do_page_fault` 拿出错地址去进程的 maple tree 里查,落在哪个 VMA 区间内——

- **查不到任何 VMA**(落在空洞):非法访问,发 `SIGSEGV`(段错误)。这就是野指针崩溃的由来。
- **查到了**:再看 `vm_flags` 权限对不对(往只读区写?也 SIGSEGV),对了才进 §4 的 `handle_mm_fault` 真正给页。`vm_file` 是否为 NULL,又决定了走 §4 分派里的 `do_anonymous_page` 还是 `do_fault`。

### 翻译:虚拟地址怎么变成物理地址

MMU 拿到一个虚拟地址,以 `pgd` 为根,把地址切成几段当索引,逐级查页表,最后一级页表项(pte)里存着物理页帧号,拼上页内偏移,得到物理地址:

```
   虚拟地址  ┌─ pgd 索引 ─┬─ pud 索引 ─┬─ pmd 索引 ─┬─ pte 索引 ─┬─ 页内偏移 ─┐
            └─────┬──────┴─────┬──────┴─────┬──────┴─────┬──────┴───────────┘
     mm->pgd ─────┘            │            │            │
        │  查一级                                                            
        ▼                      ▼            ▼            ▼
      [pgd项]──▶[pud项]──▶[pmd项]──▶[pte项: 物理页帧号 + 权限位]
                                                    │
                                        + 页内偏移 = 物理地址 ✓
   任何一级为空 → 翻译失败 → 缺页异常(回到 §4)
```

§4 里"页表是空的"就是这链条上某一级为空。TLB 是这套翻译的硬件缓存,`update_mmu_cache`(§4 收尾那行)就是在维护它。

> 想深入?maple tree 的设计与 API 在 `Documentation/core-api/maple_tree.rst`;进程地址空间管理(mmap / brk / VMA 合并分裂)在 `Documentation/mm/process_addrs.rst`;arm64 页表格式(几级、每级多少位、大页)在 `Documentation/arm64/memory.rst` 与 `arch/arm64/include/asm/pgtable.h`。

## §6 一页纸速览其余四块:slab / 回收 / swap / OOM

到这里主线(给 §3 + 映射 §4/§5)已经打通。剩下四块是"给"和"收"的配套,这里各给一个直觉 + 入口函数,细节推给文档——想全懂它们各自都能再写一篇。

### slab/SLUB:小对象的"专卖店"

伙伴系统最小给一整页,但内核天天要几十字节的小对象(`task_struct`、`dentry`、`inode`)。SLUB 在伙伴之上做二次切分:为每种对象开一个 `kmem_cache`(专卖店),向伙伴要整页(slab),切成同尺寸的格子按需发放。你熟悉的 `kmalloc`(`include/linux/slab.h:549`)最终就落到这里。

- 快路径:`kmem_cache_alloc`(`mm/slub.c:3381`)→ `slab_alloc`(`mm/slub.c:3364`),命中当前 CPU 的本地缓存就直接返回,无锁,极快。
- 慢路径:`___slab_alloc`(`mm/slub.c:3008`),本地缓存空了才去要新 slab。

> 想深入?`Documentation/mm/slub.rst`;`kmalloc` 的尺寸分级与 `__kmalloc`(`include/linux/slab.h:453`)。

### 回收:LRU + kswapd + 直接回收

物理页会用完(§2 第五版的墙)。内核把用户页挂在 **LRU 链表**上(`enum lru_list`,`include/linux/mmzone.h:266`,分 active/inactive、匿名/文件),近似"最近最少使用"排序。紧张时从 inactive 端往回收:干净文件页直接丢(能从磁盘重读),脏页先写回。回收一批页的核心是 `shrink_folio_list`(`mm/vmscan.c:1640`,注意 6.1 操作的是 **folio** 不是 page),它靠 §4 埋的 **rmap** 反查"这页被谁映射"、把那些页表项逐个断开,才能安全收回。

两种触发时机:

```
   空闲页水位
    高  ┌──────────────── 充足, 谁都不用管
        │
   low  ├─ 低于 low 水位 → 唤醒 kswapd(后台异步回收), 进程无感
        │     wakeup_kswapd  mm/vmscan.c:7436
        │     kswapd 主循环   mm/vmscan.c:7350 → balance_pgdat  mm/vmscan.c:7028
        │
   min  ├─ 低于 min 水位 → 来不及了! 申请者"直接回收"(同步, 当场卡住自己去收)
        │     try_to_free_pages  mm/vmscan.c:6679  (从 __alloc_pages_slowpath 调进来)
        ▼
        └─ 收不出来 → OOM
```

kswapd 是"平时就悄悄扫地的清洁工",直接回收是"客人太多、服务员被迫放下手里的活先去腾桌子"——后者会让你的 `malloc` 明显变慢,是性能问题的常见根源。核心引擎 `shrink_lruvec`(`mm/vmscan.c:5912`)两条路(kswapd 的 `balance_pgdat` 和直接回收的 `try_to_free_pages`)最终都汇到它。

> 想深入?`Documentation/mm/page_reclaim.rst`;水位见 §7。

### swap:给匿名页一个"下乡"的去处

文件页回收时能直接丢(内容磁盘上有)。但匿名页(malloc 的堆、栈)内容只在内存里,丢了就没了。**swap** 就是给它们一块磁盘,回收时把匿名页写到 swap、清空物理页;进程再访问就触发 §4 的 `do_swap_page` 换回来。这就是开篇"20 GB > 8 GB 不崩"的最后一块拼图:超出的部分可以躺在 swap 里。

> 想深入?`Documentation/mm/`(swap 相关)与 `mm/swap_state.c` / `mm/page_io.c`。

### OOM killer:山穷水尽的最后手段

回收也收不出、swap 也满了,`__alloc_pages_slowpath` 最终触发 `out_of_memory`(`mm/oom_kill.c:1116`)。它按"占用内存 × 可调分数(oom_score_adj)"给进程打分,挑最"该死"的一个,`oom_kill_process`(`mm/oom_kill.c:1023`)→ `__oom_kill_process`(`mm/oom_kill.c:926`)把它杀掉,腾出内存让系统活下去。你在 `dmesg` 里见过的 "Out of memory: Killed process ..." 就是这里打的。

> 想深入?`Documentation/mm/`(OOM)与 `mm/oom_kill.c` 顶部注释里的选择策略。

## §7 更高层的直觉:内存不是一整块,是分区的

前面为讲清主线,一直把物理内存当成"一大摞页"。真实机器上它是**分层分区**的,理解这层能让 §3 和 §6 的很多细节落位。只讲思想,数值和字段留给文档。

**node(节点)——NUMA。** 多路服务器上,每颗 CPU 都有"离自己近"的一片内存,访问远端 CPU 的内存更慢。内核按此把内存分成若干 **node**,分配时优先给"本地 node"。单路机器就一个 node,可暂时忽略。

**zone(区)——同一 node 内按用途分带。** 一个 node 内的内存还要按硬件约束分 **zone**(`struct zone`,`include/linux/mmzone.h:704`):比如老设备 DMA 只能访问低地址 → `ZONE_DMA`;常规内存 → `ZONE_NORMAL`。§3 的伙伴系统 `free_area[]` 其实是**挂在每个 zone 上**的——分配时先选 node、再选 zone,才在那个 zone 的伙伴货架上取页。

**watermark(水位)——kswapd 何时醒。** 每个 zone 有三条水位线 `enum zone_watermarks`(`include/linux/mmzone.h:546`):**high / low / min**。§6 那张水位图就是它:空闲页跌破 low 唤醒 kswapd 后台回收,目标是补回到 high;跌破 min 说明危急,申请者被迫自己直接回收。改 `/proc/sys/vm/min_free_kbytes` 就是在抬高 min 这条线,让内核留更多缓冲。

```
   物理内存
   ┌─ node 0 ──────────────────┐   ┌─ node 1 ──────────────────┐
   │ ZONE_DMA   [伙伴 free_area]│   │ ZONE_NORMAL [伙伴 free_area]│  ← 每个 zone 一套 §3 货架
   │ ZONE_NORMAL[伙伴 free_area]│   │  + 三条水位 high/low/min   │  ← 每个 zone 一组 §6 水位
   │  + 每 CPU 页缓存(pcp)      │   │  + pcp                     │
   └───────────────────────────┘   └───────────────────────────┘
```

**pcp(每 CPU 页缓存)——绕开锁的快路径。** 伙伴系统的 zone 锁是全局竞争点。为此每个 CPU 缓存一小批 order-0 页(pcp list),分配 / 释放单页时先走本 CPU 的 pcp,完全不碰 zone 锁,快且无竞争;pcp 空了或满了才批量与伙伴系统交换。这是 §3 之上最重要的性能优化,你在 `/proc/zoneinfo` 里能看到每 zone 每 CPU 的 pcp count。

> 想深入?NUMA / node / zone 的完整模型在 `Documentation/mm/physical_memory.rst`;NUMA 策略(`mbind`、`alloc_pages` 如何选 node)在 `Documentation/admin-guide/mm/numa_memory_policy.rst` 与 `mm/mempolicy.c`(`alloc_pages` @`mm/mempolicy.c:2264`)。

## §8 动手看:不改代码,把原理亲手跑出来

看懂不等于记住。下面这些**只读不改**,现在就能在你的 Linux 上敲,把前面的原理眼见为实。

**① 看伙伴系统的货架(验证 §3)。**
```bash
cat /proc/buddyinfo
```
每行一个 zone,后面 11 个数字就是 `free_area[0..10]` 各级的**空闲块个数**——第 1 个数是 order-0(1 页)有几块,最后一个是 order-10(4 MB)有几块。跑一个吃内存的程序再看,你会看到大 order 的块变少、被劈成小块。这就是 `expand` 在动。

**② 看内存总账(验证 §1 / §6)。**
```bash
cat /proc/meminfo      # MemFree/Buffers/Cached/SwapTotal/SwapFree/AnonPages...
vmstat 1               # si/so 两列 = swap in/out, 非 0 说明正在换页(§6 swap)
```

**③ 看一个进程的地址空间(验证 §5)。**
```bash
cat /proc/self/maps            # 每一行就是一个 VMA: 地址区间 + 权限 + 映射的文件
cat /proc/self/smaps           # 每个 VMA 的细账: Rss(真占的物理内存) vs Size(虚拟大小)
```
对照 `maps`:带文件路径的行是文件 VMA(§4 走 `do_fault`),`[heap]`/`[stack]`/匿名行是匿名 VMA(走 `do_anonymous_page`)。你还能亲眼看到开篇那桩事:`smaps` 里一段的 `Size` 远大于 `Rss`——申请了但没写、没触发缺页的部分,不占物理内存。

**④ 亲手触发缺页并数出来(验证 §4)。**
```bash
/usr/bin/time -v ./your_program 2>&1 | grep -i fault
# 输出里 "Minor (reclaiming a frame) page faults" 就是 §4 走 do_anonymous_page 的次数
```
写个程序 `malloc` 一大块然后逐页写一遍,minor fault 数会约等于页数——每写一个新页 = 一次 §4 主流程。

**⑤ 追一次缺页的内核路径(验证 §4 调用链,需要 root)。**
```bash
# 需要内核开了 ftrace
cd /sys/kernel/debug/tracing
echo handle_mm_fault > set_ftrace_filter
echo function > current_tracer
cat trace_pipe          # 另开一个终端跑吃内存程序, 这里能看到 handle_mm_fault 被不断命中
```

"亲手看过 buddyinfo 变化、亲手数过 page fault"的人,才算真把 §3/§4 的心智模型钉住了。
