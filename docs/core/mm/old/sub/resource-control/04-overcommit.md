# Overcommit：未来承诺的检查、保留量与回滚

Linux 6.1.158、arm64。Overcommit管理适用地址空间操作的未来需求，不是驻留计数、NUMA政策或memcg charge。

建立可写地址范围时可以尚未分配全部数据页，但后续触碰或 COW 可能产生新的物理需求。Overcommit（内存过量承诺）按映射类型对这类未来需求记账，并按策略决定是否接受；它不预留某些具体 PFN。先读 [承诺与驻留的区别](../../05-placement-and-limits.md#overcommit)，再看计入、检查和撤销的实现。

## 1. 三个不同的数量

| 数量 | 表示 |
| --- | --- |
| VMA/虚拟范围 | 地址规则允许讨论的范围 |
| `vm_committed_as` 等 | 适用操作已经加入的未来承诺 |
| 实际页与组charge | 后续内容真正形成后的供给/记账 |

区间建立成功仍可能以后缺页失败；宽松承诺不授权忽略当时物理、页表或组限制。

## 2. 哪些范围需要承诺不是只由字节长度决定

共享文件、私有可写内容、保护变化、fork复制和特殊映射有不同需求。调用者确定是否计账、多少页以及VM_ACCOUNT等状态，不能给每个mmap总长度统一收费。

核心检查在 `mm/util.c` 的 `__vm_enough_memory`，安全钩子等可使用其逻辑；它不是模块拿任意指针申请“免OOM额度”的接口。

## 3. 为什么先加账再检查？

该helper先 `vm_acct_memory(pages)`，再按模式判定。失败汇入error调用 `vm_unacct_memory(pages)`。

```text
旧承诺 C
暂时加入本次 p -> C+p
策略接受：保留该账
策略拒绝：减p -> C，返回失败
```

它不是只查询空闲RAM而没有状态改变的函数；调用者还要在后续地址空间操作失败/结束时按完整生命周期结束自己的账。

## 4. 当前三种策略的实际分支

| 模式 | 本树helper主要动作 |
| --- | --- |
| ALWAYS（1） | 加入后直接接受此项检查 |
| GUESS（0） | 包括本次pages与总RAM/swap比较的检查 |
| 严格模式（2） | 计算commit limit、扣适用保留量，比较加入后的承诺 |

Mode0不能套旧版“当前空闲减缓存”的唯一公式；mode1也只接受承诺检查，不能承诺将来每次实际页分配成功。

## 5. 严格模式的 allowed 怎样形成？

先通过 `vm_commit_limit` 得到适用基础上限，再按权限和mm状态扣除admin/user相关保留：

本树基础上限也有两个分支：

```text
设置了 overcommit_kbytes：按页大小换算其额度
否则：(totalram_pages - hugetlb_total_pages) × ratio / 100
最后加 total_swap_pages
```

例如RAM一千页、HugeTLB已占两百页、ratio50、swap一百页，基础limit为五百页。已按大页池占用的供给不能又无条件按普通承诺重复计算。该例只说明公式，不设置目标系统额度。

```text
allowed = commit_limit
非相应管理权限：减 admin_reserve 转换页数
有 mm：再减 min(mm.total_vm/32, user_reserve转换页数)
```

这些量要按 PAGE_SHIFT 换算，不用所有arm64固定4KiB。保留用于承诺策略，不等于从Buddy中移除同大小物理页。

`mm.total_vm` 又不同于已驻留页数。若把保留按RSS计算，就不是这条helper的实际算法。

## 6. 一个边界明确的数值推演

限定已扣保留的allowed=100页，旧承诺70页，无其他并发变化：

| 本次p | 加入后 | 本树该严格分支比较 `< allowed` | 结束结果 |
| --- | --- | --- | --- |
| 20 | 90 | 成立 | 接受，账90 |
| 30 | 100 | 不成立 | 撤销30，恢复70 |
| 35 | 105 | 不成立 | 撤销35，恢复70 |

这里特意保留源码的严格小于比较，不从直觉把它改写成小于等于。这是helper判定点，不是所有上层操作共同的完整边界。

## 7. Fork 和保护变化为何也相关？

私有可写范围的后续COW可能创造新后备，fork在适用条件下需要考虑未来承诺，而不是只复制一张页表后忽略新写入需求。

Mprotect等改变可写语义也可能改变计账要求。是否实际复制页是以后fault决策，承诺是提前讨论风险，二者不能合并。

## 8. 并发和 per-CPU 计数

`vm_committed_as` 使用per-CPU counter设施，检查与精确汇总/统计不必同一时刻相同。多个并发地址空间操作、后续清理和统计观察不是一张静止账本。

不要把该helper写成“持一把全局锁原子保留具体物理页”。它协调承诺政策，物理页要在另一路真正取得。

## 9. 怎样分辨故障来自哪一张账？

| 现象 | 核对 |
| --- | --- |
| 建区间/改变保护时失败 | 适用承诺、权限、范围及地址资源 |
| 区间存在，首次写失败 | 物理供给、页表、NUMA和memcg |
| Fork后写产生压力 | COW实际后备需求与先前承诺不等量 |
| 宽松模式仍发生OOM | 此策略没有豁免实际供给/组限制 |

源码为 `mm/util.c`，调用者包括适用 `mm/mmap.c`、fork/保护变化和安全检查；规则在同树 `Documentation/mm/overcommit-accounting.rst`。本文仅验算限定模型，未修改sysctl或分配巨量虚拟内存。
