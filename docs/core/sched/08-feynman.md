# 08 · 大白话讲调度器最难的跨模块概念

> 本篇用四段式(是什么 → 打比方 → 拆开讲 → 回到代码)讲清调度器里最难自己想明白的三个跨模块概念。每段结论都能在其他篇找到带行号的出处,本篇不重复行号,只给指针。
>
> 基线:Linux 6.1.158(**PREEMPT_RT `-rt58`**),arm64。

## 概念一:vruntime 为什么能保证公平

一句话:vruntime 是"按权重放慢的秒表",谁的表走得慢就先让谁跑,于是所有人都被拉到同一进度。

打比方:一群人跑步机比赛,规则不是"谁跑得快谁赢",而是"永远让累计里程最少的人上机器"。体力好(高优先级)的人,跑步机把他的里程表调慢——他实际跑了 100 米,表只记 50 米,于是系统觉得"他还欠着",会更频繁让他上。里程表就是 vruntime,调慢的倍率就是任务权重(由 nice 值映射)。

拆开讲:
- 每个任务有个 vruntime。任务运行时,vruntime 按"物理时间 ÷ 权重"增加——权重越大,增得越慢(`update_curr` 里的 `calc_delta_fair`)。
- 调度器永远挑 vruntime 最小的任务跑。红黑树把任务按 vruntime 排好序,最左边就是最小的,取它是 O(1)。
- 新来的或刚睡醒的任务怎么定初始 vruntime?不能给 0(那会永远抢占别人),也不能给太大(会饿死自己)。所以用队列的 `min_vruntime` 做基准:新任务罚一点(防 fork 炸弹),睡醒的补一点(补偿它睡觉时别人跑掉的进度)。这就是 `place_entity` 干的事。
- 关键保障:`min_vruntime` 只增不减(单调不减)。否则新任务基准会倒退,整个排序就乱了。

回到代码:机制全在 fair 子模块,数学推导见 [`sub/fair/03-algorithm.md`](sub/fair/03-algorithm.md) §1;三条不变式(min_vruntime 单调、runnable vruntime 不落后太多、有符号比较容忍回绕)是正确性的地基。vruntime 字段本身是 fair 私有,不跨模块,所以它在 [`02-objects.md`](02-objects.md) 里没登记——只有 `rq->curr` 这种真正跨模块的才登记。

## 概念二:一次 tick 到来,系统怎么决定"要不要换人"

一句话:tick 不直接换人,它只是让当前任务所在的调度类"看一眼时间到没到",到了就插个"该换人了"的旗子,等安全的时刻再真换。

打比方:上课有个打铃的(tick),但打铃不等于下课。铃响时老师(调度类)看一眼这节课上够没有——上够了就在黑板角落画个记号(need_resched),等这句话讲完(到达抢占点)才真的下课换老师。为什么不立刻换?因为可能正握着粉笔(持锁)或话说一半(临界区),硬换会出乱子。

拆开讲:
- tick 中断打到 core 的 `scheduler_tick`,core 不自己判断,而是问当前任务属于哪个调度类,调用那个类的 `task_tick` 回调(分派解耦)。
- 对 CFS 任务,`task_tick_fair` → `check_preempt_tick` 判断:这个任务这轮该跑的时间片用完没?vruntime 是不是已经落后到该让位?是就置"need_resched"旗子。
- 置旗子不等于换人。真正的切换发生在下一个"抢占点"(中断返回、系统调用返回等安全时刻),那时 `__schedule` 才跑,重新从红黑树选最小 vruntime 的任务。
- 换人时 core 走优先级链:先问 stop 类有没有活,再 dl、rt、fair、idle。这个顺序保证实时任务永远压过普通任务。

回到代码:这条链就是顶层 [`03-lifecycle.md`](03-lifecycle.md) 的跳 #10(tick 置位)→ 跳 #6/#4(重新选)。"core 问、调度类答"的分派解耦是 [`04-interactions.md`](04-interactions.md) §3.1 的核心。旗子这个动作在本树是 `resched_curr_lazy`(带 RT 的 lazy 语义),不是普通 `resched_curr`——差别见下面概念三。

## 概念三:PREEMPT_RT 的"lazy 抢占"到底改了什么

一句话:RT 树想让实时任务尽快抢到 CPU,但又不想让普通任务之间频繁互抢增加开销,于是发明了"两种紧急程度的旗子"——普通任务插的是"缓一缓"的旗子,实时任务插的是"立刻"的旗子。

打比方:办公室有两种"请让位"的便签。普通同事之间用黄色便签(lazy):看到了,等手头这段忙完再让。老板来了用红色便签(普通 resched):立刻停下让位。非 RT 内核只有红色便签,谁都用它,结果普通同事之间也频繁打断彼此。RT 内核加了黄色便签,把普通任务间的抢占降级成"不急",只有真正的实时任务才触发"立刻"。

拆开讲:
- 非 RT:抢占就一种,`resched_curr` 置 `TIF_NEED_RESCHED`,到抢占点就切。
- RT + PREEMPT_LAZY:多了 `TIF_NEED_RESCHED_LAZY`。CFS 之间的抢占(tick 到期、唤醒抢占)改用 `resched_curr_lazy`,置的是 lazy 位——只在任务自愿让出或返回用户态等时机才生效,不打断内核关键路径。实时任务的抢占仍走立刻通道。
- 一个常见误解:以为 RT 把调度器的锁都变成可睡眠的了。不对。调度器核心的锁(`rq->__lock` 等)本来就是 `raw_spinlock_t`,RT 下语义不变——调度器自己绝不能睡。RT 真正改的是抢占时机,不是锁语义。

回到代码:lazy 抢占的落点、`resched_curr_lazy` 的定义、以及"核心锁本就是 raw_spinlock"的论证,全在 [`05-concurrency.md`](05-concurrency.md) §7。fair 里所有抢占置位改用 lazy 版的具体行号在 [`sub/fair/02-internals.md`](sub/fair/02-internals.md) 的 RT 差异一节。这与 git 里 arm64 的 `thread_info.h`/`preempt.h` 改动(新增 RESCHED_LAZY 标志位)是同一件事的两端。

## 概念四:DL 吃 RT 的带宽——两个调度类为什么会"共用一个账本"

一句话:DL(截止期)任务优先级比 RT 高,它跑掉的时间会从 RT 的时间预算里扣,防止 DL 把 RT 彻底饿死时系统还以为 RT 有充足配额。

打比方:公司给"紧急项目"(RT)每月 100 小时加班预算。但有个"绝对最高优先"的董事长项目(DL)会插队占用工时。如果董事长占了 30 小时不记账,月底一看 RT 预算还剩 100 小时就继续批加班,实际人已经累垮。所以规则是:董事长占的工时也记进 RT 那本账,让预算反映真实占用。

拆开讲:
- DL 优先级 > RT > fair。DL 任务运行时,`update_curr_dl` 会把消耗的时间计进 RT 队列的 `rt_time`(带宽账本)。
- 反过来,DL 准入(能不能接受一个新 DL 任务)要用 RT 的全局带宽参数做上界——两个类共享 `global_rt_runtime()` 这个天花板。
- 这是一处"意外的强耦合":两个看起来独立的调度类,通过 `rt_rq->rt_time` 和全局带宽参数双向挂钩。但它不是 bug——是防饥饿的有意设计,而且用的是不同的锁、不同的路径,不会形成环形死锁。

回到代码:这对关系是 [`04-interactions.md`](04-interactions.md) §3.8 和 §6 依赖环表里"deadline ↔ rt"那一行;共享的 `rt_rq->rt_time` 字段在 [`02-objects.md`](02-objects.md) §2.3 与 [`04-interactions.md`](04-interactions.md) §4 登记,同步锁 `rt_runtime_lock`(raw_spinlock)见 [`05-concurrency.md`](05-concurrency.md) §1。
