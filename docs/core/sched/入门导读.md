## 开篇:一个你其实每天都在体验的怪事

你的机器上此刻大概跑着几百个进程——浏览器、编辑器、一堆后台服务、内核线程——但 CPU 只有那么几个核(假设 8 个)。按理说 8 个核同时最多跑 8 个任务,可你的体验是:**几百个进程好像都在同时、流畅地运行**,鼠标不卡、音乐不断、编译在后台照跑。

这是怎么做到的?答案就是**调度器(scheduler)**:它以极高的频率,不停地把每颗 CPU 从一个任务切到另一个任务,快到你感觉不出来切换。就像电影每秒 24 帧的静止画面骗过眼睛,调度器每秒成百上千次的任务切换骗过了你的"同时运行"直觉。

调度器要回答的核心问题只有一个:

> **此时此刻,这颗 CPU 应该跑哪个任务?**

听起来简单,但要做好,得同时满足一堆互相打架的诉求:交互任务要**响应快**(你敲键盘立刻有反应)、计算任务要**吞吐高**(编译别老被打断)、实时任务要**准时**(音频不能卡顿)、还要**公平**(别让一个进程饿死另一个)、更要**在几百个进程、几十个核的规模下依然快**(选个任务本身不能太慢)。

`kernel/sched/` 这四万多行代码,基本都是在这一个问题的不同侧面上做权衡。我们一层层来。

## §1 调度器在做什么:30 秒建立的心智模型

先把它想象成一个**反复做选择的循环**。剥掉所有细节,调度器在每颗 CPU 上做的事就三件:

```
        ┌───────────────────────────────────────────────┐
        │  1. 选谁跑 (pick)                              │
        │     从"就绪任务"里挑一个最该跑的               │
        │                                                │
        │  2. 何时换 (preempt)                           │
        │     跑着的任务,什么条件下该被换下来           │
        │                                                │
        │  3. 换的时候做什么 (context switch)            │
        │     保存旧任务的现场,恢复新任务的现场         │
        └───────────────────────────────────────────────┘
                     ↑                          │
                     └──── 循环,永不停止 ───────┘
```

就这三件事。你后面看到的所有复杂结构——红黑树、位图、优先级链、负载均衡——都是为了把**第 1 件事(选谁)**做得又快又公平又照顾实时性。第 2 件(何时换)决定切换的时机,第 3 件(怎么换)是体系结构相关的现场保存,本篇基本不碰(它在 `context_switch`,`kernel/sched/core.c:6678`,涉及汇编切页表/寄存器,属于另一个话题)。

**关键前提:调度器不是一个后台线程在轮询。** 它没有自己的"主循环线程"。它是**被动触发**的一段代码——当某个事件发生(时钟中断到了、一个任务被唤醒了、当前任务主动阻塞了),内核才会调用调度器的入口函数 `__schedule()` 来做一次选择。平时它就是"沉睡"的。记住这点,后面 §4 才不会绕晕。

> 想深入?一次调度的完整状态机在 [`03-lifecycle.md`](03-lifecycle.md)。

## §2 如果让你来设计:从最朴素的想法推出真实取舍

理解内核为什么长这样,最好的办法是假装**你来从零设计**,然后看你会撞上哪些墙。内核的每个结构,都是撞墙之后的补丁。

### 第一次尝试:一条全局就绪队列

最朴素的想法:搞一个全局链表,所有"准备好运行的任务"都挂上去。哪颗 CPU 空了,就从链表头拿一个来跑。

**撞墙①:锁争用。** 8 个核都要从这**同一条**链表拿任务、放任务,就得抢**同一把锁**。核越多,大家越多时间在等锁而不是干活。16 核、64 核时这条队列会成为整个系统的瓶颈。

**补丁:每颗 CPU 一条自己的队列。** 内核给每颗 CPU 一个运行队列结构 `struct rq`(run queue,`kernel/sched/sched.h:954`)。选任务时只碰自己这颗 CPU 的锁 `rq->__lock`,核之间互不干扰。这是调度器的第一性权衡——**本地优先**。

代价当然有:任务分散在各 CPU 的私有队列里,难免有的 CPU 忙死、有的闲死。于是需要另加一层**负载均衡**,定期把任务在队列间搬平(§7)。这就是"本地快、全局补"。

```
   朴素设计(全局一队)              真实内核(每 CPU 一队)
   ┌──────────────────┐            CPU0        CPU1        CPU2
   │  全局就绪队列    │            ┌────┐      ┌────┐      ┌────┐
   │  [T1 T2 T3 ...]  │            │ rq │      │ rq │      │ rq │
   └──────────────────┘            └────┘      └────┘      └────┘
    ↑    ↑    ↑    ↑                 ↑本地锁     ↑本地锁     ↑本地锁
   CPU0 CPU1 CPU2 CPU3              互不争抢,失衡时靠负载均衡搬平
   全都抢同一把锁 ✗
```

### 第二次尝试:简单轮流(round-robin)

队列有了,怎么从里面选?最朴素:排队,轮流跑,每人跑一小段(时间片)。

**撞墙②:一视同仁不行。** 音频播放线程晚 10ms 就爆音,它不能和一个跑一整天的科学计算排一样的队。有些任务对**延迟**极度敏感(硬实时),有些只在乎**长期拿到多少 CPU**(公平),这两种诉求**没法用同一个算法同时满足**。

**补丁:把任务按诉求分成几"类",类之间定死优先级。** 内核把调度策略分成 5 个**调度类(sched_class)**,用一条硬优先级链串起来:

```
   高优先级 ◄──────────────────────────────────────────► 低优先级
   ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌────────┐
   │  stop  │──►│ deadline │──►│   rt   │──►│  fair  │──►│  idle  │
   └────────┘   └──────────┘   └────────┘   └────────┘   └────────┘
   迁移/热插拔   EDF 硬实时     FIFO/RR       CFS 公平     兜底(什么
   的特权通道   (到点必跑)   软实时       普通任务      都没有时)
```

选任务时,`__schedule` 从最高的 stop 类开始,逐类问一句"你有任务要跑吗?"——**第一个应答的就赢**。高类只要有任务,低类就一直等着。这就是为什么实时任务(rt/dl)能压过你所有普通程序(fair)。

**这个分层是理解整个调度器的骨架。** 绝大多数任务(你的浏览器、编译器)都在 **fair(CFS)** 这一类里——所以我们下一节的重头戏就是它:普通任务之间,在没有实时诉求的前提下,怎么做到"公平"。

## §3 CFS:普通任务怎么被公平对待(重头戏)

CFS = Completely Fair Scheduler,完全公平调度器,`kernel/sched/fair.c`。你机器上 99% 的任务都归它管。它要解决的问题是:**一堆没有实时诉求的任务,怎么分配 CPU 才算"公平"?**

### 3.1 核心直觉:一本"欠账本"

先别看代码,建立直觉。CFS 的想法可以用一句话概括:

> **给每个任务记一本账:它总共用了多少 CPU 时间。每次都让"用得最少"的那个先跑。**

想象一群小孩轮流玩一个秋千。最公平的规则是什么?——**谁玩得最少,下一个就轮到谁。** 你只要盯着"每个人累计玩了多久",永远把秋千给累计时间最短的那个,长期下来大家玩的时间自然拉平。

CFS 就是这么干的。它给每个任务维护一个数字,叫 **vruntime(virtual runtime,虚拟运行时间)**,大致就是"这个任务累计跑了多久"。规则:

- 任务在 CPU 上跑,它的 vruntime 就往上涨;
- 每次要选任务时,**选 vruntime 最小的那个**(欠得最多、最亏的);
- 它跑一会儿,vruntime 涨上去了,就不再是最小的了,自然轮到别人。

长期下来,所有任务的 vruntime 会互相追赶、大致齐平——这就是"完全公平"。

### 3.2 为什么叫"虚拟"运行时间?—— nice 值的魔法

如果 vruntime 就是"实际跑了多久",那所有任务完全平权,谁也不比谁多拿。但现实里我们需要**优先级**:你希望前台程序比后台的 `make -j` 多拿 CPU。Linux 用 **nice 值**(-20 到 +19,越"nice"越谦让、优先级越低)表达这个。

CFS 的巧妙之处:**它不给高优先级任务"选择上的特权",而是让它的 vruntime 涨得更慢。** vruntime 涨得慢 → 它更容易一直是"最小的那个" → 于是更频繁被选中 → 实际拿到更多 CPU。公平的框架没变,只是每个任务的"时间流速"不同。

换算规则:每个 nice 值对应一个**权重(weight)**。权重表在 `kernel/sched/core.c:11404`:

```c
const int sched_prio_to_weight[40] = {
 /* -20 */     88761,     71755,     56483,     46273,     36291,
 ...
 /*   0 */      1024,       820,       655,       526,       423,
 /*   5 */       335,       272,       215,       172,       137,
 ...
};
```

nice 0 的权重是 **1024**(记作 `NICE_0_LOAD`,`kernel/sched/sched.h:167`)。**每差一个 nice 级,权重差约 1.25 倍。** vruntime 的涨速与权重成反比:

```
   vruntime 增量  =  实际运行时间 × (NICE_0_LOAD / 本任务权重)
```

- nice 0(权重 1024):跑 1ms,vruntime 涨 1ms × 1024/1024 = **1ms**(基准流速)。
- nice 5(权重 335):跑 1ms,vruntime 涨 1ms × 1024/335 ≈ **3.06ms**(涨得快 3 倍)。

vruntime 涨得快 3 倍,意味着它"更快显得不亏",于是更少被选中——最终 nice 0 的任务拿到的 CPU 约是 nice 5 的 3 倍。这个"约 3 倍"正好是 1024/335 ≈ 1.25⁵。

### 3.3 带读源码:vruntime 到底在哪更新

上面这套直觉,落到代码就一个函数:`update_curr()`,`kernel/sched/fair.c:882`。每当"当前任务又跑了一段",内核就调它结算这段时间。核心就三行:

```c
delta_exec = now - curr->exec_start;      // :891 这次结算距上次,实际跑了多久(纳秒)
...
curr->vruntime += calc_delta_fair(delta_exec, curr);  // :908 折算成 vruntime 累加
update_min_vruntime(cfs_rq);              // :909 更新队列里的最小 vruntime 基准
```

关键就是 `calc_delta_fair`(`kernel/sched/fair.c:694`),它把"实际时间"按权重折算成"虚拟时间":

```c
static inline u64 calc_delta_fair(u64 delta, struct sched_entity *se)
{
	if (unlikely(se->load.weight != NICE_0_LOAD))       // 权重不是基准 1024 时才需要换算
		delta = __calc_delta(delta, NICE_0_LOAD, &se->load);  // delta × 1024 / weight
	return delta;
}
```

读懂这两段,你就抓住了 CFS 的心脏:**跑得越久,vruntime 涨越多;权重越大(优先级越高),同样时间涨得越少。** 剩下的都是围绕这个数字做工程。

(`__calc_delta`@`kernel/sched/fair.c:308` 是把这个乘除做成不溢出的定点运算,细节可略,想看在下钻手册。)

### 3.4 选任务:为什么用红黑树

现在的问题变成:几百个任务,每次都要**最快地找出 vruntime 最小的那个**,而且任务跑完还要**快速重新插入**(它的 vruntime 变了,位置要变)。什么数据结构又能快速取最小、又能快速插入删除?

——**红黑树**(平衡二叉搜索树)。CFS 用一棵按 vruntime 排序的红黑树存所有就绪的 CFS 任务(`cfs_rq->tasks_timeline`)。红黑树的最左节点就是 vruntime 最小的,取它是 O(log n)、插入删除也是 O(log n)。而且内核用了 `rb_root_cached`,把"最左节点"缓存起来,取最小直接 O(1):

```c
struct sched_entity *__pick_first_entity(struct cfs_rq *cfs_rq)
{
	struct rb_node *left = rb_first_cached(&cfs_rq->tasks_timeline);  // 直接拿缓存的最左
	if (!left)
		return NULL;
	return __node_2_se(left);   // 最左 = vruntime 最小 = 下一个该跑的
}
```

(`kernel/sched/fair.c:638`。)一句话:**CFS 的就绪队列是一棵按 vruntime 排的红黑树,选任务就是取最左边那个。**

```
        cfs_rq 的红黑树(按 vruntime 排序)
                     [ 20 ]
                    /      \
                [ 12 ]     [ 30 ]
                /    \         \
           [ 8 ]   [ 15 ]     [ 45 ]
            ↑
        最左 = vruntime 最小 = 下一个被 pick_next 选中
        (rb_first_cached 缓存了这个指针,取它 O(1))
```

### 3.5 何时换人:tick 上的抢占判断

选出来跑了,什么时候把它换下来?靠**时钟中断(tick)**。每次 tick,内核调 `task_tick_fair()`(`kernel/sched/fair.c:11870`)→ `entity_tick` → `check_preempt_tick`(`kernel/sched/fair.c:4909`)。后者判断:当前任务这一轮**是不是已经跑够了它该分到的那份时间片**(`ideal_runtime = sched_slice(...)`,`fair.c:4915`)。跑够了,就打上"该换人"的标记(见 §4 的 `resched_curr`),让它在最近的抢占点让出。

时间片多长?由 `sched_slice` 按权重从一个目标周期里切出来。默认目标延迟 `sysctl_sched_latency = 6ms`(`kernel/sched/fair.c:72`),最小粒度 `0.75ms`(`fair.c:93`)——就绪任务越多,每人分到的越小,但不小于最小粒度(否则切换开销占比太高)。

**注意 tick 只是"打标记",不当场切人。** 为什么?这就要看 §4 的主循环了。

### 3.6 一个例子跟到底:A(nice 0)和 B(nice 5)

把上面全串起来。两个纯计算任务同时就绪:A 是 nice 0(权重 1024),B 是 nice 5(权重 335)。初始 vruntime 都设为 0。假设每次让被选中的跑 1ms(简化),看 vruntime 怎么演化、谁跑得多:

| 轮次 | 选谁跑(vruntime 较小者) | 跑后该任务 vruntime | A 的 vruntime | B 的 vruntime |
|---|---|---|---|---|
| 起始 | — | — | 0 | 0 |
| 1 | A(并列,取一个) | A += 1×1024/1024=1 | 1.0 | 0 |
| 2 | B(0 < 1) | B += 1×1024/335≈3.06 | 1.0 | 3.06 |
| 3 | A(1.0 < 3.06) | A += 1 | 2.0 | 3.06 |
| 4 | A(2.0 < 3.06) | A += 1 | 3.0 | 3.06 |
| 5 | A(3.0 < 3.06) | A += 1 | 4.0 | 3.06 |
| 6 | B(3.06 < 4.0) | B += 3.06 | 4.0 | 6.12 |
| 7 | A ×3 次… | … | ~7.0 | 6.12 |

看出规律没有:**A 每被选中一次 vruntime 才涨 1,B 涨 3.06,所以 A 被连续选中大约 3 次、B 才轮到 1 次。** 长期看 A 拿到的 CPU 时间约是 B 的 3 倍——正是我们想要的 nice 效果。而算法本身从头到尾只做一件事:**取 vruntime 最小的跑**。公平的框架没为优先级开任何后门,优先级完全是通过"改变 vruntime 流速"实现的。这就是 CFS 优雅的地方。

## §4 __schedule:把"选择"落地的主循环

前面反复说"打个标记,稍后换人"。现在看这个"稍后"到底怎么发生。

### 4.1 两步走:先标记,后切换

内核换任务是**两步**,分得很开:

**第一步——置标记。** 当某个事件让内核觉得"当前任务该被换下来了",它不当场切,只是在当前任务上打一个旗标 `TIF_NEED_RESCHED`(need reschedule,需要重新调度)。干这件事的函数是 `resched_curr()`(`kernel/sched/core.c:1021`)。触发它的事件主要三类:

```
   ① tick 到了      scheduler_tick → task_tick_fair → 判时间片用完 → resched_curr
      (core.c:5614)
   ② 唤醒抢占       try_to_wake_up → 新任务入队 → 若比当前更该跑 → resched_curr
   ③ 主动让出/阻塞   任务自己调 schedule() / 阻塞在锁或 IO 上
```

**第二步——真正切。** 内核只在几个安全的**抢占点**检查这个旗标:中断返回用户态时、系统调用返回时、或任务主动调用 `schedule()` 时。一旦发现旗标置着,就调用 `__schedule()` 真正做一次选择和切换。

为什么要拆成两步、不当场切?因为**中断上下文里不能随便切任务**(可能正持着锁、正处理硬件),当场切会破坏一致性。拆开后,切换点变得**可控**——都发生在内核明确知道"现在切是安全的"的位置。代价是有一点延迟(标记到真正切之间),但换来了正确性。

### 4.2 带读源码:__schedule 的骨架

`__schedule()` 在 `kernel/sched/core.c:6557`。剥掉锁和内存屏障的细节,主干就这么几步:

```c
static void __sched notrace __schedule(unsigned int sched_mode)
{
	...
	rq = cpu_rq(cpu);
	prev = rq->curr;                        // :6568 当前(即将被换下)的任务

	rq_lock(rq, &rf);                       // :6593 锁住本 CPU 运行队列
	update_rq_clock(rq);                    // :6598 更新队列时钟(vruntime 结算要用)

	prev_state = READ_ONCE(prev->__state);  // :6606 prev 是要睡了,还是只是被抢占?
	if (!(sched_mode & SM_MASK_PREEMPT) && prev_state) {
		...
		deactivate_task(rq, prev, ...);  // :6630 若是主动睡眠 → 把 prev 移出就绪队列
	}
	                                         //   若只是被抢占 → 留在队列上,下次还能被选

	next = pick_next_task(rq, prev, &rf);    // :6640 【核心】沿优先级链选出下一个任务
	clear_tsk_need_resched(prev);            // :6641 旗标已响应,清掉
	clear_tsk_need_resched_lazy(prev);       // :6642 (RT 树的 lazy 旗标,见 §6)

	if (prev != next) {
		rq->curr = next;
		rq = context_switch(rq, prev, next, &rf);  // :6678 切页表/寄存器/内核栈
	}
	...
}
```

三个要点:
1. **`prev` 的去向取决于它为什么进来。** 主动睡眠(等 IO、等锁)→ `deactivate_task` 把它移出就绪队列,醒了才重新入队;只是被时间片抢占 → 留在队列上,它还就绪,下一轮还可能被选中。
2. **`pick_next_task`(`kernel/sched/core.c:6640`)是"选谁"的总入口。** 它就是 §2 说的那条优先级链:从 stop 类开始 `for_each_class`(`core.c:6002`)逐类问"有任务吗",第一个应答的返回。对最常见的"队列里全是 CFS 任务"情况还有快路径,直接问 fair 类,省掉遍历。
3. **`prev == next` 时不切。** 如果选出来的还是原来那个任务,连 `context_switch` 都省了——白进来一趟但没有切换开销。

### 4.3 一次调度的时间线

把 §3 和 §4 合起来,一次完整的调度长这样:

```
   时间↓
   ───────────────────────────────────────────────────────────
   (之前某刻) tick/唤醒/阻塞 → resched_curr → 置 TIF_NEED_RESCHED
   ───────────────────────────────────────────────────────────
   到达抢占点(中断返回 / syscall 返回 / 主动 schedule)
        │  发现旗标置着 → 调用 __schedule()
        ▼
   t0 │ 关中断; 锁 rq; update_rq_clock; prev = rq->curr
   t1 │ prev 要睡?→ deactivate 出队    只是被抢占?→ 留队上
   t2 │ next = pick_next_task()   沿 stop→dl→rt→fair→idle 选
   t3 │ 清 TIF_NEED_RESCHED 旗标
   t4 │ prev≠next → rq->curr=next; context_switch(切现场)
   ───────────────────────────────────────────────────────────
```

## §5 任务视角:一个任务怎么睡、怎么醒、落在哪颗 CPU

前面 §1–§4 都是 **CPU 视角**:给你一个装满任务的队列,挑一个跑。但调度器还有另一半是**任务视角**——任务不是一直待在就绪队列里等着被选,它会因为等 IO、等锁而**睡去**(离开队列),事件来了再被**唤醒**(回到队列)。§4 里 `try_to_wake_up` 被当成"触发源"点了个名却没展开,这一节把它补上,顺着一个任务走完"睡→醒"的旅程。

### 5.1 任务状态:可运行 ≠ 正在运行

先厘清一个新手最容易混的点。任务有几个基本状态(`include/linux/sched.h:85`):

```
   TASK_RUNNING (0)          可运行 —— 注意它含两种情况:
        ├── 正在某颗 CPU 上跑(同一时刻每核至多一个)
        └── 在就绪队列里排队等着被选(runnable,还没上 CPU)

   TASK_INTERRUPTIBLE (1)    睡眠,可被信号打断(等键盘、等可中断的事件)
   TASK_UNINTERRUPTIBLE (2)  睡眠,不可打断(等磁盘 IO —— 就是 ps 里那个 D 状态)
```

关键认知:**就绪队列(§3 那棵红黑树)里的任务,状态全是 `TASK_RUNNING`。** "RUNNING"不等于"此刻在 CPU 上",而是"有资格被选中"。调度器 pick 的,就是从这堆 RUNNING 里挑一个真正送上 CPU。一旦任务要等资源,它就切到 INTERRUPTIBLE/UNINTERRUPTIBLE 并离开队列——这就是"睡"。

### 5.2 睡:主动让出并出队

任务等资源时的经典写法(内核里到处是这个模式):

```c
set_current_state(TASK_INTERRUPTIBLE);   // 先把自己标记为"要睡"(include/linux/sched.h:180)
if (条件还不满足)
	schedule();                       // 主动进 __schedule,让出 CPU
__set_current_state(TASK_RUNNING);       // 醒来后把自己改回可运行
```

`schedule()` 进入 §4 的 `__schedule()`。因为此时任务状态非 RUNNING 且不是被抢占,§4.2 里那段 `deactivate_task`(`kernel/sched/core.c:2132`)就会**把它移出就绪队列**。出队后它不在红黑树里了,`pick_next_task` 再也选不到它——它就这么"睡"过去,直到被唤醒。

### 5.3 醒:try_to_wake_up 把它拉回来

事件发生了(数据到了、锁释放了),持有事件的一方调 `wake_up()`,最终落到 `try_to_wake_up()`(`kernel/sched/core.c:4191`,常简称 **ttwu**)。它做三件事:

```
   ① 把任务状态改回 TASK_RUNNING          core.c:4213  WRITE_ONCE(p->__state, TASK_RUNNING)
   ② 给它选一颗 CPU 落脚                   select_task_rq   (见 5.4)
   ③ 在那颗 CPU 的就绪队列入队,并判断要不要抢占该 CPU 当前任务
                                          check_preempt_curr   core.c:2216
```

第 ③ 步的抢占判断最能说明优先级链怎么起作用(`check_preempt_curr`,`kernel/sched/core.c:2216`):

```c
if (p->sched_class == rq->curr->sched_class)             // 被唤醒者与当前任务同类
	rq->curr->sched_class->check_preempt_curr(...);  // → 交给类自己判(CFS 比 vruntime + 唤醒粒度)
else if (sched_class_above(p->sched_class, ...))         // 被唤醒者属更高类(如 rt 醒了、当前是 fair)
	resched_curr(rq);                                //   → 立即置 need_resched,抢!
```

这就把 §4 的伏笔补全了:**`try_to_wake_up` 不只是"置个 resched 标记",它负责改状态、选核、入队,再按优先级链决定要不要抢占。** 一个 rt 任务被唤醒时压过你正在跑的浏览器,就发生在这里。

### 5.4 落在哪颗 CPU:select_task_rq 与 CPU 亲和性

唤醒时要决定任务在哪颗核上复活。入口 `select_task_rq()`(`kernel/sched/core.c:3626`):

```c
if (p->nr_cpus_allowed > 1 && !is_migration_disabled(p))
	cpu = p->sched_class->select_task_rq(p, cpu, wake_flags);  // 允许多颗 → 交给调度类挑
else
	cpu = cpumask_any(p->cpus_ptr);                            // 只允许一颗 → 没得选
```

两条线:
- **亲和性是硬约束**:`p->cpus_ptr` 是这个任务被允许运行的 CPU 集合(你用 `taskset` 或 `sched_setaffinity()` 设的就是它)。集合只有一颗核,就没得挑。
- **允许多颗时交给调度类挑**:CFS 的 `select_task_rq_fair`(`kernel/sched/fair.c:7459`)常倾向 **wake affine**(`kernel/sched/fair.c:6468`)——把被唤醒的任务放到**唤醒它的那颗核附近**。因为唤醒方和被唤醒方往往在交换数据(生产者/消费者),放近点缓存还热,省一次跨核搬运;当然也要权衡目标核忙不忙。

**和 §7 负载均衡的关系**:`select_task_rq` 是**唤醒瞬间的一次性放置**,负载均衡是**运行期的周期性再平衡**——两者都在管"任务放哪颗核",一个即时、一个周期,合起来才让多核既不空转又不挤在一颗核上。

### 5.5 生与死:补全整个旅程

补上两端。新任务(`fork` 出来的)第一次进就绪队列走 `wake_up_new_task()`(`kernel/sched/core.c:4833`);CFS 会用 `place_entity(..., initial=1)`(`kernel/sched/fair.c:4648`)给它一个**初始 vruntime**——注意**不能设成 0**,否则新任务 vruntime 最小、会疯狂抢占所有人(fork 炸弹就靠不停新建任务插队)。内核把它设成接近队列当前 `min_vruntime` 再加一点"入场惩罚",让新任务公平地排到队尾附近。

于是一个任务的完整旅程连起来了:

```
   fork ─► place_entity 设初始 vruntime ─► 就绪(在红黑树里,TASK_RUNNING)
     │                                            │
     │                                   被 pick 选中 ▼
     │                                        ┌─────────┐
     │           ┌──── 时间片用完被抢占 ◄──────│  运行   │
     │           │      (留在队列,仍就绪)     └────┬────┘
     │           ▼                        等 IO/锁 │ set_current_state + schedule
     │      (回到就绪等下一轮)                     ▼
     │                                   睡眠(deactivate 出队,不在树里)
     │                                            │ 事件到 → try_to_wake_up
     │                                            │  选核(select_task_rq)+ 重新入队
     │                                            ▼
     │                                   回到就绪(可能落在另一颗 CPU)
     ▼
    exit ─► 退出,finish_task_switch 回收
```

## §6 不止公平:实时任务与优先级链(速览)

CFS 保证"长期公平",但对"必须准时"的任务不够用——公平意味着大家轮流,而音频线程不想轮流,它想**要跑立刻就跑**。这就是 rt 和 deadline 两个实时类存在的理由。它们在优先级链上都排在 fair 前面(§2 那张图),所以只要它们有任务,你的普通程序就得让路。这里一页纸讲清思想,细节交给下钻手册。

**rt 类(`kernel/sched/rt.c`,FIFO / RR):软实时。** 100 个静态优先级,不玩 vruntime 那套公平。选任务用一个 **位图 + 每优先级一条队列** 的结构:位图记录哪些优先级有就绪任务,找最高优先级用一条 `find_first_bit` 指令搞定——O(1),不用遍历。同优先级的任务要么 FIFO(先来先跑到主动让出),要么 RR(轮转,每人一个时间片)。

```
   rt_rq:  优先级位图 active  [0 1 0 0 1 0 ... ]  ← 哪个优先级有任务
                               │   │
           queue[0..99]:  ┌────┘   └────┐
                          ▼             ▼
                       [prio 1]      [prio 4]     每个优先级一条 FIFO 链
                       T_a→T_b       T_c
           选任务 = 位图找最低置位位号(最高优先级)→ 取该链队首。O(1)
```

为防实时任务失控独占 CPU 把系统饿死,rt 类有 **带宽节流**:默认每 1 秒最多让 rt 任务跑 0.95 秒,留 0.05 秒给普通任务喘息。

**deadline 类(`kernel/sched/deadline.c`,EDF):硬实时,优先级比 rt 还高。** 任务声明三个参数:runtime(每个周期要跑多久)、deadline(截止期)、period(周期)。算法是 **EDF(Earliest Deadline First,最早截止期优先)**——谁的截止期最近就先跑,用按 deadline 排序的红黑树选任务。再配 **CBS(恒定带宽服务器)** 防止一个任务超支影响别人,以及 **准入控制**:新的 deadline 任务如果会让 CPU 总利用率超载,直接拒绝(创建失败),而不是接受后大家一起垮。

**两端还有两个"退化"类:** `stop`(最高,内核用来做 CPU 迁移、热插拔的特权通道,能抢占一切)和 `idle`(最低,四类全空时才跑的 `swapper` 空闲线程,顺便进省电状态)。这俩每 CPU 至多一个任务,没有排队结构。

### 用户怎么和调度器打交道:优先级空间与调度策略

上面讲的调度类是内核内部的组织。作为程序员,你从用户态看到的是**调度策略(policy)**和**优先级(priority)**——它们最终决定任务落进哪个类。

内核把所有优先级压进一根 0–139 的数轴(`include/linux/sched/prio.h`),数字越小越优先:

```
   内核 prio:  0 ─────────────── 99 │ 100 ───────────────── 139
               └── 实时 band(RT)──┘ │ └─── 普通 band(nice)───┘
               rt / dl 任务          │  CFS 任务
                                     │   nice -20 ─► 100(最高)
   MAX_RT_PRIO = 100 ────────────────┘   nice   0 ─► 120(默认 DEFAULT_PRIO)
   (prio.h:16)                           nice +19 ─► 139(最低)
                                         NICE_TO_PRIO: prio = nice + 120 (prio.h:26)
   SCHED_DEADLINE 比 0 还高(概念上 prio -1),压过一切 rt 与普通任务
```

所以 §3 讲的 nice 只是这根数轴**右半段(100–139)**里的挪动;实时任务活在**左半段(0–99)**,天然压过所有 CFS 任务——这正是 §6 那条"rt/dl 排在 fair 前"的优先级链在数值上的样子。

**六种调度策略,决定任务进哪个类**(`include/uapi/linux/sched.h:114`):

| 策略 | 值 | 归哪个类 | 用途 |
|---|---|---|---|
| `SCHED_NORMAL`(即 OTHER) | 0 | fair(CFS) | 默认;普通任务,靠 nice 调权重 |
| `SCHED_BATCH` | 3 | fair(CFS) | 批处理;不做唤醒抢占,对交互不友好但省切换 |
| `SCHED_IDLE` | 5 | fair(CFS) | 极低;几乎只在系统空闲时才跑 |
| `SCHED_FIFO` | 1 | rt | 实时;跑到主动让出为止,同优先级不轮转 |
| `SCHED_RR` | 2 | rt | 实时;同优先级按时间片轮转 |
| `SCHED_DEADLINE` | 6 | deadline | 声明 runtime/deadline/period,按 EDF 调度 |

**怎么设(用户接口)**:

- 改 nice(CFS 类内权重):命令 `nice`/`renice`,系统调用 `setpriority()`(`kernel/sys.c:211`)——就是 §3 那套 1024:335 的权重。
- 改策略(换类):命令 `chrt`,系统调用 `sched_setscheduler()`(`kernel/sched/core.c:8059`)。例如 `chrt -f 50 ./app` 把 app 设成 `SCHED_FIFO`、实时优先级 50,它就进了 rt 类、压过你所有普通程序;`SCHED_DEADLINE` 参数多,用 `sched_setattr()`(`kernel/sched/core.c:8085`)。
- 绑核(亲和性):命令 `taskset`,系统调用 `sched_setaffinity()`——设的就是 §5.4 那个 `p->cpus_ptr`。
- 按组分配(cgroup):cpu controller 用 `cpu.weight`(权重)和 `cpu.max`(带宽配额)管一整组任务,是 nice 的"分组版"。

一句话把两个视角接上:**`policy` 决定任务进哪个调度类,`priority`/`nice` 决定它在类内的位置,`affinity` 决定它能上哪些核。**

**一个常见坑**:把普通程序设成 `SCHED_FIFO` 高优先级又让它跑死循环,它会**独占 CPU 饿死其它任务**(包括你的 shell)。靠 §6 提到的 rt 带宽节流(默认每秒留 0.05s)兜底,但仍应谨慎——这也是为什么设实时策略通常需要特权。

> 想深入?rt 的位图选择/带宽节流深剖在 [`sub/rt/`](sub/rt/00-overview.md);deadline 的 EDF+CBS+准入+GRUB 在 [`sub/deadline/`](sub/deadline/00-overview.md);两端退化类在 [`sub/idle-stop/`](sub/idle-stop/00-overview.md)。策略/亲和性的完整 syscall ABI(`sched_setattr`/`sched_attr`)在 [`01-api.md`](01-api.md),cgroup cpu controller 参数在 [`06-tuning.md`](06-tuning.md)。

## §7 多核:负载均衡的直觉

回到 §2 埋的伏笔:每颗 CPU 一条私有队列,解决了锁争用,但会失衡——有的 CPU 排了 10 个任务,有的空着。**负载均衡**就是定期把任务在队列间搬平的那一层。这里只讲思想,数值细节留给手册。

**fair 类:周期性均衡。** 在 tick 里定期触发(`run_rebalance_domains`),找出比本 CPU 忙得多的 CPU,从它那儿"拉"几个任务过来。但搬任务有代价(要抢两把 rq 锁、任务的缓存要在新核上重建),所以不能一有差距就搬。内核用一套 **调度域(sched_domain)** 层次描述"哪些 CPU 离得近":

```
       NUMA 域   (跨内存节点,搬任务代价最大,最不愿搬)
        │
       MC 域     (共享 LLC 末级缓存的核,搬了缓存还热,较愿搬)
        │
       SMT 域    (同物理核的超线程,几乎无代价)
```

**离得越近越愿意搬**(缓存损失小),离得越远越保守(每层一个 `imbalance_pct` 容忍阈值,差距超过阈值才动手)。这棵域树由 topology 子模块根据你的 CPU 拓扑在启动时构建。

**rt / dl 类:不做周期均衡,改用即时 push/pull。** 实时任务等不起"下次 tick 再均衡"。所以本 CPU 一旦多出一个高优先级实时任务,立刻 **push**(推给一个空闲或更低优先级的 CPU);本 CPU 快空了,立刻 **pull**(从别人那拉一个)。为了 O(1) 找到"哪个 CPU 最适合接",rt 和 dl 各维护一个 **CPU 优先级堆**(cpupri / cpudeadline)。

一句话:**fair 图吞吐,慢慢搬求整体均衡;rt/dl 图延迟,立刻搬求准时。**

## §8 动手看:让调度器变得可见

读代码之外,亲手观察调度器在跑,能让上面所有抽象落地。几个不用改内核就能玩的入口:

**① 看运行队列现状** —— `/proc/sched_debug`(需 `CONFIG_SCHED_DEBUG`)。它把每颗 CPU 的 rq、每个 CFS 任务的 vruntime、红黑树内容都打出来。找一个任务,盯着它的 vruntime 随时间涨,你会亲眼看到 §3 讲的东西。

```
   $ cat /proc/sched_debug | less
   # 每 CPU 一段:cfs_rq 的 nr_running、min_vruntime、当前任务;
   # runnable tasks 列表带每个任务的 vruntime、sum_exec_runtime
```

**② 看每个任务的调度统计** —— `/proc/<pid>/sched`。单看一个进程:它被调度了多少次、等待了多久、累计跑了多久。开关在 `/proc/sys/kernel/sched_schedstats`。

**③ 追踪每一次切换** —— ftrace 的 `sched_switch` 事件,是理解"到底谁切给了谁"最直观的工具:

```
   $ cd /sys/kernel/debug/tracing
   $ echo 1 > events/sched/sched_switch/enable
   $ cat trace_pipe        # 实时看:prev_comm/prev_prio → next_comm/next_prio
```

你会看到一行行 `prev → next` 的切换记录,带优先级——直接对应 §4 的 `context_switch`。配合 `sched_wakeup`、`sched_stat_runtime` 等事件能看得更细。

**④ load average 是什么** —— `top` / `uptime` 里的 `load average: 1.20, 0.98, 0.85` 三个数,是过去 1/5/15 分钟"平均有多少任务在运行或不可中断等待"。它由 `kernel/sched/loadavg.c` 用整数定点的指数加权移动平均算出,每 5 秒采一次。注意它**不是** CPU 使用率(可以 >核数,表示排队)。

**⑤ 改 nice 值验证 §3** —— 开两个 `while :; do :; done` 死循环占满一个核,用 `renice` 把其中一个调到 nice 5,再用 `top` 看两者 CPU 占比,应接近 3:1(对应 §3.2 的 1024:335)。这是把整篇最核心的原理**亲手跑出来**。

## §9 你现在能读懂什么 + 进阶地图

如果顺着读到这,你已经建立了正确的骨架:

- 调度器是**被动触发**的"选谁跑"循环,不是后台线程(§1);
- **每 CPU 一队** + **分类成链**是两个奠基性的设计取舍(§2);
- CFS 用 **vruntime 欠账本 + 红黑树取最左** 实现公平,**nice→权重→vruntime 流速** 实现优先级(§3);
- 换人是**先置 need_resched 标记、抢占点再进 `__schedule` 真切**两步走(§4);
- 任务会**睡(出队)和醒(`try_to_wake_up` 改状态+选核+入队+抢占判断)**,亲和性与 wake affine 决定它落在哪颗核(§5);
- 实时诉求由 **rt(位图/带宽)、dl(EDF/准入)** 满足,排在 fair 前面(§6);
- 多核靠**负载均衡**补平失衡,fair 图吞吐慢搬、rt/dl 图延迟即时 push/pull(§7)。

拿着这个骨架,你现在可以**打开 `kernel/sched/fair.c` 从 `update_curr`(:882)和 `pick_next_task_fair`(:7793)读起**,再到 `kernel/sched/core.c` 的 `__schedule`(:6557)——这三个函数是整个调度器最该先读的。

**接下来往哪深入(从这张地图挑):**

```
   想彻底搞懂 CFS 的工程细节(带宽/组权重/负载均衡内核)
       → sub/fair/  (深度样板,4 篇)

   想搞懂实时调度
       → sub/rt/ (FIFO/RR + 带宽节流)   sub/deadline/ (EDF+CBS+准入)

   想搞懂调度核心机制(抢占动态切换/远程唤醒队列/迁移准入/SMT 核调度)
       → sub/core/

   想搞懂负载/利用率信号怎么算(PELT)、拓扑域怎么建、怎么驱动调频
       → sub/pelt/   sub/topology/   sub/schedutil/

   想搞懂压力/时间的可观测(PSI、sched_debug、cpuacct)
       → sub/observability/

   查接口、对象、并发、调参、观测 → 顶层 01~07 手册
   任何结论想复现出处          → 99-evidence.md
```

顶层导航总表在 [`00-overview.md`](00-overview.md) §8。这篇导读是入口,那套手册是目的地——读手册时若某处卡住,回到本篇对应小节重建直觉,往往就通了。
