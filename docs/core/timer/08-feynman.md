## §1 clocksource 和 clockevent 为什么必须分成两个东西？

### 先举个例子

想象你在厨房里做饭，你需要两样完全不同的东西。

**第一样是墙上的挂钟。** 你随时抬头看一眼，就知道现在几点了。
挂钟从来不主动找你，它只是**一直在那里走**，你想知道时间就去读它。
它的好坏标准是"走得准不准"。

**第二样是定时闹钟。** 你说"15 分钟后叫我"，然后就可以去干别的事，
时间到了它**主动响**。它的好坏标准是"该响的时候响不响"。

**现在关键问题来了：能不能用挂钟当闹钟？**
理论上可以——你每隔十秒抬头看一次挂钟，看到时间到了就自己起来。
但这意味着**你什么别的事都干不了了**，你得一直盯着钟。

**反过来能不能用闹钟当挂钟？** 更不行——闹钟只会在某一刻响一声，
你问它"现在几点"，它答不上来。

⇒ **所以厨房里必须有两样东西，因为"随时能读"和"到点主动叫"
是两种完全不同的能力。**

内核里也一样：
- **clocksource = 挂钟**：一个一直在走的计数器，随时能读
- **clockevent = 闹钟**：你能设定"到这个数的时候给我一个中断"

**而"CPU 一直盯着挂钟看"就是忙等**（`udelay()`），
这正是为什么忙等只能用于极短的延时——它把 CPU 完全占住了。

### 回到代码

| 事实 | 证据 |
|---|---|
| clocksource **没有** `irq` 字段 | `include/linux/clocksource.h:96-130` 整个结构体里没有中断相关字段 |
| clockevent **有** `irq` 字段 | `include/linux/clockchips.h:127` |
| clocksource 的核心是 `read()` | `include/linux/clocksource.h:97` |
| clockevent 的核心是 `set_next_event()` | `include/linux/clockchips.h:102` |
| clocksource 有 `mask`，clockevent 没有 | `include/linux/clocksource.h:98`；`clockchips.h` 里找不到 |

**官方文档用一句话概括了这件事**：clockevent 是 clocksource 的
"conceptual reverse"（`Documentation/timers/timekeeping.rst` 的 "Clock events" 一节）。

**`mask` 的有无最能说明问题**：挂钟会转满一圈回到 12 点，
所以读挂钟的人必须知道"一圈是多少"（这就是 `mask`）。
闹钟不需要——**没人会设一个"一圈以后"的闹钟**，
系统不会安排超出事件设备时间视野的事件。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **厨房里挂钟和闹钟是两个物件，内核里可能是同一块硬件。**
   arm64 的架构定时器一份硬件同时提供两者：读 `CNTVCT_EL0`（挂钟）、
   写 `CNTV_CVAL_EL0` + PPI 中断（闹钟）。
   ⇒ **"一个驱动实现两个抽象"和"一个抽象有两面"是不同的事**
   （02 §1.0.A 用对比表逐行否掉了后一种理解）。

2. **挂钟只有一个，闹钟可以每人一个。** 内核里 clocksource
   全系统选一个最好的（`curr_clocksource`，`kernel/time/clocksource.c:100`），
   而 clockevent **每个 CPU 一个**（`tick_cpu_device`，`kernel/time/tick-common.c:28`）。
   ⇒ 这个不对称在类比里完全看不出来。

3. **你读挂钟得到的是"几点几分"，读 clocksource 得到的是一个裸数字。**
   把裸数字变成"几点"是**第三个东西**干的活（timekeeper），
   类比里没有对应物。⇒ 02 §1.0.B 专门讲这一层。

## §2 为什么内核有两套定时器，不能合并成一套？

### 先举个例子

想象你开一家医院，要处理两类完全不同的"预约"。

**第一类是"手术预约"。** 病人约了周三下午三点做手术，
**这个时间必须准**，早了晚了都是事故。这类预约数量不多，
而且**约了就一定会执行**。

**第二类是"复诊提醒"。** 医生说"三个月后来复查"，
系统就登记一条。这类登记**数量极大**，而且——关键在这里——
**绝大多数病人在三个月内就因为别的原因来过了，这条提醒被划掉了**。

**如果你用同一套系统管这两类**，会出现什么问题？

手术预约要求"精确到分钟"，所以你的系统得按分钟建索引。
但复诊提醒有几十万条，按分钟建索引意味着**每登记一条都要维护一个精确排序的结构**——
而这几十万条里 90% 根本不会被执行到，你为它们做的排序工作全部白费。

**医院的真实做法是分开管**：
- 手术预约用**精确的时间表**，插入时就排好序，代价是插入慢一点
- 复诊提醒用**粗筐子**：按"哪一个月"扔进对应的抽屉，扔进去就不管了。
  到了那个月才把抽屉倒出来，按天重新分一遍

**"扔进抽屉"极便宜，"倒抽屉"比较贵——但因为 90% 的条目在被倒出来之前
就被划掉了，总账是赚的。**

内核里就是这两套：
- **hrtimer = 手术预约**：红黑树，插入时排序，到期准
- **`timer_list` = 复诊提醒**：时间轮 + 级联（倒抽屉），插入 O(1)，到期不准

### 回到代码

| 事实 | 证据 |
|---|---|
| `timer_list` 用哈希桶 | `vectors[WHEEL_SIZE]` —— `kernel/time/timer.c:213` |
| hrtimer 用红黑树 | `struct timerqueue_node node` —— `include/linux/hrtimer.h:119` |
| `timer_list` 的时间单位是 jiffies | `unsigned long expires` |
| hrtimer 的时间单位是纳秒 | `ktime_t _softexpires` —— `include/linux/hrtimer.h:120` |
| `timer_list` 只有 4 个字段 | 整个结构体（`include/linux/timer.h`）—— **这就是"便宜"的物质基础** |

**"90% 会被取消"这个前提是官方文档明确写出来的**
（`Documentation/timers/hrtimers.rst`）：

> The vast majority of those timers never expire and are rarely
> recascaded because the expected correct event arrives in time so they
> can be removed from the timer wheel before any further processing of
> them becomes necessary.

**而且文档记录了"曾经试过合并，失败了"**：
"After a lot of back and forth trying to integrate high-resolution and
high-precision features into the existing timer framework ... we came to
the conclusion that the timer wheel code is fundamentally not suitable"。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **医院里"手术"和"复诊"是按重要性分的，内核里是按"会不会被取消"分的。**
   一个非常重要的超时（比如看门狗）照样应该用 `timer_list`——
   **判据不是"重要不重要"，是"到期前会不会被取消"和"要不要准"**。

2. **医院的抽屉倒出来是人工操作，内核的级联是在到期路径上同步做的。**
   ⇒ **这意味着"倒抽屉"的开销会直接算在某个定时器的到期延迟里**，
   官方文档称之为 "unpredictable O(N) overhead of cascading"。
   ⇒ 03 §B6 那个 `nr_hangs` 计数器就是在抓这类拖延。

3. **两套系统在内核里不是平级的**：hrtimer **能**要求硬件"到这一刻中断我"，
   `timer_list` **不能**——它只能等 tick 来推它一格（02 §2）。
   ⇒ **这是架构上的层级差别，医院的类比里两个抽屉是平级的。**

## §3 `jiffies` 为什么不能直接用 `>` 比大小？

### 先举个例子

老式汽车的里程表只有五位数，跑到 `99999` 公里之后，
再跑一公里就变成 `00000`。

现在假设你在 `99998` 公里的时候记了个"该换机油了，到 `00003` 公里换"。
过了五公里，表显 `00003`，该换油了。

**但如果你写代码判断"到了没有"，写成 `if (当前 > 目标)`，会发生什么？**
当前是 `00003`，目标是 `00003`，勉强算到了。
可如果目标是 `00005` 而当前是 `00003`，`3 > 5` 是假——**这是对的**。
再往前，当前 `99998`、目标 `00003`：`99998 > 3` 是**真** ⇒
**代码认为已经到了，实际还差 5 公里。**

**问题的本质**：里程表绕回之后，"数值大"不等于"时间晚"。

**正确的做法是算差值再看符号**：`(当前 - 目标)` 按五位数算，
`00003 - 99998 = 00005`（借位），是正的小数 ⇒ 已经过了 5 公里。
而 `99998 - 00003 = 99995`，如果把它当**有符号数**看就是 `-5` ⇒ 还差 5 公里。

⇒ **这就是 `time_after()` 干的事：做减法，然后按有符号数判断符号。**

### 回到代码

| 事实 | 证据 |
|---|---|
| `jiffies` 是 `unsigned long` | `include/linux/jiffies.h` |
| 32 位上 `HZ=1000` 约 **49.7 天**绕一圈 | `2^32 / 1000 / 86400 ≈ 49.7` |
| 必须用 `time_after()` / `time_before()` | `include/linux/jiffies.h`（01 §2） |
| 内核自己也在用 | `if (time_before(jiffies, base->next_expiry))` —— `kernel/time/timer.c:2049` 一带（03 §A8 引过） |

**注意内核代码里几乎看不到裸的 `jiffies >` 比较**——
这不是巧合，是纪律。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **里程表只增不减，`jiffies` 在 NO_HZ 下会"跳"。**
   CPU 睡了 3 秒再醒，`jiffies` 一次加 3000
   （`tick_nohz_idle_exit()` 里补齐，`kernel/time/tick-sched.c:1348`）。
   ⇒ **依赖"每一格都被执行到"的逻辑会坏**，
   类比里里程表是连续走的。

2. **`time_after()` 只在"差值小于半圈"时正确。**
   如果你比较的两个时刻相差超过 ~24.8 天（32 位 `HZ=1000`），
   **符号判断会得出相反的结论**。
   ⇒ 长周期定时不能靠 `jiffies`，要用 `ktime_t`。

3. **64 位系统上 `jiffies` 实际上不会绕回**（`unsigned long` 是 64 位，
   要几亿年）。⇒ **arm64 上这个坑本身不会触发**，
   但**代码规范仍然要求用 `time_after()`**——因为代码可能被移植到 32 位。
   ⇒ **所以这是一个"在你的平台上不会出错但仍然必须遵守"的规则**，
   这类规则最容易被新人省略掉。

## §4 为什么把 cycles 换成纳秒只用乘法和右移？

### 先举个例子

假设你有一个每秒响 24576000 次的节拍器，你要把"响了 N 次"换成"过了多少纳秒"。

**数学上的答案**：`纳秒 = N × 1000000000 / 24576000`。

**但除法在 CPU 上非常慢**——比乘法慢一个数量级，而且
在 32 位 CPU 上做 64 位除法要调一个库函数。
而这个换算**每次读时间都要做一遍**，一秒可能几百万次。

**省除法的办法**：把除数变成 2 的幂。
`1000000000 / 24576000 ≈ 40.69`。我们想要 `N × 40.69`，
但只能用整数。于是**先放大再右移**：

- 取 `shift = 24`（也就是除以 `2^24 = 16777216`）
- 算 `mult = 40.69 × 16777216 ≈ 682864525`
- 于是 `纳秒 ≈ (N × 682864525) >> 24`

**右移就是除以 2 的幂，一条指令。** 乘法一条指令。**除法没了。**

**这就像超市定价**：不写"每个 0.333 元"（会有除不尽的问题），
而写"三个 1 元"。你把单位放大到能整除的地方。

### 回到代码

| 事实 | 证据 |
|---|---|
| 换算式就是乘 + 右移 | `timekeeping_delta_to_ns()` —— `kernel/time/timekeeping.c:374` |
| `mult` / `shift` 存在 `tk_read_base` 里 | `include/linux/timekeeper_internal.h:38-39` |
| 由注册函数代算 | `clocksource_register_hz()` → `__clocksource_register_scale()`（01 §7） |
| 官方文档明确写了这个公式 | `Documentation/timers/timekeeping.rst`：`ns ~= (clocksource * mult) >> shift` |

**`~=` 那个波浪号是文档原文**——它在提醒你**这是近似值，不是精确值**。

**NTP 微调时钟快慢，改的就是 `mult`**（03 §B4）：
把 `mult` 调大一点，同样多的 cycles 就算出更多纳秒 ⇒ 时钟走快了。
**而 `maxadj`（`include/linux/clocksource.h:102`）限制单次能调多少**，
防止一次错误调整把时间搞飞。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **超市定价的误差不累积，时钟的误差会累积。**
   每次换算都丢一点小数，所以 timekeeper 有一个
   `xtime_nsec` 字段（`include/linux/timekeeper_internal.h:40`）
   **专门存这些丢掉的小数部分**，下次接着算。
   ⇒ 类比里完全没有对应物。

2. **放大不能无限制。** `shift` 太大，`N × mult` 会溢出 64 位。
   所以 `mask`（有效位数）和 `shift` 是**互相约束**的，
   核心算出一个 `max_cycles` 上界（02 §5.6）——
   **这个上界又反过来限制了 NO_HZ 能睡多久**（03 §B5 的第四道门）。
   ⇒ 一个纯粹的算术优化，最后限制了电源管理，类比里看不出这条链。

3. **`raw` 时基有自己独立的一套 `mult`。**
   `struct timekeeper` 里有 `tkr_mono` 和 `tkr_raw` 两份
   （02 §5.9）⇒ **同一个硬件读数，两套换算参数**，
   一套被 NTP 调、一套不调。类比里一个节拍器只有一个换算率。

## §5 为什么"周期 tick"本身是一个定时器？

### 先举个例子

想象一个老式工厂，每小时整点鸣一次汽笛，工人靠汽笛知道该换班了。
汽笛是**专门的一套设备**：一个机械钟连着气阀，整点自动放气。

现在工厂现代化了，装了一套**可编程的报警系统**：
你可以让它在任意时刻响。

**问题：还需要那套专门的整点汽笛吗？**

不需要。因为"整点鸣笛"只是"任意时刻报警"的一个特例——
你只要在每次响完之后，**顺手把下一次设成一小时后**，
就得到了整点汽笛的效果。

**而且这样做多了一个巨大的好处**：如果某天全厂放假，
没人需要换班提醒，你**干脆就不设下一次**——汽笛就停了，省了气。
那套机械汽笛做不到这一点，它只会一直响。

内核里完全一样：
- **"周期 tick"就是那个整点汽笛**
- **hrtimer 就是可编程报警系统**
- **NO_HZ（tickless）就是"放假时不设下一次"**

### 回到代码

**`struct tick_sched` 里第一个字段就是一个 hrtimer**：

```c
struct tick_sched {
	struct hrtimer			sched_timer;
	...
};
```
—— `kernel/time/tick-sched.h:55-56`

| 事实 | 证据 |
|---|---|
| 周期 tick 是一个 hrtimer | `tick_sched.sched_timer` —— `kernel/time/tick-sched.h:56` |
| 系统启动时**不是**这样，是先低精度再切换 | `hrtimer_switch_to_hres()` —— `kernel/time/hrtimer.c:756` |
| 切换是"懒"的，在下一次低精度 tick 里发生 | `kernel/time/hrtimer.c:1954-1955`（03 §A6） |
| 官方文档记录了这个转换 | `Documentation/timers/highres.rst` 的 "dynamic ticks" 一节 |

**文档原话**："Dynamic ticks are the logical consequence of the
hrtimer based periodic tick replacement (sched_tick)."
—— **"logical consequence"（逻辑上的必然结果）** 这个措辞很关键：
tickless 不是一个额外加上去的功能，**它是"用定时器实现 tick"之后自动获得的能力**。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **工厂里报警系统和汽笛是两套独立设备，内核里是循环依赖。**
   hrtimer 需要 tick 层去碰硬件（`tick_program_event()`，
   `kernel/time/hrtimer.c:1886`），而 tick 层的周期 tick 又是个 hrtimer。
   ⇒ **这个循环是内核初始化顺序特别绕的根本原因**（03 §C3），
   类比里完全没有这个问题。

2. **"顺手设下一次"在内核里有个坑。**
   hrtimer 回调 `return HRTIMER_RESTART` 之前**必须先
   `hrtimer_forward_now()`**，否则到期时间没变 ⇒ 立刻再到期 ⇒ 死循环
   （01 §4.1、05 §1.3）。类比里"设成一小时后"是自然而然的，
   代码里是个必须显式做的动作。

3. **"放假就不设"在内核里不是无条件的。**
   停 tick 要过四道门（03 §B5），其中一道是
   **必须至少留一个 CPU 继续 tick 来维护系统时间**
   （`Documentation/timers/no_hz.rst` 明确的约束）。
   ⇒ **全厂放假是可以的，但门房必须有人**——类比里没有这条。

## §6 为什么内核启动时先用一个最差的时钟？

### 先举个例子

你搬进一间新房子，正式的挂钟还在快递路上。
但你**现在就需要知道时间**——你要记录"几点开始搬家的"、
"水电什么时候来接"。

**你的做法**：先用手机上那个不太准的秒表，或者干脆数自己的脉搏。
**难看，但比完全不知道时间强。** 等挂钟到了，换上去。

**关键洞见**：如果你坚持"必须有准钟才开始计时"，
那么挂钟到货之前发生的所有事情**都没有时间戳**——
而恰恰是这段时间最容易出问题、最需要日志。

内核完全一样。它启动时的顺序是：

1. 先把 timekeeper 建起来，**用一个 rating 只有 1 的兜底时钟源**
2. 然后架构代码才去探测真正的硬件定时器
3. 真硬件注册上来，rating 高得多 ⇒ **自动换掉兜底的那个**

### 回到代码

**启动顺序是"先 timekeeping，后 time_init"**——反直觉但确实如此：

| 步 | 位置 |
|---|---|
| `timekeeping_init()` | `init/main.c:1063` |
| `time_init()`（架构探测真硬件） | `init/main.c:1064` —— **在后面** |

**兜底时钟源就是 `jiffies`**：

| 字段 | 值 | 位置 |
|---|---|---|
| `.name` | `"jiffies"` | `kernel/time/jiffies.c:33` |
| `.rating` | **1** | `kernel/time/jiffies.c:34` —— **注释就写着 `lowest valid rating`** |

**`clocksource_default_clock()` 是 `__weak` 的**
（`kernel/time/jiffies.c:71`）⇒ 架构可以覆盖，arm64 没覆盖 ⇒ 用 jiffies。
`timekeeping_init()` 在 `kernel/time/timekeeping.c:1661` 调它。

**换掉的时刻**：arm64 的 arch timer rating 是 **400**
（`drivers/clocksource/arm_arch_timer.c:235`），注册时触发
`clocksource_select()`（`kernel/time/clocksource.c:130`）⇒ 400 ≫ 1 ⇒ 换掉。

**所以"rating 的最低有效值是 1 而不是 0"这个细节有了解释**：
要留一个"比什么都强"的档位给兜底的那个。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **换挂钟的时候你会对一下表，内核换时钟源时不需要。**
   因为 timekeeper 存的是**纳秒基准 + 增量**（02 §3.1），
   换时钟源只是换了算增量的方式，**已经累积的时间不动**。
   ⇒ 类比里"换钟要重新设时间"，代码里不需要。

2. **兜底时钟源不会消失。** 它一直在全局链表里，
   只是 rating 低选不上。⇒ **如果你在运行中看到
   `current_clocksource` 变回 `jiffies`，说明好的那个被看门狗判死了**
   （04 §5.2、07 §6.5）——这是明确的故障信号，不是"回到初始状态"。

3. **"数脉搏"在类比里是笨办法，`jiffies` 时钟源在代码里是个正经的
   `struct clocksource`。** 它有完整的 `read()`/`mask`/`mult`/`shift`，
   走的是和真硬件**完全相同的代码路径**。
   ⇒ **这才是这个设计真正优雅的地方**：不是"启动期有一套特殊逻辑"，
   而是"启动期用同一套逻辑配一个很差的实现"。

## §7 为什么 CPU 深度睡眠需要别人"广播"叫醒？

### 先举个例子

宿舍里四个人，每人床头有个闹钟。晚上都设好第二天的闹钟，睡觉。

**问题：有些宿舍的电闸是总控的。** 为了省电，
最后一个睡的人把总电闸拉了——**四个闹钟全断电了**。
第二天没人醒。

**解决办法**：留一个人的闹钟接在**不受总闸控制的插座**上
（或者用电池闹钟）。它响的时候把该起的人叫醒。
⇒ **一个"永远有电"的闹钟，替所有断电的闹钟干活。**

内核里：
- **CPU 本地定时器 = 床头闹钟**（进深度省电态时会断电停摆）
- **广播设备 = 那个永远有电的闹钟**
- **`CLOCK_EVT_FEAT_C3STOP` = "我这个闹钟会断电"的声明**

### 回到代码

| 事实 | 证据 |
|---|---|
| 声明"我会停"的 feature 位 | `CLOCK_EVT_FEAT_C3STOP`（04 §1.1；全树 9 个文件用它） |
| arm64 的架构定时器会声明它 | `drivers/clocksource/arm_arch_timer.c`（04 §1.1 的表） |
| **DTS 的 `always-on` 直接控制这件事** | `arch_timer_c3stop = !of_property_read_bool(np, "always-on");` —— `drivers/clocksource/arm_arch_timer.c:1401` |
| 进出深度睡眠时登记/恢复 | `tick_broadcast_enter()` / `_exit()` —— `include/linux/tick.h:99` / `:103` |
| arm64 用 hrtimer 模拟广播设备 | `tick_setup_hrtimer_broadcast()` —— `arch/arm64/kernel/time.c:62` |

**那一行 `!of_property_read_bool(np, "always-on")` 是整套机制的开关**：
DTS 里写了 `always-on` ⇒ 不声明 C3STOP ⇒ 不安排广播（06 §5.1）。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **宿舍里那个"永远有电的闹钟"是独立硬件，arm64 上它是
   另一个 CPU 上的 hrtimer。** `tick-broadcast-hrtimer.c`（111 行）
   用**还醒着的 CPU** 替睡着的 CPU 计时（04 §1.3）。
   ⇒ **所以它有个前提：必须有至少一个 CPU 不进深度睡眠。**
   类比里那个闹钟是无条件可用的。

2. **类比里"断电"是全有全无，硬件上是分级的。** C3STOP 这个名字
   来自 x86 的 C3 电源状态，arm64 借用了它。
   ⇒ **是不是真的会停，取决于具体进哪一级 idle 状态**，
   不是一个静态属性。这是为什么 `always-on` 写错的后果
   **只在特定电源状态下才暴露**（06 §5.2）。

3. **`always-on` 写错的两个方向后果完全不对称。**
   该写没写 ⇒ 多一层广播开销，**功能正确**；
   不该写却写了 ⇒ **CPU 睡过头，系统看起来卡死**。
   ⇒ **默认（不写）是安全的那一侧** ——
   类比里"多留一个备用闹钟"的代价也很小，这一点倒是对上了。

## §8 为什么实时内核要把定时器搬进一个线程？

**这一节是本树特有的**——因为 `arch/arm64/Kconfig:96` 的
`select ARCH_SUPPORTS_RT` 是本地新增的一行（01 §0.1）。

### 先举个例子

医院急诊室，规矩是"来了病人立刻处理，处理完才做别的"。

现在来了个**需要缝 20 针的伤口**。按规矩，医生得一口气缝完。
就在缝到第 5 针的时候，**一个心跳骤停的病人推进来了**。

**按原规矩，这个病人得等 15 针的时间。** 这就是"最坏延迟"。

**实时医院的改法**：把"缝合"从"必须一口气做完的急诊动作"
改成"**一个可以被打断的常规任务**"。给它排一个优先级——
比挂号高，比心跳骤停低。这样缝到第 5 针时心跳骤停进来，
**缝合让位，先救命，之后再回来缝**。

**代价是什么？** 缝合总耗时变长了（多了两次"放下-拿起"），
而且缝合过程中的连续性变差了。
**换来的是什么？** 心跳骤停的等待时间从"15 针"降到"一次切换"。

内核里完全一样：
- **softirq = "必须一口气做完的急诊动作"**（不可被普通任务抢占）
- **定时器回调 = 那个缝合**（可能很长，而且数量多）
- **`timersd` 线程 = 把缝合改成可被打断的常规任务**

### 回到代码

**这就是本树 4 处改动做的事**（01 §0.1、03 §B2）：

| 非 RT | RT |
|---|---|
| `raise_softirq(TIMER_SOFTIRQ)` | 置位 `pending_timer_softirq` + 唤醒 `timersd` |

| 事实 | 证据 |
|---|---|
| RT 下有个专用 per-CPU 线程 | `DECLARE_PER_CPU(struct task_struct *, timersd)` —— `include/linux/interrupt.h:613` |
| 它有自己的 pending 位图 | `DECLARE_PER_CPU(unsigned long, pending_timer_softirq)` —— `include/linux/interrupt.h:614` |
| 它是 FIFO 低优先级 | `sched_set_fifo_low(current)` —— `kernel/softirq.c:1013` |
| 非 RT 上那三个包装函数就是原调用的直译 | `include/linux/interrupt.h:624-638` 的 `#else` 分支 |
| 执行逻辑完全复用 | `run_timersd()` 把 pending 位塞回普通掩码然后调 `__do_softirq()` —— `kernel/softirq.c:1022` 一带 |

**最巧妙的一点在最后一行**：它**没有另写一套定时器执行逻辑**，
而是"把 pending 位从私有变量搬回普通掩码，然后调普通的 `__do_softirq()`"。
⇒ **执行逻辑零重复，改变的只是执行的上下文。**

### 这个类比什么时候会误导你？

⚠️ **四处**：

1. **医院里"缝合让位"是医生的判断，内核里是调度器的机械行为。**
   `timersd` 是 FIFO **低**优先级，所以**任何优先级更高的实时任务都会抢占它**——
   **包括那些其实不那么紧急的**。
   ⇒ 这就是为什么 RT 上定时器抖动变大是**设计预期，不是 bug**（07 §6.4）。

2. **类比里只有"缝合"一件事变了，内核里 `HARD` 回调没变。**
   **`HRTIMER_MODE_*_HARD` 的回调在 RT 上仍然跑在硬中断里**（05 §1.4）。
   ⇒ **所以"RT 内核上定时器都在线程里"是错的** ——
   只有 `SOFT` 的那一半是。

3. **"可以被打断"带来一个类比里没有的新问题**：
   如果有人在等这个回调跑完（`timer_delete_sync()`），
   而等的人优先级更高，**自旋等就会永久饿死那个回调**。
   ⇒ 所以 RT 上额外加了 `expiry_lock`（`kernel/time/timer.c:203`），
   把"自旋等"改成"睡着等"（03 §B2.3）。

4. **两个唤起函数不对称，类比里看不出来。**
   `raise_timer_softirq()` 置位**并且**唤醒，
   `raise_hrtimer_softirq()` **只置位不唤醒**
   （`kernel/softirq.c:1049` vs `:1044`）——
   因为后者的调用点在硬中断里，中断返回时自然会检查。

## §9 为什么"永久停掉定时器"要把函数指针置成 NULL？

### 先举个例子

你要拆掉一台自动售货机。规矩是：拔电源、清货、拉走。

**问题**：机器里有个"缺货自动补货"的电路。你拔了电源开始清货，
清到一半，**另一个同事看到货架空了，顺手按了"补货"按钮**——
如果机器还有备用电池，它就开始动了。而你的手正在里面。

**两种防法**：

**防法一（不彻底）**：拔电源之后**检查一遍所有能触发补货的入口**，
确认没人会按。⇒ 问题是**你未必知道所有入口**，而且新同事可能加一个新按钮。

**防法二（彻底）**：**把"补货"这个动作本身拆掉**——
把执行补货的那根连杆卸了。之后谁按按钮都没用，**按钮还在，但什么都不会发生**。

⇒ **`timer_shutdown_sync()` 用的是防法二**：
它不去检查"还有没有人会 `mod_timer()`"，而是**把回调指针置成 NULL**，
让"启动定时器"这个动作本身失效。

### 回到代码

| 函数 | 做什么 | 之后能重启吗 |
|---|---|---|
| `timer_delete_sync()` | 删除 + 等回调跑完 | **能** ⇒ 防法一 |
| `timer_shutdown_sync()` | 删除 + 等回调跑完 + **`function = NULL`** | **不能** ⇒ 防法二 |

| 事实 | 证据 |
|---|---|
| 走同一个底层，靠一个 `shutdown` 参数区分 | `__timer_delete(timer, shutdown)` —— `kernel/time/timer.c:1315` |
| `shutdown` 为真时在持锁下置 NULL | `kernel/time/timer.c:1334-1337` 一带 |
| 之后 `mod_timer()` 返回 0 并**静默丢弃** | 返回值注释：`%0 - The timer was inactive and started or was in shutdown state and the operation was discarded` —— `kernel/time/timer.c:1182`、`:1207` |
| kerneldoc 明说了为什么需要它 | `kernel/time/timer.c:1584-1624`：`This function cannot guarantee that the timer is not rearmed again ... If such a guarantee is needed, e.g. for teardown situations then use timer_shutdown_sync() instead.` |

**那段 kerneldoc 是本子系统写得最好的一段文档**：
它先老实承认 `timer_delete_sync()` 的返回值在并发重启时**没有意义**，
然后指出该用哪个。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **售货机拆了连杆是永久的，`timer_shutdown_sync()` 之后
   重新 `timer_setup()` 就又能用了。** 它不是"销毁对象"，
   只是"把这个对象的回调清掉"。⇒ **真正的用法是"对象即将被释放"**，
   所以实际上不存在"之后再用"的场景。

2. **类比里按按钮"什么都不会发生"是显而易见的，
   代码里它是 `mod_timer()` 返回 0。**
   ⚠️ **而 0 在正常情况下表示"之前未 pending"** ——
   **两种含义共用一个返回值** ⇒ 调用者分不出"启动成功了"
   和"被丢弃了"（07 §7.2）。这是个真实的接口缺陷。

3. **类比里只有一个危险（手被夹），代码里 `timer_delete_sync()`
   还有第二个完全不同的危险：死锁。**
   持有任何会在中断上下文被拿到的锁时调它就会死锁——
   **即使那把锁和这个定时器毫无关系**
   （`kernel/time/timer.c:1584-1624` 给了 CPU0/CPU1 的对照图，01 §3.4）。
   ⇒ 这个危险和"重新启动"是两回事，`timer_shutdown_sync()` **不能**解决它。
