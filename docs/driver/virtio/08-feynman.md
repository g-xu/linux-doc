## §1 virtio 有"总线"，但总线的另一端是什么？

### 先举个例子

想象两栋写字楼之间要传文件。

**方案一（PCI 那样的硬件总线）**：拉一根专线，两端接读卡器。
文件通过电信号在导线上传输。**协议由电气规范定义**——
电压多少代表 1、时序怎么排，都写在硬件手册里。

**方案二（virtio 的做法）**：两栋楼之间有一个**共用的储物柜间**。
A 楼把文件放进 3 号柜，然后**打个电话**说"3 号柜有东西"。
B 楼去开 3 号柜取走，处理完放回，再打电话说"好了"。

**关键差别**：
- **文件本身没有"传输"过** ——它一直在储物柜里，只是换了归属
- **打电话（通知）才是唯一真的"通信"**
- **协议不是电气规范，而是两栋楼签的一份"柜子使用协议"**

**virtio 就是方案二**：
- **储物柜间 = 共享内存（vring）**
- **打电话 = 通知机制**（写一个寄存器 / 发一个中断）
- **柜子使用协议 = OASIS VIRTIO 规范**

⇒ **所以 virtio 的 `bus_type` 是真的**（有匹配、有 probe、25 个驱动绑在上面），
**但"总线"上跑的不是电信号，是"对共享内存的约定"。**

### 回到代码

| 事实 | 证据 |
|---|---|
| `virtio_bus` 是一条完整的驱动模型总线 | `drivers/virtio/virtio.c:343`，有 `.match` / `.probe` / `.remove` |
| 有 25 个真的 driver 绑在上面 | 01 §1.2（跨 22 个目录） |
| **但协议在树外** | ⚠️ **本树没有 `Documentation/virtio/`**（99 §1.4 三种变体全试过） |
| ABI 落在 uapi 里 | **27 个 `include/uapi/linux/virtio_*.h`** |
| "打电话"是唯一的陷入 | `notify` 函数指针（`drivers/virtio/virtio_ring.c:200`，注释带 `FIXME: commonalize hcalls!`） |

**和 timer 那两个"假总线"对比**（02 §1.0.A）：
timer 的 `clocksource_subsys` **一个 driver 都没有**，是纯 sysfs 容器；
**virtio 的总线是真的，只是"物理层"换成了共享内存。**

### 这个类比什么时候会误导你？

⚠️ **四处**：

1. **储物柜是中立的，vring 不是。** vring 由**驱动侧分配**
   （`vring_create_virtqueue()`，`drivers/virtio/virtio_ring.c:2546`），
   然后把地址告诉对端。⇒ **"柜子"是 A 楼建的，钥匙给了 B 楼。**

2. **两栋楼是平等的，virtio 的两端不平等。** 驱动侧必须
   **假设对端可能是恶意的**（03 §B3 的三层防御），
   ⇒ **所以驱动要存影子字段、要校验对端写回来的 id**。
   类比里"B 楼往柜子里塞炸弹"不在考虑范围内。

3. **"打电话"在两个方向上不对称。** 驱动→对端叫 `notify`
   （写寄存器），对端→驱动是**中断**。⇒ **两条路的代价差很多**，
   这就是为什么"少通知"是 virtio 性能优化的主线（§2、01 §3.2）。

4. **"另一端"因传输层而异。** 01 §1.1 那 9 个传输层里，
   对端分别是 hypervisor（PCI/MMIO/CCW）、**远端固件**（remoteproc）、
   **用户态进程**（UML）、**硬件**（vDPA）。
   ⇒ **"对端是 QEMU"是最常见的情况，不是唯一情况**（99 §5.5）。

## §2 为什么数据不经过 hypervisor，只有"通知"经过？

### 先举个例子

回到 §1 的储物柜。现在问：**为什么不让门卫（hypervisor）转交文件？**

**门卫转交的流程**：A 楼把文件交给门卫 → 门卫登记 → 门卫走到 B 楼 → 交给 B 楼。
**每一份文件都要门卫走一趟。**

**储物柜的流程**：A 楼自己放进柜子 → 打电话 → B 楼自己去取。
**门卫只接了一个电话，一步路都没走。**

**如果一天有一万份文件**：
- 门卫转交：**门卫走一万趟**
- 储物柜：**门卫接一万个电话** ——但如果 A 楼**攒够十份再打一个电话**，
  就只有一千个电话

⇒ **这就是 virtio 的全部性能逻辑**：
**数据面零陷入，控制面（通知）可批量。**

**"门卫走一趟"在虚拟化里叫 vmexit** ——CPU 从 guest 切到 hypervisor
再切回来，代价是几千个时钟周期。

### 回到代码

| 事实 | 证据 |
|---|---|
| 数据面完全在驱动侧代码里 | `virtio_ring.c`(2876 行) 直接读写共享内存，**不调任何 `config_ops`** |
| 通知是唯一的陷入 | `virtqueue_notify()`（`drivers/virtio/virtio_ring.c:2247`）→ `vq->notify()` → 传输层写寄存器 |
| **通知可以合并** | `virtqueue_kick_prepare()`（`:2230`）和 `virtqueue_notify()`（`:2247`）是**分开的两个函数** |
| 对端也能说"别通知我" | `VRING_USED_F_NO_NOTIFY`（`include/uapi/linux/virtio_ring.h:57`）+ EVENT_IDX 机制（03 §B4） |

**`kick` 被拆成两步这件事就是为了批量**（01 §3.2）：
提交 N 个缓冲区，只在最后判断一次要不要打电话。

**对端还能更精细地说"攒到第 N 项再叫我"** ——
这就是 `used_event_idx`（§4）和 `virtqueue_enable_cb_delayed()`（01 §3.4）。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **储物柜是无限大的，vring 不是。** 队列满了 `virtqueue_add_*()`
   返回 `-ENOSPC`（01 §9.2）。⇒ **这是正常背压，不是错误** ——
   类比里"柜子满了"会让人觉得是故障。

2. **"自己去取"在代码里要付内存屏障的代价。** A 楼放好文件和
   打电话之间必须有**写屏障**（03 §B1），否则 B 楼可能看到"电话来了但柜子是空的"。
   ⇒ **类比里"放好了再打电话"是自然顺序，代码里是必须显式写的约束。**

3. **不是所有传输层都能"零陷入"。** vDPA 的对端是硬件
   ⇒ **必须走 DMA API、必须用强屏障**（03 §B1.2、§B2）。
   ⇒ 类比里"储物柜"的位置和访问方式是固定的，代码里
   `use_dma_api` / `weak_barriers` 两个字段就是在描述"柜子到底在哪、怎么开"。

## §3 为什么要分成描述符表、available 环、used 环三段？

### 先举个例子

想象一个餐厅的后厨，服务员和厨师要协作。

**最笨的办法**：一块白板，服务员写"3 号桌要牛排"，厨师做完在旁边打勾。
**问题**：服务员和厨师**在同一块板上写字**，会撞在一起；
而且"已完成"的行还占着位置，板子很快写满。

**餐厅的真实做法是三样东西**：

1. **一叠点菜单（描述符表）** ——每张单子写清"什么菜、几份、送到哪桌"。
   **单子是复用的**：用完回到"空白单"那一叠。
2. **一根"待做"挂钩（available 环）** ——服务员把单子挂上去，**只有服务员挂**
3. **一根"做好了"挂钩（used 环）** ——厨师把做完的单子挂上去，**只有厨师挂**

**三样东西的好处**：
- **两根挂钩各自只有一个人写** ⇒ 不用抢
- **单子本身可以很长很复杂**（多道菜串起来），挂钩上只挂**单子编号**
- **单子循环使用** ⇒ 不需要不断分配新纸

**virtio 的 split ring 就是这三样**：
`desc[]`（点菜单）+ `avail`（待做钩）+ `used`（做好钩）。

### 回到代码

**布局在 02 §5.1 有字节级的图**，这里只点三个关键设计：

| 设计 | 证据 |
|---|---|
| **描述符是复用的** | `free_head`（`drivers/virtio/virtio_ring.c:176`）——**空闲描述符串成一条链** |
| **描述符能串起来** | `VRING_DESC_F_NEXT`(=1)（`include/uapi/linux/virtio_ring.h:41`）+ `next` 字段 |
| **环里放的是描述符编号，不是描述符** | `avail->ring[]` 是 `__virtio16`（`include/uapi/linux/virtio_ring.h:114-118`）——**只是索引** |
| **两个环各有一个写者** | 02 §5.1 的"谁写谁读"列：avail 段驱动写、used 段对端写 |
| **描述符 16 字节** | `addr`(8) + `len`(4) + `flags`(2) + `next`(2)，`include/uapi/linux/virtio_ring.h:107-112` |

**"单子可以很复杂"对应 `VRING_DESC_F_INDIRECT`**(=4，`:45`)：
一个描述符可以指向**另一张描述符表** ⇒ 一次提交能挂几百段
（`virtqueue_add_sgs()` 的 scatterlist 很长时会用它）。

### 这个类比什么时候会误导你？

⚠️ **四处**：

1. **餐厅的两根挂钩是物理隔开的，virtio 的两段挤在一块连续内存里。**
   而且 **每一段的末尾还插了一个归对方写的字段**（§4）
   ⇒ **"只有一个人写这一段"这句话有例外。**

2. **厨师不会伪造单子编号，对端会。** 对端写回一个越界的
   `used_elem.id` ⇒ 驱动必须校验（03 §B3 的第三层防御）。
   ⇒ **类比里"厨师是可信的"，代码里不是。**

3. **挂钩是有限长的，而且长度必须是 2 的幂。**
   `vring_size()`（`include/uapi/linux/virtio_ring.h:209`）按 `num` 算，
   **规范要求 `num` 是 2 的幂**（`include/uapi/linux/virtio_ring.h:171` 的注释
   `We assume num is a power of 2`）⇒ 这样取模可以用位与。

4. **packed ring 把三样合成了一样**（§9）——
   ⇒ **所以"必须分三段"其实不成立**，它只是 split ring 的做法。
   **真正的必要性是"两个方向的写者要分开"，不是"必须三段内存"。**

## §4 为什么两个"事件索引"插在对方那段的末尾？

### 先举个例子

回到 §3 的后厨。现在服务员和厨师都嫌"每做完一道菜就喊一声"太吵，
想说得更精细：

- **厨师想说**："别每挂一张单子就喊我，**攒到第 20 张再喊**"
- **服务员想说**："别每做完一道就喊我，**做完第 15 道再喊**"

**这两句话写在哪？**

直觉上：厨师的要求写在"厨师那块牌子"上。
**但实际做法反过来**：厨师的要求**写在"待做挂钩"的末尾**，
服务员的要求**写在"做好挂钩"的末尾**。

**为什么这么怪？** 因为这两个字段是**后来加的**。
最早的版本没有它们，两根挂钩的长度是固定的。
**要加新字段又不能改已有的偏移**（否则老版本认不出）
⇒ **只能塞在每一段的最后面，往后延一个字段。**

**而"谁的要求塞在哪一段"就随便挑了一个组合** ——
既然都是往后延，塞在自己那段还是对方那段没有技术差别。

### 回到代码

**头文件的注释逐字说了这件事**
（`include/uapi/linux/virtio_ring.h:194-195`）：

> We publish the used event index at the end of the available ring, and vice
> versa. They are at the end for backwards compatibility.

**两个访问宏**（`include/uapi/linux/virtio_ring.h:196-197`）：

```c
#define vring_used_event(vr)  ((vr)->avail->ring[(vr)->num])
#define vring_avail_event(vr) (*(__virtio16 *)&(vr)->used->ring[(vr)->num])
```

⇒ **`[(vr)->num]` 正好越过环的最后一项** ——落在那个"延出来的"字段上。

| 字段 | 物理位置 | 谁写 | 谁读 |
|---|---|---|---|
| `used_event_idx` | **available 环末尾** | **对端** | 驱动 |
| `avail_event_idx` | **used 环末尾** | **驱动** | 对端 |

**`vring_init()` 的偏移计算能看出这一点**
（`include/uapi/linux/virtio_ring.h:199-207`）：

```c
	vr->used = (void *)(((uintptr_t)&vr->avail->ring[num] + sizeof(__virtio16)
		+ align-1) & ~(align - 1));
```

⇒ **`+ sizeof(__virtio16)` 就是在跳过那个多出来的字段。**

**`vring_size()` 里那个 `(3 + num)`**（`:211`）也是同一件事：
`avail_flags` + `avail_idx` + **`used_event_idx`** = 3 个 `__virtio16`。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **"随便挑一个组合"不完全对。** 从**缓存**角度看这个选择其实有道理：
   **驱动读 `used_event_idx` 时正在写 avail 段** ⇒ 两者在同一个缓存行附近
   ⇒ 少一次缓存未命中。但头文件只说了 backwards compatibility，
   **性能这层是推测**（99 §5.3）。

2. **餐厅的"攒够 N 张"是个计数，virtio 的是个索引。**
   `used_event_idx` 是"**到达这个 idx 值时通知我**"，
   **不是"攒 N 个"** ——它是绝对位置，不是数量。
   ⇒ 所以叫 `event_idx` 而不是 `event_count`。

3. **这两个字段只在协商了 EVENT_IDX 时才有效。**
   `vring_virtqueue.event`（`drivers/virtio/virtio_ring.c:173`，
   注释 `Host publishes avail event idx`）为假时用的是老的 flag 机制
   （`VRING_USED_F_NO_NOTIFY` / `VRING_AVAIL_F_NO_INTERRUPT`，02 §5.4）。
   ⇒ **两套机制并存，不是新的替换了旧的**（03 §B4）。

## §5 为什么 feature 协商要"写进去再读回来"？

### 先举个例子

你和一个外国同事合作，语言能力不完全重叠。

**做法一（各报一份清单，取交集）**：
你说"我会中文、英文、日文"，他说"我会英文、法文" ⇒ **交集是英文** ⇒ 用英文。
**看起来够了。**

⚠️ **但有个漏洞**：交集是**你算出来的**。
如果他其实"英文只会读不会说"，交集"英文"就是错的，而**他没有机会反驳**。

**做法二（多一步确认）**：
你算出交集"英文"，**写在纸上给他看**，然后问："这样行吗？"
**他可以把纸划掉，表示"不行"。**

**virtio 用的是做法二。**

**为什么必须多这一步**：feature 位之间**有依赖关系**。
设备可能"单独支持 A，也单独支持 B，但 A 和 B 一起就不行"。
**取交集算不出这种约束** ——只有设备自己知道。

### 回到代码

**三步在 `virtio_features_ok()` 里**（`drivers/virtio/virtio.c:171-202`）：

```
  ① 驱动写：virtio_add_status(dev, VIRTIO_CONFIG_S_FEATURES_OK)   :194
  ② 驱动读回：status = dev->config->get_status(dev)                :195
  ③ 位还在吗？
       在  ⇒ return 0                        设备接受了
       没了 ⇒ dev_err("virtio: device refuses features: %x")  :197-198
              return -ENODEV
```

⇒ **"设备把位清掉"就是它说"不行"的唯一方式。**

**完整的协商时序在 03 §A4/§A5**，关键是三点：
① `finalize_features()` 在 `validate()` **之前**就调了一次（`:282`）；
② `validate()` 改了会**再调一次**（`:295`）；
③ 然后才做这个握手（`:301`）。

⚠️ **legacy 设备跳过这个握手**：
`drivers/virtio/virtio.c:191` 的
`if (!virtio_has_feature(dev, VIRTIO_F_VERSION_1)) return 0;`
⇒ **0.9.X 设备没有 `FEATURES_OK` 这个位** ⇒ **只能盲信**。

### 这个类比什么时候会误导你？

⚠️ **四处**：

1. **同事能解释"为什么不行"，设备不能。** 它只能把位清掉，
   **不能告诉你是哪个组合有问题**。
   ⇒ **`%x` 打出来的只是回读到的状态字节，不是"哪些位不接受"**（07 §2.2）。

2. **纸上写的不只是交集。** 传输层的 feature 位**不参与取交集**，
   由核心无条件保留（`drivers/virtio/virtio.c:277` 的注释
   `Transport features always preserved to pass to finalize_features`）
   ⇒ **写给设备的那份比"交集"多一些位。**

3. **"你算交集"这一步会 `BUG`。** 驱动的 `feature_table` 里
   写了 ≥64 的位号 ⇒ `BUG_ON(f >= 64)`
   （`drivers/virtio/virtio.c:256` / `:265`）——**直接崩**，不是报错。
   ⇒ 类比里"清单写错了"最多是沟通不畅，代码里是崩机器（07 §2.3.2）。

4. **确认之后就不能改了。** `probe()` 里改 `dev->features`
   **不会有第三次 `finalize_features()`** ⇒ **驱动和设备的认知分叉**，
   而且**不报错**，表现是数据格式错乱（01 §4.3）。
   ⇒ **类比里"说错了可以再说一遍"，代码里只有 `validate()` 这一次机会。**

## §6 为什么回收缓冲区时还给你的是你自己的指针？

### 先举个例子

你去干洗店送三件衣服，店员给你**三张号码牌**。

**做法一（凭衣服认）**：取衣服时店员说"这件蓝色衬衫是你的吧"。
⚠️ **问题**：万一店员搞错了，把别人的衣服给你，**你未必看得出来**。
更糟的是，如果店员是坏人，可以给你一件**里面藏了东西的**衣服。

**做法二（凭号码牌认）**：你给号码牌，店员按号取。
**店员只需要知道"3 号好了"，不需要（也不能）告诉你"3 号是什么"** ——
**"3 号是什么"这个信息在你手上。**

**virtio 用的是做法二**：
你提交缓冲区时给一个 `data` 指针（号码牌），
`virtqueue_get_buf()` **把那个指针原样还给你**。
**对端只能说"第 N 项完成了"，说不出"这是哪个对象"。**

### 回到代码

| 事实 | 证据 |
|---|---|
| 提交时给 token | `virtqueue_add_outbuf(vq, sg, num, data, gfp)` 的 `data`（`include/linux/virtio.h:41`） |
| 回收时原样还回 | `virtqueue_get_buf(vq, len)` 返回的就是那个 `data`（`include/linux/virtio.h:70`） |
| token 存在驱动侧 | `desc_state` / `desc_extra`（`drivers/virtio/virtio_ring.c:103-104`）——**不在共享内存里** |
| 对端只能给编号 | `struct vring_used_elem` 只有 `__virtio32 id` + `__virtio32 len`（`include/uapi/linux/virtio_ring.h:121-127`） |

**`used_elem.id` 用 `__virtio32` 而不是指针**，
头文件注释解释了宽度选择（`include/uapi/linux/virtio_ring.h:120`）：
`u32 is used here for ids for padding reasons`。
⇒ **但"用编号而不是指针"这个决定本身是安全设计**：
**指针从对端传过来是不可接受的。**

**同一个思路还体现在"影子字段"上**（03 §B3）：
`avail_flags_shadow` / `avail_idx_shadow`（`drivers/virtio/virtio_ring.c:94` / `:100`）
—— **"我上次写了什么"另存一份，不读共享内存**，
因为共享内存里那份对端能改。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. **干洗店的号码牌是店员给你的，virtio 的 token 是你给的。**
   ⇒ **所以 `data` 不能是 NULL** ——核心用它认这次提交（01 §3.1）。

2. **号码搞错了你会发现，编号越界要靠核心校验。**
   对端写回一个越界的 `id` ⇒ 核心把队列标 broken
   （`BAD_RING()` 宏，`drivers/virtio/virtio_ring.c:57-62`，03 §B5）。
   ⇒ **默认配置下只是标死，不崩；开 `DEBUG` 就 `BUG()`**（07 §4.2）。

3. **`len` 还是对端给的。** `virtqueue_get_buf(vq, &len)` 的 `len`
   是**对端写进 `used_elem.len` 的值** ⇒ **它是不可信的**。
   ⚠️ **驱动必须自己检查 `len` 没超过当初提交的缓冲区大小** ——
   **这一条 token 机制保护不了你**，是 virtio 驱动的一类真实漏洞来源。

## §7 为什么框架不帮你加锁？

### 先举个例子

想象一个共享办公室的打印机。

**方案一（打印机自带锁）**：打印机内部排队，谁按都行，它自己保证不串页。
**好处**：用户什么都不用管。
⚠️ **代价**：**每个人**都要付排队检查的开销，
**包括那个整栋楼唯一会用这台打印机的人**。

**方案二（谁用谁负责）**：打印机不排队，**贴一张纸："自己协调"**。
一个人独占的打印机 ⇒ **零开销**；
多人共用的 ⇒ 他们自己商量（挂个牌子/排个班）。

**virtio 选了方案二** ——因为**大多数 virtqueue 是"一个上下文独占"的**：
收方向只在中断/NAPI 里碰，发方向只在发送路径里碰。
**给这些场景加锁是纯浪费。**

### 回到代码

| 事实 | 证据 |
|---|---|
| `struct virtqueue` 没有锁 | `include/linux/virtio.h:29-39` 的 9 个字段里一个锁都没有 |
| `struct vring_virtqueue` 也没有 | `drivers/virtio/virtio_ring.c:154` 起，全部字段无锁 |
| **代码明确写了"你们负责"** | `drivers/virtio/virtio_ring.c:26` 的注释：`Caller is supposed to guarantee no reentry.` |
| 有一个 DEBUG 期的检测 | `START_USE(_vq)`（`drivers/virtio/virtio_ring.c:27-33`）——**重入就 `panic()`** |
| 设备级有两把锁 | `vdev->config_lock` / `vdev->vqs_list_lock`（`include/linux/virtio.h:119-120`） |

**那张"贴的纸"就是 `in_use` 字段**
（`drivers/virtio/virtio_ring.c:205-207`，注释 `They're supposed to lock for us.`）：
**它记的是 `__LINE__`**（`:32`）⇒ panic 消息直接告诉你上次是从哪一行进来的。

### 这个类比什么时候会误导你？

⚠️ **四处**：

1. **打印机串页你立刻看得见，virtqueue 竞态不会。**
   两个 CPU 同时 `virtqueue_add_outbuf()` ⇒ **描述符链被交叉写坏**，
   表现是**偶发数据错乱或对端读到垃圾** ——**几小时才出一次**。
   ⇒ **所以 `DEBUG` 模式的 `START_USE` 不是可选的检查**（07 §4.3）。

2. **"自己协调"在代码里有一个非直觉的边界**：
   **不同 vq 之间天然不需要锁**，但**同一个 vq 的收和发**（如果共用一个 vq）
   需要。⇒ 05 §1.3 列了五种情况。

3. **设备级还是有锁的。** 配置变更（`config_lock`）和队列链表
   （`vqs_list_lock`）是框架加的 ⇒ **"框架完全不加锁"是错的**，
   **准确说法是"数据面不加锁"**。

4. **打印机的开销是固定的，virtqueue 的锁开销在热路径上。**
   `virtqueue_add_*()` / `get_buf()` 是**每个数据包都要走**的路径
   ⇒ **一次原子操作的代价在这里会被放大几百万倍**，
   这才是这个设计的真正理由。

## §8 为什么同一个字段的字节序会"看情况"？

### 先举个例子

两个国家的邮局交换包裹，日期格式不一样：
A 国写 `日/月/年`，B 国写 `月/日/年`。

**2014 年之前**：没有统一标准，两边**各按自己国内的习惯写**，
靠"我知道你是 A 国的"来解读。
⚠️ **问题**：只要有一方猜错来源国，`03/04` 就会被读成不同的日期。

**2014 年之后**：签了协议，**所有国际包裹一律用 `年-月-日`**。

⚠️ **但老包裹还在流通** ⇒ **邮局必须同时认两种格式**，
而"用哪种"取决于**这个包裹是签协议前还是签协议后的**。

**virtio 一模一样**：
- **协商上 `VIRTIO_F_VERSION_1`（现代设备）⇒ 一律小端**
- ⚠️ **legacy（0.9.X）设备 ⇒ 宿主字节序**（guest-native）

### 回到代码

| 事实 | 证据 |
|---|---|
| 判断函数 | `virtio_is_little_endian(vdev)`（`include/linux/virtio_config.h:333`），实现是 `virtio_has_feature(vdev, VIRTIO_F_VERSION_1) \|\| ...`（`:335`） |
| 转换要带 `vdev` | `virtio16_to_cpu(vdev, val)`（`include/linux/virtio_config.h:340`）——**第一个参数就是设备** |
| 底层 6 个 inline | `include/linux/virtio_byteorder.h:16` · `:24` · `:32` · `:40` · `:48` · `:56` |
| legacy 的判断 | `virtio_legacy_is_little_endian()`（`include/linux/virtio_byteorder.h:7`） |
| **类型名就在提示这件事** | **`__virtio16` 不是"小端 16 位"，是"端序取决于协商结果的 16 位"** |

**两个"无条件小端"的例外**：`virtio_le_to_cpu()`（`:437`）和
`virtio_cread_le()`（`:454`）——**规范里有些字段明确规定就是小端**。
**`virtio_input.c` 全篇用的都是 `_le` 版本**（05 §1.1）。

**packed ring 干脆不给选择**：`struct vring_packed_desc` 的字段是
`__le64` / `__le32` / `__le16`（`include/uapi/linux/virtio_ring.h:239-248`），
**而 split ring 的 `struct vring_desc` 是 `__virtio64/32/16`**（`:107-112`）
⇒ **packed 是 1.1 才有的，1.1 已经强制小端**（02 §1.0.D）。

### 这个类比什么时候会误导你？

⚠️ **四处**：

1. **邮局能从邮戳看出包裹是哪年的，virtio 要靠协商结果。**
   ⇒ **同一个 `__virtio16` 字段，在协商完成前你不知道该怎么读**
   ⇒ 这就是为什么所有转换函数都要带 `vdev` 参数。

2. ⚠️ **arm64 上这个坑完全不会暴露。** arm64 通常是小端，
   而现代设备也是小端 ⇒ **`le16_to_cpu()` 和 `virtio16_to_cpu()` 结果相同**。
   ⇒ **这是一条"在你的平台上不会出错但仍必须遵守"的规则**
   （和 timer 的 `jiffies` 用 `time_after()` 是同一类，05 §4）。

3. **不是所有字段都"看情况"。** 规范明确规定小端的字段要用
   `_le` 版本 ⇒ **用错方向也是 bug**（用 `virtio_cread()` 读一个
   规定小端的字段，在 legacy + 大端下会错）。
   ⇒ **判据是查规范，不是查平台**（05 §7.2）。

4. **"两种格式"在内存布局上还有更深的差别。** legacy 的 MMIO
   用 `QUEUE_PFN`（页帧号）给队列地址，现代用三段各一对 LOW/HIGH
   （04 §2.2）⇒ **不只是字节序，连"地址怎么表达"都不一样。**

## §9 为什么 packed ring 能更快？

### 先举个例子

回到 §3 的后厨，但换个规模：现在是一个每分钟出 300 单的快餐店。

**三样东西的问题在高频下暴露出来**：服务员挂一张单子要碰
"单子那一叠"和"待做挂钩"两个地方；厨师取单子也要碰两个地方。
**每一次都是两次"走过去"**。

**快餐店的改法**：**只有一条传送带**。
单子直接放在传送带上，**用一个小旗子的颜色表示"待做"还是"做好了"**。
- 服务员放单子 + 把旗子翻成红色
- 厨师做完 + 把旗子翻成绿色

**一次操作只碰一个地方。**

**packed ring 就是这条传送带**：一段内存，
**用描述符 `flags` 里的两个 bit 表示归属**。

### 回到代码

| | split ring | packed ring |
|---|---|---|
| 段数 | **3** | **1** |
| 归属怎么表示 | 靠 `avail->idx` / `used->idx` 两个游标 | **靠 flags 的两个 bit** |
| bit 号 | — | `VRING_PACKED_DESC_F_AVAIL` = **7**（`include/uapi/linux/virtio_ring.h:51`）· `VRING_PACKED_DESC_F_USED` = **15**（`:52`） |
| 描述符 | `struct vring_desc`（`:107`） | `struct vring_packed_desc`（`:239`） |
| 代码里怎么选 | `vring_virtqueue.packed_ring`（`drivers/virtio/virtio_ring.c:158`） | 同上 |
| 两套数据 | **一个 `union`**（`drivers/virtio/virtio_ring.c:191-197`）⇒ **运行期二选一** | 同上 |
| 创建入口 | `vring_create_virtqueue_split()`（`:1101`） | `vring_create_virtqueue_packed()`（`:1996`） |
| 怎么决定 | `virtio_has_feature(vdev, VIRTIO_F_RING_PACKED)`（`drivers/virtio/virtio_ring.c:2559` 一带） | 同上 |

**"翻旗子"用的是 wrap counter**：环绕一圈之后 bit 的含义翻转
⇒ **不需要额外的"这一圈是第几圈"字段**。
**`last_used_idx` 的高位就塞了这个 wrap counter**
（`drivers/virtio/virtio_ring.c:180-186` 的注释说明了 split 和 packed 的不同含义）。

### 这个类比什么时候会误导你？

⚠️ **三处**：

1. ⚠️ **"更快"没有在本套里被测量过。** 本套没编译没运行
   （99 §5.1）⇒ **"缓存行为更好"是从"段数从 3 变 1"推出来的**，
   **不是实测结论**（99 §5.3 登记为推断）。

2. **两个 bit 号是 bit 号，不是掩码。** `VRING_PACKED_DESC_F_AVAIL` = **7**、
   `_USED` = **15**，而 §3 提到的 `VRING_DESC_F_NEXT` = **1** 是**掩码**。
   ⇒ **同一个头文件里两种约定并存**（02 §5.5）——
   **看代码时必须确认是 `& FLAG` 还是 `& (1 << FLAG)`。**

3. **packed ring 不是"新的替代了旧的"。** 它靠 feature 位协商，
   **对端不支持就还是 split** ⇒ **两套代码都必须维护**，
   这也是 `virtio_ring.c` 有 2876 行的原因之一。
   ⇒ 类比里"换了传送带就拆掉旧挂钩"，代码里两套并存。
