# 用大白话理解网卡驱动

基线 `f6e38ae624cf`（Linux 6.1.158），arm64-only。本篇挑八个「读了代码还是觉得别扭」的地方，每个都按同一个套路讲：先举个日常例子，再回到源码看它真正在做什么，最后说清这个例子在哪儿会把你带偏。

类比的作用是让你记住形状，不是让你据此推断行为。每一节的第四段——「这个类比什么时候会误导你」——才是这一节真正的内容。

## §1 中断来了，为什么第一件事是把中断关掉？

### §1.1 先举个例子

想象一个前台，桌上有个呼叫铃。客人来了按铃，前台抬头接待一位。客流小的时候这套很好用：不用一直盯着门口，铃响才干活。

但如果来了一辆大巴，五十个人排队按铃，前台的时间全花在「听到铃、抬头、看到人、接待、坐下、又听到铃」这个循环上——每次抬头坐下的动作本身就要花时间，五十次抬头坐下比连续接待五十个人慢得多。

聪明的做法是：第一次铃响之后，前台**把铃拔掉**，然后说「排队的都过来吧」，一口气处理完队伍，最后再把铃插回去。这样五十个人只付一次「抬头」的成本。

如果队伍太长一次处理不完，前台也不会一直不休息——处理够一定人数就先去干别的事，队伍留着下次继续，铃保持拔掉的状态。

### §1.2 回到代码

内核里「铃」就是网卡的中断，「拔掉铃」就是驱动在中断处理函数里关掉网卡中断，然后调 `__napi_schedule()`（`include/linux/netdevice.h:458`）把这个 NAPI 实例挂到当前 CPU 的处理队列上。真正收包的活留给软中断上下文里的 `poll` 回调。

「一次处理多少人」就是 budget。默认值是全局的 `netdev_budget = 300`（`net/core/dev.c:4424`），单个设备一轮的权重是 `dev_rx_weight = 64`（`net/core/dev.c:4430`）。`napi_poll` tracepoint（`include/trace/events/napi.h:14`）把这两个数摊开给你看：`work` 是这次实际收了几个包，`budget` 是给了多少预算。

「队伍太长先去干别的」在代码里是：`poll` 回调返回值等于 budget 时，核心不调 `napi_complete_done()`，中断保持关闭，这个 NAPI 实例留在队列里等下一轮软中断。`/proc/net/softnet_stat` 的第三列 `time_squeeze`（见 `07-debug.md` §10）数的就是这种「预算用光被迫让出」的次数。

「把铃插回去」是 `poll` 收的包少于 budget 时调 `napi_complete_done()`，它负责重新打开网卡中断。

### §1.3 这个类比什么时候会误导你

**第一，「拔掉铃」不是原子的一步。** 前台伸手拔铃的那一瞬间，铃可能正在响。网卡驱动里对应的竞态是：关中断和检查「环里还有没有包」这两步之间到达的包，可能既没触发中断（已关）、也没被这轮 poll 看到（当时还没到）。所以驱动关中断之后**必须再检查一次接收环**，这是 NAPI 驱动最经典的一类 bug 来源。前台的例子完全掩盖了这个问题，因为人不会「同时」按铃和排队。

**第二，budget 不是「一次最多收 300 个包」。** `netdev_budget` 是**一轮软中断里所有设备加起来**的总预算，单设备一轮拿到的是 `dev_rx_weight`（64）。而且还有第二道限制是时间：`netdev_budget_usecs`（`net/core/dev.c:4426`）。所以「调大 budget 就能提吞吐」经常不成立——先看 `time_squeeze` 到底涨不涨。

**第三，前台是一个人，NAPI 不是。** 多队列网卡有多个 NAPI 实例，分别绑在不同 CPU 上，互不相干地各自关中断、各自轮询。类比里的「前台」实际上是每个队列一个。这也是为什么「CPU0 软中断打满而其它 CPU 空闲」这种现象在网络里很常见——不是核心没做负载均衡，是中断亲和性和队列数没配好。

**第四，铃拔掉的时候队伍是看得见的，网卡不是。** 前台能看到还有多少人在排队，驱动只能看到接收环里有几个已完成的描述符。线上还在传输、DMA 还没写完的包，驱动看不到，也不能等。所以 `work < budget` 不等于「包收干净了」，只等于「环里现在没有已完成的了」。

## §2 为什么「网卡驱动」不是注册在某条网络总线上的驱动？

这是本子系统最容易被类比错的一组关系，值得先破掉再讲。

### §2.1 先举个例子

想象一栋写字楼。楼里有很多公司，每家公司要在物业登记（拿门禁卡、报消防），这是「注册到楼里」。同时每家公司又在工商局注册，拿营业执照——这是「注册到行业里」。

两件事完全不同：物业管的是「你占哪间房、水电走哪路」，工商局管的是「你是什么性质的企业、经营范围是什么」。一家公司搬到另一栋楼，营业执照不变；一家公司改了经营范围，物业不需要知道。

现在的关键问题是：**工商局那本册子上登记的，是「公司」，不是「入驻这栋楼的公司」。** 工商局不管你在哪栋楼，它只管你是不是一家合法企业。

网卡的情况就是这个形状。

### §2.2 回到代码

一块网卡有两个身份：

- 它是一个**硬件设备**，挂在真实的总线上——PCIe 网卡是 `pci_device`、SoC 内置的 MAC 是 `platform_device`。probe 就是这条线上发生的，`module_platform_driver()` / `module_pci_driver()` 注册的驱动是**这一层**的驱动。
- 它是一个**网络接口**，登记在 `net_class` 里。`net_device` 里嵌了一个 `struct device dev;`（`include/linux/netdevice.h:2317`），`register_netdev()` 把它挂到 `static struct class net_class`（`net/core/net-sysfs.c:1926`）下——这是 `/sys/class/net/eth0` 那条路径的来源。

⚠️ **关键点：网络设备是注册到一个 `class` 上，不是注册到一个 `bus_type` 上。** 全树没有 `net_bus_type` 这个东西。这意味着：

- 没有「网络总线」的 match 函数，所以 `net_device` **不会被绑定任何 driver**。它不是「等着驱动来认领的设备」，它是「驱动创建出来的一个对外接口」。
- 驱动和 `net_device` 的关系不是「driver 绑到 device 上」，而是「driver 分配一个 `net_device`、往里填一堆函数指针（`net_device_ops` 的 86 个槽位、`ethtool_ops` 的 68 个槽位）、然后注册它」。
- 拆除的方向也因此反过来：不是总线解绑驱动，是驱动主动 `unregister_netdev()`。

作为对照，MDIO 那一侧**确实有**总线：`struct bus_type mdio_bus_type`（`drivers/net/phy/mdio_bus.c:1045`，`.name = "mdio_bus"` 在 `:1046`），PHY 驱动（`struct phy_driver`，`include/linux/phy.h:784`）是真正意义上被 match 上去的驱动。所以同一块网卡上，**PHY 侧是「设备等驱动」的经典模型，MAC 侧不是**。

### §2.3 这个类比什么时候会误导你

**第一，「两个身份」不代表「两个对象」。** 写字楼的例子里公司只有一个实体，但网卡这边真的是两个 C 结构体：`platform_device`（或 `pci_dev`）一个，`net_device` 一个。它们靠 `net_device` 里那个 `struct device dev` 的 `dev.parent` 指针缝在一起。很多「设备找不到」的问题就出在这个指针上——`07-debug.md` §8.1 里提到 `netdev_drivername()` 在 `dev.parent` 为 NULL 时返回空串，就是这条缝没接上的直接后果。

**第二，工商局的册子是全局唯一的，`net_class` 不是。** 网络接口是 per-namespace 的：不同 network namespace 里可以各有一个 `eth0`。写字楼的类比里没有这一层，它会让你以为接口名是全局唯一的。

**第三，「营业执照不变」这个部分不成立。** 网卡换总线不是「搬楼」，是重新 probe——`net_device` 会被销毁重建，MAC 地址可能变、接口名可能变。类比里那种「身份稳定」的暗示在这里是错的。

**第四，别把这套结论推广到别的子系统。** i2c、spi、usb 都有自己的 `bus_type`，它们的设备**确实**在等驱动来认领。网络这边的形状是特例，恰恰因为「网络接口」不是一个被发现的硬件，而是一个被创建的抽象。

## §3 发送队列已经有长度限制了，BQL 还在限制什么？

### §3.1 先举个例子

一家餐厅的传菜口。厨房做好的菜放在传菜口，服务员来取走送到桌上。

老板想知道「传菜口该放多少盘菜」。第一个想法是数盘子：最多放 20 盘。听起来合理，直到某天来了一桌点了 20 份汤——汤上得慢、放久了凉，客人投诉。另一天来了 20 份凉菜，秒送秒走，传菜口空着，厨房干等。

问题在于**盘子数不代表工作量**。20 盘汤和 20 盘凉菜对服务员是完全不同的负载。

正确的度量是「传菜口上的菜，服务员要花多久才能送完」。老板改成按这个来限：传菜口上未送出的菜，总送达时间不超过 30 秒。汤多的时候自然只放几盘，凉菜多的时候可以堆很多。

还有一层：这个上限不该是老板拍的。老板应该观察——如果传菜口一直空着（服务员来了没菜拿），说明放少了，调高；如果传菜口一直满着，说明放多了，调低。

### §3.2 回到代码

`tx_queue_len` 就是「数盘子」：它限制 qdisc 里能排多少个包，单位是包。BQL（Byte Queue Limits）限制的是**已经交给网卡硬件、还没发完的字节数**。

实现只有 138 行（`lib/dynamic_queue_limits.c`），头文件 108 行（`include/linux/dynamic_queue_limits.h`）。驱动侧的接口是一对：发送时调 `netdev_tx_sent_queue(txq, bytes)`，完成回收时调 `netdev_tx_completed_queue(txq, pkts, bytes)`。BQL 拿这两个数的差算出「在飞的字节数」，也就是 `07-debug.md` §4.3 里那个 `inflight`——它不是一个存起来的字段，而是 `bql_show_inflight()`（`net/core/net-sysfs.c:1370`）现算的 `dql->num_queued - dql->num_completed`。

「老板观察着调」这一层就是 dynamic 那个词的含义：`limit` 会自己涨落，用户能设的是 `limit_min` 和 `limit_max` 两个边界（sysfs 位置见 `07-debug.md` §4.3）。

为什么要限：不限的话，1000 个包的 qdisc 队列会被一口气全塞进硬件环，然后一个高优先级的小包排在这 1000 个包后面。限制之后大部分包留在 qdisc 里，qdisc 的调度器（优先级、公平队列）才有机会起作用。**BQL 的目的不是提吞吐，是让 qdisc 的调度真的有效**——吞吐几乎不变，延迟大幅下降。

### §3.3 这个类比什么时候会误导你

**第一，餐厅老板能看见「菜凉了」，BQL 看不见时间。** BQL 完全不测时间，它只数字节。「字节数」是延迟的代理指标，成立的前提是链路速率稳定。链路速率一变（自适应速率的无线、被限速的虚拟网卡），同样的字节数对应的时间完全不同，BQL 不知道这件事。

**第二，服务员取菜是老板能看到的，BQL 依赖驱动自己汇报。** 传菜口的类比里「送出去了」是客观事实；代码里「完成了多少字节」是驱动调 `netdev_tx_completed_queue()` 告诉 BQL 的。⚠️ **驱动漏调这个函数，BQL 会认为字节永远在飞，`limit` 被压到底，吞吐掉到地板，而且不打任何日志**（`07-debug.md` §4.3）。类比里没有「服务员送完了但不告诉老板」这种情况，代码里这是最常见的 BQL bug。

**第三，「30 秒送达」是一个目标值，BQL 没有目标值。** BQL 的算法不追求任何具体的延迟数字，它只是在「有没有出现过硬件饿死」和「排队有多深」之间做反馈调节。所以不要指望通过设 BQL 参数达到某个确定的延迟——`limit_min`/`limit_max` 是护栏，不是设定点。

**第四，一个传菜口对应一条发送队列，不是一块网卡。** BQL 的状态是 per-txq 的，多队列网卡上每条队列各有一套。看 `inflight` 的时候要看对队列号，看错队列会得出「一切正常」的结论。

## §4 GRO 把包合起来，合的到底是什么？

### §4.1 先举个例子

一个部门收到二十封内部邮件，内容是同一份报告的第 1 页到第 20 页，分二十封发过来的。收件人有两种处理方式：

一是把二十封邮件逐封转给领导，领导拆二十次信封、读二十次抬头、二十次判断「这是谁发的、归哪个项目」。

二是收件人先看一眼：这二十封的发件人相同、项目号相同、页码连续——那就拆开信封把二十页订成一本，只往上递一次。领导只判断一次归属，然后读二十页。

关键在于收件人**没有改动任何一页的内容**，也没有做「本来该是一份文件、被拆开了、我给还原」这种事。他只是发现这二十封在处理上可以合并，于是合并了。二十页还是二十页。

而且合并有窗口：不能等一整天凑齐所有可能的邮件。攒够一定数量，或者时间到了，就往上递。

### §4.2 回到代码

GRO 在 `net/core/gro.c`（817 行）。它做的事是：从网卡收上来的多个 skb，如果头部字段满足「可以合并」的条件（同一个流、序号连续、标志位允许），就把它们的数据挂到第一个 skb 的分片数组上，只把这一个 skb 递给协议栈。

两个「窗口」参数都在这个文件的开头：`MAX_GRO_SKBS 8`（`net/core/gro.c:7`）限制同时在攒的流数量，`gro_normal_batch = 8`（`net/core/gro.c:15`）控制攒够多少个就往上递。攒的数据放在 skb 的分片数组里，上限是 `MAX_SKB_FRAGS`（`include/linux/skbuff.h:358` 和 `:360` 两个分支）。

驱动侧的入口是 `napi_gro_receive()`（调用点周边可见 `net/core/gro.c:654` 的 tracepoint），或者页片形态的 `napi_gro_frags()`（`net/core/gro.c:779`）。全树 93 个文件用了前者、17 个用了后者（口径见 `04-extensions.md` §12.2）。

「谁能合、怎么合」由各协议自己注册的回调决定，注册函数是 `dev_add_offload()`，全树只有 7 个文件调它——TCP、UDP、IP 各自登记自己的 `gro_receive`/`gro_complete`。这也是为什么 GRO 只对少数协议有效：没登记的协议根本不参与合并。

### §4.3 这个类比什么时候会误导你

**第一，GRO 不是 IP 分片重组，两者是完全不同的机制。** 邮件的例子很容易让人以为「本来是一份大文件，被切成二十封，GRO 把它还原了」。不是。GRO 合并的是二十个**各自完整合法**的报文——每个都有自己的完整 IP 头和 TCP 头，各自独立可路由。IP 分片重组（`ip_defrag`）处理的才是「一个报文被切开」，它在协议栈里另有其人。把两者混起来会导致一类误判：以为关掉 GRO 能解决分片相关的问题。

**第二，「不改动内容」只在数据部分成立。** 合并后的那个 skb 的头部被改了：长度字段变成合计长度，`gso_size` 被填上原始分段大小。所以 GRO 之后的包如果要再发出去（转发场景），会走 GSO 重新切分——**收进来是 20 个包，转发出去也是 20 个包，但中间那一段它是 1 个**。抓包工具在不同位置看到的包数不一样，不是抓漏了。

**第三，收件人是免费的，GRO 不是。** 合并本身要读每个包的头部、比较字段、操作分片数组，这是实打实的 CPU 开销。对小流量、或者流特别多（每个流只有一两个包）的场景，GRO 是净损失——攒不到东西，白比较一场。这就是为什么 `ethtool -K <if> gro off` 在某些负载下反而更快。

**第四，「时间到了就递」这层在 GRO 里不是靠定时器。** 邮件的类比暗示有个闹钟。GRO 的刷出点实际上是 NAPI 一轮轮询结束（`napi_complete_done` 之前），以及 `gro_normal_batch` 攒满。真正跟时间挂钩的是另一个东西——`gro_flush_timeout`（`07-debug.md` §4.1），而它是 NAPI 层的延迟中断参数，不是 GRO 的攒包计时器。名字里带 gro 让这两件事经常被搞混。

## §5 收包为什么要自己管一个页池，不直接用 alloc_page？

### §5.1 先举个例子

一家咖啡店用杯子。最省事的做法是每次现拿一个新纸杯，用完扔掉——简单，但成本高。

改成用瓷杯：客人用完还回来，洗一遍再用。省了纸杯钱，但多了洗杯子的活。

现在关键的一层来了。这家店的咖啡机很特殊，它要求「杯子必须先在机器上登记过位置」才能接咖啡——登记这个动作很慢。纸杯每次都要重新登记，瓷杯只要**第一次**登记，之后洗完还是同一个位置，不用再登记。

于是真正的收益不在杯子钱，在**省掉了重复登记**。而这也带来一个约束：还回来的杯子必须还给这台机器的杯架，不能随手放到别的柜子里——否则登记信息就丢了，下次还得重新登记。

### §5.2 回到代码

「登记」就是 DMA 映射。网卡收包用的页必须先 `dma_map_page()` 建立地址映射，这个动作在带 IOMMU 的系统上开销可观（arm64 SoC 上普遍有 SMMU）。

`page_pool`（`net/core/page_pool.c`，938 行）做的就是「瓷杯 + 保留登记」：页从池里拿出来时已经是映射好的，还回池里时映射不解除。参数结构 `struct page_pool_params`（`include/net/page_pool.h:74-85`）里的 `PP_FLAG_DMA_MAP`（标志定义在 `:37-49`）就是「让池子负责登记」这个开关。

拿页：`page_pool_alloc_pages()`（`include/net/page_pool.h:212`）或者带默认 GFP 的 `page_pool_dev_alloc_pages()`（`:214`）。还页：`page_pool_put_full_page()`（`:331`）。

「还给这台机器的杯架」这个约束在代码里是 `skb_mark_for_recycle()`（`include/linux/skbuff.h:5127`）：驱动把页挂到 skb 上之后要打这个标记，协议栈释放 skb 时才知道这些页要还给 page_pool 而不是还给伙伴系统。⚠️ **漏打这个标记不会崩、不会报错——页被当普通页释放掉，池子慢慢空掉，性能悄悄退化回「每次现拿纸杯」的水平。**

配套的还有 `page_pool_release_page()`（`:252`），它做的是相反的事：把页从池子里彻底解绑（解除映射），用在「这页要交给别人长期持有」的场合。

全树用 `page_pool_create` 的有 12 到 13 个驱动文件（两种口径见 `04-extensions.md` §12.2）——**这是个新机制，绝大多数驱动还在用老办法**。arm64 的五个代表驱动里有四个用了。

### §5.3 这个类比什么时候会误导你

**第一，瓷杯是「一个杯子一杯咖啡」，页不是。** 一个 4K 页在多数网卡上可以切成两个 2K 的收包缓冲区（页分割），也可以整页给一个大包。所以「还回来」的粒度不是页而是页里的一份引用——页上的引用计数归零了才真的回池。这让「什么时候能复用」比洗杯子复杂得多，也是 page_pool 里最容易出 bug 的部分。

**第二，洗杯子是同步的，回池不是。** 客人还杯子、店员洗、放回杯架，这是一条线。代码里页的归还可能发生在完全不同的 CPU 上（skb 在另一个核上被释放），所以 page_pool 内部有 per-CPU 的快速路径和一个跨 CPU 的慢速环。「为什么我的 page_pool 命中率不高」的答案经常是包在另一个核上释放了。

**第三，「省了杯子钱」是次要收益这句话反过来也要小心。** 在没有 IOMMU、DMA 映射几乎免费的平台上，page_pool 的收益就只剩下「少走一遍伙伴系统」，可能小到测不出来。所以「用了 page_pool 就一定更快」不成立，它是一个和平台强相关的优化。

**第四，咖啡店可以决定不用瓷杯，驱动不能随便切换。** page_pool 和驱动的收包路径是绑死的：用了它，skb 的构造要走 `napi_build_skb()`（`include/linux/skbuff.h:1259`）这条路，释放要靠标记，XDP 的页归属也跟着变。它不是一个能后加的开关，而是一次收包路径重写。

## §6 MAC 驱动和 PHY 驱动，谁调用谁？

### §6.1 先举个例子

一栋楼里有内部电话系统（MAC）和外线接口盒（PHY）。内部电话负责楼里的通话，接口盒负责把信号接到外面的电话线上。

直觉上会觉得：内部电话是主，接口盒是从——内部电话要打外线，就调用接口盒。

实际的运维关系不是这样。接口盒会自己检测外线状态：线插没插、对面协商出多少速率、是全双工还是半双工。这些信息**接口盒先知道**，然后它得告诉内部电话「现在外线是 1000M 全双工，你按这个配」。内部电话要做的是提供一个「我可以被配置」的接口，等着被通知。

所以方向是：**接口盒检测到变化 → 通知内部电话 → 内部电话按通知调整自己**。

更麻烦的是，有些楼的外线不是一个固定的接口盒，而是一个插槽——可以插光模块、插铜口模块、也可能什么都不插。这时候需要一个中间人来管「插槽里现在是什么、状态变了通知谁」。

### §6.2 回到代码

老的模型（phylib）：`struct phy_driver`（`include/linux/phy.h:784`）是真正被 MDIO 总线 match 上去的驱动，MAC 驱动调 `phy_connect()` 把 PHY 接过来，然后在自己的 `adjust_link` 回调里接收状态变化通知。全树 28 个文件用 `phy_connect`。

新的模型（phylink）：中间加了一层，因为要处理 SFP 插槽、背板、以及「MAC 支持哪些接口模式」这类协商。MAC 驱动填的是 `struct phylink_config`（`include/linux/phylink.h:133-144`）和 `struct phylink_mac_ops`（`:160-179`），然后调 `phylink_create()`（`drivers/net/phy/phylink.c:1450`）。⚠️ **注意 `phylink_mac_ops` 是「MAC 提供给 phylink 调用的回调」，不是「MAC 调用 phylink 的接口」——方向和名字给人的第一印象相反。**

`phylink_config` 里的 `mac_capabilities` 用 `MAC_*` 一族标志（`include/linux/phylink.h:53-72`）声明「这个 MAC 支持哪些速率和双工组合」，phylink 拿它和 PHY 那边的能力求交集。

链路启停是 `phylink_start()`（`drivers/net/phy/phylink.c:1889`）/ `phylink_stop()`（`:1961`），在 `ndo_open`/`ndo_stop` 里调。整个 phylink 有 3530 行，PHY 子系统合计 85 个文件、59610 行（`drivers/net/phy/`）。

⚠️ **arm64 上这件事已经一边倒了**：五个代表驱动（am65-cpsw / mtk_eth / mvneta / mvpp2 / stmmac）里，用 `phylink_create` 的是 5 个，用 `phy_connect` 的是 **0** 个（`04-extensions.md` §0.2）。全树 `phylink_create` 15 个文件、`phy_connect` 28 个——**看总数会以为 phylib 还是主流，但在 arm64 SoC 这一侧它已经不是了**。

### §6.3 这个类比什么时候会误导你

**第一，「接口盒通知内部电话」这个方向对了，但通知不是同步调用。** 类比里像是接口盒打个电话过去。代码里 PHY 的状态检测跑在一个独立的工作队列上（或者由 PHY 中断触发），回调发生在那个上下文里，MAC 驱动的 `mac_link_up`/`mac_link_down` 回调**不在 `ndo_open` 的调用栈上**。所以在这些回调里不能假设任何 `ndo_*` 层面的锁状态。

**第二，「插槽」的类比让人以为 SFP 是可选的复杂度，其实它改变了整个状态机。** 有 SFP 的情况下，「PHY」可能压根不存在（直连光模块），phylink 要处理「没有 PHY 但链路是好的」这种状态。`06-devicetree.md` §4.4 里那三条「返回 0 但没有连上 PHY」的路径就是这个状态机的产物——它们不是错误路径。

**第三，phylib 和 phylink 不是「老的和新的同一个东西」。** phylink **建立在** phylib 之上：phylink 内部还是通过 phylib 去操作 PHY 寄存器（`phy_read()` `include/linux/phy.h:1041` 那一族）。所以说「迁移到 phylink 就不用 phylib 了」是错的，两者是叠的不是替的。这个类比说「新装了一个中间人」比说「换了一套系统」准确。

**第四，MAC 也不总是被动的。** 类比里内部电话纯粹等通知。实际上 MAC 驱动在 `mac_config` 回调里要主动配置自己的串行接口模式（RGMII/SGMII/2500Base-X 等），而这个选择可能受它自己的时钟、引脚约束限制——phylink 提出一个组合，MAC 有权拒绝。这是双向协商，不是单向通知。

## §7 驱动说「忙」和包被丢掉，为什么不是一回事？

### §7.1 先举个例子

你去柜台交一份材料，可能得到三种回应：

一是「收了」——材料到了对方手上，你手里没东西了。
二是「现在忙，材料你先拿回去，过会儿再来」——材料还在**你**手上，你要负责保管，一会儿还得再来一趟。
三是「收了，但我告诉你我这边快堆满了，你下次少送点」——材料到了对方手上，同时你得到一个提示。

第二种和另外两种有个根本区别：**材料归谁保管变了。** 第一、三种情况下你走的时候是空手，第二种情况下你手里还捏着东西。如果你搞错了，以为「忙」也算交出去了，那份材料就没人管了——要么丢，要么被两个人同时处理。

### §7.2 回到代码

发送路径上有三套返回值编码，`07-debug.md` §11.1 有完整对照。这里只讲「谁负责释放 skb」这一条线：

| 返回值 | 定义 | skb 归谁 |
|---|---|---|
| `NETDEV_TX_OK` | `include/linux/netdevice.h:122` | 驱动。核心不再碰它 |
| `NETDEV_TX_BUSY` | `include/linux/netdevice.h:123` | **调用方**。驱动一个字节都不许动它 |
| `NET_XMIT_DROP` | `include/linux/netdevice.h:107` | 已经被释放掉了 |
| `NET_XMIT_CN` | `include/linux/netdevice.h:108` | 已发出，附带拥塞提示 |

`enum netdev_tx` 在 `include/linux/netdevice.h:120-124`，注释直接写了 `NETDEV_TX_OK` 是「driver took care of packet」、`NETDEV_TX_BUSY` 是「driver tx path was busy」。

判定靠数值区间，约定写在 `include/linux/netdevice.h:127-129` 的注释里：`NETDEV_TX_MASK`（0xf0，`:118`）`> NET_XMIT_MASK`（0x0f，`:109`）`>= 0`，且返回值小于 `NET_XMIT_MASK` 就意味着 skb 已被消耗。`NETDEV_TX_BUSY` = 0x10 恰好在 `NET_XMIT_MASK` 之上，所以它落在「skb 没被消耗」那一侧。

第三种情况（「收了但快满了」）在往上传的路上会被改写掉。两个宏在 `include/linux/netdevice.h:114-115`：

```c
114 #define net_xmit_eval(e)	((e) == NET_XMIT_CN ? 0 : (e))
115 #define net_xmit_errno(e)	((e) != NET_XMIT_CN ? -ENOBUFS : 0)
```

`:111-113` 的注释解释了为什么 CN 被当成成功：它不保证这个包丢了，只是提示发慢点。

### §7.3 这个类比什么时候会误导你

**第一，「材料还在你手上」在代码里是一个没人检查的约定。** 柜台的例子里你不可能没注意到手里还捏着东西。代码里 `NETDEV_TX_BUSY` 之后驱动如果顺手把 skb 释放了，编译能过、大多数时候也不崩——直到调用方重发那个已经被释放的 skb。这类 bug 的表现是随机的内存损坏，离发送路径很远才暴露。

**第二，三种回应在柜台是并列的选项，在代码里不是。** `NETDEV_TX_BUSY` 是驱动**应该尽量避免**返回的：现代驱动的做法是自己在环快满时调 `netif_stop_queue()` 停掉队列，让核心根本不来送。返回 BUSY 意味着「我没能提前停队列，让你白跑一趟」。所以 `07-debug.md` §5.1 里那个 `net_dev_xmit` tracepoint 的 `rc` 字段持续非零，本身就是驱动侧的问题信号，不是正常的反压手段。

**第三，「你走的时候空手」不代表包发出去了。** `NETDEV_TX_OK` 只是说 skb 的所有权转移了，包还在硬件环里排队。真正发完是在完成中断里。类比里「交出去」和「办完了」是一件事，代码里差了很远——这就是为什么发送侧的统计要在完成路径上加，而不是在 `ndo_start_xmit` 里加。

**第四，用户态看到的成功和这三种都不是一回事。** `dev_queue_xmit()` 的 kerneldoc（`include/linux/netdevice.h:99-102`）说明：物理设备的发送是异步的，返回值不往上传；虚拟设备是同步的，驱动返回码被 `dev_queue_xmit()` 消费，其余才往上传。所以**同一个错误在物理网卡和虚拟网卡上，用户态的可见性不一样**。柜台的例子里回应总是传到你耳朵里，这里不是。

## §8 统计计数器为什么要专门包一层 `u64_stats_sync`？

### §8.1 先举个例子

一个仓库的进货台账，用两块小黑板记：一块写「万位以上」，一块写「万位以下」。当前是 3 万 9999 件，两块板分别是 `3` 和 `9999`。

来了一件货，记账员要改两块板：先把 `9999` 擦掉写 `0000`，再把 `3` 擦掉写 `4`。

现在有个查账的人在这两步之间看了一眼：他看到「万位 = 3、个位 = 0000」，算出 3 万件——**账上凭空少了 9999 件**。这个数字从来没有真实存在过。

解决办法不是给黑板上锁（记账员每次记账都要等查账的人走开，太慢）。办法是加一个「修改中」的序号牌：记账员开始改之前把序号 +1，改完再 +1。查账的人记下开始时的序号、看完再看一次序号——**如果两次序号不一样，或者是奇数，就说明中间有人在改，重新看一遍**。

记账员完全不用等任何人。查账的人可能要重看几次，但从不会读到一个不存在的数字。

### §8.2 回到代码

这就是 `u64_stats_sync`（`include/linux/u64_stats_sync.h`，217 行）。网卡的收发包数、字节数都是 64 位计数器，在 32 位机器上更新它不是一条指令——就是那两块小黑板。

写侧：`u64_stats_update_begin()` / `u64_stats_update_end()`。读侧：`u64_stats_fetch_begin()` / `u64_stats_fetch_retry()`，后者返回真就重读一遍。

⚠️ **在 64 位平台（包括 arm64）上，这一整套是空操作。** 64 位计数器的读写本身就是原子的，不需要序号牌。所以在 arm64 上加不加这层，生成的代码几乎一样——它存在纯粹是为了 32 位平台的正确性。

### §8.3 本树在这里打了补丁

本树相对上游有一处改动落在这个头文件上：`include/linux/u64_stats_sync.h` **删掉了 12 行**，被删掉的是 `u64_stats_fetch_begin_irq()` 和 `u64_stats_fetch_retry_irq()` 这对带 `_irq` 后缀的变体。⚠️ **在本树上写这两个函数名会编译失败。**

配套的改动是 `drivers/net/ethernet/` 下 47 个文件、204 处插入 / 204 处删除——**一对一的机械改名**，把 `_irq` 变体全部换成不带后缀的版本。这属于 PREEMPT_RT 的一次回合并（同一批补丁还改了 `net/core/dev.c` 里 `trigger_rx_softirq()` 的实现，以及给 `struct softnet_data` 加了 `defer_csd`/`defer_work` 两个字段，`include/linux/netdevice.h:3202-3206`）。

写驱动或者移植上游驱动到本树时，这是唯一会撞上的编译错误来源。详见 `01-api.md` §0.6 和 `05-usage.md` §1.7。

### §8.4 这个类比什么时候会误导你

**第一，序号牌保护的是「读到自洽的一组数」，不是「读到最新的数」。** 查账的人重读成功之后拿到的仍然是一个可能已经过时的数字——记账员在他算完之后又记了十笔。类比里容易以为「重读成功 = 拿到当前真值」。代码里 `u64_stats` 只保证你读到的是**某个时刻的一致快照**，不保证是现在。所以 `ip -s link` 连着跑两次，数字对不上是正常的。

**第二，只有一个记账员这件事是硬约束，类比没体现。** `u64_stats_sync` 只允许单写者。多个 CPU 同时更新同一个计数器需要另外的锁或者 per-CPU 计数器。网卡驱动的做法是每条队列一套计数器，读的时候把所有队列加起来——**加起来这个动作本身又不是原子的**，所以汇总值可能不对应任何一个真实瞬间。

**第三，「64 位上是空操作」不等于「64 位上可以不写」。** 驱动代码要跨平台，省掉这层在 arm64 上测不出问题，在 32 位 ARM 上就是随机的统计跳变。而且是**只有统计数字不对、其它一切正常**的那种问题——最难被怀疑到。

**第四，序号是奇偶判断这个细节在实现上不通用。** 类比里说「奇数说明有人在改」，这是 seqcount 的经典形态；`u64_stats_sync` 在不同配置下的实现不完全是这个（64 位上根本没有 seq 变量）。别把类比里的实现细节当成可以依赖的行为——判据只有一条：`u64_stats_fetch_retry()` 返回真就重读。
