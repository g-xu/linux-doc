# RTC 子系统 · 费曼版

> 用大白话讲 RTC。不需要代码基础，只需要知道"电脑关机后时间不会停"。

## §1 RTC 是什么

RTC = Real Time Clock = 实时时钟。就是你主板上那颗小小的芯片，靠一颗纽扣电池活着，电脑关机了它还在走。

它做的事很简单：**记住现在几点几分几秒、几月几号星期几**。

Linux 内核需要一个统一的框架来管理各种各样的 RTC 芯片——I2C 接的、SPI 接的、直接焊在 CPU 里的、藏在电源管理芯片里的——这就是 RTC 子系统。

## §2 框架做了什么

把框架想象成一个**翻译官 + 补全器 + 模拟器**：

**翻译官**：不管芯片是 I2C 的还是 SPI 的，用户态都用同一套 ioctl 操作。驱动告诉框架"我的芯片能读时间、能设闹钟"，框架告诉用户态"`/dev/rtc0` 可以读时间、可以设闹钟"。

**补全器**：有些芯片的闹钟只存了"几点几分"，没存"几月几号"。框架帮你用当前时间补全——"现在是 8 月 27 日，闹钟设的 7:30 今天已经过了，那就是明天 8 月 28 日 7:30"。

**模拟器**：硬件不支持的功能（比如每秒中断），框架用软件定时器帮你模拟。你以为硬件在每秒报时，其实是框架在后台帮你数秒。

## §3 谁在用 RTC

| 用户 | 怎么用 |
|---|---|
| **系统启动** | 读 RTC 的时间来设系统时钟（`hctosys`） |
| **NTP 同步** | 定期把系统时间写回 RTC（`systohc`），约每 11 分钟一次 |
| **休眠唤醒** | 设一个闹钟，到点了把系统从休眠中叫醒（`alarmtimer`） |
| **用户程序** | 通过 `/dev/rtc0` 读时间、设闹钟、监听中断 |

## §4 一个 RTC 的一生

```
工厂出厂 → 焊到板子上 → 内核启动
                            ↓
                    驱动 probe()
                    "我是 pcf8563，接在 I2C 总线 0x51 地址"
                            ↓
                    devm_rtc_allocate_device()
                    框架分配一个 rtc_device
                            ↓
                    驱动填表：
                    "我能读时间、设时间、设闹钟"
                    "我的年份范围是 2000 到 2099"
                    "我的闹钟精度只到分钟"
                            ↓
                    devm_rtc_register_device()
                    框架注册 /dev/rtc0、sysfs、procfs
                    框架跑 hctosys：读 RTC 时间 → 设系统时钟
                            ↓
                    alarmtimer 看到了这个新 RTC
                    "它能设闹钟吗？能当唤醒源吗？"
                    "都能！那以后休眠唤醒就靠你了"
                            ↓
                    系统正常运行
                    用户 cat /sys/class/rtc/rtc0/time → "14:30:00"
                    用户 echo +60 > /sys/class/rtc/rtc0/wakealarm → 1 分钟后叫醒
                            ↓
                    系统休眠
                    闹钟响了 → 中断 → 系统醒来
```

## §5 两把锁的故事

框架里有两把锁，各管各的事：

**`ops_lock`（互斥锁）**：管"跟硬件说话"的事。读时间、设时间、设闹钟——这些操作要跟芯片通信（I2C/SPI 传输），可能要好几毫秒。互斥锁的意思是"排队等，但可以让出 CPU 去做别的事"。

**`irq_lock`（自旋锁）**：管"中断来了怎么办"的事。中断处理必须快，不能等。自旋锁的意思是"原地转圈等，不让出 CPU"。

两把锁不冲突——一个管慢操作，一个管快操作。几乎不需要同时拿两把锁。

## §6 闹钟补全的故事

假设你的 RTC 芯片只存了"7 点 30 分"的闹钟，没存日期。框架要帮你补全"哪一天的 7:30"。

框架的做法很直觉：

1. 先看现在几点——"现在是 8 月 27 日 14:00"
2. 闹钟是 7:30——今天的 7:30 已经过了
3. 那就设成**明天**的 7:30——8 月 28 日 7:30

但如果读闹钟和读当前时间之间刚好跨了分钟（比如读闹钟时是 14:00，读时间时变成了 14:01），补全就可能出错——你可能用 14:00 的数据补全，但实际已经是 14:01 了。

框架的解决办法是**读两次当前时间，对比一下**——如果两次不一样（说明刚好跨了分钟），重新来过，直到两次一致。这叫"三次读取 + 一致性校验"。

## §7 定时器队列的故事

框架用一个红黑树（按到期时间排序）管理多个软件定时器。这就像一张**待办事项清单**，按时间排列：

```
  8:00 → 闹钟 A
  9:30 → 闹钟 B
  14:00 → 闹钟 C
```

硬件闹钟寄存器里永远只装**最早那个**（8:00 的闹钟 A）。当 8:00 到了，硬件触发中断，框架在后台处理：

1. 闹钟 A 到期了 → 执行它的回调
2. 下一个最早的是 9:30 的闹钟 B → 把硬件闹钟重设为 9:30
3. 如果闹钟 A 是周期性的（比如每小时响一次）→ 把 9:00 的闹钟 A 重新排进队列

这个机制让多个闹钟可以共存——用户设的闹钟和 `alarmtimer` 设的闹钟共用同一条队列，互不覆盖。

## §8 范围映射的故事

RTC 芯片通常只能存 2 位数的年份（00–99）。框架需要知道"00 代表哪一年"。

DT 里的 `start-year = <2000>` 告诉框架："0 代表 2000 年"。于是：

- 硬件显示 00 → 框架说 2000 年
- 硬件显示 99 → 框架说 2099 年
- 硬件显示 24 → 框架说 2024 年

如果系统想让这个 RTC 服务更长的时间范围（比如 2024–2199），框架会算一个偏移量：把硬件的 00–99 映射到 2100–2199，这样系统就能用 200 年的范围了。

## §9 alarmtimer 的故事

`alarmtimer` 是 RTC 框架最大的消费者。它提供两个特殊的 POSIX 时钟：`CLOCK_REALTIME_ALARM` 和 `CLOCK_BOOTTIME_ALARM`——这两个时钟的定时器在系统休眠时仍然能触发。

alarmtimer 怎么找到 RTC 的？它不主动去找——它注册了一个"监听器"（`class_interface`），每当有新的 RTC 注册到系统里，监听器就会被触发。然后它问三个问题：

1. 我已经选过 RTC 了吗？（是 → 不选了）
2. 这个 RTC 支持闹钟吗？（否 → 不选它）
3. 这个 RTC 能当唤醒源吗？（否 → 不选它）

三个都是"是"→ 选中！以后所有休眠唤醒的闹钟都通过这个 RTC 的硬件闹钟实现。

⚠️ **第一个满足条件的 RTC 获胜**。如果系统有多个 RTC，只有第一个被选中。

## §10 竞态的故事

框架里有几个精妙的竞态处理：

**闹钟设置的竞态**：你设了一个 3 秒后的闹钟。但设置过程本身（I2C 传输）可能花了 4 秒。框架的做法是：设完之后**再读一次时间**，如果发现闹钟时间已经过了，返回 `-ETIME`，让调用者重试。

**定时器队列的重试**：到期处理函数在重设硬件闹钟时，如果硬件返回"这个时间已经过了"（`-ETIME`），它会重新读时间、重新找最早的定时器、再试一次。最多重试 100 次——如果 100 次都不行，说明有什么东西坏了，放弃并打印错误。

**UIE 模拟的两阶段**：硬件不支持秒更新中断时，框架用轮询模拟。第一阶段每 50ms 读一次 RTC（每秒 20 次 I2C 传输），检测到秒变化后切换到第二阶段——精确的 1 秒定时器。这样既不错过秒变化，又不浪费太多 I2C 带宽。

## §11 调试速查

| 想看什么 | 命令 |
|---|---|
| 现在几点 | `cat /sys/class/rtc/rtc0/time` |
| 今天几号 | `cat /sys/class/rtc/rtc0/date` |
| 有没有设唤醒闹钟 | `cat /sys/class/rtc/rtc0/wakealarm` |
| 设一个 1 分钟后的闹钟 | `echo +60 > /sys/class/rtc/rtc0/wakealarm` |
| 看框架的跟踪日志 | `echo 1 > /sys/kernel/tracing/events/rtc/enable` |
| 看 procfs 的汇总信息 | `cat /proc/driver/rtc` |
| 这个 RTC 是不是系统时钟 | `cat /sys/class/rtc/rtc0/hctosys`（1 = 是） |
| RTC 的硬件范围 | `cat /sys/class/rtc/rtc0/range` |
| 时钟校正偏移 | `cat /sys/class/rtc/rtc0/offset` |
| 开了 RTC 调试 | `dmesg \| grep rtc` |

## §12 一句话总结

RTC 子系统是一个**翻译官 + 补全器 + 模拟器**：翻译各种芯片的方言成统一接口，补全硬件存不下的信息，模拟硬件不支持的功能。它用两把锁保护慢操作和快操作，用红黑树管理多个闹钟，用三次读取避免竞态，用偏移映射扩展硬件的年份范围。
