# 嵌入式Linux设备驱动程序开发指南
## 1. 嵌入式Linux构建系统与开发环境搭建

### 1. 嵌入式Linux系统概述&lt;u&gt;&lt;/u&gt;
章节开篇介绍了嵌入式Linux的优势（开源、可移植、协议支持广）及其体系结构。一个完整的嵌入式Linux系统由以下**五个主要组件**组成：
*   **引导加载程序 (Bootloader)：** 系统上电后运行的第一段代码，负责初始化硬件并加载内核。书中重点介绍了**U-Boot**，它是ARM Linux的标准引导程序，具有启动快、可移植、可配置等特点。
*   **Linux内核 (Kernel)：** 系统的核心，负责管理硬件和进程。书中介绍了内核的版本分类（主线、稳定版、长期维护版），并指出本书使用**长期支持版本 Kernel 4.9.y** 进行开发。
*   **系统调用接口 (System Call Interface)：** 用户空间与内核空间交互的桥梁。
*   **C运行时库 (C Runtime Library)：** 如glibc，封装了系统调用。
*   **系统共享库 & 根文件系统 (Root Filesystem)：** 包含应用程序运行所需的库文件（如libc, libm等）和符合FHS标准的文件目录结构（/bin, /etc, /dev等）。

### 2. Linux启动过程
详细描述了从上电到用户进程运行的流程：
1.  **上电复位 (POR)：** 运行片上启动ROM代码。
2.  **引导加载：** U-Boot运行，初始化DDR，将内核镜像(zImage)和设备树(dtb)加载到内存。
3.  **内核启动：** U-Boot跳转到内核，内核初始化MMU、调度器、驱动，挂载根文件系统。
4.  **用户空间：** 执行第一个用户进程 `init`。

### 3. 构建嵌入式Linux系统的方法
书中比较了三种构建方法：
1.  **手动构建：** 繁琐，难复现。
2.  **使用完整发行版 (如Debian/Ubuntu)：** 易获取，但难定制。
3.  **使用构建框架 (如Yocto, Buildroot)：** 易定制，可复现，是嵌入式领域的趋势。

**本书的选择策略：**
*   对 **NXP i.MX7D** 和 **Microchip SAMA5D2** 处理器，使用 **Yocto工程** 构建。
*   对 **Broadcom BCM2837 (树莓派3)**，使用 **Debian (Raspbian)** 发行版。

## 2. Linux设备与驱动模型

### 1. Linux设备与驱动模型的核心概念
Linux 2.6版本引入了统一的设备模型，旨在提供一种单一的机制来表示设备及其拓扑结构。
*   **目的：** 减少代码冗余，将设备驱动与控制器驱动分离，提供电源管理能力，并构造系统设备的完整树状结构。
*   **三个核心组件：**
    1.  **总线 (Bus)：** 处理器与设备之间的通道（如USB, PCI, I2C, SPI，甚至是虚拟的Platform总线）。
    2.  **设备 (Device)：** 连接到总线上的物理或虚拟对象。
    3.  **驱动 (Driver)：** 负责探测、关联设备并进行管理的软件实体。

### 2. 总线、设备与驱动的交互机制
书中详细描述了这三者如何协同工作，特别是“绑定（Binding）”的过程：

#### A. 总线核心驱动 (Bus Core)
*   **职责：** 定义总线类型（`bus_type`结构体），注册总线。它维护两个列表：**设备列表**和**驱动列表**。
*   **匹配逻辑 (Match)：**
    *   当一个**新驱动**注册时 (`driver_register`)，总线会遍历设备列表，调用`match`函数查找该驱动支持的设备。
    *   当一个**新设备**被发现/注册时 (`device_register`)，总线会遍历驱动列表，查找能处理该设备的驱动。
    *   一旦匹配成功，就会调用驱动程序的 `probe()` 函数，这被称为**“绑定”**。

#### B. 总线控制器驱动 (Bus Controller Driver)
*   系统中可能存在多个同类型的总线控制器（如多个I2C控制器）。
*   主要负责发现设备和配置资源，通常在内核初始化阶段通过解析设备树发现。

#### C. 设备驱动 (Device Driver)
*   **核心结构：** `device_driver`。
*   **关键回调函数：**
    *   `probe()`: 当总线认为驱动与设备匹配时调用。负责初始化设备、映射内存、注册中断等。
    *   `remove()`: 当设备移除或驱动卸载时调用，负责清理资源。

### 3. 设备树 (Device Tree, DT)
这是嵌入式Linux开发中描述硬件的标准方式，用于替代过去内核中硬编码的板级文件（.c文件）。

*   **定义：** 一种树状数据结构，通过节点（Node）和属性（Property）来描述系统硬件。引导加载程序（如U-Boot）将设备树加载到内存并传递给内核。
*   **文件类型：**
    *   `*.dtsi`：头文件，通常包含SoC级或系列通用的硬件描述。
    *   `*.dts`：源文件，描述具体的板级硬件配置。
*   **核心属性 `compatible`：**
    *   这是驱动匹配中最关键的属性。
    *   它包含一个字符串列表（从最精确到最通用），内核利用它将设备节点与特定的驱动程序绑定。
*   **设备树在Linux中的三大用途：**
    1.  **平台区分 (Platform Identification)：** 内核通过根节点的 `compatible` 属性来识别当前运行的机器类型（Machine Type），从而执行特定的初始化代码。
    2.  **运行时配置 (Runtime Configuration)：** 通过 `/chosen` 节点传递内核启动参数（如 `bootargs`）和内存盘位置，无需重新编译内核。
    3.  **设备填充 (Device Population)：** 内核启动时解析设备树，通过 `of_platform_populate()` 函数遍历节点，自动创建对应的 `platform_device` 实例，从而触发驱动的加载和 `probe`。

### 总结
第2章从理论高度解释了**“为什么你只需要写驱动代码和修改设备树，驱动就能自动跑起来”**。
它解释了幕后的机制：**总线**负责牵线搭桥，**设备树**负责描述硬件存在，**驱动**负责具体的控制逻辑。当设备树中的节点被内核解析为设备，且与驱动中的 `compatible` ID匹配时，内核自动调用 `probe` 函数，驱动程序正式开始工作。

## 3. 最简驱动程序

### 1. 核心理论：内核态与用户态的隔离
*   **设计理念：** Linux系统将用户应用程序与底层硬件隔离。应用程序运行在虚拟地址空间，不能直接访问物理硬件（如寄存器）。
*   **驱动的作用：** 只有内核驱动程序能访问硬件。这种隔离提供了**健壮性**（防止应用错误导致系统崩溃）和**可移植性**（应用无需修改即可在不同硬件平台运行）。
*   **内核模块（LKM）：** 驱动可以静态编译进内核，也可以作为模块（`.ko`文件）在运行时动态加载。模块化开发更灵活，无需重启即可测试。

### 2. 内核模块的基本结构
一个最基础的Linux内核模块必须包含以下部分：
*   **加载函数 (`init`)：** 模块加载时执行（`insmod`），用于初始化资源。使用宏 `module_init()` 指定。
*   **卸载函数 (`exit`)：** 模块移除时执行（`rmmod`），用于释放资源。使用宏 `module_exit()` 指定。
*   **许可证声明 (`MODULE_LICENSE`)：** **非常重要**。必须声明为 "GPL" 相关协议。如果不声明，内核会被标记为“受污染（Tainted）”，导致无法使用某些内核功能，且社区会拒绝处理相关Bug。

### 3. 三个基础实验

#### 实验 3-1：“helloworld” 模块（最基础）
*   **功能：** 在加载和卸载模块时，向内核日志缓冲区打印信息。
*   **关键点：**
    *   使用 `pr_info()` 函数打印日志（它是 `printk` 的封装，建议使用）。
    *   日志级别：`KERN_ERR`, `KERN_INFO` 等决定了消息的重要性。
    *   构建系统：介绍了如何编写 `Makefile`，并利用之前配置好的交叉编译环境（Eclipse或命令行）生成 `.ko` 文件。

#### 实验 3-2：“带参数的 helloworld” 模块（交互）
*   **功能：** 演示如何在加载模块时传递参数，以及如何在运行时修改参数。
*   **关键机制：** `module_param()` 宏。
*   **交互方式：**
    1.  **加载时：** `insmod module.ko num=10`
    2.  **运行时（Sysfs）：** Linux内核会通过 `/sys/module/&lt;模块名&gt;/parameters/` 目录将参数暴露为虚拟文件，用户可以通过读写这些文件来修改驱动中的变量。

#### 实验 3-3：“helloworld 计时” 模块（功能扩展）
*   **功能：** 计算模块从加载到卸载之间经过的时间。
*   **实现：**
    *   在加载时记录当前时间，在卸载时计算时间差。
    *   使用了 `do_gettimeofday()` 内核函数（虽然在较新内核中逐渐被替代，但本书基于4.9内核仍使用此方法）和 `timeval` 结构体来获取秒和微秒级时间。

### 4. 跨平台支持
本章的代码示例虽然逻辑通用，但作者提供了适配三种目标板（NXP i.MX7D, Microchip SAMA5D2, Broadcom BCM2837）的源码版本，强调了Linux驱动在不同ARM平台上的通用性。

**总结：**
第3章是“Hello World”级别的入门章节，不涉及具体的硬件操作（如GPIO或I2C），而是聚焦于**“如何写一个合法的内核模块”**，如何编译它，如何加载它，以及如何通过参数和日志与它进行基本的交互。这是后续开发字符设备驱动的基础。

## 4. 字符设备驱动

### 1. 字符设备驱动的核心概念

*   **隔离与交互：** 操作系统设计上将用户态应用与底层硬件细节隔离。字符设备驱动充当用户态应用（通过标准系统调用如 `open()`, `read()`, `write()`, `ioctl()` 等）与内核态硬件交互的桥梁。
*   **虚拟文件：** 字符设备在 `/dev` 目录下表现为特殊文件（设备节点），尽管它们不是真正的物理文件。用户应用通过读写这些设备文件来与驱动交互，内核负责数据在用户态和驱动数据缓冲区之间的拷贝（使用 `copy_from_user()` 和 `copy_to_user()`）。
*   **设备号：** 每个设备通过一对设备号（主设备号 `major` 和从设备号 `minor`）来唯一标识。
    *   **主设备号：** 标识设备类型，决定哪个驱动来处理。
    *   **从设备号：** 标识特定设备实例，由驱动管理。
    *   可以通过 `ls -l /dev` 查看设备号。
*   **`file_operations` 结构体：** 字符设备驱动的核心。这是一个函数指针集合，包含了驱动程序需要实现的用户态文件操作（如 `open`, `read`, `write`, `ioctl`, `release` 等）对应的回调函数。

### 2. 字符设备的注册与注销

*   **静态分配设备号：**
    *   使用 `register_chrdev_region()` 函数指定主设备号和请求的从设备数量来分配设备号区域。
    *   使用 `MKDEV` 宏将主、从设备号组合成 `dev_t` 类型。
*   **动态分配设备号（推荐）：**
    *   使用 `alloc_chrdev_region()` 函数让内核自动分配一个可用的主设备号和从设备号范围。
*   **字符设备结构 `cdev`：**
    *   代表一个字符设备，需要被初始化（`cdev_init()`，传入 `file_operations` 结构体）并添加到内核（`cdev_add()`）。
    *   移除时需要调用 `cdev_del()` 和 `unregister_chrdev_region()`。

### 3. 设备节点的创建

*   **传统静态方式 (`mknod`)：**
    *   旧方法，需要手动在 `/dev` 目录下使用 `mknod` 命令创建设备节点（例如 `mknod /dev/mydev c 202 0`，其中 `c` 表示字符设备，`202` 是主设备号，`0` 是从设备号）。这种方式在现代Linux开发中已不推荐，但作为教学示例出现。
*   **动态方式（设备文件系统 `devtmpfs`）：**
    *   现代Linux（2.6.32+）引入 `devtmpfs`，内核启动时自动挂载到 `/dev`。
    *   当驱动程序注册设备时，内核会自动在 `/dev` 目录下创建设备节点。
    *   **`CONFIG_DEVTMPFS_MOUNT`** 内核选项控制此行为。
*   **使用`sysfs`和`udevd`：**
    *   `sysfs` 是一个虚拟文件系统，将内核设备模型中的设备信息导出到用户态。
    *   `udevd` （或 `mdev`）是一个用户态程序，它根据 `sysfs` 中的信息和 `/etc/udev/rules.d` 中的规则，自动在 `/dev` 下创建设备节点，并设置正确的权限。

### 4. 三个基础实验（结合理论）

#### 实验 4-1：“helloworld字符设备”模块（静态设备节点）
*   **功能：** 实现一个基本的字符设备，只在加载和卸载时打印信息，并支持 `open()` 和 `ioctl()` 操作。
*   **关键点：**
    *   使用 `register_chrdev_region()` 静态分配设备号。
    *   通过 `mknod` 手动创建 `/dev/mydev` 设备节点。
    *   实现了 `my_dev_open()` 和 `my_dev_ioctl()` 函数作为 `file_operations` 的回调。
    *   **强调：** 这是一个教学示例，手动 `mknod` 已不推荐。

#### 实验 4-2：“class字符设备”模块（自动创建设备节点）
*   **功能：** 在实验4-1的基础上，利用Linux设备模型和 `sysfs` 自动创建设备节点，而无需手动 `mknod`。
*   **关键点：**
    *   引入 `class_create()` 和 `device_create()` 内核API。
    *   `class_create()` 在 `/sys/class` 下创建一个类别目录（例如 `/sys/class/hello_class`）。
    *   `device_create()` 在该类别目录下创建设备条目（例如 `/sys/class/hello_class/mydev`），并自动在 `/dev/mydev` 创建设备节点。
    *   `class_destroy()` 和 `device_destroy()` 用于清理。

#### 实验 4-3：“杂项字符设备”模块 (Misc Device Framework)
*   **功能：** 进一步简化字符设备驱动的开发，使用“杂项框架”（Misc Device Framework）来避免设备号冲突和简化设备注册。
*   **关键点：**
    *   杂项驱动分配一个官方主设备号（MISC_MAJOR，通常是10）。
    *   驱动只需定义 `miscdevice` 结构体（包含 `minor`、`name` 和 `file_operations`）并调用 `misc_register()`。
    *   内核会根据 `miscdevice` 结构体自动分配从设备号，并在 `/sys/class/misc/` 下创建目录和在 `/dev/` 下创建设备节点。
    *   这种方式极大地简化了设备号管理，推荐用于小型、功能单一的字符设备。

### 5. 将模块集成到内核构建
章节最后还介绍了如何将驱动程序从可加载模块（`.ko`）变为**静态编译进内核**。
*   **操作：** 修改内核源码树下的 `Kconfig` 文件（添加配置选项）和 `Makefile` 文件（指示编译）。
*   **结果：** 重新编译内核后，驱动程序将作为内核的一部分自动加载，无需 `insmod`。
*   **验证：** 可以通过 `cat /proc/devices` 查看已分配的主设备号，或检查 `/sys` 目录下的设备条目。

**总结：**
第4章是Linux驱动开发的核心入门，它详细阐述了字符设备作为最基本的用户态-内核态交互方式。通过引入`file_operations`、设备号、`cdev`、`sysfs`和`miscdevice`框架，循序渐进地展示了如何编写、注册、管理和与字符设备进行交互，为读者后续开发更复杂的设备驱动奠定了坚实的基础。

## 5. 平台设备驱动

### 1. 平台设备驱动模型 (Platform Driver Model)
*   **概念：** 并非所有设备都连接在物理总线（如USB、PCI）上，许多设备（如UART、SPI、I2C控制器、GPIO控制器等）直接集成在SoC内部。Linux内核为此创建了一条虚拟的**“平台总线 (Platform Bus)”**。
*   **核心机制：**
    *   **静态枚举：** 不同于USB的动态发现，平台设备通常需要在设备树（Device Tree）中静态描述。
    *   **匹配方式：** 平台驱动（`platform_driver`）通过`of_match_table`中的`compatible`字符串与设备树节点进行匹配。
    *   **Probe函数：** 一旦匹配成功，内核调用驱动的`probe()`函数，这是驱动初始化的入口（替代了模块的`init`）。

### 2. 引脚控制子系统 (Pinctrl Subsystem)
在操作硬件之前，必须正确配置引脚的功能（复用）和电气属性（上拉/下拉、驱动能力等）。
*   **功能：** 将引脚复用（Pin Muxing）和配置逻辑从驱动代码中剥离，交给专门的Pinctrl子系统管理。
*   **设备树绑定：** 在设备树中定义引脚组（如`pinctrl-0`, `pinctrl-names="default"`）。
*   **状态管理：** 驱动加载时，核心会自动将引脚设置为“default”状态；设备休眠时可切换到“sleep”状态以省电。

### 3. GPIO子系统与描述符接口 (GPIO Descriptor Interface)
*   **新旧接口：** 书中重点介绍了**基于描述符的GPIO接口（`gpiod_*`系列）**，这是现代Linux内核推荐的方式，替代了旧的基于整数的GPIO接口（`gpio_*`）。
*   **核心API：**
    *   `devm_gpiod_get()`: 从设备树获取GPIO描述符（处理了极性反转等细节）。
    *   `gpiod_direction_output/input()`: 设置方向。
    *   `gpiod_set_value()`: 设置高低电平（逻辑值，驱动会自动处理低电平有效的情况）。
*   **映射：** 介绍了如何在设备树中使用 `xxx-gpios` 属性将硬件引脚映射给驱动程序。

### 4. MMIO (内存映射I/O) 与资源获取
*   **资源获取：** 驱动程序不应硬编码物理地址，而应通过 `platform_get_resource()` 从设备树获取硬件资源（如寄存器基地址、中断号）。
*   **地址映射：** 物理地址必须映射为虚拟地址才能被内核访问。
    *   **`ioremap`**: 传统的映射函数。
    *   **`devm_ioremap`**: **推荐使用**。这是“托管（Managed）”版本的函数，当驱动卸载时会自动释放映射，简化了错误处理和清理代码。

### 5. Linux LED类 (LED Class)
为了标准化，控制LED不应只写字符设备驱动，而应对接内核的LED子系统。
*   **Sysfs接口：** 注册后，系统会在 `/sys/class/leds/` 下生成节点，用户可以通过写 `brightness` 文件控制LED。
*   **触发器 (Triggers)：** LED子系统支持各种触发器（如心跳 `heartbeat`、磁盘活动、CPU活动等），无需编写复杂代码即可实现闪烁效果。

### 6. 用户空间驱动 (UIO)
章节的最后部分介绍了一种特殊的驱动开发方式——**UIO (Userspace I/O)**。
*   **原理：** 内核只负责极少量的中断处理和内存映射，大部分驱动逻辑在**用户空间**的应用程序中完成。
*   **优势：** 适合私有协议、不需要高性能中断处理、或者为了规避GPL协议的驱动。
*   **实现：** 驱动端使用 `uio_register_device`，用户端通过 `mmap()` 直接访问硬件寄存器。

### 7. 本章涉及的实验
本章通过四个循序渐进的实验串联起上述知识：
1.  **实验 5-1 “平台设备”模块：** 将之前的字符设备驱动改造为平台驱动，学习 `probe`、`remove` 和设备树匹配。
2.  **实验 5-2 “RGB LED平台设备”模块：** 使用 MMIO (`devm_ioremap`) 直接操作寄存器来控制LED，学习资源获取和地址映射。
3.  **实验 5-3 “RGB LED类”模块：** 抛弃手写的字符设备接口，改用标准的 Linux LED Class 框架来控制LED，并支持设备树中的子节点解析。
4.  **实验 5-4 “LED UIO平台”模块：** 编写一个UIO驱动，演示如何在用户空间直接操作寄存器控制LED。

**总结：**
第5章是Linux驱动进阶的关键。它教导读者**“按套路出牌”**：使用**Platform总线**管理生命周期，使用**Device Tree**描述硬件，使用**Pinctrl**配置引脚，使用**Managed API (`devm_`)** 管理资源，以及使用**标准子系统（如LED Class）**来暴露功能，而不是什么都自己写一个字符设备。

## 6. I2C从端驱动

### 1. I2C与SMBus基础
*   **协议简介：** I2C是飞利浦开发的双线串行总线（SDA数据线, SCL时钟线），广泛用于连接传感器、EEPROM等低速外设。
*   **SMBus (System Management Bus)：** 是Intel定义的I2C协议的子集。
*   **开发建议：** 书中强烈建议驱动开发时**尽可能使用SMBus命令**（如 `i2c_smbus_read_byte_data`），而不是原始的I2C传输。因为SMBus命令在纯I2C适配器上可以被模拟，但在纯SMBus适配器上也能工作，因此兼容性更好。

### 2. Linux I2C子系统架构
Linux I2C子系统采用了典型的分层设计，主要包含三个部分：
1.  **I2C核心 (Core)：** 位于 `drivers/i2c/i2c-core.c`，负责管理I2C总线驱动和设备驱动的注册、注销以及匹配。
2.  **I2C控制器驱动 (Bus Driver / Adapter)：** 位于 `drivers/i2c/busses/`。这是SoC内部I2C控制器的驱动（如i.MX7D的I2C控制器），它被注册为平台设备。它实现了底层的字节传输逻辑。
    *   关键结构体：`i2c_adapter`。
3.  **I2C设备驱动 (Device Driver / Slave Driver)：** 位于 `drivers/` 下的各个子目录（如 `input`, `iio`, `misc`）。这是我们需要编写的驱动，用于控制具体的外设芯片。
    *   关键结构体：`i2c_driver` 和 `i2c_client`。

### 3. 编写I2C从端驱动的核心步骤
开发一个I2C设备驱动通常包含以下步骤：

*   **定义 `i2c_driver` 结构体：**
    *   包含 `probe` 和 `remove` 回调函数。
    *   包含 `id_table`（用于传统ID匹配）和 `of_match_table`（用于设备树匹配）。
*   **注册驱动：** 使用 `module_i2c_driver()` 宏简化注册流程。
*   **Probe函数实现：**
    *   当驱动与设备匹配成功时调用。
    *   `i2c_client` 结构体代表了挂在总线上的从设备。
    *   使用 `i2c_set_clientdata(client, data)` 将私有数据绑定到 `i2c_client`，以便在其他函数中获取。
*   **数据传输 API：** 使用内核提供的SMBus API与硬件通信，例如：
    *   `i2c_smbus_read_byte_data(client, reg)`
    *   `i2c_smbus_write_byte_data(client, reg, value)`

### 4. 设备树中的I2C描述
*   **控制器节点：** 在SoC的 `.dtsi` 文件中定义（通常已由厂商提供，如 `i2c3`）。
*   **从设备节点：** 必须作为控制器节点的**子节点**进行声明。
*   **关键属性：**
    *   `reg`：设备的I2C 7位地址（如 `0x72`）。
    *   `compatible`：用于匹配驱动程序。
    *   `pinctrl-*`：引脚复用配置。
    *   `status = "okay"`：启用设备。

### 5. Sysfs文件系统接口
本章还详细介绍了如何通过 `sysfs` 向用户空间暴露控制接口，使用户可以通过读写文件来控制硬件，而无需编写复杂的 `ioctl`。
*   **`DEVICE_ATTR` 宏：** 用于定义属性（文件）及其读写回调函数（show/store）。
*   **注册属性：** 使用 `sysfs_create_group()` 或 `device_create_file()` 将属性文件创建在 `/sys/bus/i2c/devices/...` 目录下。

### 6. 两个关键实验

#### 实验 6-1：“I2C I/O扩展设备”模块
*   **硬件：** PCF8574 I/O扩展芯片。
*   **内容：**
    *   在设备树中配置I2C引脚复用。
    *   编写一个“杂项设备”驱动，在 `read`/`write` 函数中调用 `i2c_smbus` 函数来控制PCF8574的GPIO电平。
    *   演示了最基本的I2C读写操作。

#### 实验 6-2：“I2C多显LED”模块
*   **硬件：** LTC3206 LED控制器（控制RGB LED和数字显示）。
*   **内容：**
    *   展示了更复杂的I2C寄存器操作（配置位掩码、模式选择）。
    *   **引入 `sysfs` 交互：** 不创建 `/dev` 节点，而是通过在 `/sys` 下创建自定义文件（如 `set_led`, `rgb_select` 等）来控制LED的颜色和亮度。用户可以通过 `echo 1 > led_on` 这样的命令直接控制硬件。

**总结：**
第6章是嵌入式Linux中最常用总线驱动的入门。它教会读者如何基于Linux设备模型编写**I2C Client Driver**。核心要点是：**设备树描述硬件连接、`i2c_driver` 描述驱动逻辑、`SMBus API` 进行数据传输、`sysfs` 提供用户控制接口**。

## 7. 处理设备驱动中的中断

### 1. 中断基础与架构
*   **IRQ号的概念：** Linux内核使用虚拟的**IRQ号**来标识中断，它与硬件中断号（Hardware IRQ / hwirq）通过**IRQ Domain（中断域）**进行映射。这使得内核可以统一处理来自不同中断控制器（如GIC、GPIO控制器）的中断。
*   **设备树描述：**
    *   在设备树中，使用 `interrupt-parent` 指定中断控制器。
    *   使用 `interrupts` 属性描述具体的中断源和触发方式（如边缘触发、电平触发）。
*   **中断申请 API：**
    *   **`devm_request_irq()`：** 推荐使用的资源托管型API。
    *   参数包括：设备结构体指针、中断号、**中断处理函数(ISR)**、触发标志（如 `IRQF_TRIGGER_FALLING`）、设备名称和私有数据指针。

### 2. 中断处理程序 (ISR) 的限制
*   **执行上下文：** 中断处理程序运行在**中断上下文（Atomic Context）**。
*   **硬性规定：**
    1.  **执行时间必须极短：** 不能长时间占用CPU。
    2.  **严禁睡眠：** 不能调用任何可能导致阻塞或睡眠的函数（如 `msleep`, `mutex_lock`, `copy_to_user`）。
    3.  **返回值：** 必须返回 `IRQ_HANDLED`（处理成功）、`IRQ_NONE`（非本设备中断）或 `IRQ_WAKE_THREAD`（唤醒线程处理）。

### 3. 延迟工作机制（下半部 / Bottom Halves）
为了解决ISR不能处理耗时操作的问题，Linux提供了“延迟工作”机制，将不紧急的任务推后执行。
*   **软中断 (SoftIRQ)：** 优先级最高，保留给内核核心子系统（如网络、块设备）使用，驱动开发通常不用。
*   **Tasklet：** 基于软中断实现，运行在**中断上下文**（不能睡眠），但开销小，适合执行非常短且急迫的任务。
    *   API: `tasklet_schedule()`.
*   **工作队列 (Workqueue)：** 运行在**进程上下文**（内核线程），**可以睡眠**。是驱动开发中最常用的延迟机制。
    *   API: `schedule_work()`, `schedule_delayed_work()`.
*   **定时器 (Timer)：** 用于在指定时间后执行一次性任务，运行在中断上下文。
*   **线程化中断 (Threaded Interrupts)：**
    *   API: `devm_request_threaded_irq()`.
    *   机制：将中断分为两部分。`handler`（上半部）在中断上下文快速运行；`thread_fn`（下半部）在内核线程中运行。
    *   **适用场景：** 如果中断处理需要访问I2C或SPI等慢速总线（这些操作会睡眠），必须使用线程化中断。

### 4. 并发控制与同步
由于中断会打断进程执行，多核CPU可能同时访问共享资源，因此必须使用锁机制。
*   **自旋锁 (Spinlock)：**
    *   用于保护**中断上下文**或**极短的临界区**。
    *   **`spin_lock_irqsave()`**：在获取锁的同时关闭本地中断，防止死锁，是在ISR中加锁的标准做法。
*   **互斥锁 (Mutex)：** 只能在**进程上下文**使用，获取锁失败时会睡眠。

### 5. 睡眠与唤醒机制 (Wait Queues)
介绍了如何让用户进程在驱动中阻塞等待数据。
*   **等待队列 (`wait_queue_head_t`)：** 存放睡眠进程的链表。
*   **睡眠：** `wait_event_interruptible()` —— 让进程进入休眠，直到条件满足。
*   **唤醒：** `wake_up_interruptible()` —— 通常在中断处理程序中调用，告知进程“数据到了，醒醒”。

### 6. 内核线程 (Kernel Threads)
介绍了如何在驱动中创建和运行独立的内核线程（`kthread_run`），用于执行后台任务（如LED闪烁控制）。

### 7. 本章涉及的实验

#### 实验 7-1：“按钮中断设备”模块
*   **内容：** 最基础的中断实验。
*   **逻辑：** 按下按键 -> 触发GPIO中断 -> ISR运行 -> 打印日志。
*   **目的：** 验证设备树中断配置和 `request_irq` 的使用。

#### 实验 7-2：“睡眠设备”模块 (阻塞I/O)

#### 实验 7-3：“keyled类”模块 (综合应用)

    3.  **自旋锁：** 使用 `spinlock` 保护这个全局周期变量，防止中断处理程序和内核线程同时修改/读取它导致竞态。

**总结：**
第7章是驱动开发中**难度较高且极其重要**的一章。它解释了Linux内核如何处理异步硬件事件。核心要点是：**理解中断上下文的限制（不能睡）、学会使用下半部机制（Workqueue/Threaded IRQ）来处理耗时任务、以及正确使用自旋锁和等待队列来解决并发与同步问题。**

## 8. 在Linux驱动中分配内存

### 1. 虚拟内存与MMU机制
*   **虚拟内存系统：** Linux是一个虚拟内存系统，程序看到的地址（虚拟地址）与硬件实际使用的地址（物理地址）不同。MMU（内存管理单元）负责这种转换。
*   **页表查询 (Page Table Walk)：**
    *   介绍了ARM架构如何使用转换表（Translation Table）将虚拟地址映射到物理地址。
    *   **TLB (快表)：** 用于缓存页表转换结果，减少访问内存的开销。
    *   **页表层级：** 介绍了PGD（全局目录）、PUD、PMD、PTE（页表项）的四级（或ARM的2级/3级）分页模型。
    *   **TTBR寄存器：** 介绍了 `TTBR0`（用于用户空间映射，随进程切换而变化）和 `TTBR1`（用于内核空间映射，全局固定）。

### 2. Linux中的五种地址类型
理解这些地址的区别对驱动开发至关重要：
1.  **用户虚拟地址 (User Virtual Addresses)：** 用户态程序看到的地址。
2.  **物理地址 (Physical Addresses)：** 处理器和内存条之间使用的真实地址。
3.  **总线地址 (Bus Addresses)：** 外设（如DMA控制器）看到的地址（通常与物理地址相同，但有IOMMU时不同）。
4.  **内核逻辑地址 (Kernel Logical Addresses)：** 位于线性映射区（LowMem）。它们与物理地址有固定的偏移量，**物理上是连续的**。主要由 `kmalloc` 分配。
5.  **内核虚拟地址 (Kernel Virtual Addresses)：** 映射到内核空间的地址，但**物理上不一定连续**。例如 `vmalloc` 分配的内存或 `ioremap` 映射的寄存器地址。

### 3. 内核内存布局与区域 (Zones)
内核将物理内存划分为不同的区域（Zones）进行管理：
*   **ZONE_DMA：** 用于旧式DMA传输的低端内存。
*   **ZONE_NORMAL (LowMem)：** 映射到内核逻辑地址空间的内存，内核可以直接访问。
*   **ZONE_HIGHMEM (HighMem)：** 高端内存，内核不能直接访问，需要临时映射（`kmap`）才能访问。

### 4. 三大内核内存分配器

#### A. 页面分配器 (Page Allocator)
*   **地位：** 内核最底层的分配器，管理物理页面。
*   **算法：** 伙伴算法（Buddy Algorithm），用于减少外部碎片。
*   **API：** `alloc_pages()`, `get_free_pages()`。
*   **GFP标志 (Get Free Page Flags)：** 这一部分非常关键。
    *   **`GFP_KERNEL`**：标准分配，**可能会睡眠**（阻塞），只能在进程上下文使用。
    *   **`GFP_ATOMIC`**：原子分配，**绝不会睡眠**，用于中断处理程序或持有自旋锁的场合，但容易失败。
    *   **`GFP_DMA`**：从DMA区域分配。

#### B. SLAB分配器
*   **地位：** 建立在页面分配器之上，用于管理**小块内存**或**频繁创建/销毁的内核对象**。
*   **作用：** 减少内部碎片，提供对象缓存（Object Caching）以提高性能。
*   **变体：** 内核中有 SLAB, SLUB (默认), SLOB 三种实现。
*   **概念：** Cache（高速缓存）和 Slab（由一个或多个物理页组成的块）。
*   **API：** `kmem_cache_create()`, `kmem_cache_alloc()`。

#### C. kmalloc分配器 (最常用)
*   **地位：** 基于SLAB分配器实现，提供了类似C标准库 `malloc` 的通用接口。
*   **特点：** 分配的内存**在物理上是连续的**（这对于DMA很重要）。
*   **API：**
    *   `kmalloc()`: 分配未初始化的内存。
    *   `kzalloc()`: 分配并清零内存。
    *   `kfree()`: 释放内存。
    *   **`devm_kmalloc()` / `devm_kzalloc()`**：**推荐使用**。这是资源托管版本，设备卸载时自动释放内存，防止内存泄漏。

### 5. 实验 8-1：“链表内存分配”模块
*   **内容：** 编写一个驱动，创建一个循环单链表。
*   **实现细节：**
    *   定义链表节点结构体。
    *   在 `probe` 函数中使用 `devm_kmalloc` 动态分配链表节点和缓冲区。
    *   通过 `write` 函数向链表缓冲区填充数据。
    *   通过 `read` 函数遍历链表读取数据。
*   **目的：** 演示如何在内核驱动中正确地动态分配、使用和管理内存结构。

**总结：**
第8章主要解决了**“驱动程序需要内存时该找谁要”**的问题。它详细解释了从底层的物理页管理到上层的 `kmalloc` 接口的层次结构。对于驱动开发者来说，核心要点是：**理解虚拟地址与物理地址的区别，区分 `kmalloc`（物理连续）和 `vmalloc`（物理不连续），以及在不同上下文（进程vs中断）中正确使用 `GFP_KERNEL` 和 `GFP_ATOMIC` 标志。**

## 9. 在Linux设备驱动中使用DMA

### 1. DMA与缓存一致性 (Cache Coherency)
这是DMA操作中最棘手的问题。
*   **问题根源：** CPU有自己的高速缓存（Cache），而DMA控制器通常直接访问主存（RAM）。如果CPU修改了缓存但没写回内存，DMA就会读到旧数据；反之，DMA更新了内存，但CPU读取的是缓存中的旧数据。
*   **一致性架构：** 某些高端SoC硬件支持硬件一致性（硬件自动同步），但在嵌入式领域很多还是**非一致性架构**。
*   **解决方案：** 驱动程序必须负责维护一致性。
    *   **一致性映射 (Coherent Mapping)：** 申请一块**未缓存（Uncached）**的内存区域（使用 `dma_alloc_coherent`），CPU和DMA直接读写内存，无需软件干预，但性能稍低。
    *   **流式映射 (Streaming Mapping)：** 使用普通的已缓存内存，但在DMA传输前后，驱动必须显式调用API（如 `dma_map_single` / `dma_unmap_single`）来**刷新（Flush）**或**无效化（Invalidate）**缓存。

### 2. Linux DMA引擎 API (DMA Engine API)
Linux内核提供了一套通用的、与硬件无关的DMA API（Async TX API），用于替代特定处理器的私有DMA实现。
*   **核心步骤：**
    1.  **申请通道 (`dma_request_chan`)：** 获取一个DMA通道。
    2.  **配置参数 (`dmaengine_slave_config`)：** 设置传输方向、总线宽度、突发长度、源/目的地址等。
    3.  **准备描述符 (`device_prep_dma_*`)：** 准备传输事务，可以是内存到内存（memcpy）、设备到内存（slave_sg）或循环传输（cyclic）。
    4.  **提交事务 (`dmaengine_submit`)：** 将描述符放入挂起队列。
    5.  **启动传输 (`dma_async_issue_pending`)：** 告诉DMA控制器开始干活。
    6.  **回调通知：** 传输完成后，内核会调用驱动设置的回调函数。

### 3. DMA映射类型详解

#### A. 一致性DMA映射 (Coherent)
*   **API：** `dma_alloc_coherent()`。
*   **特点：** 返回两个地址，一个是CPU用的虚拟地址，一个是DMA用的总线地址。
*   **适用：** 控制结构、描述符链表等小块、频繁访问的数据。

#### B. 流式DMA映射 (Streaming)
*   **API：** `dma_map_single()` / `dma_unmap_single()`。
*   **特点：** 临时建立映射。
*   **方向：** 必须指定数据流向（`DMA_TO_DEVICE`, `DMA_FROM_DEVICE` 等）。
*   **适用：** 网络包、文件数据等大块数据传输。

#### C. 分散/聚集映射 (Scatter/Gather)
*   **背景：** 在虚拟内存系统中，用户看似连续的大块缓冲区，在物理内存中往往是**碎片化**的（不连续）。
*   **机制：** `scatterlist` 结构体。DMA控制器支持硬件链表，可以一次性处理多个不连续的物理内存块，而无需CPU介入进行数据拷贝拼接。
*   **API：** `dma_map_sg()`。

### 4. 用户态DMA (Userspace DMA)
章节后半部分探讨了如何让用户空间的应用程序利用DMA来搬运数据，而不需要CPU进行 `memcpy`。
*   **mmap机制：** 驱动程序实现 `mmap` 操作，将内核分配的DMA缓冲区（物理连续）映射到用户进程的虚拟地址空间。
*   **交互流程：**
    1.  用户程序通过 `mmap` 获取缓冲区指针。
    2.  用户直接读写这块内存。
    3.  用户通过 `ioctl` 通知驱动程序启动DMA传输（例如将这块内存的数据搬运到另一块内存，或者发送给硬件）。

### 5. 三个核心实验
本章通过三个实验逐步深入：

#### 实验 9-1：“流式DMA”模块 (Memory-to-Memory)
*   **功能：** 使用DMA将数据从一个内核缓冲区（`wbuf`）复制到另一个（`rbuf`）。
*   **要点：**
    *   使用 `dma_map_single` 进行流式映射。
    *   使用 `dmaengine_prep_dma_memcpy` 准备描述符。
    *   使用 `completion` 机制等待DMA传输完成。

#### 实验 9-2：“分散/聚集DMA设备”模块 (Scatter/Gather)
*   **功能：** 演示如何处理物理上不连续的内存。
*   **要点：**
    *   构造 `scatterlist` 数组。
    *   使用 `dma_map_sg` 进行映射。
    *   使用 `dmaengine_prep_slave_sg` 准备传输。这模拟了更真实的场景，如从外设读取大量数据到碎片化的内存中。

#### 实验 9-3：“用户态DMA”模块 (Zero-Copy)
*   **功能：** 实现零拷贝的数据处理。
*   **要点：**
    *   驱动中分配DMA缓冲区 (`dma_alloc_coherent`)。
    *   实现 `mmap` 回调，允许用户程序直接访问该缓冲区。
    *   实现 `ioctl`，用户程序填好数据后，通过ioctl触发驱动内的DMA引擎进行数据搬运，全程无需CPU参与数据复制。

**总结：**
第9章是高性能驱动开发的关键。它解释了如何绕过CPU直接在内存和外设之间高速移动数据。核心要点是：**理解Cache一致性问题及其解决方法，掌握通用的DMA Engine API编程流程，以及如何处理物理内存不连续（Scatter/Gather）的情况。**

## 12. 在Linux设备驱动程序中使用regmap API

### 1. 为什么要引入 regmap API？
*   **背景问题：** 在旧的内核版本中，如果一个芯片（如ADXL345传感器）同时支持I2C和SPI接口，开发者往往需要写两套几乎一样的逻辑代码，分别调用 `i2c_transfer` 和 `spi_write/read`。这导致了大量的代码冗余和维护困难。
*   **解决方案：** Linux 3.1 引入了 **regmap API**。它将底层的总线传输（I2C, SPI, MMIO等）抽象出来，提供了一套统一的读写接口。
*   **核心优势：**
    1.  **代码复用：** 驱动的核心逻辑代码只需编写一次，即可通过regmap适配不同的总线。
    2.  **统一接口：** 无论底层是I2C还是SPI，上层都统一调用 `regmap_read` 或 `regmap_write`。
    3.  **内置功能：** regmap子系统自动处理了**缓存机制（Caching）**（减少慢速总线访问）、**互斥锁/自旋锁**机制，以及**字节序转换**等繁琐工作。

### 2. regmap 的核心数据结构与配置
使用 regmap 的核心在于正确配置 `regmap_config` 结构体。

*   **`struct regmap_config` 的关键成员：**
    *   `reg_bits`：寄存器地址的位数（如8位、16位）。
    *   `val_bits`：寄存器值的位数。
    *   `max_register`：最大有效的寄存器地址。
    *   `writeable_reg` / `readable_reg` / `volatile_reg`：回调函数，用于判断某个寄存器是否可写、可读或是否易失（Volatile，易失寄存器不走缓存，必须直读硬件）。
    *   `read_flag_mask` / `write_flag_mask`：**这在SPI中非常重要**。许多SPI设备在读写时需要在地址高位设置特定的标志位（如读置1，写置0），regmap可以通过掩码自动处理这些细节。
    *   `fast_io`：如果设为true，内部使用自旋锁（用于中断上下文）；否则默认使用互斥锁。

### 3. 初始化与使用 API
*   **初始化（通常在 `probe` 函数中）：**
    *   I2C设备：`devm_regmap_init_i2c(i2c_client, &config)`
    *   SPI设备：`devm_regmap_init_spi(spi_device, &config)`
    *   这些函数返回一个 `struct regmap *` 指针，后续操作都基于这个指针。
*   **数据操作 API：**
    *   `regmap_write(map, reg, val)`：写寄存器。
    *   `regmap_read(map, reg, &val)`：读寄存器。
    *   `regmap_update_bits(map, reg, mask, val)`：**非常实用的函数**。它执行“读-改-写”操作，只修改寄存器中的特定位，而不会影响其他位。
    *   `regmap_bulk_read/write`：批量读写。

### 4. 驱动架构的演变
本章提倡一种**分离式**的驱动架构：
1.  **总线特定代码（Bus Specific）：** 包含 `adxl345_i2c.c` 和 `adxl345_spi.c`。它们只负责定义 `regmap_config` 并初始化 regmap 实例，然后调用核心代码。
2.  **核心通用代码（Core）：** 包含 `adxl345_core.c`。这里包含所有的业务逻辑（如IIO通道设置、中断处理、数据读取），它只接收 `regmap` 指针，完全不关心底层是I2C还是SPI。

### 5. 实验 12-1：“SPI regmap IIO设备”模块
*   **目标：** 重写之前的 ADXL345 驱动。之前是直接使用 SPI API 写的，现在改用 **regmap + IIO** 框架。
*   **实现细节：**
    *   定义了 `adxl345_spi_regmap_config`，其中特别设置了 `read_flag_mask`（针对ADXL345的SPI协议，读操作需要设置地址的第7位和第6位）。
    *   在 `probe` 中初始化 regmap。
    *   在 IIO 的 `read_raw` 回调中，使用 `regmap_bulk_read` 读取加速度数据。
    *   在中断处理函数中，使用 `regmap_read` 读取状态寄存器。
*   **效果：** 展示了如何通过 regmap 屏蔽 SPI 总线的协议细节（如读写位掩码），使得业务逻辑代码更加清晰简洁。

**总结：**
第12章通过引入 **regmap**，将驱动开发提升到了**“硬件抽象”**的层次。它教导读者如何编写**通用性强、代码复用率高**的驱动程序。这是现代Linux内核驱动（特别是传感器、PMIC、Codec等设备）的标准开发模式。掌握 regmap 是从编写“能用的驱动”进阶到编写“高质量、符合内核标准驱动”的关键一步。
