# Linux 复杂模块文档

让会写 C、了解基本操作系统概念但不熟悉目标模块的读者，先说清“它解决什么问题、各部分如何协作”，再能按问题找到对应专题和源码入口。

沿用另外两个 skill 中有价值的方法：从独特设计动机切入，用真实使用场景解释机制，回到源码核对结论。复杂模块额外关注共享对象、状态转移、策略与机制的分工，以及异步或并发交接。不要求继承它们的篇数、模板或全量 API 清单。

## 范围与输出

- 源码只读；写文档不意味着允许编译、加载模块、修改内核配置或执行示例中的系统调参命令。
- 在当前站点根目录定位 `zensical.toml` 和 `docs/`。产物写入 `docs/core/<模块>/`，专题写入 `docs/core/<模块>/sub/<专题>/`。本仓库是 `docs/core/`，不是 `doc/core/` 或 `output/`。
- 已有用户指定路径优先。找不到源码或站点根目录且无法判断时，问一个定位问题，不凭空生成源码结论。
- 默认中文、普通 Markdown、相对文档及图片链接。新文章用 `# 标题` 即可，`title` 元数据可选；保留现有 `index.md` 的目录元数据。不生成 Docsify 侧栏，也不改部署配置。
- 尊重现有文件名和用户修改。局部续写不重排整套文档；旧稿只能作为待核对材料，不能依据修改时间、篇幅或 AI 进度表直接覆盖。
- 详细写作要求按下文链接读取三个指南，不依赖其他 skill 或本目录内的自检脚本。

## 选择本次深度

| 用户意图 | 本次交付 |
| --- | --- |
| 没有指定深度，或“先了解、写总览、入门” | `00-overview.md` 与简短的 `99-evidence.md`；建立全局地图，列明尚未展开的专题 |
| “深入某条路径、算法或子模块” | 仅展开选定专题，补必要的父级背景、阅读入口和证据；不顺带生成所有子模块 |
| 明确要求完整文档集 | 按模块地图分批完成全局说明与各专题，完成度按实际文件和覆盖内容登记 |
| “继续、补齐、重写已有文档” | 先核对现有基线、正文、链接和缺口，再补指定部分；进度声明以当前文件为准 |

只提问、比较方案或要求分析时，不擅自创建文档。生成任务中可先给简短的范围说明，随后执行，不为机械流程反复要求确认。

## 工作流程

### 1. 定位基线和问题

读用户目标、现有总览及相关专题；找到目标源码、公共及内部头文件、Kconfig、Makefile 和同版本官方文档。以用户指定版本为准，本仓库常用 arm64，但不要将其写成所有目标的永久限制。

记录源码版本、Git revision 与工作树修改（若有）、架构范围、已知补丁和配置边界。尤其区分：源码中存在某个配置选项、源码含某补丁、实际构建启用了该选项。存在 `PREEMPT_RT` 定义不等于已应用特定 RT 补丁，更不等于运行内核启用了 RT。

没有 `.config` 或运行环境时，只解释条件编译下的行为，明确实际启用情况未知。源码无 Git 历史仍可工作，记录版本文件和补丁核对方式，不伪造 revision。

### 2. 建立地图，再选择阅读深度

先读主入口、调度或派发逻辑、共享对象和回调契约，跟踪典型请求如何穿过模块边界；然后补读所需内部实现。不逐文件通读整个子系统，也不只凭索引工具生成调用链。

按职责、输入输出、状态归属和策略分工划分专题，文件与目录只是证据。一个大文件可以承载交错的多种职责；多个文件也可以组成一个专题。不要用行数阈值或连续行号切片代替边界分析。

把握核心链路后即可开始总览。理解尚不完整时标明边界，不把“未追踪”写成“无依赖”。先交付可读总览，再按请求深入，而不是先填完所有矩阵才让读者看到入口。

总览阶段达到以下条件就收束广泛搜索并写出完整首稿：能解释职责及主要分工；能跟完一条代表性正常路径和一个相关分支；已有支持这些解释的关键对象与源码锚点。不要为写总览穷举配置、接口、补丁影响或官方文档。余下阅读只用于核对首稿中实际使用的论断；不影响主线的不确定项记入附录，缺少证据的结论则删除或缩小范围。

### 3. 写总览和阅读地图

首次总览、或需要重整阅读入口时，读 [总览指南](references/overview-guide.md)。

总览必须独立可读：解释任务、核心直觉、关键对象、主要职责、正常路径及有代表性的异常路径。允许用小段伪代码和关键内部函数帮助理解，不把所有细节都变成跳转链接。

给出“想解决的问题 → 该看哪个专题 → 源码从哪里进”的地图。已完成文章用可点击链接；未写的专题仅列名称、源码入口和“未展开”，不造空文件或链接到不存在的文章。

### 4. 按问题下钻

展开专题或全局关系专篇时，读 [深入指南](references/deep-dive-guide.md)。

专题先给理解机制所需的背景，再深入数据结构、操作路径、算法与同步；文件数由实际内容决定。紧凑专题可只有一篇，复杂专题再拆 API、内部实现、算法或调试说明，不强制每个专题六篇。

跨模块契约在父级保留一份权威说明；专题可以复述必要上下文并链接它，不禁止出现其他模块或静态函数。不得将读者理解所需的解释全部推给另一个文件，尤其不能回指尚未写出的章节。

### 5. 核对与收尾

每个写作批次都按 [取证与检查指南](references/evidence-guide.md) 核对关键结论、源码位置、实际链接和版本条件。

总览和证据附录作为同一交付批次完成。目标文章未写完时不添加可点击引用，先用正文源码锚点支持已写部分；不能交付一个依赖不存在附录的“完成”总览。

更新总览阅读地图与 `99-evidence.md` 的覆盖表。只标记本次实际完成的部分；未展开、已写但待复核、完成分别记录。不要用“全套完成”描述仅完成样板专题的文档集。

现有 `PROGRESS.md` 可作为输入，但不自动新增公开进度文件。若用户要求单独的写作台账，将它放在 `docs/` 外的工作区，避免导航和搜索收录内部记录。

结束时说明新增或修改的文章、覆盖范围、未解决问题及检查结果。不自动提交、推送或发布。

## 文件组织

最小交付：

```text
docs/core/<模块>/
  00-overview.md       全局认识、主路径、按问题阅读地图
  99-evidence.md       基线、关键结论依据、覆盖范围与待核对项
```

按需要增加全局手册：

| 文件 | 何时值得单独写 |
| --- | --- |
| `01-api.md` | 用户需要查外部接口、回调契约或使用示例 |
| `02-objects.md` | 共享对象及字段归属成为主要理解障碍 |
| `03-lifecycle.md` | 生命周期或异步状态交接需要独立走查 |
| `04-interactions.md` | 跨模块协作无法在总览中简洁讲清 |
| `05-concurrency.md` | 锁序、无锁协议和上下文约束需要专门解释 |
| `06-tuning.md` / `07-debug.md` | 用户需要调参或诊断具体运行问题 |

选定专题放在 `sub/<专题>/`。从 `00-overview.md` 开始，按内容增加 `01-api.md`、`02-internals.md`、`03-algorithm.md`、`04-debug.md`；证据默认汇入父级 `99-evidence.md`，体量大或需独立使用时再增加专题 `99-evidence.md`。编号用于稳定排序，不要求连续，也不为填编号生成空篇。

## 写作底线

- 先讲具体问题和设计约束，再给术语和符号；类比只用于建立直觉，随后说明其边界。
- API 手册、字段字典、代码块和表格都服务于读者的问题。总览不穷举接口，算法不只给调用链，表格不替代解释。
- 分开“源码直接体现的事实”“官方注释或历史说明的意图”“作者推断”。找不到设计者原话时，不编造选择某策略的历史原因。
- 不以全量 N×N 矩阵、完整函数清单、固定篇幅或精确页数作为完成标准。只给能核对的数字，确需全量统计时说明范围和方法。
- 不混入目标版本没有的机制、另一架构入口或未经验证的性能结论。公式、锁序、错误返回及失败回退都要能落到目标源码。
