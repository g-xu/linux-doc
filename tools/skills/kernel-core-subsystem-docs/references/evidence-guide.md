# 取证与检查：可复核，不堆原始日志

## 基线

在 `99-evidence.md` 记录内核版本、源码位置、Git revision 与工作树修改（若有）、架构、已核对补丁和配置边界。源码路径可以辅助复现，但正文不要依赖某台机器的绝对路径。

用目标树的 Makefile、revision 和实际变更核对基线。RT 分别记录补丁来源 / 内容与构建启用状态；现代主线也可能自带配置项，不能从 `config PREEMPT_RT` 命中推断外部补丁已打入。

版本或配置未知时保留未知，不为了继续写作虚构事实。源码离线可阅读就继续基于它；缺少官方说明时标明证据边界。

## 证据形式

正文关键位置给简短锚点，附录汇总可复现证据：

| 结论或机制 | 来源：文件 / 符号 / 必要行号 | 类型与边界 |
| --- | --- | --- |

类型区分“源码事实”“官方说明 / 历史意图”“作者推断”“待验证”。历史意图需要实际注释、版本对应的官方文档或可查的提交记录；不把合理解释包装成维护者原话。

源码文件使用相对源码根的完整路径，例如 `kernel/sched/core.c`。行号须当次打开核对；同时保留符号，使以后换版本还能定位。代码片段标明来源与删节，公式核对变量、单位和有效条件。

不为每个普通术语重复引用，不粘贴长段命令输出。只保存对判断有帮助的命令、结果摘要及搜索范围。

## 重要论断怎么核对

- 调用链：看真实调用者和条件，追踪回调与异步交接。静态函数出现顺序不等于运行顺序。
- 字段 / 锁语义：看声明、关键读写与约束，不依据名字推断；引用、存活、互斥与内存序分别核对。
- 接口：核对目标版本中声明、实现与至少一个相关调用者，区分宏、inline、导出符号和 ABI。
- 否定 / 全称结论：确认工具成功、搜索范围、函数族、宏 / inline 与条件分支；一次零命中只能说明本次搜索未找到。
- 数字：说明统计对象和范围，必要时给重算方法；不引入无关精确计数，不估测已读函数数或 API 总量。
- 实验：仅实际运行过的结果标记“验证通过”；代码阅读、机械检查和运行测试分别报告。

## 完成度

附录使用短覆盖表即可：

| 已识别职责 / 专题 | 当前文章或覆盖位置 | 状态及待补问题 |
| --- | --- | --- |

状态至少区分“完成”“已写待核对”“未展开”。以实际文章内容而非预定篇数、旧 checkbox 或文件存在为依据。
不能把语法检查或行号未越界当成语义正确，不把所有空白项改成完成来通过检查。

## 交付检查

1. 基线一致；关键符号、公式、字段、错误和配置条件已回源码核对，未确定项有边界。
2. 图、正常路径与异常路径相互一致；跨模块交接与同步没有相互矛盾的描述。
3. 阅读地图只链接真实文件；相对路径、大小写、标题锚点和子目录中的回指都有效。
4. 新增内容进入自动导航；保留现有页面元数据，不生成内部台账或空占位文章污染公开站点。
5. 每个完成专题确实回答它负责的问题；总览不要求全部下钻，但未展开项必须可见。

本仓库已有环境时，可在站点根目录构建并检查：

运行前确认命令所在的站点根目录、配置文件和输出目录。`tools/site.ps1` 会自动切换到仓库根目录；用户指定了隔离或试验输出根时，不调用正式站点脚本，也不把构建或安装写回正式目录。隔离目录没有完整站点配置时，仅做 Markdown、文件链接和源码锚点检查，明确没有验证站点构建，不为验证而复制整个站点或安装新环境。

```powershell
.\tools\site.ps1 build
.\tools\site.ps1 check
```

WSL / Linux 使用已安装 Zensical 的环境：

```bash
zensical build --clean
python tools/check_site.py
```

检查脚本只验证生成站点的文件和锚点，不验证源码语义；它允许 `known-source-issues.json` 中的旧问题，仍应审阅具体报告。只改当前任务涉及的基线项，不为消除错误任意增加忽略条目。

工具缺失、预览正在重建或未获运行权限时，做能完成的只读检查并明确未运行部分；不要将机械步骤变成写作前的无限阻塞，也不要声称没有执行的检查已通过。
