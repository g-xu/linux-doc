# Linux 内核基础工具模块文档化工作流

本 skill 把"为内核基础工具模块写文档"的流程固化下来。适用于相对独立、功能单一的工具模块（如 list_head、spinlock、RCU、workqueue 等），不适用于完整子系统（如 IOMMU、PCI、SPI 等，那些用 `kernel-subsystem-docs` skill）。

## 前置约束

- **源码树只读**：只用 Read / Grep / Glob 和只读 git 命令，不改源码。需要改动时先问用户
- **文档输出目录**：每个分组一个目录 `output/<分组名>/`，A 级模块各一个文档，B 级模块合并到 `misc-*.md`，外加一个对比总结文档
- **进度跟踪**：`output/infrastructure-progress.md` 记录全部 14 个分类、147 个模块的状态。每次工作前先读它，写完模块后更新它
- **目标架构**：默认 arm64。涉及体系结构只走 `arch/arm64/` 路径
- **语言**：默认中文
- **每写一条因果链就回到源码确认**：`rg` + `Read` 是取证主力
- **不限页数**：内容多少决定文档长短，API 多的模块自然长，API 少的自然短。把内容讲全比控制篇幅重要

## 输出骨架

每个分组产出一个目录，目录内包含：
- 一个 `00-overview.md`：本组所有模块的对比总结
- A 级模块各一个 `<模块名>.md`（完整 §1-§6）
- B 级模块按主题合并到 `misc-<主题>.md`（每模块 20-50 行简要介绍）

全局进度跟踪文件：`output/infrastructure-progress.md`

### 单模块文档结构（6 节）

每个 `<模块名>.md` 定位是"速查 + 深入理解"——快速查阅 API，同时理解设计意图和常见陷阱。

```
§1 定位        这个模块解决什么问题、核心设计思想、与同类模块的区别
§2 核心 API    固定三列表格：API / 说明 / 备注
§3 使用模式    典型使用场景，每个场景有问题描述 + 代码骨架 + 关键点 + 常见错误
§4 常见陷阱    错误写法 / 正确写法 / 原因 / 源码依据
§5 代码示例    完整示例（标注真实代码或伪代码），每个符号全树 grep 确认存在
§6 取证摘要    读了哪些文件、关键论断出处、未验证项
```

### 对比总结文档结构（00-overview.md）

`00-overview.md` 是本组模块的横向对比，帮助读者在多个相似工具中做选择。

```
§1 一句话定位表
   表格：模块 / 一句话 / 独特价值
   "一句话"讲它是什么，"独特价值"讲它解决了什么其他模块解决不了的问题
   让读者 30 秒内找到该用哪个

§2 选型决策
   按场景或按问题组织，告诉读者"如果你的需求是 X，用 Y"
   可以有决策树、对比表、或场景列表
   补充判断：需要 RCU 无锁读？需要 1R1W 无锁？需要内建锁？需要 O(1) 取最小值？

§3 核心对比表
   逐维度对比本组模块的核心差异
   维度由模块特性决定（不是固定模板），常见维度：
   - 数据结构 / 索引类型 / 查找复杂度 / 插入删除复杂度
   - 有序遍历 / 锁模型 / 侵入式 vs 非侵入式 / 动态大小 / 内存开销

§4 使用规模
   表格：遍历/查找调用量 / 插入修改调用量 / 头文件声明量 / 核心文件行数
   所有数字必须附带 grep 命令且当场跑过

§5 设计模式速览
   本组模块共享的设计模式（如侵入式容器、编译期特化）
   每种模式给出代码示例和优劣分析

§6 锁模型对比
   表格：数据结构 / 读侧 / 写侧 / 典型场景
   特别标注 RCU 支持和无锁场景

§7 RCU 支持（如果适用）
   表格：数据结构 / RCU 读 / RCU 写 / 头文件

§8 阅读顺序建议
   首次学习 / 快速选型 / 复习三种路径
```

## 工作流（3 个阶段）

### 阶段 1：基线与规模

**1. 先定基线。** `git log -1` 判断树是否干净。

**2. 量规模。** `wc -l` 定出核心文件。工具模块通常 1-3 个核心文件，可以全读。

**3. 定架构范围。** 默认 arm64-only。工具模块通常架构无关，但涉及内存屏障、原子操作时要走 `arch/arm64/` 路径。

### 阶段 2：核心阅读

**4. 先读头文件。** `include/linux/<module>*.h` 是最高信息密度的入口。API 和数据结构全在这里。

**5. 再读核心 .c。** 按依赖顺序。核心文件逐行读。

**6. 读 `Documentation/`。** 搜索 `Documentation/core-api/<module>*`、`Documentation/<module>*`。工具模块通常有较好的官方文档。

**7. 找使用者。** `grep -rn '<api>(' --include=*.c | head -20` 找典型使用者，理解实际用法。

### 阶段 3：写文档

**产出顺序：先写各模块文档，最后写 00-overview.md。** 总结文档需要基于各模块文档的定稿内容来写，提前写会变成空泛的概述。

**批次控制：每写完 1 篇文档，必须立即自检，自检通过后才能开始下一篇。** 自检内容：API 覆盖率（总数 vs 已列出数）、代码示例正确性、关键陷阱是否覆盖。自检不通过：先修复本篇，再开始下一篇。不需要用户确认，自己判断即可。

#### 单模块文档规则

**8. §1 定位——必须提炼该模块"不可替代的设计洞察"。** 不是填模板，是独立思考这个模块为什么存在、它解决了什么其他模块解决不了的问题。

**反面教材（模板填空）：** "X 是内核的通用 Y。它提供了 Z 功能。"——这种话放在任何模块上都成立，等于没说。

**正面教材（data-structures 实例）：**
- **list_head**：侵入式容器的源头——`struct list_head` 嵌入用户结构，零额外内存分配
- **hlist**：`pprev` 技巧消除删除的特殊分支——`pprev` 指向"指向我 next 字段的指针"，使头部删除和中间删除共用同一段代码
- **rbtree**：结构性操作（rebalance）与比较性操作（search）分离——内核提供前者，用户必须写后者
- **xarray**：统一了 radix tree 和 IDR；位索引分块查找（每次处理 `BITS_PER_LONG` 位）；单调递增索引 + 2 的幂掩码
- **kfifo**：单调递增索引 + 2 的幂掩码——`in & mask` 代替 `in % size`，满/空无歧义（不需要牺牲一个槽位或额外标志位）
- **bitmap**：不是容器而是集合运算工具包；编译期常量退化为单寄存器运算（`small_const_nbits` 检查）

**检验标准：** 把 §1 的第一段话拿出来，问"这段话能不能套到其他模块上？"如果能，重写。

**9. §2 核心 API——精确计数，从源文件统计。** 固定三列表格：`API / 说明 / 备注`。
   - 「说明」一句话讲它做什么
   - 「备注」放上下文标签、返回值陷阱、参数类型提示
   - 签名只写"函数名 + 形参名"，不带类型
   - 位置只精确到文件，不精确到行号
   - **API 数量不设上限——有多少写多少，全部 grep 确认存在**

   **API 计数方法：** 打开头文件，逐行扫描所有 public API：
   - `static inline` 函数
   - `extern` 函数声明
   - 宏定义（`#define`）
   - 分别统计，最后汇总。不要估算，不要"~N"

   **容易遗漏的 API 类型：**
   - 带锁变体（如 `kfifo_in_spinlocked` / `kfifo_in_spinlocked_noirqsave`）
   - 已废弃别名（如 `kfifo_in_locked`）——仍然要列出，标注"已废弃"
   - 设备管理变体（如 `devm_bitmap_alloc`）
   - 用户空间拷贝变体（如 `kfifo_from_user` / `kfifo_to_user`）
   - 数组转换函数（如 `bitmap_from_arr32` / `bitmap_to_arr64`）
   - 辅助宏（如 `bitmap_size` / `BITMAP_LAST_WORD_MASK`）

**10. §3 使用模式。** 典型使用场景（数量不限，按实际情况），每个场景：
   - 问题描述
   - 代码骨架（伪代码或真实代码片段）
   - 关键点说明
   - 常见错误

**11. §4 常见陷阱。** 陷阱数量不限，按实际情况覆盖。每个陷阱：
   - 错误写法
   - 正确写法
   - 为什么会出错
   - 源码依据（行号）

**12. §5 代码示例。** 典型用法的完整示例（数量不限）。
   - 示例要覆盖典型用法
   - 每个示例有注释说明关键点
   - 示例中的每个符号都要全树 grep 确认存在
   - 真实代码标注文件路径，伪代码明确标注"伪代码"

**13. §6 取证摘要。** 记录：
   - 读了哪些文件
   - 关键论断的出处
   - 未验证项（如果有）

#### 对比总结文档规则

**14. 00-overview.md 写法。**
   - §2 速查表的每一行都要能对应到组内具体模块文档
   - §3 选型决策要基于真实差异，不是泛泛而谈——每个建议都要有源码依据
   - §4 关键差异对比用表格，维度由模块特性决定（不是固定模板）
   - §5 组合使用模式要给出真实内核代码中的组合实例

## 格式规则

**15. 签名只写"函数名 + 形参名"。** 让表能一眼扫完。类型不是删掉而是搬家（返回值语义、回调原型移进「备注」）。

**16. API 表格固定三列：`API / 说明 / 备注`。** 「说明」一句话，其余全部进「备注」。

**17. 代码示例要标注来源。** 如果是真实代码，标注文件路径；如果是伪代码，明确标注"伪代码"。

**18. 每个数字都要能一条命令重跑。** 不许写"~N"估算——必须当场 grep 给出精确值。

**19. 全称断言必须全树 grep。** "全树唯一 / 共 N 个"这类论断，必须在整棵树上 grep 验证。

**20. 不许用裸文件名引用。** 必须写全路径（如 `include/linux/spinlock.h`，不是 `spinlock.h`）。

**24. ★★ 批量生产后的机械验证（不是建议，是必须执行的步骤）：**

以下验证在每批文件写完后**立即执行**。不通过就不许开始下一批。这些命令针对的是反复出现的三类失败模式：格式漂移、数字幻觉、agent 产出未验证。

**24a. B 级文档三段式验证（防格式漂移）：**

```bash
# 对每个 B 级文件：功能/实现方式/应用场景 的数量必须等于模块数
for f in output/<分类>/misc-*.md; do
  modules=$(grep -c '^## ' "$f")
  func=$(grep -c '^\*\*功能\*\*' "$f")
  impl=$(grep -c '^\*\*实现方式\*\*' "$f")
  scene=$(grep -c '^\*\*应用场景\*\*' "$f")
  echo "$f: modules=$modules 功能=$func 实现=$impl 场景=$scene"
  # 判定：func == impl == scene，且 >= 1（单模块文件）或 == modules（多模块文件）
done
```

如果任何文件 `func != impl` 或 `func != scene` 或全为 0 → **整批返工**，不是修几个文件。

**24b. 00-overview.md 结构验证（防模板漂移）：**

```bash
# 必须包含 §1 到 §8（可以有 §9/§10 附加节）
for f in output/<分类>/00-overview.md; do
  for i in 1 2 3 4 5 6 7 8; do
    if ! grep -q "^## §$i" "$f"; then
      echo "FAIL: $f missing §$i"
    fi
  done
done
```

如果任何 § 缺失 → **该文件重写**。

**24c. 数字抽样验证（防幻觉）：**

每批改完后，从所有修改过的文件中**随机抽 10 个数字**，对每个数字：
1. 在文件中找到该数字及其对应的符号名
2. 跑 `grep -rw '<符号名>' --include='*.c' --include='*.h' . | wc -l`
3. 比较：文档数字 vs grep 结果，偏差 > 10% → 该文件所有数字全部重跑

**不许跳过这一步。** "看起来对"不算验证。

**24d. Agent 产出验证（防"agent 说完成就等于完成"）：**

Agent 报告完成后，**必须自己跑 24a/24b/24c**。agent 的自检报告不可信——它可能用了错误的 grep 方法论（子串匹配 vs 精确词匹配），也可能只检查了前几个文件。

**24e. 首文件门控（防批量复制错误）：**

批量生产（无论是自己写还是 agent 写）前：
1. **先写 1 个文件**
2. **自己跑 24a/24b 验证这 1 个文件**
3. 通过后，把这个文件作为 agent prompt 的**参考样例**（不只是文字描述格式，而是把整个文件内容贴进 prompt 说"照这个格式写"）
4. 然后再批量启动

**24f. 上下文压缩后的恢复协议：**

上下文被压缩后，**第一件事**是重新 Read 本 skill 文件的格式模板部分（B 级模板在 ~317-352 行，overview 模板在 ~68-104 行）。不许凭记忆中的"大概结构"继续写。记忆会在压缩中丢失细节——这正是格式漂移的根因。

## 全基础设施工作流

本 skill 不仅覆盖单个分组的文档，还管理全部 14 个分类、约 147 个模块的文档化进度。

### 模块分级

每个模块分为 A 级或 B 级：

| 级别 | 判据 | 文档形式 |
|------|------|----------|
| **A 级** | 广泛使用 + API 丰富 + 有独特设计洞察 | 独立文档，完整 §1-§6 |
| **B 级** | 使用较少 / 功能简单 / 是 A 级的变体或补充 | 合并到一个综合文档，每模块 20-50 行简要介绍 |

**A 级判据（三条全满足）：**
1. 全树调用点 > 100 处（`grep -r '\b<api>\b' --include='*.c' | wc -l`）
2. 有独立的设计决策值得在 §1 提炼（不是"X 是 Y 的封装"能概括的）
3. API 数量 > 10 个（含 inline + 宏 + extern）

**B 级典型情况：**
- 是某个 A 级模块的变体（如 `raw_spinlock` 是 `spinlock` 的 RT 变体）
- 功能极简（如 `sort` 只有一个 `sort()` 函数）
- 使用面窄（如 `assoc_array` 只有 keyring 用）
- 与 A 级模块高度重叠（如 `radix_tree` 被 `xarray` 替代）

### 进度跟踪

**进度文件：`output/infrastructure-progress.md`**

这是整个文档化项目的状态表。每写完一个模块或合并文档，立即更新状态。

**每个分类有三类交付物，全部 tracked 在进度表中：**

| 交付物类型 | 进度表标记 | 说明 |
|-----------|-----------|------|
| A 级模块 | 独立行，状态 ✅ | 每个模块一行 |
| B 级合并文档 | `misc-*.md` 行，状态 📦→✅ | 按主题分组 |
| **分类总结文档** | **`00-overview.md` 行，状态 ⏳→✅** | **每分类一个，必须在本分类所有模块完成后写** |

**进度表格式（每个分类末尾必须有一行总结文档）：**

```markdown
| 模块 | 级别 | 状态 | 文档 | 备注 |
|------|------|------|------|------|
| list_head | A | ✅ | `data-structures/list-head.md` | |
| ... | ... | ... | ... | ... |
| 分类总结 | — | ⏳ | `data-structures/00-overview.md` | 本分类全部模块完成后写 |
```

**工作协议：**
1. **开始工作前先读进度文件**——找到下一个 ⏳ 状态的条目（A 级模块、B 级合并文档、或分类总结）
2. **写完一个模块后立即更新**——把 ⏳ 改为 ✅，把 📦 改为 ✅（当合并文档中所有模块都完成时）
3. **中断后恢复**——读进度文件，继续 ⏳ 的第一个模块，不需要回忆之前做了什么
4. **不要跳着写**——按进度表顺序，从上到下。每个分类内先写完所有 A 级，再写 B 级合并文档，**最后写分类总结**
5. ★★ **分类完成门控：在进度表中本分类的"分类总结"行变为 ✅ 之前，不许开始下一个分类。** 这是防止总结文档被遗漏的硬卡点。完成一个分类后，逐条检查：(a) 所有 A 级 ✅ (b) 所有 B 级 📦→✅ (c) 分类总结 ✅——三项全齐才能继续

### B 级合并文档格式

同一分类下的 B 级模块合并到一个文件中。文件名按主题分组（如 `misc-lists.md`、`misc-trees.md`）。

```markdown
# <分类名> — 补充模块

本文收录本分类中不单独成文档的模块。每个模块简要介绍定位、核心 API 和使用注意。

## <模块 A>

### 定位

**功能**：一段话说明这个模块提供什么能力——它解决什么问题、能做什么操作。

**实现方式**：一段话说明核心实现机制——用了什么数据结构、关键算法、并发模型。讲清"怎么做到的"。

**应用场景**：一段话说明谁在用、用在哪里——列举主要消费者（子系统/驱动目录）和典型用途。

### 核心 API
| API | 说明 | 备注 |
|-----|------|------|
| ... | ... | ... |

### 使用注意
关键陷阱或与 A 级模块的选择要点。2-5 条。

## <模块 B>
...（同上结构）
```

**B 级文档的质量要求（低于 A 级但仍有底线）：**
- 每个 API 必须 grep 确认存在
- 定位段必须包含**功能 / 实现方式 / 应用场景**三段，不能是模板填空——要讲清这个模块做了什么、怎么做的、谁在用
- 代码示例不强制，但如果有关键用法值得展示则给出
- 取证摘要简化为一句话（"头文件：`include/linux/xxx.h`，实现：`lib/xxx.c`"）

### 工作顺序

每个分类内的固定顺序：
1. 先写所有 A 级模块的独立文档（按进度表顺序）
2. 再写 B 级合并文档（按主题分组，一组一个文件）
3. 最后写 `00-overview.md`（需要覆盖所有 A 级 + B 级模块）
4. ★★ **更新进度表：把"分类总结"行标记为 ✅。只有这一步完成后才能开始下一个分类。**

跨分类的顺序：按进度表的分类编号（一 → 十四）。

**★★ 历史教训（2026-08-28）：** 14 个分类的 `00-overview.md` 全部被遗漏，直到用户发现。根因是进度表只跟踪了 A 级模块和 B 级合并文档，没有为分类总结单独设行——执行者逐行打勾，表里没有的条目就不会触发。修复方式：进度表每分类末尾加一行"分类总结"，工作协议加门控规则（第 5 条）。

## 实例积累

### data-structures 组（2026-08-28 重写）

**§1 独特价值实例：**

| 模块 | 独特价值（不可替代的设计洞察） |
|------|-------------------------------|
| list_head | 侵入式容器的源头——`struct list_head` 嵌入用户结构，零额外内存分配 |
| hlist | `pprev` 技巧消除删除的特殊分支——`pprev` 指向"指向我 next 字段的指针"，使头部删除和中间删除共用同一段代码 |
| rbtree | 结构性操作（rebalance）与比较性操作（search）分离——内核提供前者，用户必须写后者 |
| xarray | 统一了 radix tree 和 IDR；位索引分块查找（每次处理 `BITS_PER_LONG` 位）；单调递增索引 + 2 的幂掩码 |
| kfifo | 单调递增索引 + 2 的幂掩码——`in & mask` 代替 `in % size`，满/空无歧义（不需要牺牲一个槽位或额外标志位） |
| bitmap | 不是容器而是集合运算工具包；编译期常量退化为单寄存器运算（`small_const_nbits` 检查） |
