# 00-overview.md 模板

> 写 00-overview.md 前先读本文件。本文件定义 00 的必写结构、质量标准和常见陷阱。
> 质量基准：`output/i2c/00-overview.md`（661 行，由 Opus 产出，经四轮 review 验证）。

---

## 必写结构（8 节）

### §1 一句话定位

这个模块是什么 + **"帮你省掉了什么"**（地址冲突检测、锁与并发、设备枚举、协议仿真……）。不是功能列表，是**价值主张**。读者读完这一节就知道"为什么需要这个子系统而不是自己直接操作寄存器"。

### §2 背景（本篇最大节，目标 200+ 行）

> ★ 这一节讲的是子系统存在的物理/逻辑根基，不是内核代码。后面大量设计选择（锁、恢复、mux、回调……）是这些约束的直接后果，必须先讲透。
> ★ 凡是内核代码里有对应实现的，标 `文件:行号`；纯规范/硬件手册的标明出处。
> ★ 根据阶段 1 §3b 判定的子系统类型，选择对应路径：

#### 路径 A：硬件总线型（有 bus_type，如 I2C / SPI / MMC / USB）

必须覆盖以下子节（可根据总线特性增减，但不能整体省略）：

**(a) 物理层**
- 线/引脚、电气特性（开漏/推挽、上拉/下拉）、拓扑图（ASCII）。
- 必须解释"这个物理特性导致了什么软件设计"。
- 例：I2C 开漏 → 需要 `bus_recovery_info`；SPI 推挽 → 不需要总线恢复。

**(b) 位与时序**
- 时钟相位/极性组合（如 CPOL/CPHA 四模式）、数据采样规则。
- 画波形图（ASCII）。
- 标注内核里对应的常量定义位置（如 `include/uapi/linux/spi/spi.h:7-13`）。

**(c) 一次完整事务的波形**
- 至少 2-3 个具体例子（写、读、带地址的读），用 ASCII 画信号线翻转。
- 每个例子后面标出内核侧的对应函数和行号。

**(d) 地址/CS 空间与保留**
- 地址范围、CS 编号、保留值、内核里的校验函数和行号。

**(e) 流控/错误恢复机制**
- 从设备如何反压、总线卡死怎么办、内核恢复函数行号。

**(f) 速率档位**
- 规范定义的各档频率表，对应内核常量。

**(g) 与相近总线的对比**
- 用表格对比（全双工/半双工、CS vs 地址、速率、线数等）。

**(h) arm64 SoC 上的实际硬件形态**
- SoC 内部拓扑图 + 板上外设 + 故障源对照表。
- 驱动目录量化统计 + in-tree arm64 DTS 节点实例。

#### 路径 B：框架型（无 bus_type，如 pinctrl / regmap / clk / DMA）

框架没有物理协议可讲，§2 改为「问题背景与核心抽象」：

**(a) 问题域描述**
- 框架解决什么问题？没有它调用者要自己做什么？
- 例：pinctrl → 引脚多路复用+配置；regmap → 寄存器访问抽象；clk → 时钟树管理。

**(b) 核心抽象**
- 框架提供哪些核心概念/对象？它们之间的关系（ASCII 图）。
- 例：pinctrl → pin_desc / pinctrl_state / pinctrl_setting；regmap → map + bus + config。

**(c) 为什么不能直接操作硬件**
- 框架替调用者屏蔽了哪些复杂性？（并发、引用计数、状态机、硬件差异……）
- 用具体代码路径说明"不用框架要写多少代码"。

**(d) 与相近框架的对比**
- 用表格对比职责边界。例：pinctrl vs GPIO lib vs pinconf-generic。

**(e) arm64 上的实际形态**
- 控制器驱动量化统计 + in-tree arm64 DTS 节点实例（框架消费者侧）。

#### 路径 C：虚拟总线 / 跨边界 ABI 型（有 bus_type 但没有电气层，如 virtio / rpmsg / vdpa / vsock）

★ 这类子系统**没有波形可画**，但有比波形更硬的约束：一份树外规范 + 一个不在本树里的对端。§2 改为「规范背景与边界」：

**(a) 规范是什么、哪一版在本树实现**
- 规范名称/版本 + 本树实现到哪一版的判据（**必须是代码里的常量，不是记忆**）。
- 例：`VIRTIO_F_VERSION_1` = 32（`include/uapi/linux/virtio_config.h:67`）区分 legacy 与 modern。

**(b) ABI 边界在哪**
- ★ `include/uapi/linux/<subsys>*.h` 是**与对端共享的契约**，不是普通头文件；改一个字节就破协议。
- 给出数量和清单入口：`ls include/uapi/linux/virtio_*.h | wc -l` → 27 个。
- 明确哪些结构体是"两侧都会读写的共享内存"，哪些只是内核内部的。

**(c) 能力/特性协商机制**
- feature bits 怎么协商（谁提议、谁接受、协商失败会怎样）、协商结果存在哪个字段。
- **字节序是这一节的必写项**：`__virtio16` / `virtio_legacy_is_little_endian()`（`include/linux/virtio_byteorder.h:7`）——legacy 走宿主机字节序、modern 强制小端，是本子系统最容易写错的一处。

**(d) 传输层有几种、住在哪**
- 这类子系统通常**双层可插拔**：传输层实现 ops、设备驱动实现另一套 ops。两层都要给量化统计。
- virtio 实例：`virtio_config_ops` 有 9 个实现、散在 5 个目录（`drivers/virtio/` 4 个文件里 5 个 + `drivers/s390/virtio/`、`drivers/remoteproc/`、`drivers/platform/mellanox/`、`arch/um/drivers/` 各 1 个）——★ 数「实现」要数**赋值点**而不是文件数，`virtio_pci_modern.c` 一个文件里有 2 个（`grep -rn 'struct virtio_config_ops [a-z_]* = {' --include=*.c .`）；`struct virtio_driver` 的实现散在 22 个（叶子）目录、25 个文件（`grep -rln "struct virtio_driver" --include=*.c . | xargs -n1 dirname | sort -u | wc -l`，口径区分见 04 模板）。

**(e) ★ 对端在哪，本文档集覆盖到哪为止**
- 明确写出对端是谁（QEMU / `drivers/vhost/` / 远端固件 / hypervisor）、**边界停在哪一行**。
- 这一段是路径 C 的独有必写项，配套 99 §5.5（见 methodology 第 26 条）。不写读者会以为整条路径都核对过了。

**(f) 与相近机制的对比**
- 表格对比职责边界（如 virtio vs vfio vs vdpa vs 直通）。

**(g) arm64 上的实际形态**
- ★ 注意**发现路径可能不止一条，且只有一部分走 DT**：`virtio,mmio` 有 DT 绑定（`Documentation/devicetree/bindings/virtio/mmio.yaml`，arm64 DTS 里 3 个文件在用），virtio-pci 走 PCI 枚举完全不碰 DT。分诊表放 06（见 06 模板）。

### §3 概念模型

- 用一张分层图把核心角色（如 controller/device/driver 或 adapter/client/driver）的关系画出来。
- 每层一句话定位。
- **指出哪些关系是设备模型的 device↔driver 匹配，哪些只是指针。**

### §4 核心数据结构速览

- 把 02 的结构体表压进来（表 + 一行说明）。
- 加命名规则表（"看到一个名字就知道它是什么"）。
- 加锁摘要（哪些锁、保护什么、字段行号）。

### §5 核心机制速览

- 把 03 的 Part A + Part B 压成"每个机制一句话 + 一个行号"。
- 排列顺序和 03 完全一致。
- 每节标题后标 `(03 §Ax/§Bx)`，让读者知道去 03 哪里看细节。
- 复习时读这节，要改代码去 03。

### §6 端到端调用路径

- 画一条从最常见的高层 API 到硬件寄存器写入的完整 ASCII 调用链。
- 每步标 `文件:行号`。
- **指出锁在哪层加、重试在哪层做、tracepoint 埋在哪层。**

### §7 与内核其它子系统的关系

- 表格列出与 driver model / DT / pinctrl / clk / regulator / 中断 / PM / regmap / ftrace / devres / debugfs / PREEMPT_RT 等的关系。
- 每行一句话 + 行号。

### §8 本文档集导读

- 每篇一句话定位。
- 按读者角色（只想用 / 要写控制器驱动 / 要看懂核心 / 要复核结论 / 隔了几个月复习）的阅读路径建议。

## 常见陷阱

1. **把 00 写成功能列表而非价值主张。** §1 要回答"帮你省掉了什么"，不是罗列功能。
2. **省略 §2 背景。** 这是最容易偷懒省掉的一节。硬件总线型必须讲透物理约束（开漏/推挽、CS/地址），否则读者无法理解锁、恢复、mux 的设计选择。框架型必须讲清问题域和核心抽象，否则读者无法理解框架为什么存在、替调用者屏蔽了什么。★ 虚拟总线型最容易在这里犯的错是**照抄路径 A 去编硬件细节**——它没有电气层，该写的是规范版本、feature 协商、字节序和 ABI 边界。
3. **§5 机制速览不标 03 章节号。** 不标 `(03 §Ax)` 读者就不知道去哪看细节，速览就变成了死胡同。
4. **§6 调用路径不标锁/tracepoint。** 端到端路径的价值在于"指出锁在哪层加、tracepoint 埋在哪层"，否则只是一棵调用树。
5. **§8 阅读路径不分角色。** 只列文件索引不够，要按"你想做什么"分路径。
6. ★ **路径 C 漏掉「对端在哪、覆盖到哪为止」那一段。** 少了它，整篇读起来像是把两侧都核对过了，而对端根本不在本树（见 methodology 第 26 条）。
7. **行号不验证。** 00 里的行号是最容易被后续 review 打脸的——因为 00 是浓缩篇，行号从 02/03 抄来时容易抄错。定稿前必须逐个 `sed` 打开核对。
