# 01-api.md 模板

> 质量基准：`output/i2c/01-api.md`（480 行）。每个子系统的 01 都应达到同等密度。

## §0 代码地图：四张子表缺一不可

### 0.1 核心文件表

四列：`文件 / 职责 / 本篇里对应的 API / 实现剖析`。

- "本篇里对应的 API"列让读者从文件反查到章节号
- "实现剖析"列指向 03 的对应 Part/§
- **不放逐文件行数**——行数只在 99 §2.1，对查 API 的读者无用

### 0.2 外围目录表

子系统特有的子目录（如 `busses/`、`muxes/`、`algos/`）。没有子目录时描述文件命名约定。

### 0.3 头文件映射表

三列：`头文件 / 面向 / 本篇引用它的小节`。

- 把"什么声明在哪个 .h"一次摊开
- uapi 头文件要说明"为什么在 uapi"——通常是用户态接口共享

### 0.4 Kconfig 表

三列：`选项 / 类型 / 效果`。

- **类型**写 bool/tristate/被 select
- **效果**写"编入哪个文件、关掉后什么后果"，不是重复 Kconfig 的 help 文本
- 表后加一段"容易搞错的"说明

## §1+ 对外 API：每张表后必须有解释性文字

表格三列 `API / 说明 / 备注` 不变，但表后要跟：

- **返回值语义**：成功/失败各返回什么、是否有"不是 0 也不是负数"的陷阱
- **struct 定义**：核心结构体贴出字段 + flags 表 + 代码示例
- **常见坑**：错误码多源、锁顺序、ERR_PTR vs NULL、上下文约束
- **回调约定子节**：控制器/驱动必须实现的回调表，标明"必需/可选"

## 用户态 API（如有）

ioctl 表四列：`ioctl / 值 / 参数 / 说明`。参数列保留实参类型。

## 错误码表

三列：`错误码 / 含义 / 谁产生`。表后跟一段给驱动作者的实操建议（哪些码必须正确返回、哪些码核心会自动重试）。

## 上下文速查表

末尾一张"想在这里调用→能用什么"的表，覆盖进程上下文、中断上下文、关机路径、slave 回调等场景。
