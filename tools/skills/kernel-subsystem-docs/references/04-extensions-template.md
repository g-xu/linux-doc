## 篇首声明

- 组织轴：一节一个独立框架，互不调用
- 分诊表：哪几个框架在目标架构（arm64）上真会碰到

## ★ 消费者散得很开时（几十个平级驱动），先给分布表再挑代表

有的子系统的"扩展"不是几个子框架，而是**几十个平级的设备驱动**：virtio 的
`struct virtio_driver` 的实现散在 22 个目录、25 个文件、跨 5 个顶层目录
（`drivers/` 20 文件、`net/` 2、`sound/` 1、`fs/` 1、`arch/` 1）：

```bash
grep -rln "struct virtio_driver" --include=*.c . | xargs -n1 dirname | sort -u | wc -l   # 22 个目录
grep -rln "struct virtio_driver" --include=*.c . | wc -l                                 # 25 个文件
grep -rln "struct virtio_driver" --include=*.c . | cut -d/ -f2 | sort | uniq -c          # 顶层分布
```

★ **三个口径要分清**：顶层目录数（5）说明"铺到内核的哪几个大区"，叶子目录数（22）说明
"覆盖多少个设备类别"，文件数（25）才是实现数的上界。写"散在 N 个目录"时必须说明是哪个口径，
否则读者复算时得到另一个数。这时候**硬凑"一节一个框架"会写成目录清单**。改法：

1. 先给一张**分布表**：顶层目录 × 该目录里有几个实现 × 这类设备是什么（块 / 网络 / console / GPU …）
2. 再按 03 时间线的挂载点分组，**每组挑一个代表**逐节展开（选法登记在 99 §2.2，判据同阶段 2 步骤 4.1）
3. 其余只讲契约：必须实现哪些回调、feature bits 怎么声明、probe 里必须做什么

分布表本身就是"这个子系统到底铺得多广"的答案，比逐个罗列有用。

## 每个框架的固定结构

1. **它是什么**：一句话定位
2. **挂在 03 时间线的哪一点**：明确挂载点
3. **核心数据结构**：贴字段 + 说明
4. **入口函数**：签名 + 调用关系
5. **陷阱列表**：使用这个框架容易踩的坑（至少 2-3 条）
6. **全树使用统计**：`grep -rn` 结果含调用点计数，不仅是"唯一"断言

## 字符设备框架的额外要求

如果子系统有字符设备（如 spidev、i2c-dev）：
- ioctl 实现流（不只是 ioctl 名称表）
- open/release 路径
- 与核心框架的数据交换路径

## ★ 篇末第二张表：每个框架的全树使用统计（强制）

一行一个框架，**每格都要有数字和能重跑的命令**：

| 框架 | 消费者/使用者 | 文件数 | 调用点或 DTS 节点数 | 重跑命令 |
|------|-------------|-------|-------------------|---------|
| spi-mem | 2（`drivers/mtd/spi-nor`、`drivers/spi/spi-mem.c` 的调用方） | 24 | 27 处赋值 | `grep -rln "spi_mem_" --include=*.c drivers/ \| wc -l` |
| spi-mux | 4 个 arm64 DTS（Microchip Sparx5） | 4 | 5 个节点 | `grep -rln "spi-mux" arch/arm64/boot/dts/` |
| loopback-test | 0（无 in-tree 使用者） | 0 | 0 | `grep -rn "spi_test" --include=*.c drivers/ \| grep -v loopback` |

这张表的价值不在读者，在编者：它把"到底有没有人用"从形容词变成数字，
**而填格子的过程本身就是查错器**——spi 那次的 spi-mux 错误正是填这张表时掉出来的。

「0 个使用者」是合法结果，但必须给出证明它为 0 的命令。

## 常见陷阱

- 把多个框架混在一节讲（应该一节一个框架）
- 全树 grep 只做框架自己的目录（应该 grep 全树，**使用者不一定住在框架目录下**，
  控制器驱动同理——spi-mem 的消费者在 `drivers/mtd/`）
- ★★ **否定性断言只过了一道门**。"树里没有 X 的实例"要过两道：
  ```bash
  grep -rn "<被否定的东西>" arch/arm64/boot/dts/   # 门 1：树里到底有没有
  grep -rn "<被否定的东西>" output/<子系统>/*.md    # 门 2：自己有没有在别处引用过它
  ```
  spi 实例：`04` 写"spi-mux 没有 in-tree arm64 实例"，而 `06 §2.4` 从初稿起就在引用其中一个节点。
  **两篇给出相反答案、各自内部却都自洽**，只有门 2 能发现
- ★ **"依据"栏写着"某命令输出为空"却没真跑**。这比写错结论更严重——读者理所当然认为它执行过了
- 只讲框架的 API 不讲陷阱（读者抄完代码就踩坑）
- 字符设备只列 ioctl 名称不讲实现流（读者不知道数据怎么走的）
