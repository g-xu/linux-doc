## §A. 26 条方法论原文

### 1. 先定基线

`git log -1` + `git status` 判断树是否干净、是否打了补丁；**如果打了补丁，必须先查清目标子系统有没有被改**。

i2c 实例：树有 175 个 RT 补丁改动 + `localversion-rt`，但 `git status --porcelain -- drivers/i2c include/linux/i2c.h ...` 空输出 → i2c 未被 RT 触碰 → 文档描述的是纯净上游代码。这一步推翻了一个自然猜测：`bus_lock` 是 `rt_mutex` 看似 RT 补丁改的，实际是上游 6.1 本来就是——为优先级继承。

### 2. 量规模

`wc -l` 定出核心/外围的边界。核心通常 5k~10k 行可以全读；驱动目录几万到十几万行只能讲契约。

i2c 实例：核心 7,326 行（全读），busses/ 133 个文件 89,120 行（只讲契约）。逐文件行数只留在 99（对"决定哪些文件要全读"有用），01 代码地图里只留文件名和职责。

### 3. 先读头文件

`include/linux/<subsys>.h` 或 `include/linux/<subsys>/*.h` 是最高信息密度的入口。数据结构和 API 全在这里，读完就有了骨架。

### 4. 再读核心 .c

按依赖顺序（base → 协议 → 扩展）。一等证据（逐行读完）和二等证据（只读符号表）的分界在 99 §2.1/§2.2 明确登记。

**驱动目录很大时要选代表驱动**，不要全读：一个最简实现（PIO / bit-bang）、一个全功能实现（DMA / 多队列）、一个本树 arm64 DTS 实际在用的。选法登记在 99 §2.2，其余驱动只讲契约。

### 5. 读 Documentation/<subsys>/

⚠️ **阻塞性前置步骤，必须在写任何文档之前完成。** 它给的是**设计意图和已知陷阱**，代码里读不出来。典型高价值内容：设计 rationale（如 clk 的 prepare/enable 分离、两把锁设计）、必选条件矩阵（如 clk 按硬件类型列出哪些回调必须实现）、核心模式的官方示范、内核参数（`clk_ignore_unused`、`threadirqs`）、故障码文档（`fault-codes.rst`、`*-topology.rst`）。

搜索路径：`Documentation/<subsys>/`、`Documentation/driver-api/<subsys>*`、`Documentation/devicetree/bindings/<subsys>/`。

注意三等证据的风险：内核文档偶尔落后于代码（如 clk.rst 仍用 `clk_register` 而非 `clk_hw_register`）。凡是冲突的地方以代码为准并显式指出不一致。

**在 99 §1 登记读了哪些文件、哪些内容被纳入、哪些因过时被标注。** 反向覆盖率用 `check_doc_coverage.sh` 查（§G）：官方文档里 0 次被引用的文件，要么补正文，要么在对应章节补一句"官方原文见 Documentation/…"。

### 6. 一开始就定死体系结构范围

默认 arm64-only。不是写完再删——它改变**读哪些文件**、**统计怎么做**、**举例用什么**（DTS 必须取自 `arch/arm64/boot/dts/`）。裁掉了什么要显式记下来，否则读者会当成遗漏。

i2c 实例：ACPI 枚举（847 行）直接不读，只在 04 §6 保留"存在另一条枚举路径"的一句话提及；SPD/DIMM 自动注册依赖 DMI，降为"提一句"。

### 6b. 判定子系统类型

决定后续模板怎么适配。三种类型：

| 类型 | 例子 | 判据 | 模板适配 |
|---|---|---|---|
| 硬件总线型 | i2c / spi / usb / pci / mmc | 有自己的 `bus_type` | 全套模板直接适用 |
| 框架型 | clk / pinctrl / irq / dma / regmap / iommu | 无 `bus_type`，被其他驱动通过 API 消费 | 02 改画"核心抽象↔消费者"；03 主轴是"注册/配置/回调"而非"传输"；04 没有子框架时并入 03；06 没有 DT 绑定时改讲替代配置机制 |
| ★ 虚拟总线 / 跨边界 ABI 型 | virtio / rpmsg / vdpa / vsock / xen 前端 | **有 `bus_type` 但没有电气层**；协议由树外规范定义，ABI 落在 `include/uapi/`；对端是 hypervisor / 远端固件 / 用户态 | 00 §2 走路径 C（规范背景）；02 加内存布局图 + "几层可插拔"；06 改发现路径分诊表；99 §5 加第五层「对端不在本树」（第 26 条） |
| 协议/网络型 | net / crypto / block | 设备是逻辑的，路径是"协议栈→驱动" | 05 角色枚举侧重协议层而非硬件层 |

**检测要分两道门，只跑第一道会把 virtio 误判成硬件总线型：**

```bash
rg 'struct bus_type' drivers/<subsys>/*.c include/linux/<subsys>*.h   # 门 1：有没有 bus_type
ls include/uapi/linux/<subsys>*.h | wc -l                             # 门 2：ABI 在不在 uapi
rg -n 'struct <subsys>_config_ops [a-z_]+ = \{' --include=*.c .        # 门 2：传输层有几个实现、住在哪
```

门 1 空 → 框架型/协议型；门 1 有 + 门 2 有 → 虚拟总线型；门 1 有 + 门 2 空 → 硬件总线型。

virtio 实例：`drivers/virtio/virtio.c:343` 确实有 `struct bus_type`，但 `include/uapi/linux/virtio_*.h` 有 27 个规范头文件，`virtio_config_ops` 有 9 个实现、散在 5 个目录——**"总线"在这里是一层软件抽象，底下的传输才是真硬件**。判定结果和两道门的实际输出都登记在 99 §1。

### 7. 设备树单独成篇，每条属性都要找到消费者

先建"谁消费什么"的三方分工表：通用 DT/驱动模型 / 子系统核心 / 具体控制器驱动。再对每个属性跑 `rg -n '"属性名"' drivers/<subsys>/`。**找不到消费者的属性就是死字**，而绑定文档不会告诉你（它只会说 "may not be supported by all drivers"）。举例一律用 in-tree 的真实节点，读者能 diff。

i2c 实例：`multi-master` 只有 3 个驱动读、核心不读；`smbus-alert` 布尔属性只有 1 个驱动读，真正创建 ARA 的是 `interrupt-names` 里的 `"smbus_alert"`——推翻了初始假设。`i2c_parse_fw_timings()` 调用点全在驱动里、核心不调用 → 那 8 个时序属性在不调它的驱动上完全是死字。

### 8. 索引工具只用来导航，不用来取证

宏生成的符号查不到（`TRACE_EVENT_FN`、`DEVICE_ATTR_RO`、`module_i2c_driver()` 等）；函数指针间接调用查不到（`algo->master_xfer`、`slave_cb`、`muxc->select` 等）。而内核的核心机制几乎全靠这两样。所以：**索引负责导航，`rg` + `Read` 负责取证。** cbm 的输出不作为任何等级的证据。

### 9. 每写一条因果链就回去确认一次

初稿阶段就有假设被源码推翻。逐篇 review 后暴露的数量级更大：

| 篇 | review 形式 | 修正数 |
|---|---|---|
| 00/01 | 用户提结构性意见 → 重排 | 各若干 |
| 02 | 用户提类比问题 → 补 §1.0 | 3 |
| 03 | 用户问"组织逻辑" → 全量重排 | 15 处陈旧引用 + 时间线次序 |
| 04 | 用户不熟 → **自审** | 19 |
| 05 | 用户不熟 → **自审** | ~20（含 3 个根本不存在的符号） |
| 06 | 用户说"读起来费劲" → 重排 | 15 处重排 + 5 处行号 |
| 07 | 用户不熟 → **自审** | 21（含 2 处凭空编造） |
| 99 | **自审本篇** | 6 |

两条结论：
- **初稿的错误率与"这一篇有没有人能提问"强相关**：用户不熟的篇靠自审，而自审抓出的错比用户 review 抓出的**更严重**——用户能发现"读不懂"，自审才能发现"根本不存在"
- **每一轮 review 自己会产生新的错误**：自审的对象必须包含自审这一轮新写的文字

### 9b. 内容审查要做 severity 分级

当用户要求"审查一下文档内容"时，按三类报告：

- **ERROR**：事实错误（函数不存在、返回值错、行为描述错、行号指向无关代码）
- **Minor imprecision**：行号偏差 1–2 行、范围略宽/略窄、措辞不精确但不影响理解
- **Unverifiable**：依赖外部规范或硬件手册、无法从本树源码直接验证

优先复查的高危论断：函数返回值（`-EBUSY` vs `-EOPNOTSUPP`）、引用计数（"不加引用"常错）、`__init` 标记、范围校验（仅上界还是上下界）、锁行为（等待 vs try-and-fail）、初始化顺序、宏展开实际设置了哪些字段。

文档集很大时可以每篇派一个 Agent 并行审查（每个 Agent 必须"全文读完 + 每个论断验证"），但**跨篇一致性和交叉验证必须由主 Agent 汇总**：同一论断改一处就要 grep 全文统一所有出现位置。

### 10. 老实记下没验证的部分

99 §5 的价值不低于前面九篇。必须四层分层记录：未编译/未运行的代码和命令、只读了符号表的函数、推断而非观察的结论、版本时效性。

### 11. 按"查询动作"而不是"内容类别"分篇

判断标准：**读者的一次提问，应该只落在一篇文档里。** 代码地图并入 01 §0（"找文件"和"找 API"是同一次查询）。00 定位为**复习入口**——把 02/03 的骨架浓缩进去，隔几个月回来只读 00 就能恢复全貌，要细节再按行号下钻。

### 12. API 篇表格固定三列：API / 说明 / 备注

统一规则只有一条：**「说明」一句话讲它做什么，其余全部进「备注」**——上下文标签（粗体前置的"可睡眠/不可睡眠/原子可用"）、返回值陷阱、参数类型提示、`inline`/宏、已废弃、arm64 不涉及。

### 13. 签名只写"函数名 + 形参名"，位置只精确到文件

- 签名不带类型：`i2c_transfer(adap, msgs, num)` 比 `int i2c_transfer(struct i2c_adapter *adap, ...)` 一屏能多看一倍。类型移进「备注」
- 逐 API 的 `文件:行号` 删掉，换成每节开头一行「头文件：…；实现：…」。行号在 API 篇是噪声，集中在 03 和 99 里维护
- 三个例外**不要动**：C 代码块（骨架示例必须能编译）、ioctl 表的"参数"列、本身是变量而非函数的符号

### 14. 数据结构篇开头必须先破歧义，再画图

图画得再全，也补不上一个没被显式否掉的错误类比。做法三步：
- **先否掉错误类比再讲正确的**（"不是 device↔driver，它等同于 `file_operations`"），比只正面陈述有效
- **用对比表把"是不是 struct device / 注册到哪条总线 / 会不会绑 driver"逐行摊开**
- **把"为什么不会发生"也找到代码依据**。否定性论断同样要给行号

i2c 实例："适配器永不绑定 driver"不是推测，而是 `i2c_verify_client()` 的 `dev->type` 判断（`drivers/i2c/i2c-core-base.c:725-730`）+ `i2c_device_probe()` 里 `if (!client) return 0;`（`:496-497`）两处代码保证的。

### 15. 每个模块都要交代"它和它的父总线是什么关系"

子系统总线几乎都是"控制器在 platform 总线上、设备在子系统总线上、两者只由 `dev.parent` 缝在一起"。三个必查点：
- 控制器 DT 节点由谁变成设备（`of_platform_populate` 还是子系统自己的扫描函数）
- 子节点会不会被 platform 层继续下钻（查 `of_default_bus_match_table[]`，不在表里就不会）
- 两条总线的连接点具体是哪一行赋值

**没有自己 bus_type 的子系统**（clk / pinctrl / regmap）改为讲：核心抽象与消费者的关系，以及消费者如何获取子系统服务（`of_parse_phandle` → provider 查表 → 拿到句柄）。

### 16. 组织轴要显式声明，正文必须真的按那个轴排

- 一篇文档只承诺一条主轴，其余内容显式分区。分区用 A/B/C 前缀写进章节号，引用自带"在哪条轴上"的信息
- 长文档（800+ 行）开篇必须有导航节：分层图 + 生命周期时间线图 + "哪些内容不在本篇"的去处表
- **时间线的顺序要用代码验证**：判据是"谁调用谁"，排完检查别处有没有抄走同一个错误次序
- Part A 主流程表必须含拆除 / unregister 路径，不能只写注册
- Part C 评价必须列源码里的设计债（REVISIT / FIXME / TODO 注释）

### 17. "框架篇"（04）没有读者能提的问题，就自己当红队逐条回验

四条规律：
- **错误全部集中在"写了概述、没有逐字引用源码"的段落**。判断标准不是"我理解得对不对"，而是"我有没有把源码原样搬过来"——理解可以对，概述仍然会漏掉决定性的那半句
- **表格里的"—"和"可配"是欠债的记号，必须清掉**。同一类记号还有**含糊词**："`xxx.dts:42-70` 一带"、"`:100` 附近"、"从 `:55` 起"、"20+ 个"——它们都表示"我没去把边界确认到底"。改法是回去把准确范围/数字取出来（`awk` 定区间见 §H），取不到就写清取不到的原因
- **"全树唯一 / 没有一个 / 只有 X 这么用"这类全称断言，必须在整棵树上 grep**。框架的使用者不一定住在框架自己的目录下——**控制器驱动同理**（SPI 的 bitbang 使用者散在 `drivers/spi/` 之外，spi-mem 的消费者在 `drivers/mtd/`）。检查动作：`grep -rn "<框架入口函数>(" --include=*.c | grep -v <框架自己的目录>`
- ★★ **否定性断言要过两道门，不是一道**。第一道是全树 grep，第二道是 **grep 自己的文档集**——如果姊妹篇正在引用你说"树里没有"的那个东西，两篇里必有一篇是错的：
  ```bash
  grep -rn "<被否定的东西>" arch/arm64/boot/dts/   # 门 1：树里到底有没有
  grep -rn "<被否定的东西>" output/<子系统>/*.md    # 门 2：自己有没有在别处引用过它
  ```
  spi 实例：`04` 写"spi-mux 没有 in-tree arm64 实例"，而 `06 §2.4` 从初稿起就一直在引用 `sparx5_pcb125.dts` 里的 spi-mux 节点（全树共 4 文件 / 5 节点）。**两篇文档给出相反答案，各自内部却都自洽**，只有门 2 能发现
- ★ **"依据"栏里写"某命令输出为空"，必须在写下这句话的当下真跑一遍**。这类文本比结论本身更容易蒙人——读者理所当然地认为它执行过了。写"为空"而实际有输出，是伪造依据，比写错结论更严重
- **反例要老实留在文档里**——它把结论的方向性钉准了（A⇒B 成立，B⇒A 不成立）

组织上还有四条硬要求：组织轴是"一节一个独立框架、互不调用"，要在篇首声明并给一张"哪几个在 arm64 上真会碰到"的分诊表；每个框架都要交代它挂在 03 时间线的哪一点上；篇末必须有汇总表（框架 × 职责 × 挂载点 × arm64 是否相关）。

第四条：**篇末汇总表旁边再放一张「每个框架的全树使用统计」表**，一行一个框架，列 = 消费者数 / 文件数 / 调用点或节点数 / **重跑命令**。这张表的价值不在读者，在编者：它把每个框架的"到底有没有人用"从形容词变成数字，而填格子的过程本身就是查错器（spi 那次的 spi-mux 错误正是填这张表时掉出来的）。"0 个使用者"是合法结果，但必须给出证明它为 0 的那条命令。

### 18. "示例篇"（05）的自审动作：先验符号存在性，再验行号

05 是唯一会被读者直接抄进代码的篇，错误代价最高。额外动作：把正文里出现的每个内核函数名/宏名/标志名/内核打印的字符串，都跑一次全树 grep 确认本版本存在。空结果 = 幻觉，不管你多确信。

四条规律：
- **检查动作固定**：`grep -rn "<符号名>" --include=*.c --include=*.h`（含 `include/`）。注意 grep 的 **tab 陷阱**：内核头文件里 `#define` 和宏名之间常是一个 TAB，`grep "define SPI_NBITS"` 返回空并不代表符号不存在。固定写法 `grep -nE "define[[:space:]]+SPI_NBITS"`
- ★ **"符号存在"不等于"读者能用"**。判据是 `EXPORT_SYMBOL*` **加上**头文件里有声明，**不是"有没有 kerneldoc 注释"**。一个写满 kerneldoc 却 `static`、不导出、不在头文件里的内部函数，比一个没注释的函数更危险——它长得像公开 API。spi 实例：`spi_async_locked()`（`drivers/spi/spi.c:4114`）有完整 kerneldoc（`:4083-4113`），却是 `static`、`spi.h` 里查不到、全树唯一调用者是同文件的 `:4226`
- **"名字很像"是高危信号**：近邻符号要成对写进文档并点明区别。★ 光靠"在各节陷阱表里顺手提一句"不够——**05 必须有一节专门装它**（`§N 近邻符号区分：名字很像，行为不一样`），一组一小节，每组给"错用会怎样"。散在各处的等于没有入口，读者要先知道有坑才找得到
- ★ **"X 是 Y 的别名"这句话不许直接写**，必须打开定义把它落到具体机制上。改名期的子系统里至少有四种形式，只有两种真的是"一份代码"：

  | 形式 | 长相 | 会不会分叉 |
  |---|---|---|
  | (1) `#define` 兼容层 | `#define spi_master_get spi_controller_get` | 不会（一份代码） |
  | (2) 平行独立 inline / 平行导出函数 | `spi_alloc_master()` 与 `spi_alloc_host()` 各自实现、各自 `EXPORT_SYMBOL_GPL` | ★★ **会**（两份独立代码） |
  | (3) 真实重复字段 | `spi_device.master` 与 `.controller` 两个成员，赋值处同时写两遍 | 会（靠一行同步维持一致） |
  | (4) `union` 同址双名 | `union { ctlr->slave; ctlr->target; }` | 不会（一份存储） |

  形式 (2) 是真陷阱：两份代码可以各自演进。而且**上层不一定跟着 union 走**——`spi_controller_is_slave()` 和 `spi_controller_is_target()` 是两个逐字相同、互不调用的 inline
- **示例篇最容易积攒跨篇陈旧引用**：自审必须包含一遍交叉引用回访（跑 `check_xrefs.py`）
- **同一个数字在不同路径上未必是同一个意思**：写"上限/编码"类事实时要问"哪条路径上的？超了会怎样？"。同名标志也一样：`SPI_NO_TX`（`spi->mode` 的 BIT(31)）和 `SPI_CONTROLLER_NO_TX`（`ctlr->flags` 的 BIT(2)）**不是新旧名，是两个不同对象上的两件事**
- **"被引用的地方" ≠ "调用者"**：`static inline` 包装函数的 grep 命中里混着声明、`EXPORT_SYMBOL` 行、头文件注释。数调用点要排掉这些，或者直接用"文件数 / 赋值点数"这种能重跑的口径

另外：篇首必须声明"骨架未编译"，别把免责声明只放在 99；篇首枚举本子系统有哪些角色，每个角色一节，不能漏。

### 19. "内容对但读不懂"是一类独立的缺陷，要单独走一遍重排

重排轮**只换承载形式，事实一条不动**；顺手发现的行号错另立一张表，下一轮再改。五种"费劲"形态的固定改法见 **§C**。

最后：**重排会动章节号，所以重排轮结束必须跑 `check_xrefs.py`。**

### 20. "调试篇"（07）自审对象是输出本身

整篇都在教读者"去看某个输出"，所以自审的对象是那些输出本身，不是文档的措辞。六条固定检查动作见 **§D**。

### 21. 取证篇（99）也要自审，但失效方式是"过期"而不是"写错"

四条固定动作：

**(1) 把本篇里所有可机械复现的东西全部重跑一遍。** 基线命令、规模统计、能力普查、工具版本、文档行数、自陈问题行号。**只要有一个数字对不上，整篇从"取证"降级成"回忆"。**

**(2) 每轮补读之后要回来升级证据等级。** 判据：本轮新引用的行号，有没有落在本篇登记的"详读范围"之外？落在外面就说明范围变了。这条最容易漏。

**(3) 跨篇引用要用脚本查，不能靠手工回访。** 手工回访会漏，脚本不会。i2c 那次 97 条引用里，手工自认为查过的 3 条恰好就是失效的那 3 条——脚本一跑就出来了（`00-overview.md:297` 和 `07-debug.md:467` 都还指着重排前的 `03 §6`）。三个脚本见 **§G**。

**(4) 一等/二等证据的分界线本身要写清"为什么"。** 读者据此决定哪些结论可以直接用、哪些要自己再确认。所以"只读了符号表"必须落到具体函数和行号区间。

### 22. ★★ 收拢成一张必须填满的表，比再读一遍更能查出错

十篇写完之后，"再通读一遍"的边际收益迅速趋零——**因为流水的正文可以蒙混过关，空格子不能**。所以自审后期要把散落在各篇的同类判断强行收进表格，一行一个对象，每列都必须有值：

| 收什么 | 收成什么表 | 在 spi 那次抓出了什么 |
|---|---|---|
| 每个子框架的使用情况 | 框架 × 消费者数 × 文件数 × 重跑命令（§A17） | spi-mux 的 arm64 实例断言写反了 |
| 每组近邻符号 | 符号 A × 符号 B × 区别 × 错用后果（§A18） | `spi_async_locked` 有 kerneldoc 但不导出 |
| 每个"X 是 Y 的别名"的说法 | 名字 × 机制形式 × 会不会分叉（§A18 四形式表） | 漏掉了第四种（`union` 同址） |
| 篇末的跨篇引用汇总 | 去哪篇 × 哪一节 × 讲什么 | 同一条 §3.5→§3.6 的错引用在同篇里出现了两次 |

spi 那次自审后期修的四个内容错，**四个全部是填格子时掉出来的，没有一个来自重读正文**。

配套的两条动作：

- **跨篇数字与断言对账要单独走一轮**，不能指望顺手统一。做法：把同一个事实在全篇的所有出现位置 `grep` 出来并排看（"三种形式"→ 发现四篇都写着三）。改一处必须 `grep` 全集，包括**同一篇内部**——spi 那次 `05` 的开篇和篇末表引用了同一个章节号，第一轮只改了开篇
- **一条引用可以"有效但指错"**：章节号真实存在，只是不讲那件事。`check_xrefs.py` 天然抓不到这类，只能靠对账轮

### 23. 已经摸清一条改名线，不代表机制清单完整了——显式换一条线再走一遍

改名期的子系统里，同一次重命名在不同字段上可能用了不同手法。摸清 `master→controller` 那条线之后，**必须显式挑另一条线（如 `slave→target`）从头走一遍**，否则会把"我见过的形式"当成"存在的形式"。

spi 实例：`master→controller` 线上出现了 `#define` / 平行 inline / 重复字段三种形式，据此写了"三种形式"并同步进四篇文档；直到查 `slave→target` 线才发现第四种（`union` 同址双名，`include/linux/spi/spi.h:561-566`、`:679-682`）。**发现新形式后要回去改的是所有说"共 N 种"的地方**（见第 22 条的对账轮）。

顺带一条：同一批标志位的命名可能有三种情况并存——双名（新旧都在）、**只有旧名**、**只有新名**。别假设改名是齐刷刷的。

### 24. 跟另一套文档集比对时，先写完自己的，再读对方

用另一套独立生成的文档集（别人做的、或者换个工具重做的）当参照，是很强的查错手段，但**读的顺序决定它还有没有效**：先读对方就没有独立对照了，只剩下抄。固定协议：

1. 自己按 skill 从头生成一遍，自审跑完，三个脚本全绿
2. **然后**才读对方，逐篇 diff
3. 对方赢的地方，分两类落地：**吸收**（补进自己的文档 + 回写 skill）和**明确不吸收**（把权衡理由写进 99，以免下次又"发现"一遍）
4. 对方的错误也要记录——★★ **两套独立产出写了同一句错话，标记的不是谁粗心，而是源码本身在这里有歧义**，这种地方要在文档里显式写"为什么容易看错"

pinctrl 那轮对照又补出三条可复用的：

5. ★★ **"对方有一节我没有"最常见的原因不是漏了，而是拆到了别的篇。** 判断"是不是真漏"的唯一办法是拿对方那一节里的**事实清单**（不是章节名）去 grep 自己的全套文档。pinctrl 那轮按章节名看有 6 个缺口，按事实清单查下来只有 3 个是真的（另 3 个分别落在本套的 05 §5、07 §0+§6、05 §1.7 里，而且更细）
6. ★★ **对方最大的贡献往往不是"补了一节"，而是"逼你发现自己有一句话说宽了"。** pinctrl 那轮对方只提了一句 PREEMPT_RT，本套原来的结论「没有额外风险」经不起追问：核心成立（只有 mutex），驱动不成立（18 个文件用 `raw_spinlock`，RT 上不转换）。**先写完再对照的收益就在这里**——先看了对方的，大概会直接抄一句"驱动用 raw_spinlock"，不会去查那两个数和实际临界区
7. **引用对方文档的章节号，写法必须和引用本套区分开**：本套写 `` `NN-xxx.md` §X ``，对方写「对方 NN 篇 §X」。否则 `check_xrefs.py` 会拿对方的章节号去本套里找，报一堆假失效（pinctrl 那轮 4 条）。★ 注意这**不算假阳性、不要登记进 `.xref-ignore`**——读者也会以为那是本套的章节，是写法本身有歧义

### 25. 拿别的子系统文档集当模板，会把它的文件名一起拖过来

复用骨架很划算，但残留物是**别的子系统的路径**（spi 文档里出现 `i2c-core-of.c`）。这类错误肉眼扫不出来，因为它在语法和语义上都通顺。**只有 `check_line_refs.py` 的 UNRESOLVED 能抓到**——所以从模板起草的文档集，收尾必须跑它，且不能把 UNRESOLVED 当成"脚本认不出的简写"随手忽略掉。

同理，程序化批量改过文档之后（脚本插行号、批量替换章节号），要机械检查一遍**代码围栏配对**和**围栏内是否混进了 markdown 标记**。

### 26. ★ 有的子系统的知识边界不在本树里——必须把边界画出来，而不是让它悄悄消失

前七套文档集（i2c / spi / pinctrl / clk / gpio / irq / dma）有一个共同前提：**要解释的东西全在这棵树里**。对端型子系统不成立：

| 子系统 | 对端是谁 | 对端实现在哪 |
|---|---|---|
| virtio | 后端设备（device 侧） | QEMU / `drivers/vhost/` / DPU 固件——**不在本子系统目录里** |
| rpmsg | 远端处理器上的固件 | 厂商固件二进制，树里完全没有 |
| vdpa | 硬件或软件 datapath | 厂商驱动 + 硬件 |
| vsock / xen 前端 | 宿主机侧 | hypervisor |

三条固定动作：

1. **00 §2 讲规范，不讲硬件**（路径 C）。这类子系统的"物理约束"换成了**规范约束**：协议版本、feature 协商、字节序、ABI 兼容性。规范本身是三等证据里的新一档（不是 `Documentation/`，是树外规范文本），要在 99 §2.3 单列
2. **`include/uapi/` 是 ABI 边界，不是普通头文件**。改一个字节就破协议——文档必须显式指出"这些头文件是与对端共享的契约"。检查动作 `ls include/uapi/linux/<subsys>*.h`（virtio 27 个）
3. ★★ **99 §5 加第五层未验证项：「对端行为未验证，因为对端不在本树」**。否则读者会以为整条路径都被核对过了。写清楚**边界具体停在哪一行**（例如"到 `virtqueue_kick()` 写下 notify 寄存器为止；对端读到之后做什么，本文档集不覆盖"）

反过来也是一条正面收获：这类子系统的**"谁写谁读"必须逐字段标注**，因为共享内存两侧都会写（见 02 模板的内存布局图要求）。

## §B. 假阳性处理

纠错型文档里，"错值"和"旧值"是内容的一部分。99 §3 的变更记录会写"原来引的是 `03 §7`，现在改成 §A7"，机械检查器必然把那个老编号报成失效引用。这不是缺陷，是内容。

处理办法：**把假阳性逐条登记在忽略文件里并写明理由**，而不是改文档去迁就脚本。下次跑出同样几条直接跳过，跑出第 N+1 条就说明真出了新问题。

两个忽略文件放在文档目录下（跟着文档走，不跟着 skill 走）：

```
output/<子系统>/.xref-ignore      每行 `源篇号->目标篇号 §章节号`，如 99->03 §7
output/<子系统>/.lineref-ignore   每行 `路径:行号`，如 i2c-core-base.c:9999
```

两个文件都支持 `#` 注释。**注释里必须写清为什么它是假阳性**——否则半年后没人分得清"已确认无害"和"当初懒得改"。

i2c 实例：`.xref-ignore` 里两条（`99->03 §7`、`99->03 §7.4`），理由是 99 §3 变更记录和 §6.1 假阳性登记表必须原样保留老编号，否则读者看不出改了什么。

### ★★ 固定动作：只要在 99 里"引用了一条失效引用"，立刻重跑脚本并登记

这不是建议，是流程里的一步——**它在 spi 那次犯了两遍**：写 99 §6.1「失效引用长什么样」的例子表时引入 4 条新假阳性；后来写 §8.2「对方文档集的失效引用清单」时又引入 4 条。两次都是同一个机理：

> 你在文档里**引用**一条坏引用作为例子，脚本无法区分"举例"和"真引用"，于是它变成一条新的失败。

所以顺序固定为：写完这类表格 → **立刻**跑 `check_xrefs.py` → 处理新增的几条。

`check_xrefs.py` 的归属判据是**同一行里最近出现的文档名**，因此最容易踩的写法是"表格单元格里同时出现别篇文件名和本篇章节号"（spi 那次第三遍是这么犯的：表格左栏 `05-usage-template.md`、右栏本篇的 `§8.3` → 被算成 `05 §8.3`；★ 第四遍犯在**解释第三遍的那段正文里**——为了讲清楚，正文原样写出了那个文件名和那个小节号）。

★★ **处置有优先级，登记是第二选择**：

1. **先试着消除触发条件**——左栏写 `05-usage-template`（去掉 `.md`）、把"见下面的 §5.1.1"改成"见下一小节 5.1.1"、把文件名和章节号拆到两列。误报归零，读者读到的信息一个字没少
2. 只有当**内容本身必须保留那个老编号**（§3 变更记录、失效引用示例表）时，才登记进 `.xref-ignore`

而且**误报往往说明原文确实有歧义**："见下面的 §5.1.1"这句话，人读到这里也得先愣一下才知道是哪一篇的 §5.1.1。所以第 1 条不只是在讨好脚本，它同时改善了可读性。

### ★★ 同一个自指陷阱有第三种形态：99 §7 照抄脚本输出

99 §7 要报告脚本的自检结果，最自然的写法是把脚本的失败行**原样贴进来**。但脚本下一轮会把这段引述当成新的引用再解析一次——**你在文档里描述失败，就制造了失败**。pinctrl 那轮踩了两次（引述 `.xref-ignore` 的两条条目、引述"某篇某行指向不存在的小节"）。

固定做法：**只描述，不照抄脚本的失败行格式**。写「源是 03 篇，目标分别是 06 和 07，章节号是 §A7 与 §B7」而不是把 `03->06 §A7` 贴出来。

同理还有一条**跨脚本**的形态：`grep -c` 的原生输出是 `文件名:数字`，这个形状和 `路径:行号` 一模一样，直接贴进 99 §2 的统计命令注释里，会被 `check_line_refs.py` 当成越界的行号引用。**统计结果一律改写成 `文件名 → 数字`。**

### ★★ 第四种形态：99 §9 引用**对照套**的章节号

规则 29 的对照节要引用另一套文档集的章节（「对方 07 §2.3 那条」）。`check_xrefs.py` 会把「NN §X」一律当成指向**本套**的引用去校验，而对照套的章节号在本套里往往不存在 → 必然失效。

固定做法：**引用对照套时在篇号和 `§` 之间加一个"的"**——写「对照套 07 的 §2.3」。脚本的 `XREF_BARE` 要求 `(\d{2})\s*§`，中间有汉字就不匹配，于是自动跳过；**不必登记忽略项**。引用本套时才写「NN §X」。这条约定顺带让正文更清楚：读者一眼能分出"这是我们自己的"还是"这是对方的"。

同理，引用对照套时**不要写出 `NN-name.md` 形式的文件名**（`XREF_MD` 会匹配它），写「对照套 07」即可。

★ 还有一条相关的：**xref 命中总数里含 99 篇自己的引用**（§3 逐篇取证表、§9 对照表都在引用别篇），所以改 99 的正文会让这个数字变动。定稿时重跑到收敛为止，别只跑一次就把数字抄进去。

## §C. 重排轮：五种"费劲"形态与固定改法

| # | 形态 | 固定改法 | 判据 |
|---|---|---|---|
| 1 | 一个表格单元格里塞了两三件事 | 拆列，或把其中一类移到表外成段落 | **一个单元格如果需要用"；"或括号连接两个不同来源的事实，就该拆** |
| 2 | 散文在描述 if/else | 画决策树，并在危险的那条岔路上标 ★、写清后果 | 段落里出现两个以上"如果…则…" |
| 3 | 链式"否则…否则…"的 ASCII 图 | 改成优先级表（一行一个条件 + 结果 + 行号） | **ASCII 图适合画结构，不适合画优先级** |
| 4 | 一句话里同时挂着行号、日志文案和触发条件 | 按"是什么 / 谁不做什么 / 所以怎样"拆成 2–3 句编号 | 一句话里有 ≥3 个可独立验证的事实 |
| 5 | 同一类东西有 N 种写法却没有选型入口 | 先给一张选型表再展开细节 | 读者读完不知道该用哪个 |

另外三条结构性动作：

- **篇首加「按任务找章节」表**。入口应该是**动作**（"我要挂一颗芯片"），不是章节号
- **散落各节的同类事实要抽一张总表放前面**（如 06 §1.1「核心真正会读的属性」总表，必须有"写在哪个节点"一列，后面每节是它的一行展开）
- **症状清单超过 8 行就按"坏掉的范围"分组**（总线级 / 单设备级 / 参数级 / 拓扑级）。分组顺序本身就是排查顺序

06 的定位章另有固定分层：按「编译期 / 运行期静态 / 运行期动态」三层组织，并且必须有「错误消息 → 原因」映射表。

## §D. 调试篇（07）八条固定检查动作

**(1) 每条日志都要查级别，而不只是查文案存在。** 把 `dev_err` / `dev_warn` / `dev_dbg` / `pr_debug` / `WARN` / `dev_err_ratelimited` 当成**六个不同的可见性等级**逐条标注。两个特例：`WARN()` 会带栈回溯（读者会以为是 panic）；带"打印一次"标志的（如 `I2C_ALF_SUSPEND_REPORTED`）**一个对象一生只打一次**，复现时看不到第二遍。绝不能笼统写"始终输出"。

**(2) 可写的调试文件，写进去的值是什么意思必须从 setter 里读出来。** 同名"debugfs 数值文件"之间没有任何统一约定，必须逐个读。

**(3) 一个调试开关往往有多道互相独立的门，要全部列出。** `module_param()` 的权限位决定有没有 sysfs 文件；`#ifdef DEBUG` 决定代码在不在；用 `dev_dbg` 还是裸 `printk` 决定受不受 dynamic_debug 管。三者两两独立。

**(4) 错误码表的每一行都要点名"哪个函数返回它"。** 会顺带发现三件事：同一个错误码有多个来源（语义各不相同，要按语义分组展开 top-N，不能只罗列行号）、归错主、以及**错误码被中途改写**的路径（如 `i2c_recover_bus()` 把 `-EOPNOTSUPP` 改写成 0——"恢复成功"是假的）。

**(5) tracepoint 要连 `TP_CONDITION` 和字段清单一起读。** 三件事全靠它：哪些情况根本不触发、循环上界是失败前还是失败后的计数、同名字段在不同事件里未必同义。**事件组级过滤有静默陷阱**：套不上的事件会被静默改成"无过滤全量输出"，而写入还返回成功。

**(6) 示例命令的输出是和内核字符串同等级的事实，绝对不能编。** 凡是"读者会拿去 grep 或比对的字符串"，都要有出处。适配器名这类东西还有个额外坑：它本来就不固定（固定串 / `dev_name()` / `pdev->name` / `snprintf` 格式串四种写法并存），正确做法是先说明它为什么不固定，再给一个有行号的实例。

**(7) ★★ 成对 tracepoint 的"配对缺失"不能当失败信号用，除非逐字确认两个打点之间存在提前退出路径。** 有 `X` / `X_complete` 打点的子系统（clk / regulator / cpufreq 都有）很容易让人推出「只看到 `X` 没看到 `X_complete` ⇒ 中途失败了」——**这是从正确观察推出的错误结论**。固定检查动作：`sed` 打开 entry 与 `_complete` 之间的全部行，找 `return` / `goto` / `break`；**一行都没有就说明这个信号不存在**，必须在文档里显式否掉它，否则读者会得到"每次都配对，所以从来没失败"的假安心。

顺着这条往下查还有更大的收获：**提交阶段的函数很可能是 `void`**。clk 的 `clk_change_rate` 就是 `static void`（`drivers/clk/clk.c:2318`），`.set_rate` 的返回值是裸调用不接（`:2367-2368`），上层也不检查（`:2473`）。于是「`clk_set_rate()` 返回 0」只证明协商阶段通过，**不证明寄存器写成功**——这是错误码表照不到的一整片区域。**凡是"协商 + 提交"两阶段的子系统都要查一遍提交阶段的返回值通道。**

**(8) ★★ "故障注入"一节即使结论是"本子系统没有"也必须写。** "没有"本身是结论：它决定了读者**能不能测错误路径**。省掉这一节，读者会当成遗漏。固定动作：`/usr/bin/grep -rnE 'fault_inject|should_fail|DECLARE_FAULT_ATTR' <子系统目录>`，空结果就写"没有"，然后给出替代手段（KUnit / 改回调重编 / 反向开关对照）以及**替代手段的不对称之处**（如 clk 的 `clk_ignore_unused` 只能让批量关闭整体不发生，无法只对某一个时钟发生）。

> ★★ 更一般的规则：**模板里每一条都要走一遍，"这个子系统没有"不是跳过的理由。** clk 那轮漏掉故障注入节，是靠和另一套文档集对照才发现的——而对照不是每次都有。

子系统有字符设备时，07 还必须有用户态工具节 + 篇末一页速查。

## §E. 类比库（08 费曼篇用）

### 怎么给一个新子系统造类比

类比不是装饰，是**把读者已有的直觉借过来**。三条选材标准：

1. **借来的直觉必须包含要解释的那个结构关系**，而不只是气氛相近。"餐厅和菜谱"能用，是因为"多家门店共享一份 SOP"恰好就是 N 个 adapter 共享一个 algorithm 的形状
2. **类比要能被推翻**。写完立刻问"顺着这个类比往下推，第一个推错的结论是什么"——那句话就是"什么时候这个类比会误导你"段落的内容。**推不出误导点，说明类比太泛，换一个**
3. **类比之后必须落到带行号的源码**，文件路径写全。只讲故事不给行号的费曼篇是散文，不是文档

### i2c 实例库（八个主题，可作选材参考）

| 主题 | 类比 | 借来的直觉 | 类比的边界 |
|---|---|---|---|
| adapter ↔ algorithm 是什么关系 | 三家肯德基门店 + 一份 SOP | 多个实例共享一份操作流程，实例各有门牌/排队/水电，流程只有一份 | SOP 是死的，`algo` 里的函数指针可以在 probe 时按硬件能力换掉 |
| adapter 为什么注册在 i2c_bus_type 上 | USB hub | 一个东西同时是"上级总线的设备"和"下级的总线接口"，所以要两条路 | hub 自己会被 hub 驱动绑定，i2c adapter 的 `struct device` 永远不绑 driver |
| adapter 为什么不会被 driver 绑定 | 交警只拦车查驾照，不给马路发驾照 | 同一条总线上并存两类对象，只有一类需要 driver | 判据不是"看起来像不像车"，是 `dev->type` 指针相等 |
| bus_lock 为什么是 rt_mutex | 检查室里的普通病人被临时升级为急诊优先级 | 优先级继承：等待者的高优先级借给持锁者 | 继承的是调度优先级，不是"插队权"；传输本身还是要走完 |
| mux-locked ↔ parent-locked | 一个大厨房 vs 四个带门的小隔间 | 锁粒度：整条 parent 总线 vs 单个子通道 | **mux-locked 是一种让步，不是一种优化**——能用免锁变体的 mux 反而选 parent-locked |
| SMBus 仿真为什么有两条路 | 万能遥控器把按钮翻译成红外脉冲 | 高层语义操作可以由底层原语拼出来 | `-EOPNOTSUPP` 在这条路上不是错误，是"换另一条路"的信号 |
| i2c-dev 的匿名 client | 银行的临时排队号，不给你开正式账户 | 有的对象只需要一次性身份，不进设备模型 | 它仍然是完整的 `struct i2c_client`，只是没 `device_register()` |
| i2c_lock_addr ↔ i2c_check_addr_busy | 会议室预约：防重复点击 vs 查是否已被占 | 并发瞬间保护 ≠ 持续占用检查 | 前者的位图在预订完成后就清掉，不代表"没被占" |

### 结构模板（每个主题四段）

```
## §N <问题标题>            ← 只写要说明的问题，类比不进标题
### 先举个例子              ← 日常类比，可以多说几句，不必硬凑一句话
### 回到代码 / 代码在哪      ← 带行号，路径写全，不能裸 :N
### 什么时候这个类比会误导你？ ← 一个真实的技术差异，不是"当然类比不完美"
```

主题数下限 ≥6；篇末给"阅读下一篇"导航表。用户说"用大白话解释""为什么是这样""举例子""我理解不了 X"时产出这一篇。

### 自审重点

08 的自审重点是**类比边界**，不是行号精度。三件事：
- 标题里没有夹带类比
- "什么时候这个类比会误导你"确实指出了一个真实的技术差异，能落到代码上；泛泛而谈（"类比总是不精确的"）等于没写
- 类比里每个技术断言仍然要有行号——费曼篇不豁免取证

## §F. 证据等级定义

| 等级 | 来源 | 可靠度 |
|---|---|---|
| 一等 | 逐行读完的源码文件 | 直接观察，不是推断 |
| 二等 | 只读关键函数体 + 符号表（函数名+起始行） | "某函数在第 N 行"可靠，"某函数内部怎么做"只在读过的部分可靠 |
| 三等 | 内核文档 `Documentation/` | 对"设计意图"最权威，但偶尔落后于代码——冲突时以代码为准 |
| 推断 | 从代码语义或通用知识推出 | 必须标注为推断，不可当作观察 |

索引工具（cbm）的输出不作为任何等级的证据，只用于导航。

## §G. 三个批量自检脚本

都在 skill 的 `scripts/` 下，纯 stdlib，不依赖内核树以外的东西。**每次改完文档都跑，重排轮结束必须跑。**

```bash
S=.qoder/skills/kernel-subsystem-docs/scripts
D=output/<子系统>

python3 $S/check_xrefs.py     $D --ignore $D/.xref-ignore
python3 $S/check_line_refs.py $D . --ignore $D/.lineref-ignore
bash    $S/check_doc_coverage.sh <子系统> $D .
```

| 脚本 | 查什么 | 抓不到什么 |
|---|---|---|
| `check_xrefs.py` | 所有 `0X §Y` 跨篇引用是否指向真实存在的章节。认识 `06 §3.1`、`` `06-devicetree.md` §3.1 ``、`[…](03-internals.md) §B1.4` 三种写法，支持 A/B/C 前缀章节号 | 章节存在但内容已经不讲那件事了 |
| `check_line_refs.py` | 所有 `路径:行号` 是否越界。三级解析：全路径 → 靠文档自己的显式写法给简写名消歧 → 用已知前缀拼相对路径（迭代到不动点）。**UNRESOLVED 一栏还兼职抓"模板串味"**：从别的子系统文档集起草时残留的外来文件名（spi 文档里的 `i2c-core-of.c`）只有它能发现，别当成"认不出的简写"忽略掉 | **行号在范围内但指向无关代码**——这类只能逐个 `sed` 打开看 |
| `check_doc_coverage.sh` | 反向覆盖：`Documentation/<subsys>/` 等三处的每个 `.rst`/`.yaml` 在文档集里被引用了几次，0 次的列出来 | 引用了但引错了 |

两个设计要点，改脚本时别破坏：

- **简写文件名不按目录顺序猜。** 内核树里 `i2c.h` 有 12 个（17 行到 1092 行），随便取一个必然错。可靠判据是**文档在别处怎么写它的全路径**：`include/linux/i2c.h` 出现 78 次 vs `include/dt-bindings/i2c/i2c.h` 8 次 → 裸 `i2c.h` 按前者校验，并在 AMBIGUOUS 里报出用了哪个。早期版本按候选目录排序取第一个命中，制造了 7 条假的越界报告
- ★★ **`check_doc_coverage.sh` 报「【必查】共 0 篇，其中 0 篇 0 引用 → 必查档全部有引用」是假的通过。** 「共 0 篇」意味着它**一篇官方文档都没找到**，而输出把「0 篇 0 引用」和「0 篇」混成了同一句"通过"。pinctrl 就是这样：脚本按 `Documentation/**/*pinctrl*` 找，而主文档叫 **`pin-control.rst`**（带连字符，没有 pinctrl 字样），1467 行全被漏掉。**规则 6（先读官方文档）不能依赖这个脚本兜底**——每个子系统都要手工 `ls Documentation/driver-api/ | grep -i <关键字片段>` 确认一遍真实文件名，名字里有连字符、下划线、缩写的都会漏
- ★ **「被引用 N 篇」里可能有虚高的**：脚本按去掉后缀的**基名做子串匹配**，所以基名恰好是子系统名的那篇（`pinctrl.yaml`）会把正文里每一个 "pinctrl" 字样都算进去（pinctrl 那次是 3067 次）。看这一栏时只信基名"长得不像普通词"的那几个
- **`check_doc_coverage.sh` 的 0 引用有两种处置，不能一律当缺失。** (a) 内容确实没覆盖 → 补正文；(b) 覆盖了但没标出处 → 在对应章节补一句"官方原文见 Documentation/…"。i2c 那次三个 0 引用文件（`muxes/i2c-mux-gpio.rst`、`slave-eeprom-backend.rst`、`slave-testunit-backend.rst`）全是第二种

## §I. 计数与统计的纪律（★★ 最高频的错误来源）

文档里每一个数字都是一条可被读者一条命令推翻的论断，而计数出错**不会**被三个脚本中的任何一个抓到。pinctrl/spi 两轮自审里，数字类错误占了全部错误的一半以上。八条硬纪律：

| # | 纪律 | 反例（真实踩过的） |
|---|---|---|
| 1 | ★★ **统计范围必须显式列出文件，不能用 `drivers/<subsys>/*.c` 通配** | pinctrl 核心是 6 个文件，用通配会把 371 个控制器驱动一起扫进来：`-EINVAL` 从 47 变成 326，"错误码分布"这一节的全部结论作废 |
| 2 | ★★ **符号使用计数必须带 `grep -w`** | 数 `pinctrl_get` 的使用者，不带 `-w` 会把 `pinctrl_get_group_name`、`devm_pinctrl_get` 全算进去，结论方向都会反 |
| 3 | ★ **同名头文件必须写全路径** | `pinmux.h` 有两个：`drivers/pinctrl/pinmux.h`（168 行）和 `include/linux/pinctrl/pinmux.h`（85 行）。裸写 `pinmux.h:121` 时对时错，且 `check_line_refs.py` 的消歧结果会随文档内容变化而**翻转** |
| 4 | ★ **`grep -c` 数的是"含该串的行数"，不是"返回点数"** | 注释里的 `-EINVAL`、`if (ret == -EINVAL)` 这种比较位都会被算进去。要么逐行标出哪几处不是返回点，要么换成 `grep -n 'return -EINVAL'` |
| 5 | ★★ **子串包含关系会让两类被算成一类** | `grep -rl 'spinlock_t'` = 34，但 `raw_spinlock_t` 里含有 `spinlock_t` 这个子串，所以这 34 里包含了 18 个 raw 的。"另有 34 个用普通 spinlock" 是错的，正确算法是 `comm -23 <(...spinlock_t...) <(...raw_spinlock...)` = 17 |
| 6 | ★ **「不存在 / 全树唯一 / 一个都没有」这类论断本身也要 grep，而且要跨出子系统目录** | 「pinctrl 没有 tracepoint」要查到"整个 `drivers/pinctrl/` 只有 2 个文件命中 `trace_`，且都是 `mips_trace_clk`/`arm_trace_pins` 这种 JTAG 引脚组名字"这个精度，才叫验过 |
| 7 | ★★ **改了正文里的一个计数，必须回头改所有引用它的汇总表** | 计数类论断通常在 3–5 处出现（正文、篇末汇总表、00 速览、99 §2.3 命令注释）。判据：改完之后 `grep -rn '<旧数字>' output/<子系统>/` 必须为空 |
| 8 | ★★ **凡是同时给了数字和复现命令的地方，定稿前必须真跑一遍逐格对账** | 命令是后补的、数字是当时手数的——这两者对不上是常态。99 §2.3 的每一行都要跑一次，一个对不上，整篇从"取证"降级成"回忆" |

★ 还有两条不是计数、但同属"数字类"的：

- **位域打包宏必须读宏本体**，不能按直觉推字段次序（pinctrl 的 `PIN_CONF_PACKED` 是低位放 type 还是高位，猜错方向会让整节配置解析讲反）
- **内核打印的字符串必须回到源码逐字 grep**。文档里写"内核会报 `pin X already requested`"，实际字符串是 `pin %s already requested by %s; cannot claim for %s`——读者按你写的去 `dmesg | grep` 会搜不到。★ 而且同一句话可能在**多处**逐字重复（pinctrl 的这句在 `pinmux.c:129-131` 和 `:136-138` 各有一份，一份是 mux 抢占、一份是 GPIO 抢占），只写一处会让读者误判故障原因

## §H. 常用取证小配方

**函数的完整行号区间**（03 的章节标题要用）。从定义行找到第一个顶格 `}`：

```bash
awk '/^int spi_register_controller\(/{s=NR} s&&/^}/{print s"-"NR; exit}' drivers/spi/spi.c
```

两个坑：(1) 返回类型和函数名不在同一行的（`static struct spi_device *` 单独一行）匹配不到，要改成匹配函数名那一行再回退；(2) 批量跑的时候别把正则塞进 shell 函数里传递——`\(` 会被多层引用吃掉，报 `awk: invalid regexp`。批量场景直接写个 Python 脚本，比跟 shell 转义搏斗省事。

**`#define` 的 tab 陷阱**：内核头文件里 `#define` 与宏名之间常是 TAB，所以

```bash
grep -n "define SPI_NBITS"            # 可能返回空 —— 不代表符号不存在
grep -nE "define[[:space:]]+SPI_NBITS" # 正确写法
```

**判断一个符号读者能不能用**（不是"存不存在"）：

```bash
grep -nE "EXPORT_SYMBOL(_GPL)?\(spi_async_locked\)" drivers/spi/spi.c   # 有没有导出
grep -n "spi_async_locked" include/linux/spi/spi.h                      # 头文件里有没有声明
```

两条都空 = 内部函数，即使它有完整 kerneldoc（见 §A18）。
