## ★ §0 发现路径分诊表（篇首必写，先于任何属性表）

**不要先问「这个子系统有没有 DT 绑定」**——多数子系统是**多条发现路径并存，DT 只覆盖其中一部分**。
一行一条路径，读者先定位自己在哪条路上，再决定这篇要不要读：

| 发现路径 | 谁负责扫描/创建设备 | 走 DT 吗 | arm64 上用不用 | 本篇覆盖 |
|---|---|---|---|---|
| DT 节点 | `of_platform_populate` / 子系统自己的扫描函数 | ✔ | 常用 | 全篇 |
| ACPI | ACPI 枚举代码 | ✘ | 本文档集裁掉（arm64-only 声明） | 不覆盖，仅提一句 |
| 父总线枚举 | 如 PCI 探测（virtio-pci） | ✘ | 常用 | 不覆盖，指到 01/04 |
| 板级静态注册 | `*_board_info` / 平台代码 | ✘ | 少见 | 一句话 |
| 用户态/运行时 | sysfs、`module_param`、overlay、vdpa 管理接口 | 部分 | 视子系统 | §6 |

★ **子系统没有 DT 绑定时，本篇不是「删掉」，而是这张表只剩非 DT 行，正文改讲那些路径。**

virtio 实例：`virtio,mmio` 有绑定（`Documentation/devicetree/bindings/virtio/mmio.yaml`，
arm64 DTS 里 3 个文件在用），virtio-pci 完全不碰 DT，virtio-vdpa / remoteproc-virtio 又是另两条路。
**只写 DT 那条会让读者以为 virtio 设备都从 DT 来。**

## §4 定位章

三层定位：
- 编译期：DTS 编译时的校验（schema）
- 运行期静态：驱动 probe 时的校验
- 运行期动态：运行时的行为异常

症状清单按坏掉的范围分组（因子系统类型而异）：

**硬件总线型**（I2C / SPI / MMC 等）：
- 总线级：整条总线不工作
- 单设备级：一个设备不工作
- 参数级：设备工作但参数错
- 拓扑级：设备树结构错（子节点位置错）

★ **虚拟总线 / 跨边界 ABI 型**（virtio-mmio / rpmsg 等）：
- 发现级：节点在不在、`compatible` 对不对（设备根本没被创建）
- 协商级：feature bits / 版本协商失败（设备创建了但 probe 失败）
- 布局级：共享内存的对齐、大小、字节序不符（能跑但数据是乱的）——★ 这一级**内核往往不报错**
- 对端级：★ 症状根源在对端（QEMU 参数、远端固件），**本树里查不到原因**，要显式告诉读者去哪查

**框架型**（pinctrl / clk / regmap 等）：
- 控制器注册级：控制器 probe 失败，整个框架不可用
- 消费者获取级：设备拿不到框架资源（如 pinctrl handle / clk）
- 配置冲突级：多个消费者争用同一资源（如引脚 mux 冲突）
- PM 状态级：suspend/resume 后配置丢失

## 常见陷阱

- 绑定文档写了但核心不消费的属性（死字）
- 属性名拼错但内核静默忽略
- `#address-cells` / `#size-cells` 不匹配导致子节点解析错
- ★ **只写 DT 一条发现路径**，读者以为所有设备都从 DT 来（见 §0 分诊表）
- ★ **把「症状根源在对端」的情况写成本树的 bug**（虚拟总线型专属，要指路而不是硬猜）
