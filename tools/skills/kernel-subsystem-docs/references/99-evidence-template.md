三处搜索路径都要覆盖：`Documentation/<subsys>/`、`Documentation/driver-api/<subsys>*`、`Documentation/devicetree/bindings/<subsys>/`。**反向覆盖率用 `check_doc_coverage.sh` 查**（见 §6.1）：官方文档里 0 次被引用的文件，要么补正文，要么在对应章节补一句"官方原文见 Documentation/…"。子系统没有官方文档时，把这个事实本身登记在这里。

★ **`check_doc_coverage.sh` 要在开始写本篇之前先跑**，不是写完再补——它的输出决定这张表怎么填，
而且 0 引用的文件往往要回到 00-08 去补一句出处，那是正文的活，不是取证篇的活。

### §5.5 ★ 对端 / 树外实现（虚拟总线型必写，其余类型写「不适用」）

| 边界 | 本文档集覆盖到哪一行为止 | 对端行为的依据 |

| 例：virtqueue 通知 | 到 `virtqueue_kick()` 写下 notify 寄存器为止 | 规范文本（树外），非本树代码 |

它不是 `Documentation/`（三等），要在 §2.3 旁边单列，并写明读的是规范的哪一版哪一节
（见 methodology 第 26 条）。

### §6.1 批量机械自检（每轮 review 结束必跑）

三个脚本在 skill 的 `scripts/` 下。本节要贴**最近一次运行的实际输出**，不是命令清单：

```bash
S=.qoder/skills/kernel-subsystem-docs/scripts
D=output/<子系统>

python3 $S/check_xrefs.py     $D --ignore $D/.xref-ignore
python3 $S/check_line_refs.py $D . --ignore $D/.lineref-ignore
bash    $S/check_doc_coverage.sh <子系统> $D .
```

| 脚本 | 上次结果 | 忽略项 |
|------|---------|-------|
| `check_xrefs.py` | 命中 N 条 / 失效 0 条 | M 条 |
| `check_line_refs.py` | 扫描 N 条 / 越界 0 条 | M 条 |
| `check_doc_coverage.sh` | 官方文档 N 个 / 0 引用 M 个 | — |

**假阳性登记表**（对应 `.xref-ignore` / `.lineref-ignore` 里的每一条，理由写在这里）：

| 条目 | 出现在 | 为什么是假阳性 |
|------|-------|--------------|

纠错型内容天然会触发假阳性——§3 变更记录里"原来引的是 `03 §7`"必须原样保留老编号，否则读者看不出改了什么。**处置是登记，不是改文档去迁就脚本。**

★★ **固定动作：本节（或任何"失效引用长什么样"的示例表）写完，立刻重跑 `check_xrefs.py`。**
你在文档里**引用**一条坏引用当例子，脚本分不清"举例"和"真引用"，于是它变成一条新的失败。
`check_xrefs.py` 按"同一行里最近出现的文档名"归属，所以最容易踩的写法是
**表格单元格里同时出现别篇文件名和本篇章节号**。
（spi 那次这个机理犯了四遍：本节的示例表、"另一套文档集的坏引用清单"、"回写 skill 的落点表"，★ 第四遍犯在**解释前三遍的那段正文里**。）

★★ **处置有优先级**：先试着**消除触发条件**（文件名去掉 `.md` 写成 `05-usage-template`、
把"见下面的 §5.1.1"改成"见下一小节 5.1.1"、文件名与章节号拆到两列）——
误报归零而信息一个字没少；只有**内容本身必须保留那个老编号**时才登记进 `.xref-ignore`。
而且误报往往说明原文真有歧义："见下面的 §5.1.1"人读到这儿也得愣一下。

三个脚本都抓不到的那两类：
- **行号在范围内但指向无关代码**——只能逐个 `sed` 打开核对
- **引用有效但指错对象**（章节号真实存在，只是不讲那件事）——只有跨篇对账轮能抓

### §6.2 缺陷统计与"什么手段抓出了它"

一张表统计自审累计发现的问题数，按缺陷类型分行。**关键的一列是"靠什么手段发现的"**——
它决定下一个子系统该先做哪一步。已知的高产手段（spi 实例）：

| 手段 | 抓出了什么 |
|---|---|
| ★★ 填一张必须填满的表 | 四个内容错，**四个全部来自填格子，没有一个来自重读正文** |
| 逐条 `sed` 打开行号 | 行号偏差、指向无关代码 |
| 全树 grep 全称断言 | 否定性断言写反了 |
| grep 自己的文档集 | 两篇给出相反答案、各自内部自洽 |
| 三个脚本 | 失效引用、越界行号、模板串味的外来文件名 |

结论写清楚：**把散落的判断收拢成一张必须填满的表，是比再读一遍更有效的查错手段——
因为空格子无法蒙混过关，而流水的正文可以。**

### §6.3 与另一套独立产出的文档集对比（如果有）

顺序是**先写完自己的、再读对方**（先读就没有独立对照了）。本节四张表：

1. **独立性声明**：什么时候开始读对方的（必须在自己三个脚本全绿之后）
2. **脚本对比**：两套各跑三个脚本的结果
3. **吸收清单**：对方赢在哪 → 吸收了什么 → 回写了 skill 的哪一条
4. **明确不吸收清单**：★ 连理由一起写下来，**以免下次又"发现"一遍**

对方的错误也要单列一张表。★★ **两套独立产出写了同一句错话，标记的不是谁粗心，
而是源码本身在这里有歧义**——这种地方要回到正文里显式写"为什么容易看错"。

- 复核步骤说明：先跑脚本清机械错，再抽 §3 里的高危论断逐个 `sed` 核对

所有数字都要能一条命令重跑。每轮 review 后全部重跑。

## 常见陷阱

- 二等证据不写"详读了哪几行"（读者不知道可信度边界）
- 自审修正记录缺失（无法证明做过自审）
- 未验证项平铺不分层（读者不知道哪里要加倍小心）
- 数字过期不重跑（从"取证"降级成"回忆"）
- **写完"失效引用示例表"没有立刻重跑 `check_xrefs.py`**（那张表自己就会造出新的失效引用）
- **§3 的"依据"栏写着某命令输出为空，而那条命令其实有输出**（伪造依据）
- **前一轮补读的代码没回来升级证据等级**（判据：本轮新引用的行号有没有落在登记的详读范围之外）
- **"明确不吸收"的理由没写下来**（下一轮又"发现"一遍同一件事）
- ★ **虚拟总线型漏了 §5.5**（对端不在本树这件事被静默吞掉，读者以为两侧都核对过了）
