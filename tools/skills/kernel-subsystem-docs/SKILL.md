# Linux 内核子系统文档化工作流

本 skill 把"为内核子系统写一套可复核的文档集"这一流程固化下来。方法提炼自 i2c 文档集（硬件总线型）和 pinctrl / clk / gpio / irq / dma / spi 六套文档集（含框架型），七套均经多轮自审验证。骨架按**四种子系统类型**分支适配（见阶段 1 步骤 3b）：硬件总线型 / 框架型 / 虚拟总线-跨边界 ABI 型（virtio、rpmsg、vdpa）/ 协议网络型——**判定类型是第一步，它决定 00 §2、02、06、99 §5 各走哪条路径**。首次为某个子系统建档时，先进入 Plan Mode 敲定范围、代表驱动和费曼选题。

## 前置约束

- **源码树只读**：只用 Read / Grep / Glob 和只读 git 命令，不改源码。需要改动时先问用户
- **文档输出目录**：所有文档写入 `output/<子系统名>/`
- **目标架构**：默认 arm64。涉及体系结构只走 `arch/arm64/` 路径，不做多架构对照；裁掉了什么显式记在 99 §2.7
- **索引工具定位**：codebase-memory-mcp (cbm) 只用于导航和找候选，**不用于取证**。宏生成的符号和函数指针间接调用是它的两大盲区——恰好是内核最核心的机制
- **语言**：默认中文
- **每写一条因果链就回到源码确认**：`rg` + `Read` 是取证主力，不是索引工具

## 工作流（5 个阶段）

### 阶段 1：基线与规模

**1. 先定基线。** `git log -1` + `git status` 判断树是否干净、是否打了补丁。**如果打了补丁，必须先查清目标子系统有没有被改**——这一步直接决定整份文档的定性。验证方法：`git status --porcelain -- <子系统目录> include/linux/<subsys>**` 看有没有输出。子系统目录可能是 `drivers/<subsys>`、`net/`、`kernel/irq/`、`mm/` 等。

**2. 量规模。** `wc -l` 定出核心/外围的边界，据此决定"读全"与"读符号表"的分界线。核心通常 5k~10k 行，可以全读；驱动目录通常几万到十几万行，只能讲契约。逐文件行数只留在 99 取证篇（对读者无用，对编者决定"读哪些"有用），01 代码地图里只留文件名和职责。

**3. 一开始就定死体系结构范围。** 默认 arm64-only。这个决定不是写完再删——它改变**读哪些文件**（如 ACPI 相关直接不读）、**统计怎么做**（要按 arm64 过滤）、**举例用什么**（DTS 必须取自 `arch/arm64/boot/dts/`）。裁掉了什么要显式记下来（99 §2.7），否则读者会当成遗漏。

**3b. 判定子系统类型。** 决定后续模板怎么适配。**四种类型**：
- **硬件总线型**（SPI / I2C / USB / PCI / MMC）：有自己的 `bus_type`，控制器在父总线上、设备在子系统总线上。全套模板直接适用
- **框架型**（regmap / clk / pinctrl / irqchip / iommu / DMA / GPIO）：无 `bus_type`，通过 API 被其他驱动消费。02 改画"核心抽象↔消费者"图；03 主轴是"注册/配置/回调"而非"传输"；04 没有子框架时并入 03；06 没有 DT 绑定时改讲替代配置机制（sysfs / module_param / ACPI）
- ★ **虚拟总线 / 跨边界 ABI 型**（virtio / rpmsg / vdpa / vsock / xen 前端 / vhost）：**有 `bus_type` 但没有电气层**，"对端"是另一个软件实体（hypervisor / 远端固件 / 用户态），且协议由一份树外规范定义、ABI 落在 `include/uapi/` 里。00 §2 走**路径 C（规范背景）**而不是硬件背景；02 必须加**内存布局图**和**"几层可插拔"**；06 改用**发现路径分诊表**；99 §5 必须有**第五层「对端不在本树」**（见 `references/methodology.md` 第 26 条）
- **协议/网络型**（net / crypto / block）：设备是逻辑的，路径是"协议栈 → 驱动"。05 角色枚举侧重协议层而非硬件层

判定分两道，**只跑第一道会把 virtio 误判成硬件总线型**：

```bash
# 门 1：有没有自己的 bus_type
rg 'struct bus_type' drivers/<subsys>/*.c include/linux/<subsys>*.h
# 门 2（门 1 有输出时必跑）：协议 ABI 在不在 uapi 里 / 对端在不在本树
ls include/uapi/linux/<subsys>*.h | wc -l      # 一群规范头文件 = 跨边界 ABI
rg -n 'struct <subsys>_config_ops [a-z_]+ = \{' --include=*.c .    # 传输层有几个实现、住在哪
```

门 1 无输出 → 框架型或协议型；门 1 有输出且门 2 也有 → 虚拟总线型；门 1 有、门 2 空 → 硬件总线型。virtio 实例：`drivers/virtio/virtio.c:343` 有 `bus_type`，但 `include/uapi/linux/virtio_*.h` 有 27 个规范头文件、`virtio_config_ops` 有 9 个实现、散在 5 个目录（`drivers/virtio/` 4 个文件里 5 个——`virtio_pci_modern.c` 一个文件有 2 个；`drivers/s390/virtio/`、`drivers/remoteproc/`、`drivers/platform/mellanox/`、`arch/um/drivers/` 各 1 个）→ 虚拟总线型。**在 99 §1 登记判定结果和两道门的实际输出。**

### 阶段 2：核心阅读

**4. 先读头文件。** `include/linux/<subsys>*.h` 或 `include/linux/<subsys>/*.h` 是最高信息密度的入口。数据结构和 API 全在这里，读完就有了骨架。

**4.1 选代表驱动。** 驱动目录很大时（如 SPI 有 100+ 控制器），不要全读。在 99 §2.2 登记选法：优先挑一个最简实现（PIO/bit-bang）、一个全功能实现（DMA/多队列）、一个本树 arm64 DTS 实际在用的。其余驱动只讲契约。

**5. 再读核心 .c。** 按依赖顺序（base → 协议 → 扩展）。核心文件逐行读，外围文件只读符号表——二者的分界在 99 §2.1/§2.2 里明确登记。

**6. 读 `Documentation/<subsys>/` 和 `Documentation/driver-api/<subsys>*`。** ⚠️ **这是阻塞性前置步骤，必须在写任何文档之前完成。** 它给的是**设计意图和已知陷阱**，这些从代码里读不出来。典型高价值内容：
   - **设计 rationale**（为什么这样分层，如 clk 的 prepare/enable 分离、两把锁设计）
   - **必选条件矩阵**（如 clk 按硬件类型列出哪些回调必须实现）
   - **核心模式说明**（如 container_of 模式的官方示范）
   - **内核参数**（如 `clk_ignore_unused`、`threadirqs`）
   - **已知陷阱和故障码文档**（如 `fault-codes.rst`、`*-topology.rst`）

   搜索路径：`Documentation/<subsys>/`、`Documentation/driver-api/<subsys>*`、`Documentation/devicetree/bindings/<subsys>/`。
   注意三等证据的风险：内核文档偶尔落后于代码（如 clk.rst 仍使用 `clk_register` 而非 `clk_hw_register`），凡是文档与代码冲突的地方以代码为准并显式指出。
   **在 99 §1 登记读了哪些 Documentation 文件、哪些内容被纳入了文档、哪些因过时被标注。** 收尾时用 `scripts/check_doc_coverage.sh` 反查覆盖率（阶段 5）。

**7. 索引工具只用来导航，不用来取证。** 宏和函数指针是内核的两大主力机制，恰好是索引工具的两大盲区。用 cbm 找候选和结构，然后在文档定稿前用 `rg` 针对真实树确认。

### 阶段 3：写 10 篇文档

按上面的骨架产出。以下是跨篇通用的格式与组织规则：

**7.5 先建「引用台账」，再写正文。** 一篇文档的墙钟时间大头不是写，是"凭记忆写了行号 → 事后逐条核对 → 逐条纠正"这条返工链（clk 02 §3 一次纠了约 20 处偏移）。固定做法：
- **开写前**用 1 次 Bash 调用，把这篇要用到的 `行号:符号` 一次性 dump 出来（多个 `sed -n` / `grep -n` 用 `echo "=== 标题 ==="` 分段拼在同一条命令里），写正文时**只查台账，不再回源码**
- **没有阅读价值的行号就不写**（`container_of` 宏的位置、`EXPORT_SYMBOL` 行），规则 10 本来也只要求精确到文件；每个可省的行号都省掉一次核对
- **每篇写完立刻跑 `check_line_refs.py`**，不要攒到整套写完——一篇之内定位错误比十篇之后便宜得多
- **产出顺序用 `01→02→…→08→00→99`**：00 的定位是复习入口，最后写就变成对已定稿内容的纯浓缩，零重新推导；99 的逐篇取证表同理

**8. 按"查询动作"而不是"内容类别"分篇。** 判断标准：**读者的一次提问，应该只落在一篇文档里。** 代码地图并入 01 §0（"找文件"和"找 API"是同一次查询），不要拆到 00。00 的定位是**复习入口**——把 02/03 的骨架浓缩进去，隔几个月回来只读 00 就能恢复全貌。

**9. API 篇的表格固定三列：`API / 说明 / 备注`。** 统一规则：**「说明」一句话讲它做什么，其余全部进「备注」**——上下文标签、返回值陷阱、参数类型提示、`inline`/宏、已废弃、arm64 不涉及。

**10. 签名只写"函数名 + 形参名"，位置只精确到文件。** 让表能一眼扫完：类型不是删掉而是搬家（返回值语义、回调原型移进「备注」）。逐 API 的 `文件:行号` 删掉，换成每节开头一行「头文件：…；实现：…」。行号在 API 篇是噪声，集中在 03 和 99 里维护。三个例外不要动：C 代码块、ioctl 表的"参数"列、本身是变量而非函数的符号。

**11. 数据结构篇开头必须先破歧义，再画图。** 图画得再全，也补不上一个没被显式否掉的错误类比。做法三步：(1) 先否掉错误类比再讲正确的；(2) 用对比表把"是不是 struct device / 注册到哪条总线 / 会不会绑 driver"逐行摊开；(3) 把"为什么不会发生"也找到代码依据——否定性论断同样要给行号。

**12. 每个模块都要交代"它和它的父总线是什么关系"。** 多数子系统是"控制器在 platform 总线上、设备在子系统总线上、两者只由 `dev.parent` 缝在一起"这个形状。三个必查点：(1) 控制器 DT 节点由谁变成设备；(2) 子节点会不会被 platform 层继续下钻（查 `of_default_bus_match_table[]`）；(3) 两条总线的连接点具体是哪一行赋值。**如果子系统没有自己的 bus_type（如 regmap、clk、pinctrl），改为讲核心抽象与消费者的关系，以及消费者如何获取子系统服务。**

**13. 组织轴要显式声明，而且正文必须真的按那个轴排。** 一篇文档只承诺一条主轴，其余内容显式分区。分区用 A/B/C 前缀写进章节号里，引用自带"在哪条轴上"的信息。长文档（800+ 行）开篇必须有导航节（分层图 + 时间线图 + "哪些内容不在本篇"的去处表）。**时间线的顺序要用代码验证**：判据是"谁调用谁"，排完检查别处有没有抄走同一个错误次序。

**14. 设备树单独成篇，每条属性都要找到消费者。** 先建"谁消费什么"的三方分工表（通用 DT/驱动模型 / 子系统核心 / 具体控制器驱动），再对每个属性跑一次 `rg -n '"属性名"' drivers/<subsys>/`。**找不到消费者的属性就是死字**，而绑定文档不会告诉你。举例一律用 in-tree 的真实节点，读者能 diff。

**14.1 费曼解释篇（08）的结构固定。** 用户说"用大白话解释""为什么是这样""举例子""我理解不了 X"时，这一篇的优先级提到最前面。每概念四段式：
- **问题标题**：只写要说明的问题，不要夹带类比。例如 `controller 和 device 为什么分两条总线注册？`
- **先举个例子**：用日常生活类比引入，可以多说几句，不必硬凑一句话总结。选材标准和 i2c 八主题类比库见 `references/methodology.md` §E
- **回到代码**：给出关键源码行号，文件路径写全，不能裸 `:N`
- **这个类比什么时候会误导你？**：明确类比和代码之间的真实技术差异，这是费曼法的核心。**推不出误导点说明类比太泛，换一个**

### 阶段 4：分篇自审

**15. 每写一条因果链就回去确认一次。** 初稿阶段就有假设被源码推翻。但真正的数量级是逐篇 review 之后才暴露的。可复用的结论两条：
- **初稿的错误率与"这一篇有没有人能提问"强相关**：用户能发现的是"读不懂"，自审才能发现"根本不存在"
- **每一轮 review 自己会产生新的错误**：自审的对象必须包含自审这一轮新写的文字

**16. 内容审查要做 severity 分级。** 当用户要求"审查一下文档内容"时，按以下三类报告：
- **ERROR**：事实错误（函数不存在、返回值错、行为描述错、行号指向无关代码）
- **Minor imprecision**：行号偏差 1-2 行、范围略宽/略窄、措辞不够精确但不影响理解
- **Unverifiable**：依赖外部规范或硬件手册、无法从本树源码直接验证的论断

优先复查的高危论断：函数返回值（如 `-EBUSY` vs `-EOPNOTSUPP`）、引用计数（"不加引用"常错）、`__init` 标记、范围校验（仅上界还是上下界）、锁行为（等待 vs try-and-fail）、初始化顺序、宏展开实际设置哪些字段、本项目「裸 `:N`」约定。

**17. 跨文档一致性必须单独走一遍——而且靠表格，不靠重读。** 同一论断（某个函数的返回值、初始化顺序、某个标志的语义、"一共有几种形式"）会在多篇里各写一遍。两条动作：

- **改一处就 `grep` 全集**，包括**同一篇内部**——同一条错引用在一篇的开头和篇末表里各出现一次是常态，只改第一处等于没改
- ★★ **把散落的判断收拢成一张必须填满的表**（框架使用统计、近邻符号对照、"X 是 Y 的别名"的机制归类、篇末引用汇总）。**空格子无法蒙混过关，流水的正文可以**——spi 那次自审后期修的四个内容错，四个全部是填格子时掉出来的，没有一个来自重读正文。表的形态和实例见 `references/methodology.md` **§A22**

一条脚本永远抓不到的缺陷类型：**引用有效但指错对象**（章节号真实存在，只是不讲那件事）。它只会在对账轮里暴露。

**18. 文档集很大时启动多 Agent 并行审查。** 每个 Agent 只负责一篇文档，必须"全文读完 + 每个论断验证"。自己负责汇总交叉验证所有 Agent 发现的关键错误，尤其是跨文档重复错误。（本项目默认不自动派 Agent，用户要求时才用。）

**19. 自审方法：把全篇 `文件:行号` 逐个 `sed` 打开核对，不抽样。** 四条规律：
- **错误全部集中在"写了概述、没有逐字引用源码"的段落**。凡是贴了真实代码片段的地方一处没错；凡是图省事写成"大意是 X"的地方错误率极高。判断标准不是"我理解得对不对"，而是"我有没有把源码原样搬过来"
- **表格里的"—"和"可配"是欠债的记号，必须清掉**。同一类记号还有**含糊词**："`xxx.dts:42-70` 一带"、"`:100` 附近"、"从 `:55` 起"、"20+ 个"——它们都表示"我没去把边界确认到底"。改法是回去把准确范围/数字取出来（`awk` 定区间见 §H），取不到就写清取不到的原因
- **"全树唯一 / 没有一个 / 只有 X 这么用"这类全称断言，必须在整棵树上 grep**。框架的使用者不一定住在框架自己的目录下。检查动作：`grep -rn "<框架入口函数>(" --include=*.c | grep -v <框架自己的目录>`
- **反例要老实留在文档里**——它把结论的方向性钉准了

**20. 示例篇（05）的自审动作不一样：先验符号存在性，再验行号。** 05 是唯一会被读者直接抄进代码的篇，错误代价最高。额外动作：把正文里出现的每个内核函数名/宏名/标志名/内核打印的字符串，都跑一次全树 grep 确认它在本版本存在。空结果 = 这个符号是幻觉，不管你多确信。四条补充：

- **符号存在性这一遍要覆盖全部十篇，不只是 05**。05 优先级最高（读者会照抄），但幻觉符号在 01/04/07 里同样是 ERROR
- **grep 的 tab 陷阱**：`#define` 与宏名之间常是 TAB，`grep "define SPI_NBITS"` 返回空并不代表符号不存在。固定写法 `grep -nE "define[[:space:]]+SPI_NBITS"`
- ★ **"存在"和"读者能用"是两条判据**。后者 = `EXPORT_SYMBOL*` **且**头文件里有声明，**不是"有没有 kerneldoc"**。写满 kerneldoc 却 `static`、不导出的内部函数比没注释的更危险——它长得像公开 API
- **"被引用的地方" ≠ "调用者"**：`static inline` 包装的 grep 命中里混着声明行、`EXPORT_SYMBOL` 行、注释。数调用点要排掉这些，或改用"文件数 / 赋值点数"这种能重跑的口径

**"名字很像"是高危信号**：近邻符号要成对写进文档并点明区别，而且 **05 必须有独立一节承载它们**（见骨架里 05 的 ★ 条）——散在各节陷阱表里等于没有入口。

**21. "内容对但读不懂"是一类独立的缺陷，要单独走一遍重排，而且不能顺手改结论。** 重排轮只换承载形式，事实一条不动；顺手发现的行号错另立一张表。五种"费劲"形态的固定改法见 `references/methodology.md` **§C**。**重排会动章节号，重排轮结束必须跑 `check_xrefs.py`。**

**22. 调试篇（07）整篇都在教读者"去看某个输出"，自审的对象是输出本身。** 八条固定检查动作（日志可见性等级、可写调试文件的 setter 语义、调试开关的多道门、错误码点名函数+被改写路径、tracepoint 的 TP_CONDITION+字段清单、示例命令输出不许编、**成对 tracepoint 的"缺 _complete"不是失败信号 + 提交阶段的返回值黑洞**、**故障注入一节即使结论是"没有"也必须写**）见 `references/methodology.md` **§D**。

**23. 费曼篇（08）的自审重点是"类比边界"，不是行号精度。** 检查三件事：标题里没有夹带类比；"这个类比什么时候会误导你？"确实指出了一个真实的技术差异而不是泛泛而谈；类比里的每个技术断言仍然带行号（费曼篇不豁免取证）。

**24. 改名期的子系统：摸清一条改名线不等于机制清单完整，必须显式换一条线再走一遍。** 同一次重命名在不同字段上可能用了不同手法。`master→controller` 线上见到 `#define` / 平行 inline / 重复字段三种，不代表只有三种——`slave→target` 线上还有第四种（`union` 同址双名）。所以：

- **"X 是 Y 的别名"这句话不许直接写**，必须打开定义归到四种形式之一，并注明**会不会分叉**（平行 inline / 重复字段会，`#define` / `union` 不会）
- 标志位命名可能三种情况并存：双名、只有旧名、只有新名。别假设改名是齐刷刷的
- 发现新形式后，要改的是**所有说"共 N 种"的地方**（走第 17 条的对账轮）

四形式对照表和 spi 实例见 `references/methodology.md` **§A18 / §A23**。

**25. 拿别的子系统文档集当模板起草时，收尾必须看 `check_line_refs.py` 的 UNRESOLVED。** 模板会把它原主人的文件名一起拖过来（spi 文档里的 `i2c-core-of.c`），这类错误肉眼扫不出来——语法语义都通顺，只有这个脚本能抓。不要把 UNRESOLVED 当成"脚本认不出的简写"随手忽略。程序化批量改过文档之后（插行号、批量替换章节号），另外机械检查一遍**代码围栏配对**和**围栏内混进 markdown 标记**。

### 阶段 5：取证附录与批量自检

**26. 老实记下没验证的部分。** 99 §5 的价值不低于前面九篇——它决定了读者该在哪里加倍小心。必须记录：未编译/未运行的代码、只读了符号表的函数、推断而非观察的结论、版本时效性。

**27. 取证篇（99）也要自审，但它的失效方式是"过期"而不是"写错"。** 四条固定动作：
- **把本篇里所有可机械复现的东西全部重跑一遍**：基线命令、规模统计、能力普查、工具版本。只要有一个数字对不上，整篇从"取证"降级成"回忆"
- **每轮补读之后要回来升级证据等级**：判据——本轮新引用的行号有没有落在登记的"详读范围"之外
- **跨篇引用要用脚本查，不能靠手工回访**：手工回访会漏，脚本不会
- **一等/二等证据的分界线本身要写清"为什么"**：读者据此决定哪些结论可以直接用、哪些要自己再确认
- ★★ **只要在 99 里"举例引用了一条失效引用"（失效引用长什么样、别人文档集的坏引用清单、回写 skill 的落点表），写完那张表立刻重跑 `check_xrefs.py`。** 这是流程里的一步，不是提醒——spi 那次同一个机理犯了四遍——★ **第四遍是在"解释前三遍"的那段文字里犯的**，可见它不是记性问题。`check_xrefs.py` 按"同一行里最近的文档名"归属，所以"单元格里同时出现别篇文件名和本篇章节号"必然假阳性。★ **处置优先消除触发条件**（文件名去掉 `.md`、把"见下面的 §5.1.1"改成"见下一小节 5.1.1"、文件名与章节号拆两列），登记 `.xref-ignore` 是第二选择，留给"内容本身必须保留老编号"的场合（见 **§B**）
- **`check_doc_coverage.sh` 要在开始写 99 之前先跑**，不是写完再补：它的输出决定 99 §1 的 Documentation 登记表怎么填

**28. 三个批量自检脚本，每次改完文档都跑。** 纯 stdlib，无外部依赖：

```bash
S=.qoder/skills/kernel-subsystem-docs/scripts
D=output/<子系统>

python3 $S/check_xrefs.py     $D --ignore $D/.xref-ignore        # 跨篇 0X §Y 引用是否命中
python3 $S/check_line_refs.py $D . --ignore $D/.lineref-ignore    # 路径:行号 是否越界
bash    $S/check_doc_coverage.sh <子系统> $D .                    # 官方文档反向覆盖率
```

三者都抓不到的那一类是「行号在范围内但指向无关代码」——只能逐个 `sed` 打开看，脚本不替代第 19 条。还有一类是「章节存在但不讲那件事」，只有第 17 条的对账轮能抓。

两条输出不能当噪声跳过：

- **`check_line_refs.py` 的 AMBIGUOUS**（同名头文件，内核树里 `i2c.h` 有 12 个、`spi.h` 有 3 个）意味着脚本是**猜**着校验的。看到它就要把该文件的每条**裸文件名**引用打开确认一遍，或者干脆把文档里的路径补全
- **UNRESOLVED** 见第 25 条：它兼职抓"模板串味"，别当成"认不出的简写"

假阳性不要靠改文档去迁就脚本：登记在 `$D/.xref-ignore` / `$D/.lineref-ignore` 里并写明理由，做法见 `references/methodology.md` **§B**。脚本的两个设计要点（简写文件名怎么消歧、0 引用的两种处置）见 **§G**。

★★ **`check_doc_coverage.sh` 报「【必查】共 0 篇 → 必查档全部有引用」是假的通过**——「共 0 篇」意味着它一篇官方文档都没找到（pinctrl 的主文档叫 `pin-control.rst`，带连字符，不匹配 `*pinctrl*`）。规则 6 不能依赖这个脚本兜底，每个子系统都要手工确认一遍 `Documentation/driver-api/` 下的真实文件名。

★★ **99 §7 报告脚本结果时只描述、不照抄失败行的格式**——脚本下一轮会把这段引述再解析一次，你描述失败就制造了失败。同理 `grep -c` 的 `文件名:数字` 原生格式会被行号检查器当成越界行号，统计结果一律改写成 `文件名 → 数字`。三种自指形态见 **§B**。

**29. 有另一套独立产出的同子系统文档集可比对时，顺序是"先写完自己的，再读对方"。** 先读对方就没有独立对照了，只剩下抄。固定协议：自己按 skill 生成 → 自审 → 三个脚本全绿 → **然后**逐篇 diff → 对方赢的地方分「吸收（补文档 + 回写 skill）」和「明确不吸收（把权衡理由写进 99，以免下次又发现一遍）」两类落地。★★ 对方的错误也要记：**两套独立产出写了同一句错话，标记的不是谁粗心，而是源码本身在这里有歧义**，这种地方要在文档里显式写"为什么容易看错"。

★★ 三条容易做错的细节：(1) **"对方有一节我没有"最常见的原因是拆到了别的篇**——判断是否真漏，要拿对方那节的**事实清单**去 grep 自己全套，按章节名比对会虚报缺口（pinctrl 那轮 6 个"缺口"里 3 个是假的）；(2) **对方最大的贡献往往是逼你发现自己有一句话说宽了**，而不是补一节（pinctrl 的「PREEMPT_RT 没有额外风险」对核心成立、对驱动不成立）；(3) **引用对方章节号要写成「对方 NN 篇 §X」**，和本套的 `` `NN-xxx.md` §X `` 区分开，否则 `check_xrefs.py` 会拿去本套里找并报假失效——这不算假阳性，不要登记忽略。详见 `references/methodology.md` **§A24**。

**30. ★★ 每一个数字都是一条能被读者一条命令推翻的论断，而计数错误三个脚本一个都抓不到。** pinctrl / spi 两轮自审里数字类错误占了全部错误的一半以上。八条硬纪律：统计范围**必须显式列文件**不能用 `drivers/<subsys>/*.c` 通配（pinctrl 的 `-EINVAL` 会从 47 变成 326）；符号使用计数**必须带 `grep -w`**；**同名头文件必须写全路径**（`pinmux.h` 有两个，168 行 vs 85 行）；`grep -c` 数的是**含该串的行数不是返回点数**；★ **子串包含会把两类算成一类**（`spinlock_t` 的 34 里含了 18 个 `raw_spinlock_t`）；「不存在 / 全树唯一」这类论断**本身也要 grep 且要跨出子系统目录**；改了一个计数**必须回头改所有引用它的汇总表**（判据：`grep -rn '<旧数字>' output/<子系统>/` 为空）；★★ **凡是同时给了数字和复现命令的地方，定稿前必须真跑一遍逐格对账**。另加两条同类：位域打包宏必须读宏本体不能猜字段次序；**内核打印的字符串必须回到源码逐字 grep**（还要查是否多处逐字重复）。详见 `references/methodology.md` **§I**。
